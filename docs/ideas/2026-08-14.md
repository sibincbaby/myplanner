### 1. nginx (config, reverse proxy, TLS) `OSS`

**Why it's powerful:** nginx serves or fronts roughly a third of all websites — hundreds of millions of sites — and is the default ingress for a huge fraction of Kubernetes clusters via ingress-nginx. The config language is a real programming surface: `server`/`location` blocks with prefix and regex matching, `upstream` load balancing with keepalive and health checks, `proxy_pass` URI-rewriting semantics, caching via `proxy_cache_path` with stale-while-revalidate, rate limiting (`limit_req`, `limit_conn`), TLS termination with OCSP stapling, `map` blocks, `try_files`, websocket upgrade handling, header manipulation, and Lua/njs scripting. It is the substrate under most self-hosted apps, VPS deployments and small-shop production — the piece of infrastructure a solo founder inherits from a blog post and never understands.

**Why people bounce off it:** nginx punishes tiny syntactic details with completely silent wrong behaviour. The trailing slash in `proxy_pass http://app:3000/` versus `http://app:3000` changes URI rewriting entirely and is the single most common cause of 404s behind a proxy. Location matching precedence — `=`, then `^~`, then regex in file order, then longest prefix — is genuinely counterintuitive, so a regex block quietly swallows static files. `add_header` inside a `location` silently discards every parent `add_header`, which means security headers vanish with no warning. `if` is documented as evil and still used everywhere. Proxy buffering makes SSE and streaming hang with no error at all. Websockets return 400 unless `Upgrade`/`Connection` are explicitly forwarded. The default `client_max_body_size 1m` yields `413 Request Entity Too Large` on uploads and the fix has to go in the right context. And the diagnostics are minimal: a bare 502 in the browser, with `connect() failed (111: Connection refused) while connecting to upstream` sitting in a log file the user does not know to open.

**AI operator:** A config operator that reads the live config tree over SSH, parses it into an AST with `crossplane` (nginx's own official parser) rather than regexing text, and is pre-loaded with skills for reverse-proxy and websocket/SSE patterns, TLS + ACME wiring, cache and rate-limit design, location-precedence reasoning, header propagation and access/error log analysis. It never writes to live config: it generates a diff, runs `nginx -t` against a sandboxed copy, applies with an automatic backup, then `nginx -s reload` (never restart) with rollback if a health probe fails. Certificate and port-binding changes are flagged as downtime-risky. Modes: **do-it**, **diagnose** (given "everything under /api 404s", it reasons over the location tree and the trailing-slash rule and points at the exact line), **audit** (security headers, TLS posture, missing `client_max_body_size`, `if` misuse, duplicate `server_name`, upstreams pointing at dead hosts, unrotated logs), and **explain** (annotate an inherited 400-line config in plain English).

**Killer example:** A solo founder says: "my SPA loads but every API call 404s, and file uploads over 1MB die." The operator reads the config and finds `location /api { proxy_pass http://backend:8000; }` — no trailing slash, so `/api/users` is proxied through as `/api/users` while the backend mounts its routes at root. It shows both possible fixes with their exact URI-rewriting consequences instead of guessing which one the user wants. It adds `client_max_body_size 50m` in the right context and explains why `http` versus `location` placement matters here. Then it surfaces something nobody asked about: an `add_header X-Frame-Options` inside the SPA location block has been silently nuking the `Strict-Transport-Security` and CSP headers set at the server level for months — a real security regression invisible to any test the founder would think to run — and a stale `location ~ \.php$` block inherited from a template sits ahead of the static regex doing nothing but confusing future readers.

**Integration path:** Filesystem config management over SSH or a local agent (`/etc/nginx/nginx.conf`, `conf.d/`, `sites-available` + `sites-enabled`), `crossplane` to turn config into a JSON AST and back for safe programmatic editing, `nginx -t` for validation, `nginx -s reload` for zero-downtime apply, `stub_status` (or NGINX Plus `/api`) for live metrics, certbot's CLI for ACME, and access/error log parsing. Honest gap: OSS nginx has no config API and no runtime introspection of the effective merged config — you cannot ask a running nginx "which location will match this URI", so match simulation must be reimplemented from the documented precedence rules and can diverge on exotic regex and `map` interactions. NGINX Plus adds a real API but is paid and rare in the long tail.

### 2. Docker & Docker Compose `OSS`

**Why it's powerful:** Docker is effectively universal in software — over 20 million monthly active developers, Docker Hub serving billions of pulls a month — and Compose is how the large majority of small teams actually run multi-service local and small-production stacks. The surface is genuinely deep: multi-stage builds, BuildKit cache mounts and build secrets, healthchecks with `depends_on: condition: service_healthy`, named volumes and bind-mount propagation, user-defined bridge networks with DNS-based service discovery, resource limits, restart policies, profiles, `extends`, multi-file override merge semantics, and `docker compose watch` for sync/rebuild loops.

**Why people bounce off it:** The failure modes are famously opaque to anyone who is not already an expert. `Bind for 0.0.0.0:5432 failed: port is already allocated` — but by what? Containers cannot reach each other because someone used `localhost` instead of the service name, or because the app binds `127.0.0.1` inside the container so port publishing does nothing at all. Volume mounts silently shadow image contents, so `node_modules` disappears and you get `Cannot find module`. On Mac and Windows, bind-mount file watching does not fire and builds run an order of magnitude slower, and nobody knows the `:delegated`/VirtioFS knobs exist. `depends_on` without a healthcheck starts the app before Postgres is ready, producing intermittent `ECONNREFUSED` that people "fix" with sleep loops. Images balloon to 2GB because the Dockerfile copies before installing and busts the cache every build, or because a missing `.dockerignore` ships `node_modules` and `.git` as build context. `docker compose down -v` deletes the database with no undo. Env var precedence across `.env`, `environment:`, `env_file:` and the shell is a documented table nobody reads. And UID mismatches on Linux bind mounts produce `EACCES` that Stack Overflow answers with `chmod 777`.

**AI operator:** A local operator with skills for Compose authoring and refactoring, Dockerfile optimisation (multi-stage, layer ordering, cache mounts, base-image and CVE/size tradeoffs), networking and port diagnosis, volume and permission diagnosis, healthcheck and startup-ordering design, resource limits, and build-context hygiene. The safety model turns on the read/mutate boundary: `ps`, `inspect`, `logs`, `events` and image history run freely, while anything that destroys data — `down -v`, `volume rm`, `system prune` — is hard-gated behind an explicit inventory of what will be deleted, its size on disk, and an offer to snapshot the volumes first. Modes: **do-it** (edit compose/Dockerfile and bring the stack up), **diagnose** (read logs plus inspect plus network state and name the actual cause rather than the loudest error), and **audit** (image size, layer cache efficiency, running as root, secrets in build args, missing healthchecks, unpinned `latest` tags).

**Killer example:** A data scientist says: "my API works on my laptop but in Compose it just says connection refused to the database, and it worked yesterday." The operator inspects the network, sees the app connecting to `localhost:5432`, and rewrites it to the service name. Then it finds the real reason it "worked yesterday": a stale named volume `pgdata` left over from an earlier Postgres 15 image, while the compose file now pins 16 — so Postgres exits at startup with `database files are incompatible with server`, visible only in the db container's logs, which the user never opened because the app's error was louder. It offers a `pg_upgrade` path or a dump/restore, explicitly refuses to just run `down -v` (which would silently delete six months of local research data), and separately flags that the build context is 1.7GB because there is no `.dockerignore`, which is why every rebuild takes four minutes.

**Integration path:** Docker Engine API over the local socket (`GET /containers/json`, `/containers/{id}/logs`, `/containers/{id}/json`, `/networks`, `/volumes`, `/images/{name}/history`, `/events`, `POST /build` with BuildKit), plus the `docker compose` CLI with `--dry-run`, `config --format json` for the fully resolved model, and `ps --format json`; Docker Desktop's extensions SDK for a GUI surface; registry APIs plus Scout or Trivy for CVE data. Honest gap: the Engine API has no notion of a Compose "project" as a first-class transactional object — Compose is a client-side construct, so orchestrated multi-service changes are not atomic. And the Docker Desktop VM's filesystem and networking behaviour on macOS and Windows is not introspectable through the API, so the single most common bug class (host↔VM file watching and mount performance) has to be diagnosed heuristically.

**Demand 5/5 · Buildability 5/5**

### 3. AWS Cost Explorer + Billing / Cost Optimization Hub `closed`

**Why it's powerful:** Every one of AWS's millions of active customers has a bill, and Cost Explorer is the built-in surface for understanding it: 38 months of history, hourly and resource-level granularity, roughly 30 dimensions (service, usage type, operation, linked account, region, AZ, instance type, purchase option, tag, cost category), Savings Plans and RI coverage/utilisation reports, purchase recommendations, anomaly detection with subscriptions, budgets with actions, and Cost Optimization Hub aggregating rightsizing, idle-resource, Graviton and commitment recommendations across an Organization. CUR 2.0 in Athena or Redshift gives line-item-level truth underneath. Cloud spend is a board-level line item, and FinOps is now a discipline with its own certification precisely because this data is so hard to turn into action.

**Why people bounce off it:** The reports look simple and are quietly treacherous. Unblended versus blended versus amortized versus net amortized changes the answer to "what did EC2 cost me" by tens of percent; amortized is the only one that makes Savings Plans comprehensible and it is not the default. Grouping is capped at two dimensions at once, so "which team's Lambda functions in eu-west-1 grew" takes three passes. Untagged resources land in a `No tag key: CostCenter` bucket that is usually the biggest one, and cost allocation tags only apply forward from activation — so the tag you just enabled shows nothing historical, which everyone reads as a bug. Usage types like `EUW1-NatGateway-Bytes` and `USE1-USE1-AZ-DataTransfer` require decoding a private vocabulary before you discover that inter-AZ chatter is the real spend. Anomaly alerts arrive with a dollar delta and no cause. RI and Savings Plan recommendations come with a term/payment/lookback selector where flipping the lookback from 7 to 60 days changes the recommendation completely, and nobody can articulate the blast radius of a three-year commitment. And every Cost Explorer API call costs $0.01, so exploratory clicking is itself billed.

**AI operator:** A FinOps operator pre-loaded with skills for cost querying (choosing the right metric and dimension math for the question actually asked), tag and cost-category management, anomaly investigation by correlating a spike against CloudTrail events, deployments and resource creation times, commitment analysis with break-even math and blast radius, rightsizing and idle-resource review, and budget/alert construction. Reads run free but are rate-and-cost aware — it batches and caches because each call is billed — while anything that spends money, such as purchasing a Savings Plan or creating a budget action that stops instances, requires typed confirmation with the commitment math restated. Modes: **investigate** ("why is the bill up $8k"), **optimize** (ranked actions with dollar value and risk), and **guard** (set up cost categories, allocation tags, anomaly monitors and budgets so the next surprise is caught automatically).

**Killer example:** A CTO says: "our AWS bill jumped 40% this month and finance is asking, but nothing changed." The operator pulls amortized daily cost grouped by service, isolates the jump to `EC2-Other`, drills into usage type and finds `USE1-USE1-AZ-DataTransfer` — cross-AZ traffic — starting on the 9th. Correlating with CloudTrail, it finds an EKS node group scaled from 3 to 9 nodes across three AZs on the 8th while a Redis cluster stayed pinned in a single AZ, so every cache read now crosses an AZ boundary at $0.02/GB round trip. It quantifies that at $11.4k/month and proposes topology-aware routing or a per-AZ replica. Then the extra nobody asked for: $3.1k/month of the "unchanged" baseline is NAT Gateway data processing for S3 traffic that has no VPC endpoint — a two-minute fix that has been quietly billing for three years.

**Integration path:** Cost Explorer API (`GetCostAndUsage`, `GetCostAndUsageWithResources`, `GetSavingsPlansPurchaseRecommendation`, `GetReservationCoverage`, `GetAnomalies`, `GetDimensionValues`) at $0.01 per request with resource-level granularity limited to 14 days; Cost Optimization Hub (`ListRecommendations`, `GetRecommendation`); the Budgets and Cost Categories APIs; CUR 2.0 in Athena for line-item truth; CloudTrail, Config and Compute Optimizer for causality. Honest gap: Cost Explorer data lags 24–48 hours and does not reconcile exactly with the invoice or with CUR — rounding, credits, refunds and RI amortization allocate differently — so the operator has to be explicit about which source produced a number. And there is no API that explains *why* an anomaly happened; causality is always inference the operator constructs itself.

**Demand 5/5 · Buildability 5/5**

### 4. Microsoft Teams admin center (policies, phone system, governance) `closed`

**Why it's powerful:** Teams is the collaboration substrate for 300M+ monthly active users, and its admin center drives a genuinely deep policy engine: messaging, meeting, live-event, calling and caller-ID policies; app permission and app setup policies; emergency calling and dial plans with regex normalisation rules; auto attendants and call queues with holiday schedules; voice routing policies with PSTN usages and route patterns; plus retention and information-barrier policies reaching into Purview. Policy packages bundle settings by persona, and assignment works per-user, per-group with rank-based precedence, or per-batch. Teams telephony via Direct Routing and Operator Connect is running enterprise PSTN for a large share of the Fortune 500.

**Why people bounce off it:** Policy precedence is the killer. A user receives the resolution of direct assignment, group assignment ranked by number, and the org-wide default — and the admin center only surfaces an effective policy through a separate lookup, so "why can this user still record meetings?" has no visible answer. Dial plan normalisation rules are raw .NET regex typed into a small dialog with a Test box (`^(\d{4})$` → `+914440001$1`), and one wrong anchor breaks internal dialing for an entire site. Auto attendant and call queue setup spans resource accounts, Teams Phone Resource Account licensing, routing trees and holiday sets across different blades, with "The resource account is not associated with an auto attendant or call queue" as the classic dead end. Half the surface has no GUI at all and must be driven from the MicrosoftTeams PowerShell module — `Grant-CsTeamsMeetingPolicy`, `New-CsGroupPolicyAssignment -Rank 1` — with cmdlet names that do not match the UI labels. Changes take up to 24 hours to propagate, which destroys the feedback loop for anyone learning by trial. And app setup policies with pinned-app ordering silently fail when the app is not allowed by the app permission policy, with no cross-blade warning.

**AI operator:** A tenant operator pre-loaded with skills for effective-policy resolution (walking direct → group rank → global), policy authoring and assignment including batch and group-based, telephony build-out with tested normalisation regex, meeting/recording/transcription governance, external access and federation, and drift detection against a declared baseline. Everything is read-first and produces a plan with an explicit blast radius ("this affects 4,312 users in 3 countries"); wide-scope or compliance-touching changes require typed confirmation, run against a pilot group first, and generate a rollback script up front. Modes: **do-it**, **audit** (orphan policies, users sitting on the global default who should not be, recording enabled for externals, anonymous join, unassigned resource accounts, regex rules that never match), **explain** (why can Priya not create private channels — the exact precedence chain and the cmdlet that fixes it), and **simulate** (dry-run normalisation rules against a list of real dialed numbers).

**Killer example:** A one-person IT team says: "our new Bangalore office can't dial 4-digit internal extensions and the CEO is angry." The operator pulls the tenant's dial plans and runs the site's normalisation rules against sample dialed strings, finding that the India dial plan's `^(\d{4})$` rule is shadowed by an earlier `^(\d{3,5})$` that rewrites to a Chennai prefix — the priority order is wrong, not the regex. It proposes the reorder with a simulation table showing 4001 → +914440004001 before and after. While in there it flags that 27 users at that site have no Teams Phone policy at all and are inheriting a global default that blocks outbound international calling, and that one auto attendant's holiday set expired in December and has been silently routing to a disconnected resource account ever since.

**Integration path:** The MicrosoftTeams PowerShell module is the real surface (`Get-CsOnlineUser`, `Get-CsUserPolicyAssignment`, `Grant-CsTeamsMeetingPolicy`, `New-CsGroupPolicyAssignment -GroupId -PolicyType -Rank`, `New-CsTeamsTranslationRule`, `New-CsAutoAttendant`, `New-CsCallQueue`), authenticated app-only with certificate-based auth under the Teams Administrator or Teams Communications Administrator role; Microsoft Graph covers adjacent objects (`/teamwork`, `/teams/{id}/channels`, `/communications/callRecords`, `/admin/teams/settings`) with scopes like `TeamSettings.ReadWrite.All` and `CallRecords.Read.All`. Honest gap: Graph does not expose the Teams policy engine at all — there is no REST endpoint for meeting/messaging/calling policies or for assignment precedence — so the operator must host a PowerShell runtime, deal with app-only auth quirks and per-cmdlet throttling, reimplement the precedence rules itself, and accept the up-to-24-hour propagation delay before it can verify that a change actually landed.

**Demand 5/5 · Buildability 4/5**

### 5. Okta (Workforce Identity) `closed`

**Why it's powerful:** Okta is the largest independent identity provider, with roughly 20,000 customers and tens of millions of users, running SSO against a 7,000+ app integration network. It does far more than SSO: adaptive MFA with possession and knowledge factors, global session policy plus per-app authentication policies, network zones and behaviour detection, inline and event hooks, group rules, a universal directory with custom profile attributes and mappings, SCIM provisioning with attribute transforms, lifecycle states from staged through deprovisioned, Workflows for no-code automation, and API access management with OAuth authorization servers, scopes, claims and policies.

**Why people bounce off it:** The precedence model is where admins drown. Global session policy, authentication policy and the legacy sign-on policy are each ordered rule lists with first-match-wins evaluation, so inserting a rule at the wrong position silently changes access for everyone. Answering "why is this user being prompted for MFA — or not" means mentally simulating group membership, network zone, device trust and rule order across two different policy types. Profile mappings use Okta Expression Language (`String.substringBefore(user.email, "@")`) in a tiny textbox with no real test harness, and mapping direction — Okta→app versus app→Okta — is a constant source of overwritten data. SCIM provisioning failures surface as a generic admin-queue task reading "Automatic provisioning of user to app failed: Error while trying to push profile update", with the actual cause buried in the System Log. SAML app setup means matching ACS URL, audience URI, name-ID format and attribute statements against a vendor doc, where one typo yields an opaque vendor-side "invalid SAML response". Group rules cannot be reordered and do not run retroactively the way people expect. And the System Log — the only real debugging tool — is queried with an unfamiliar SCIM-filter syntax.

**AI operator:** An identity operator with skills for users, groups and lifecycle, app assignment and SAML/OIDC config, authentication and global-session policy authoring backed by an internal evaluation simulator, network zones, profile mapping and Expression Language authoring with tests, SCIM provisioning diagnosis, and System Log forensics. Reads and simulations are free; any policy write is shown as an ordered before/after rule list with an impact estimate ("this rule newly applies to 412 users, and it moves 3 service accounts out of the MFA exemption"). There is a hard interlock: the operator refuses to apply a change that would lock out all super admins or remove the last break-glass account without an explicit override phrase. Modes: **do-it**, **simulate** ("what happens when contractor Jane on an unmanaged Mac from Brazil opens Salesforce?" — a full rule-by-rule trace), and **audit** (dormant apps, users with no MFA enrollment, admin role sprawl, rules that can never match, apps still on SHA-1 SAML or with expiring certificates).

**Killer example:** An IT lead says: "make contractors use a phishing-resistant factor for Salesforce and Workday, but don't break the mobile sales team." The operator simulates first and discovers the contractors' group is nested inside "All Employees" via a group rule, so the existing employee authentication policy rule at position 2 already matches them and would shadow anything appended at the bottom — it proposes the new rule at position 2 with a scoped exclusion instead. It writes the FIDO2/WebAuthn requirement with device-trust and network-zone conditions, previews that it affects 87 users, and names the 6 mobile sales users who would be caught with no WebAuthn enrolled, offering a staged enrollment grace window. Then the surprise: Workday's SAML signing certificate expires in 19 days, and that app's provisioning has been silently failing for three weeks on 14 users because a profile mapping pushes an empty `costCenter` that Workday rejects — both visible only in System Log entries nobody reads.

**Integration path:** Okta Management API with an API token or OAuth service app — `/api/v1/users`, `/api/v1/groups`, `/api/v1/apps`, `/api/v1/policies` plus `/policies/{id}/rules`, `/api/v1/mappings`, `/api/v1/zones`, `/api/v1/logs`, `/api/v1/idps` — with scopes like `okta.policies.manage` and `okta.logs.read`; org-wide rate limits per endpoint bucket (commonly 600–1200 req/min by tier) exposed through `X-Rate-Limit-Remaining`; Workflows and the Terraform provider as alternate write paths. Honest gap: there is no official policy-evaluation or what-if API, so the simulator must be reimplemented from documented precedence rules and will drift from Okta's real evaluator on edge cases — device trust signals, behaviour heuristics and risk scoring are opaque. The profile mapping API is also partially undocumented and Expression Language has no server-side test endpoint.

**Demand 5/5 · Buildability 4/5**

### 6. Google BigQuery `closed`

**Why it's powerful:** BigQuery is serverless petabyte-scale analytics with separated storage and compute, automatic partitioning and clustering, materialized views, BI Engine in-memory acceleration, BigQuery ML (logistic regression, boosted trees, ARIMA and remote Vertex models trained in SQL), Omni for cross-cloud, and Data Transfer Service for SaaS ingest. It is the default warehouse for GCP customers and underpins the GA4 raw export, which alone pushed BigQuery into millions of Google Analytics properties. Pricing is either on-demand per TiB scanned or capacity slots via reservations with autoscaling and editions. Crucially, `INFORMATION_SCHEMA` exposes per-job bytes billed, slot-ms and referenced tables, which makes the entire cost surface introspectable by an agent.

**Why people bounce off it:** The first bill is the wall. GA4 export tables are partitioned by `event_date`, and a `SELECT *` over `events_*` without a `_TABLE_SUFFIX` filter scans years of data — the console's "This query will process 4.7 TB when run" estimate is trivially easy to click past. Partitioning and clustering must be declared at table creation and cannot be added in place, so users learn they needed `CREATE TABLE ... PARTITION BY` only after building everything on an unpartitioned table. Reservations, commitments and assignments form a three-object model people cannot hold, and idle-slot sharing across projects surprises everyone. Errors like "Resources exceeded during query execution: the query could not be executed in the allotted memory" or "Quota exceeded: Your project exceeded quota for concurrent queries" offer no remediation. BI Engine silently fails to accelerate queries using unsupported functions with no clear "why wasn't this accelerated" signal. Authorized views, row-level access policies, Dataplex column policy tags and IAM at project/dataset/table level interact so that a user can see a table listed and still get "Access Denied: User does not have permission to query table" with no path forward. And streaming inserts versus the Storage Write API versus load jobs is another fork nobody explains until the streaming line item shows up.

**AI operator:** A warehouse operator with skills for cost forensics over `INFORMATION_SCHEMA.JOBS`, physical-design rewrites (partition, cluster and materialized-view proposals with dry-run before/after byte estimates), reservation and slot sizing, BI Engine fit analysis, access-policy tracing across IAM plus authorized views plus row policies, and scheduled-query and Data Transfer management. Every proposed query is dry-run first with predicted bytes and dollars reported; any DDL, DML, table recreation, reservation change or IAM grant needs explicit approval showing the exact SQL and the cost delta; and a hard `maximumBytesBilled` guard is set on everything the operator executes. Modes: **audit** (top-cost queries and tables this month with a fix list ranked by dollars saved), **explain** (translate a job's cost or an access-denied error into cause and fix), **do-it** (execute approved changes, then re-run the benchmark query to prove the savings).

**Killer example:** A marketing lead says: "our BigQuery bill jumped from $900 to $6,100 last month, find it." The operator queries `INFORMATION_SCHEMA.JOBS_BY_PROJECT` across 30 days, ranks by total bytes billed, and finds a Looker Studio dashboard firing the same GA4 query 4,000 times because the data source has caching off and eleven people keep the tab open. Then the part nobody suspected: the query filters on `event_date` in the WHERE clause, but the underlying table is partitioned on ingestion time, so partition pruning never happens and every single run scans 14 months. It proposes a materialized view over the last 90 days plus a BI Engine reservation sized at 4 GB, dry-runs the rewritten query to show 2.1 TB → 8 GB per run, and projects the bill back down to roughly $700 before asking permission to apply anything.

**Integration path:** BigQuery REST API v2 (`jobs.insert` with `dryRun`, `jobs.query`, `tables.insert/patch`, `datasets.patch`), the Reservations API (`bigqueryreservation.googleapis.com` — `reservations.create`, `capacityCommitments`, `assignments`), BI Engine via `bireservation`, Data Transfer Service, plus the `bq` CLI and client libraries; IAM through Cloud Resource Manager `setIamPolicy` and Dataplex policy tags; scopes `bigquery` and `cloud-platform`. Honest gap: you cannot alter partitioning or clustering on an existing table, so the operator must orchestrate a create-copy-swap with a rename — genuinely risky on large tables and impossible to do atomically under concurrent writes. BI Engine acceleration reasons are only partially exposed via a coarse `bi_engine_statistics` code, and slot-level attribution for a single query inside a shared reservation is approximate.

**Demand 5/5 · Buildability 4/5**

### 7. Twilio (Messaging Services + A2P 10DLC + Studio) `closed`

**Why it's powerful:** Twilio Programmable Messaging is the default SMS rail for a huge share of US business texting — 300k+ active customer accounts, 10M+ developer accounts, and effectively every major retail and fintech brand's OTP and marketing traffic. Messaging Services give sender pools with sticky sender, geomatch and area-code matching, scheduled sends, and automatic fallback across long codes, toll-free and short codes. Studio is a drag-and-drop IVR/SMS flow builder with Send Message, Split Based On, HTTP Request, Run Function and Gather Input widgets. Verify, Conversations, Lookup, Messaging Insights and the Error Logs together give carrier-level deliverability forensics per message SID.

**Why people bounce off it:** A2P 10DLC registration alone kills small senders. You must create a Trust Hub Customer Profile with an EIN that exactly matches IRS records, then a Brand, then a Campaign with a use case, then attach the Messaging Service — and any mismatch returns an opaque `Brand Registration Failed` with a Campaign Registry vendor reason code that Twilio passes through verbatim and never explains. The Console splits this across Trust Hub, Messaging > Services, Phone Numbers and Regulatory Compliance: four left-nav sections for one logical task. Then messages start failing with 30034 (unregistered sender), 30007 (carrier filtered), 30032 (toll-free not verified), 21610 (opted-out recipient), and the Console shows the code while the fix lives on a docs page you have to go find. Studio flows silently misroute because `Split Based On` compares `{{widgets.gather_1.Digits}}` as a string while people write `= 1` expecting a number, and Liquid typos render empty rather than erroring. Opt-out handling is auto-managed at the Messaging Service level but *not* at the raw number level, so migrating numbers quietly starts violating TCPA. And throughput is governed by MPS per number times pool size times the carrier's daily brand-tier cap — a three-variable model no single Console screen ever shows.

**AI operator:** A messaging operator with skills for the Trust Hub / Brand / Campaign registration state machine, Messaging Service and sender-pool composition, number purchase and regulatory bundles, Studio flow JSON authoring and validation, and error-code triage against the Message resource plus Error Logs. Registration submissions and number purchases cost money and are hard to reverse, so both require explicit confirmation with a cost line; Studio publishes land in a Draft revision the user approves before `Publish`; read-only diagnosis needs no approval at all. Modes: **do-it** (register brand, build service, author flow), **audit** (scan every Messaging Service for missing opt-out, unregistered senders, unverified toll-free numbers, and throughput headroom against actual send volume), **explain** (decode any error code or delivery failure against the real message record), plus a deliverability watch that flags carrier-filtering trends before a campaign gets blocked outright.
