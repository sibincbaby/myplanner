### 1. Shopify — Discount Function API `closed`

**Why it's powerful:** Shopify Functions are merchant-owned WebAssembly modules that execute inside Shopify's own checkout, and the unified Discount Function API (2025-04+) collapsed the old separate product/order/shipping discount APIs into one surface: a single function now emits `Order`, `Product` and `Shipping` discount classes from `cartLinesDiscountsGenerateRun` and `cartDeliveryOptionsDiscountsGenerateRun`, returning a `CartLinesDiscountsGenerateRunResult` of operations under one discount code. The input is a GraphQL query over the live cart — lines, merchandise, cost, buyer identity, metafields — so eligibility can depend on collection membership, customer segment, tags or any metafield. Functions are free on every plan with no per-execution fee and run at checkout speed. This is the machinery behind every promotion more interesting than "10% off".

**Why people bounce off it:** A merchant cannot express even "buy 2 get the cheapest free, excluding sale items" from the Admin UI — the native discount screens can't combine tiering × collection × segment × exclusion, and stacking is governed by `combinesWith` flags plus discount-class semantics that are invisible until a real cart misbehaves. Writing a function means Rust or JS/AssemblyScript (the compiled artifact must stay under the ~200 KB WASM cap, which Go's output blows and Python can't even attempt), packaged as an app, deployed via `shopify app deploy` with versioned extensions — and custom apps containing Function APIs only run on Plus. The Scripts→Functions migration was not a Ruby-to-Rust translation but an architectural change from imperative cart mutation to declarative operations, so when Shopify Scripts was finally sunset on 30 June 2026 (after one deadline slip from 28 Aug 2025) and remaining published Scripts were deactivated, a lot of stores discovered on 1 July that their promo logic was simply gone; "Additional scripts" removal followed on 26 Aug 2026. Worst of all, failure is silent in both directions: a function returning no operations produces a checkout with no discount and no error anywhere in the Admin, while a misconfigured `combinesWith` produces a 46%-off cart nobody modelled. Testing requires hand-authoring JSON cart fixtures for `shopify app function run`. What people do instead: pay agencies for custom function builds, install a stacking/discount app with monthly fees and an extra checkout dependency, or quietly downgrade the promotion to something the native UI can express (flat % off) and eat the margin.

**AI operator:** Reads catalog and collections, customer segments, existing `discountNode`s with their metafield configs, and a sample of recent real carts. The LLM emits a **promotion spec** — eligibility predicates, tier table, exclusions, combination policy, schedule, caps — never Rust and never WASM. A deterministic layer binds that spec into a pre-audited, parameterized generic function whose entire behaviour is driven by the discount's metafield payload, so nothing is ever compiled from model output; it then applies via `discountAutomaticAppCreate` / `discountCodeAppCreate`. Self-verification replays 200+ sampled historical carts through `shopify app function run` and diffs expected vs actual discount amounts and post-discount margin, then creates the discount inactive. Guardrails: max-discount-% and negative-margin tripwires, a mandatory dry-run cart matrix before activation, and no edit of a live discount without a before/after allocation diff.

**Killer example:** A merchant says: *"Run buy-2-get-the-cheapest-free on the Autumn collection for two weeks, but never on stuff that's already marked down, and don't let it stack on top of the VIP 15%."* The operator builds the spec, replays 1,842 real carts, and reports that **61 carts stack to 46% off** because the VIP 15% is an order-class discount while the BOGO is product-class — so it sets `combinesWith.orderDiscounts = false`. Then the non-obvious finding: 3 SKUs sit in both Autumn and Clearance, so the "free" item is already 40% off and the bundle lands at −8% gross margin. It excludes those three, schedules the discount inactive, and returns the projected 14-day cost.

**Integration path:** Function APIs `cartLinesDiscountsGenerateRun` and `cartDeliveryOptionsDiscountsGenerateRun` (Discount Function API, 2025-04+); Admin GraphQL `discountAutomaticAppCreate`, `discountCodeAppCreate`, `discountNode` + metafields; Shopify CLI `app deploy` and `app function run`; OAuth for the custom/public app. A free Partner dev store plus the free CLI gives a complete local build — no sales call, no Plus contract needed to develop.

**Demand 5/5 · Buildability 5/5**

### 2. Salesforce — Enterprise Territory Management `closed`

**Why it's powerful:** A territory model is a full parallel org structure: `Territory2Model` → `Territory2` hierarchy typed by `Territory2Type`, populated by `Territory2Rule` criteria, with per-territory access levels for Account, Opportunity, Case and Contact that drive record sharing *independently of the role hierarchy*. Models live in Planning / Active / Archived states, so an entire reorg can be built and previewed against real data before activation. Territory forecasts, forecast types, quotas and adjustments hang off the active model. Opportunity assignment runs through a deployable Apex class implementing `OpportunityTerritory2AssignmentFilter`, and every assignment materializes as queryable `ObjectTerritory2Association` / `UserTerritory2Association` rows. It ships in Enterprise, Performance, Unlimited and Developer editions — i.e. essentially every mid-market-and-up org in the world's largest CRM install base, with a documented ceiling of 1,000 territories per model.

**Why people bounce off it:** The rule criteria UI lies about data types. Salesforce's own guide has to warn that ZIP codes are alphanumeric, so in a comparison "9 is 'higher' than 80000", and that with state/country picklists enabled, state criteria must use `contains` and never `equals`. Then the silent no-op stack: rules only fire on account create/update when the model is **Active**, *and* UI updates additionally require the "Evaluate this account against territory rules on save" checkbox on the account layout, *and* API updates require `AssignmentRuleHeader` to be set, *and* inserts require "Run territory assignment rules during account inserts" in Territory Settings. Miss any one of the four and rules never run again, forever, with no error. "Apply to Child Territories" combined with separately assigning the same rule to a child produces duplicate assignments — the documentation has to tell admins not to do it. Territory Type Priority is a numeric scheme you invent ("001 can indicate highest or lowest") that does nothing at all unless your Apex filter reads it. Opportunities aren't rule-assignable; you must write and deploy Apex. Archiving a model deletes territory forecasts, forecast types, quotas and adjustments; activation fires no triggers on `Territory2Model`, `Territory2` or `UserTerritory2Association`, so custom automation silently skips; and cloning a model copies rules, users and manual accounts but **not** leads. In practice RevOps buys a territory ISV (Fullcast, Kubaru, Gradient Works), pays a Salesforce partner for a reorg project, or runs the whole thing in spreadsheets with manual `ObjectTerritory2Association` uploads via Data Loader.

**AI operator:** Reads `Territory2Model` / `Territory2` / `Territory2Type` / `Territory2Rule` metadata via Metadata + Tooling API, plus SOQL over `ObjectTerritory2Association`, `UserTerritory2Association`, account field distributions and open-pipeline sums. The LLM emits a **territory plan spec** (territory tree, types with numeric priorities, rule predicates as typed field/operator/value triples, access levels, user assignments) — never metadata XML. A deterministic compiler renders `Territory2*` metadata, deploys it into a **clone of the active model in Planning state**, runs assignment rules, and diffs associations before/after. Self-verification: coverage report (accounts with 0 or >1 territory), pipeline balance per territory, plus a static linter that fails the spec for string-compared ZIP ranges, `equals` on picklist states, and each of the four missing prerequisites. Guardrails: never mutate the Active model, activation needs explicit human approval, archive is blocked when quotas or forecast adjustments exist, and rollback is simply deleting the planning clone.

**Killer example:** A sales VP says: *"Split the West region in two so no rep carries more than $12M of pipeline, but don't break anyone's forecast mid-quarter."* The operator clones the active model into Planning, creates "West-North"/"West-South" under type "Region", writes zero-padded ZIP-range rules (dodging the 9-vs-80000 trap), runs rules in Planning and reports: 1,842 accounts move, West pipeline $23.4M → $11.9M / $11.5M, 3 accounts now orphaned. Then the finding nobody asked for: **214 Texas accounts have been frozen since 2023** — they've survived two prior reorgs untouched because the "Evaluate this account against territory rules on save" field isn't on the Account layout and the MDM integration user never sets `AssignmentRuleHeader`. It also refuses to archive the old model until you acknowledge that doing so deletes 38 territory quotas and 12 forecast adjustments.

**Integration path:** Metadata API types `Territory2Model`, `Territory2`, `Territory2Type`, `Territory2Rule`, `Territory2Settings` (deploy with `sf project deploy start`); SObjects `Territory2`, `Territory2Model`, `Territory2Type` (`Priority` is numeric-only and API-settable), `ObjectTerritory2Association`, `UserTerritory2Association`; Apex interface `OpportunityTerritory2AssignmentFilter`; REST/Bulk API for account profiling; OAuth 2.0 JWT-bearer connected app. **Free Developer Edition orgs include Enterprise Territory Management**, so the entire product can be built and demoed at zero cost.

**Demand 5/5 · Buildability 5/5**

### 3. Salesforce — Duplicate Management `closed`

**Why it's powerful:** `MatchingRule` metadata defines field-by-field comparison with exact and fuzzy methods (company name, first/last name, city, street), blank-field handling and normalization; `DuplicateRule` decides the action (block vs alert), the scope (create/edit) and per-profile bypass. Duplicate jobs materialize results as `DuplicateRecordSet` / `DuplicateRecordItem`; Apex `Datacloud.FindDuplicates` evaluates candidate records at runtime; merges run through `Database.merge` or SOAP `merge()`. It is a genuine, fully API-addressable identity-resolution engine living inside the CRM — and the pain around it sustains an entire ISV economy (DemandTools, Cloudingo, DataGroomr, Duplicate Check) at typically $5–20k/yr per org.

**Why people bounce off it:** The caps bite on day one: three matching rules per duplicate rule, five deployable duplicate rules per object, and duplicate jobs run one matching rule at a time and are documented to fail outright in large orgs. Standard matching rules exist only for Account, Contact and Lead. There is **no native cross-object lead-to-account matching** — the one behaviour every RevOps team actually wants. Native merge handles a maximum of three records at a time and there is no mass merge, so any cluster of four or more duplicates is structurally unmergeable without code or an ISV. Matching-rule activation is an asynchronous index build, so admins test too early, see nothing match, and conclude the feature is broken. Fuzzy-vs-exact is chosen per field and never surfaced in the result, so nobody can explain why two records matched — or why `sam@acme.com` matched while "Sam" and "Samuel" didn't. And alert-only rules train users to click "Save anyway" forever. The observed outcome: export to Excel, buy a dedupe ISV, or retain ops contractors on recurring "data hygiene" engagements.

**AI operator:** Reads existing `MatchingRule` / `DuplicateRule` metadata, per-field fill rates, record-creation-source patterns and a stratified record sample. The LLM emits a **matching spec** — per-field method and blank handling, exclusion criteria, confidence tiers, and a merge survivorship policy (master selection, field-level winner rules, child-record union) — never raw XML. A deterministic layer compiles to Metadata API XML, deploys to a scratch org or sandbox, simulates with `Datacloud.FindDuplicates` over the sample, and produces a **labeled confusion matrix before anything touches production**. Merges execute via `Database.merge` in bounded batches with a complete before/after JSON audit. Self-verification: precision/recall against a human-labeled sample, plus a post-merge integrity check for orphaned opportunities/cases and lost activities. Guardrails: never auto-merge below a confidence threshold, never merge records with open opportunities unless explicitly allowed, hard batch caps, and an exported snapshot per merge wave so every wave is reversible.

**Killer example:** An ops lead says: *"There are three 'Acme' accounts and nobody knows which one the renewal is on — clean it up and stop it happening."* The operator scans 480k accounts under a spec of fuzzy company name + exact normalized website domain + billing postal code with blanks unmatched, and finds 6,214 duplicate clusters — **412 of which contain 4 or more records and are therefore impossible for native merge's 3-record cap**, so it chains merges deterministically. It proposes survivorship (oldest `CreatedDate` as master, most-recent non-blank field wins, union of children). The non-obvious finding: 1,107 of the duplicates were created by a single integration user inside one 6-week window when the contact duplicate rule was Alert-only *and* its matching rule keyed on Email while that same integration wrote contacts with Email blank — the rule could never have fired for a single one of them.

**Integration path:** Metadata API types `MatchingRule` (inside `MatchingRules`) and `DuplicateRule`; SObjects `DuplicateRecordSet`, `DuplicateRecordItem`, `DuplicateJobDefinition` / `DuplicateJob`; Apex `Datacloud.FindDuplicates` / `Datacloud.FindDuplicatesByIds`; merge via Apex `Database.merge` or SOAP `merge()`; Bulk API 2.0 for extraction; OAuth 2.0 JWT-bearer. Free Developer Edition plus scratch orgs cover the entire MVP including the simulation harness.

**Demand 5/5 · Buildability 5/5**

### 4. Microsoft Fabric — capacity (CU) governance, throttling & Direct Lake guardrails `closed`

**Why it's powerful:** One pooled compute currency — Capacity Units — runs Spark notebooks, Warehouse T-SQL, pipelines, Dataflows Gen2, Eventhouse and Power BI DAX on the same capacity, with bursting (up to 16× briefly) and smoothing (interactive operations smoothed over 5–64 minutes, background operations over 24 hours). Direct Lake semantic models read Delta/parquet straight out of OneLake, so "refresh" becomes metadata framing in seconds rather than a data copy, while VertiPaq still answers DAX. Per-SKU guardrails govern parquet files per table, row groups, rows per table (300M at F2–F32, 1.5B at F64) and max model size. Everything is scriptable: TMDL semantic-model definitions, OneLake shortcuts, deployment pipelines, ARM capacity operations. Microsoft puts Fabric at 31,000+ customers with adoption by 70% of the Fortune 500, and every Power BI Premium/P-SKU estate is being migrated onto F-SKUs.

**Why people bounce off it:** Consumption is invisible at the moment you cause it. A notebook that ran at 02:10 is smeared across 24 hours of smoothing and throttles interactive reports at 13:35 — so the person filing "reports are slow, nothing changed" is looking at a completely different workload than the one responsible. The three throttle states (interactive delay → interactive reject with HTTP 429 → background reject) surface as opaque "capacity limits" errors with no pointer to the offending item, and the only real diagnostic is the Fabric Capacity Metrics app, itself a Power BI app whose timepoint-detail drill and CU(s)-vs-smoothed-CU semantics defeat most admins. Pausing the capacity to save money *immediately* bills outstanding overage and reconciles smoothed usage — the exact opposite of what people expect. Direct Lake then adds a second silent failure class: Direct Lake on SQL analytics endpoint **falls back to DirectQuery** when a table is built on a non-materialized view, when SQL-endpoint RLS is enforced, or when any guardrail is exceeded. Refresh "succeeds with a warning," queries still return, they're just 10× slower — and successful framing operations aren't even listed in refresh history. Direct Lake on OneLake does the reverse and fails refresh outright. Community forums are wall-to-wall "Understanding F4 capacity", "MS Fabric pricing bursting smoothing", "getting reaching capacity limits error". What people do instead: over-provision straight to F64, install FUAM or third-party monitoring, or retain Fabric consultants for an "optimization assessment".

**AI operator:** Reads the Capacity Metrics semantic model via DAX (`executeQueries` / XMLA), Fabric item inventory and job instances, Delta table statistics (file counts, row groups, V-Order state), and semantic-model TMDL definitions. The LLM emits a **remediation spec** — items to reschedule out of the interactive window, tables to OPTIMIZE / V-Order, models to convert or have fallback disabled, SKU scale and pause windows — never hand-written TMDL. A deterministic applier renders TMDL parts and calls `updateDefinition`, patches schedules, submits OPTIMIZE notebook jobs, and drives ARM suspend/resume/SKU update. Self-verification re-queries the metrics model for peak CU%, throttle state and per-item CU(s) over the next cycle, and asserts DirectQuery-fallback counters are zero in the model's query traces. Guardrails: dry-run diff of every TMDL change, never scale up without stating the dollar delta, never pause a capacity with outstanding overage, and all writes scoped to workspaces the service principal actually administers.

**Killer example:** A BI lead says: *"Every Tuesday afternoon the sales reports crawl and IT says buy more capacity."* The operator queries the Capacity Metrics model, finds a 02:10 Spark notebook consuming 41k CU(s) smoothed across 24 hours that pushes the F16 to 118% at 13:35, and correlates the interactive-delay window exactly with the slow reports. Then the non-obvious finding: the Sales Direct Lake model's fact table has **1,187 parquet files against the F16 guardrail of 1,000, so it has been silently falling back to DirectQuery for six days** since a schema change. It emits a plan — OPTIMIZE + V-Order that table (1,187 → 54 files), move the notebook to 22:30, disable fallback so future regressions error loudly — and verifies peak CU 118% → 76% and p95 report render 14 s → 2.3 s, with no SKU change and no extra spend.

**Integration path:** Fabric REST `GET /v1/capacities`, `GET /v1/workspaces/{id}/semanticModels`, `POST /v1/workspaces/{id}/semanticModels/{id}/getDefinition|updateDefinition` (base64 TMDL parts: `definition/model.tmdl`, `definition/tables/*.tmdl`, compatibilityLevel ≥ 1604); Power BI `POST /v1.0/myorg/datasets/{id}/executeQueries` for DAX against the Capacity Metrics model (requires the "Semantic model Execute Queries REST API" tenant setting), `GET /v1.0/myorg/admin/capacities`; XMLA endpoint `powerbi://api.powerbi.com/v1.0/myorg/<workspace>` with TOM/TMSL; ARM `Microsoft.Fabric/capacities` Suspend/Resume/CreateOrUpdate/Update. Auth: Entra ID service principal with capacity + workspace admin. MVP on a Fabric 60-day trial or F2 pay-as-you-go at a few dollars a day.

**Demand 5/5 · Buildability 4/5**

### 5. GSTN / NIC IRP — India e-invoicing, e-way bill & GSTR-2B / IMS ITC reconciliation `government platform`

**Why it's powerful:** The Invoice Registration Portal issues an IRN plus signed QR per invoice, auto-populates GSTR-1, generates the e-way bill directly from the IRN (Part A/B, transporter, distance-based validity), and feeds the Invoice Management System where every inward invoice must be accepted, rejected or kept pending — which in turn determines GSTR-2B, which determines claimable input tax credit. Cancellation of an IRN is possible only within 24 hours; after that it's a credit note. Mandatory for every GST-registered business above the ₹5 crore AATO e-invoicing threshold, sitting on top of roughly 1.4 crore GST registrations filing GSTR-1/3B monthly. The forcing function is dated: **from April 2026 the portal hard-blocks any GSTR-3B where Table 4A ITC exceeds GSTR-2B — the return will not save.** Real money moves through this; ITC is working capital.

**Why people bounce off it:** Matching books to GSTR-2B fails on cosmetics. The same invoice is `INV/2026/0042` in the supplier's ERP and `INV-2026-42` in your purchase register, and the portal stores whatever the supplier typed — so the invoice reads as "missing" and the credit gets held back. GSTR-2B generates on the 14th and the return is due on the 20th, leaving a six-day window in which a CA must chase suppliers, action every IMS row, and re-run reconciliation. Place-of-supply errors flip IGST to CGST/SGST, so the tax exists but sits in the wrong bucket and is unclaimable. Rule 37/37A reversals (180-day non-payment, supplier default) must be tracked entirely outside the portal. E-way bill Part-B and distance validations reject at the loading dock and stop trucks. Get any of it wrong and you get interest under s.50 plus blocked ITC — and from April 2026 you simply cannot file. The universal workaround is an Excel VLOOKUP reconciliation done by hand by an article clerk every month, or a per-GSTIN ASP/GSP subscription that still dumps a 3,000-row mismatch report on a human.

**AI operator:** Reads the purchase register (Tally / Zoho / ERP export), GSTR-2B JSON, IMS state and the tax ledgers. The LLM emits a **reconciliation-and-action spec**: fuzzy match rules with tolerances, per-invoice IMS action with a stated reason, supplier follow-up list, Rule 37 reversal candidates, and a Table-4A/4B mapping — never a raw filing payload. A deterministic engine executes via GSP APIs. Self-verification: recomputed 2B totals must tie to the portal's own 2B summary; claimed ITC per tax head must tie to the books' input tax ledger; every invoice must land in exactly one bucket (matched / in-books-not-2B / in-2B-not-books / mismatch). Guardrails: the agent may **save** but never **submit or file** (no DSC/EVC path at all), never cancels an IRN, and every money-affecting action is dry-run with a diff report first.

**Killer example:** A CFO says: *"Why is my ITC ₹4.7 lakh short this month, and can I still file on the 20th?"* The operator reconciles 1,842 purchase invoices against GSTR-2B and recovers ₹2.9 lakh from 23 invoices that differed only by invoice-number formatting plus 4 with a one-rupee rounding difference; identifies 6 invoices (₹88k) where the supplier filed against the wrong GSTIN of yours and drafts the correction email with invoice numbers and dates; marks 9 IMS rows "pending" so they don't inflate Table 4A. Then the one nobody was looking for: **₹1.21 lakh of ITC already claimed in December is due for Rule 37 reversal this month** because those two suppliers remain unpaid past 180 days — an interest-bearing default in the making.

**Integration path:** NIC IRP sandbox at `einv-apisandbox.nic.in` — Authentication and Get GSTIN Details (v1.04, `/eivital/...`), Generate/Cancel IRN, Get IRN Details, Get IRN by Doc Details, Get Rejected IRNs (v1.03), Generate e-Way Bill by IRN, Cancel EWB, Get EWB by IRN (v1.03). Auth is layered: client-id/client-secret plus username/password and a 32-byte AppKey, with password+AppKey RSA-encrypted (RSA/ECB/PKCS1Padding) against the e-invoice public key; the response returns an AuthToken and SEK, and payloads are AES-256 (AES/ECB/PKCS7Padding) encrypted with the SEK; headers `Gstin`, `user_name`, `AuthToken`, subscription key. Token life 1h sandbox / 6h production. Return filing and 2B retrieval go through a licensed GSP (Vayana, Adaequare): `GET /gstr2b/get2b`, GSTR-1 section endpoints, GSTR-3B save/file. Free sandbox for taxpayers over ₹5 crore AATO or via GSP PAN registration.

**Demand 5/5 · Buildability 4/5**

### 6. F5 BIG-IP — LTM traffic policies, iRules & AS3 `closed (AS3 / DO / FAST are open-source)`

**Why it's powerful:** One platform terminates TLS, load-balances and rewrites traffic: virtual servers, pools, health monitors with send/receive strings, persistence profiles, SNAT/auto-map, OneConnect multiplexing, client/server SSL profiles, and Local Traffic Policies. On top sits iRules — event-driven TCL running inline in TMM on `CLIENT_ACCEPTED`, `HTTP_REQUEST`, `LB_SELECTED`, `HTTP_RESPONSE` — which is precisely why F5 survives every "just use an ALB" migration. Advanced WAF/ASM signatures and learning policies, APM access policies, and GTM/DNS wide IPs round it out. F5 states 85% of the Fortune 500 and 48 of the Fortune 50 run its platform; 6sense tracks ~4,300 organizations using BIG-IP as their load balancer, concentrated in banking, government, healthcare and telco.

**Why people bounce off it:** iRules execute per-connection inside the Traffic Management Microkernel, so an unguarded `HTTP::collect` or a blocking command doesn't break one app — it spikes TMM CPU or cores the microkernel and takes *every virtual server on that TMM* with it. And there is no staging: the iRule attaches to a live VIP. Health monitors are the quietest killer — a receive string of `HTTP/1.1 200` against a backend that now answers HTTP/2 marks members down while the GUI stays green. SNAT auto-map versus no-SNAT changes the return path, so correct-looking config produces half-open connections from asymmetric routing. Profile inheritance means editing a parent `http` profile silently mutates dozens of VIPs. Partitions and route domains (`%1` syntax) hide objects from each other and from the GUI's own object pickers, so references fail with cryptic validation errors. In a sync-failover device group, "changes pending" doesn't tell you which direction is safe — push the wrong way and you overwrite the good unit's config; unsaved changes vanish on reboot unless someone ran `tmsh save sys config`. Consequence: orgs freeze BIG-IP changes into quarterly windows, funnel every request through two or three certified engineers, pay F5 partners for anything nontrivial, or front BIG-IP with a cloud LB purely to avoid touching it.

**AI operator:** Reads `GET /mgmt/shared/appsvcs/declare` for current AS3 tenants, `/mgmt/tm/ltm/virtual|pool|rule|monitor|profile`, `/mgmt/tm/cm/device-group` sync state, and recent `/var/log/ltm`. The LLM emits an **AS3 declaration plus an English change plan** — never tmsh. The deterministic apply is the best-in-class part of this idea: `POST /mgmt/shared/appsvcs/declare` with `"action": "dry-run"` runs the full validation chain without touching config, and the tool diffs the dry-run result against the `retrieve` output into a structural diff. Only on approval does it re-POST with `action: deploy` (optionally async, polling `/mgmt/shared/appsvcs/task/{id}`). Guardrails: a UCS archive auto-taken before every deploy; new TCL iRules must first run against captured traffic on an isolated VE and are never authored straight into production; explicit confirmation for anything touching `/Common`, SSL profiles, or device-group sync.

**Killer example:** An engineer says: *"Our payments API is throwing 502s only for customers behind a corporate proxy, and I'm not getting a change window for this."* The operator reads `/Common/vs_payments_443`, sees `oneconnect-default` (mask 0.0.0.0) stacked with source-address persistence, counts 1,412 `Connection error ... reset` lines in ten minutes of `/var/log/ltm`, and surfaces the cause: **the pool has 6 members but monitor `https_payments` uses receive string `HTTP/1.1 200` while two upgraded members now answer HTTP/2**, so they flap down and the proxy's long-lived multiplexed connections land on the flapping pair. It emits an AS3 declaration changing the receive string to match `HTTP/(1\.1|2)` and setting the OneConnect source mask to 255.255.255.255; `action: dry-run` passes clean; after approval it deploys and confirms available pool members go 4/6 → 6/6.

**Integration path:** iControl REST `https://<bigip>/mgmt/tm/...` (Basic auth or token via `POST /mgmt/shared/authn/login`); AS3 at `/mgmt/shared/appsvcs/declare` supporting POST/GET/PATCH/DELETE with the `action` enum `deploy|dry-run|patch|redeploy|retrieve|remove` and a Controls class exposing `dryRun`, `trace`, `traceResponse`, `logLevel` (AS3 3.30+); Declarative Onboarding at `/mgmt/shared/declarative-onboarding`; f5-sdk-python, the `f5networks.f5_modules` Ansible collection, and the F5 Terraform provider. MVP: free 90-day BIG-IP VE trial plus the **non-expiring BIG-IP VE Developer Lab License** documented on DevCentral.

**Demand 5/5 · Buildability 4/5**

### 7. Meta Ads — Conversions API & dataset event quality `closed`

### 8. ZATCA Fatoora Phase 2 — clearance / reporting integration `government spec, free SDK + sandbox`

**Why it's powerful:** B2B standard invoices must be **cleared in real time** by ZATCA before they can legally be issued; B2C simplified invoices must be **reported within 24 hours**. Each document is UBL 2.1 XML with the KSA extension, carrying a XAdES B-B signature bound to a Cryptographic Stamp Identifier, a TLV-encoded QR, an ICV counter that must increment by exactly 1, and a PIH (SHA-256 of the previous invoice's canonicalised XML) forming a per-device hash chain. Onboarding runs CSR → Compliance CSID → per-document-type compliance checks → Production CSID with renewals. It applies to every VAT-registered business in Saudi Arabia, onboarded in waves still rolling through 2026 (Wave 24+ pulling in progressively smaller taxpayers) — hundreds of thousands of taxpayers and effectively every ERP and POS vendor selling into the Kingdom.

**Why people bounce off it:** Every failure mode is cryptographic and completely opaque to the finance team that owns the consequences. "Signature validation failed" almost always means one of three unrelated things: signing before XML canonicalisation, a wrong digest algorithm in SignedInfo, or a keystore still pointing at the **Compliance** CSID after go-live. BR-KSA-31 surfaces as duplicate UUIDs or a broken ICV chain — which is exactly what a retry-after-timeout produces, because the device stored a hash for an invoice ZATCA never accepted. BR-CO-15 / BR-CO-14 fire on sub-riyal rounding differences between line extension totals and the VAT total. Field-length rules like BR-KSA-F-06-C19 (item name BT-153) reject an entire invoice over one long product description. And the legacy gateway host was decommissioned in September 2025, so stale configs simply stop working. The business impact is immediate and physical: a POS that cannot clear cannot legally issue an invoice, so the till stops and the accountant on shift can only phone someone. Companies respond by hiring integrators or paying per-invoice middleware vendors.

**AI operator:** Reads the rejected XML, ZATCA's `validationResults` (errors and warnings), the device's CSR config, certificate chain and CSID type, and the local ICV/PIH ledger. The LLM emits a **remediation spec**: an ordered list of field-level patches each citing the exact BT/KSA rule it addresses, config changes, and which onboarding step must be re-run — never raw signed output. A deterministic pipeline re-canonicalises, re-hashes, re-signs, runs the **official ZATCA SDK validator locally**, then submits to the simulation `/compliance/invoices` endpoint. Self-verification: local validator clean, simulation clearance accepted, ICV strictly +1 with PIH equal to the hash of the prior accepted document, VAT totals recomputed from lines. Guardrails: production clearance/reporting submission requires human approval; CSID private keys and secrets never enter LLM context; chain re-sequencing is written to an audit log.

**Killer example:** A retail IT manager says: *"The Riyadh branch POS has been rejected since yesterday morning and 412 invoices are stuck."* The operator replays the rejection stream and isolates the first failure at 09:14 — a network timeout where the device stored the PIH of an invoice ZATCA never accepted — then shows that chain break cascading into 411 BR-KSA-31 rejections. It produces a re-sequencing plan with corrected ICV/PIH values validated against the simulation endpoint, and surfaces a second, independent defect nobody was looking for: **one of the three tills has been signing with the Compliance CSID ever since a certificate renewal 39 days ago**, so its invoices would have failed production clearance regardless of the chain fix.

**Integration path:** Base `https://gw-fatoora.zatca.gov.sa` — production `/e-invoicing/core/compliance` (compliance CSID), `/e-invoicing/core/compliance/invoices`, `/e-invoicing/core/production/csids`, `/e-invoicing/core/invoices/reporting/single`, `/e-invoicing/core/invoices/clearance/single`, with identical simulation twins under `/e-invoicing/simulation/...`. Auth: Basic with CSID + secret, versioned via API version header; payload is base64 UBL 2.1 XML plus invoice hash and UUID. ZATCA's developer portal publishes Swagger files, an SDK (hashing/QR/validation) and the *E-invoicing Detailed Technical Guidelines*. **Free, self-serve sandbox/simulation plus an official offline validator — the strongest MVP story in this digest.**
