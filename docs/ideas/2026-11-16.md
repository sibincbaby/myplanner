### 1. Salesforce Lead and Case Assignment Rules, with Escalation Rules, Auto-Response Rules and Queues (lead and case routing) `closed`

**Why it's powerful:** This is the native routing engine behind almost every Salesforce org's inbound funnel. Ordered rule entries can match up to 25 criteria each or a formula, and they route to users or queues, fire notification templates, and work alongside escalation (SLA-age) and auto-response rules. It costs nothing extra and runs on every web-to-lead, API insert, and email-to-case.

**Why people bounce off it:** Only one rule can be active per object, and entries are evaluated top-down with first match winning, so one mis-ordered entry silently swallows a whole region. There is no native round-robin. Admins fake it with an autonumber plus a MOD() formula field and one entry per rep, so changing headcount means editing many entries. Nothing in the UI shows why a specific lead landed where it did. API-inserted leads skip the rules unless a header is set. Teams pay for LeanData or Chili Piper largely to escape this screen.

**AI operator:** A routing copilot that retrieves the org's AssignmentRules, EscalationRules, AutoResponseRules, Queue and Group metadata and renders the current routing as a plain-language decision table ('entry 3: Country=DE/AT/CH AND Employees>500 -> DACH Enterprise queue'). It translates spoken routing changes into a re-ordered rule XML and maintains the round-robin helper formula field when reps join or leave. It deploys check-only to a sandbox, then replays a set of real recent leads with the auto-assign header to show exactly which entry each would hit before and after. Only after that does it promote. A 'why did this lead go to Bob?' mode re-evaluates a record against the ordered entries.

**Killer example:** A sales ops manager says: 'Why did the Siemens lead go to the generic EMEA queue? And from Monday, DACH leads over 500 employees should round-robin between Anna, Ben and Chen, with Spanish web leads getting the Spanish auto-reply.' The AI first answers the why: the Siemens lead matched entry 4 (Region=EMEA catch-all) because entry 6 (DACH Enterprise) sits below it and never fires. It has been swallowing 38 DACH leads a month since March. It then adds a RoundRobin_DACH__c formula (MOD of the lead autonumber, 3 values), inserts three DACH entries above the EMEA catch-all, deletes the dead entry 6, and adds a Spanish AutoResponseRule entry. A check-only deploy passes. It replays last week's 200 inbound leads in the sandbox: '41 change owner (14 Anna, 14 Ben, 13 Chen), 0 fall through to the default owner, nothing outside DACH moves.' The user says 'ship it' and it deploys. When Chen leaves in May, 'take Chen out of DACH' re-cuts the formula to MOD 2 and removes one entry.

**Integration path:** Salesforce Metadata API types AssignmentRules, EscalationRules, AutoResponseRules, Queue, Group and CustomField (formula), through the sf CLI (project retrieve/deploy, --dry-run validation). REST/SOAP inserts use the Sforce-Auto-Assign header or AssignmentRuleHeader for the replay test. SOQL on Lead/Case and LeadHistory/CaseHistory gives before/after owner diffs. MVP: retrieve, edit XML, validate, replay in sandbox, deploy.

**Demand 4/5 · Buildability 4/5**

### 2. Sonatype Nexus Repository (Community Edition / Pro): cleanup policies, blob stores, content selectors and CE usage limits `open-source`

**Why it's powerful:** Nexus is the most widely self-hosted artifact repository: one server proxies and hosts Maven, npm, PyPI, Docker, NuGet, Helm, apt/yum, Go and raw formats behind group repositories. Nearly every Java shop and many enterprises route all dependency downloads and CI artifact publishing through it. It has cleanup policies, blob stores (file/S3/Azure), routing rules, content selectors (CSEL) for path-scoped privileges, and scheduled tasks.

**Why people bounce off it:** The two problems every admin eventually hits are disks filling up and, since Sonatype replaced OSS with Community Edition, hitting the CE component and request-per-day caps, after which writes get blocked. Fixing either means understanding that cleanup policies only soft-delete. Policies must be attached per repository and per format with format-specific criteria (last downloaded, release vs. prerelease, regex). A 'Compact blob store' task has to run afterwards, Docker also needs separate 'delete unused manifests' tasks, and usage metrics lag by an hour. Group-repository member order and routing rules quietly change which artifact a build gets. CSEL privileges use an expression syntax almost nobody writes correctly. Most teams either never clean up or delete something a release still needed.

**AI operator:** A 'Repo Janitor' agent that inventories every repository, format, blob store and task. It samples component metadata (last downloaded, age, version patterns, size per repo) to work out where space and component count actually go. It drafts cleanup policies with a dry-run count and estimated GB freed, using the 3.95+ cleanup-policy REST dry-run where available. It attaches the policies, chains the cleanup, Docker manifest and blob-compaction tasks in the right order, and reports real space and component-count reclaimed against CE limits. It also writes CSEL content selectors and roles from plain-language access rules, and explains which group member served a given artifact.

**Killer example:** An admin says: 'We got the Community Edition over-limit warning, writes get blocked next week, and the disk is 94% full. Get us under the limits without breaking any release build.' The AI shows that 71% of the 112k components are Maven SNAPSHOTs and Docker CI tags in 4 repositories, and that 3 existing cleanup policies were created but never attached to any repo. It proposes 3 policies: keep SNAPSHOTs downloaded in the last 30 days, delete docker-ci tags matching ^pr-.* not pulled in 14 days, and purge npm-proxy cache entries unused for 180 days. It excludes every release repository and every version pulled by CI in the last 90 days. The dry-run matches 38,412 components and about 610 GB. On approval it attaches the policies and runs cleanup, then 'Docker - Delete unused manifests and images', then blob-store compaction, in that order. An hour later it confirms the count fell to 61k (under the CE cap) and disk is at 52%. It also points out that the maven-public group lists maven-central ahead of the internal releases repo, so a public artifact can shadow an internal one, and offers the one-line reorder.

**Integration path:** Nexus REST API v1 (/service/rest/v1): repositories CRUD per format, blobstores (including quota), tasks (list/run), search and components (with lastDownloaded via assets), security roles/privileges/content-selectors, routing-rules, and the cleanup-policy endpoints including the dry-run/execute API added in 3.95. Groovy scripting API is a fallback on older versions. Note: a community MIT MCP server (brianveltman/sonatype-mcp) covers basic repository, blob store and task CRUD, but not policy design, dry-run-to-compaction orchestration, CE-limit planning or CSEL authoring.

**Demand 4/5 · Buildability 4/5**

### 3. TestRail (Idera / Sembi), with Xray and Zephyr Scale for Jira as second connectors `closed`

**Why it's powerful:** TestRail is the default test-case system for QA teams in mid-size and enterprise software shops. It covers suites and sections, case templates with custom fields, shared steps, milestones, test plans that cross configurations (browser x OS x device), runs, results, defect links to Jira, and coverage and traceability reports. Xray and Zephyr give Jira-native teams the same model.

**Why people bounce off it:** Writing cases is not where people give up, and TestRail 9.5 already ships AI case generation. They give up on release-time assembly. To build a regression plan, you pick configuration groups, filter cases by priority, type and component across hundreds of sections, add one plan entry per configuration combination, and assign testers. Months later the suite has rotted: duplicate cases, shared steps that were copy-pasted instead of shared, and dead sections. Fixing it means moving cases one screen at a time. A QA lead loses half a day every release cycle to filter dialogs and the Add Plan Entry modal.

**AI operator:** A 'Release QA Operator' reads the release scope from the Jira fix version plus a short instruction. It selects cases by field and section semantics, builds the plan and configuration matrix, and balances tester assignments by past run durations. A second mode, 'suite gardening', finds near-duplicate cases and repeated step blocks, then proposes merges, shared-step extraction and section moves as a reviewable diff before writing anything.

**Killer example:** A QA lead says: 'Build the 4.2 regression plan: every P1 and P2 case under Checkout and Payments plus anything linked to tickets in fix version 4.2, on Chrome/Win, Safari/macOS and iOS 18. Split it evenly by effort between Asha, Marco and Lin, and keep Lin off iOS.' The AI resolves 4.2's 63 Jira issues to linked case IDs, unions them with the P1/P2 filter (412 cases), and warns that 5 of the 4.2 tickets have no linked case at all. It creates the milestone, calls add_plan with three configuration entries, and assigns by historical execution time: about 11.5 hours each, with Lin only on desktop. Total time is 20 minutes instead of half a day. It then reports that 37 cases in the selection repeat the same 6-step login preamble and 9 pairs are near-duplicates, and offers a one-click diff that extracts one shared step and merges the pairs.

**Integration path:** TestRail API v2 (REST/JSON, Cloud and Server) writes the wall directly: add_plan and add_plan_entry with config_ids and case_ids, add_run, add_milestone, get_cases with filters, update_cases (bulk), move_cases_to_section, copy_cases_to_section, add_shared_step and update_shared_step, add_section, get_configs and add_config. The Jira REST API supplies the fix version to linked cases. Xray Cloud uses its GraphQL API (createTestPlan, createTestExecution, addTestsToTestPlan) and Zephyr Scale uses REST v2. Risk to watch: TestRail's hosted MCP is 'read-only by default', so the operator must stay focused on plan assembly and refactoring, not case generation, which TestRail already ships.

**Demand 4/5 · Buildability 4/5**

### 4. Google Ad Grants (the nonprofit $10k/month Google Ads program): compliance and build operator `closed`

**Why it's powerful:** Eligible nonprofits get up to $10,000 a month in free Google Search ads, which is about $120k a year. They run on the full Google Ads search engine: keywords, responsive search ads (RSAs), sitelinks and other assets, conversion tracking imported from GA4, and Maximize Conversions bidding, which lets bids go above the usual $2 CPC cap. Tens of thousands of charities, churches, food banks and universities hold a grant.

**Why people bounce off it:** A second rulebook sits on top of Google Ads, and breaking it gets the account suspended: account CTR must stay at 5% or above (two months in a row below means suspension); single-word keywords are banned except brand terms and approved exceptions; keywords with Quality Score 1 or 2 must be paused; each campaign needs at least 2 ad groups with at least 2 RSAs each, at least 2 sitelinks, valid conversion tracking and geo-targeting; search partners must be off; and there is an annual program survey. The rules live only on help-center pages, and the Google Ads UI does not flag Grants violations ahead of time. Accounts are usually run by a volunteer or a one-person comms team who find out only when a warning or suspension email arrives, then face a reactivation form that requires every violation to be fixed first. A whole cottage industry of Ad Grants agencies exists to handle this.

**AI operator:** A continuous compliance auditor and fixer, plus a campaign builder that respects the rules. Each night it runs GAQL queries for keyword Quality Score, CTR and impressions, ad-group and RSA counts per campaign, sitelink assets, network settings and conversion actions. It scores every Grants rule and forecasts month-end account CTR from the month so far. It drafts a mutation plan (pause keywords with QS below 3, rewrite single-word or generic keywords into specific multi-word phrase-match ones, add the missing ad group or RSA, add sitelinks, turn off search partners), shows it as a diff and applies it after approval. It turns a plain-language program description into campaigns that are compliant from the start, and after a suspension it writes the fix-list summary for the reactivation request.

**Killer example:** A food bank's volunteer comms lead forwards Google's warning email and says: 'Our grant account is at risk. Fix it, I don't know Google Ads.' The AI finds month-to-date CTR at 3.8%, dragged down by 14 broad terms like 'food' and 'help' that eat 60% of impressions; 9 keywords at Quality Score 2; one campaign with a single ad group; and two campaigns with no sitelinks. It pauses the 9 low-QS keywords, replaces the broad terms with phrase keywords like 'volunteer at food bank chicago' and 'free groceries near me cook county', adds a second ad group with 2 RSAs, and adds 4 sitelinks (Volunteer, Donate, Find Food, Hours). It projects month-end CTR at 5.6% and turns on a nightly check that messages her before any rule is about to break. It also gives her a checklist ready to paste into the reactivation form if Google suspends the account anyway.

**Integration path:** Main path: the Google Ads API. GAQL reads cover keyword_view, ad_group_criterion.quality_info, ad_group_ad, campaign_asset and campaign.network_settings. Writes go through AdGroupCriterionService, AdGroupAdService, AssetService and CampaignService. Auth is OAuth plus a Google Cloud project at the right API access level, since Google moved access decisions from developer tokens to Cloud projects in Sept 2026. Grants accounts run on the standard Ads platform, and API mutations do work on them, with two caveats: Google's API team says Grants accounts are outside API support scope, and product-level validations apply (for example, a Search campaign targeting search partners is rejected). Test early against a live Grants account. Fallback for scheduled pause rules: a Google Ads Script installed in the account. Risk to watch: whether Google's in-product Ads Advisor agent expands to cover Grants-specific policy.

**Demand 4/5 · Buildability 4/5**

### 5. AWS KMS: key policies, grants and cross-account / cross-region encryption workflows `closed`

**Why it's powerful:** KMS sits under encryption at rest for almost every AWS service: EBS, RDS/Aurora, S3, Secrets Manager, DynamoDB, Lambda env vars, CloudTrail and backups. Customer-managed keys bring resource key policies, grants for service-linked usage, encryption-context conditions, multi-Region keys, automatic and on-demand rotation, and imported key material. It is the control point for both compliance and cross-account data sharing.

**Why people bounce off it:** Whether kms:Decrypt succeeds depends on the key policy, the caller's IAM policy, grants, SCPs/RCPs, the kms:ViaService and encryption-context conditions, and in the other account a matching policy on both sides. The console shows these on separate tabs and the error is a bare AccessDenied. Common traps that cost days: snapshots encrypted with the aws/ebs or aws/rds AWS-managed key cannot be shared and must be copied and re-encrypted under a CMK. Auto Scaling launching from an encrypted AMI fails with Client.InternalError until the AWSServiceRoleForAutoScaling grant exists. DR copies need a key in the target Region. Locking yourself out of a key policy is permanent without Support.

**AI operator:** A 'Key Warden' agent that inventories every CMK and alias across the Organization, together with the resources each key protects (from service describes plus CloudTrail kms:* usage). It explains in plain language who can use a key, for which service and from which account. It turns plain-language sharing and DR intents into the full multi-step workflow: key-policy statements in both accounts, grants, IAM policy additions, and copy/re-encrypt operations for snapshots or AMIs. Every policy goes through IAM Access Analyzer ValidatePolicy and a 'can the admin still manage this key' lockout check before PutKeyPolicy. Scope is key-centric workflows across services, distinct from the existing S3 card's bucket-level access view.

**Killer example:** A platform engineer says: 'Share last night's prod RDS snapshot and the app AMI with the analytics account, and make sure their Auto Scaling group can actually launch it. I have lost two days to AccessDenied on this before.' The AI sees the RDS snapshot is encrypted with the aws/rds managed key, which can never be shared, so it copies the snapshot under a new CMK alias/share-analytics. It adds a key-policy statement for the analytics account with kms:ViaService conditions for rds and ec2, and shares the snapshot. It copies the AMI with re-encryption under the same key and shares it. In the analytics account it creates the grant for AWSServiceRoleForAutoScaling, the step everyone misses, plus an IAM policy for their launch role. Before each PutKeyPolicy it runs Access Analyzer and a lockout check. A test launch of one instance succeeds. It posts the exact policy diffs and the CloudTrail event for the first successful Decrypt from the analytics account. The whole job takes 12 minutes.

**Integration path:** AWS KMS API (ListKeys, DescribeKey, GetKeyPolicy/PutKeyPolicy, CreateGrant/ListGrants/RetireGrant, CreateKey with MultiRegion, ReplicateKey, EnableKeyRotation/RotateKeyOnDemand), IAM Access Analyzer ValidatePolicy/CheckAccessNotGranted, IAM policy simulator, STS AssumeRole into member accounts, plus RDS CopyDBSnapshot/ModifyDBSnapshotAttribute, EC2 CopyImage/ModifyImageAttribute/CopySnapshot and CloudTrail LookupEvents (EventSource kms.amazonaws.com). No dedicated awslabs KMS MCP server was found. Overlap risks: the S3 card already writes KMS policies for S3 buckets, and Amazon Q in the console can diagnose some AccessDenied errors, so keep this card on cross-service share, re-encrypt and DR workflows.

**Demand 4/5 · Buildability 4/5**

### 6. AWS Elastic Beanstalk: forced Amazon Linux 2 to Amazon Linux 2023 platform migration `closed`

**Why it's powerful:** Elastic Beanstalk still runs a very large long tail of production web apps (PHP, Node, Python, Java, .NET-on-Linux, Docker), especially at SMBs and agencies. It bundles EC2, Auto Scaling, the load balancer, CloudWatch, deployments and managed platform updates behind one environment, configured through option settings, saved configurations, .ebextensions and .platform hooks.

**Why people bounce off it:** AWS retired every AL2-based Beanstalk platform branch (fully retired 2026-08-06, after AL2 EOL on 2026-06-30), so these apps now run on unpatched branches. Moving to AL2023 is not a version bump. .ebextensions commands that used yum/amazon-linux-extras break, and nginx/Apache config overrides move to different .platform paths. Proxy defaults, language runtime versions, IMDSv2 and instance-profile defaults all change, and AWS's guidance is 'do a blue/green with a cloned environment'. The people who own these apps are often the last developer who knew Beanstalk, and the console shows none of the incompatibilities.

**AI operator:** A 'Beanstalk Mover' agent that pulls each environment's option settings, saved config and current application version source bundle from S3. It statically scans .ebextensions, .platform, Procfile, Buildfile and Dockerrun files against a curated AL2-to-AL2023 incompatibility catalog, then rewrites them (yum to dnf, nginx conf paths, hook relocation, runtime pins) as a reviewable diff. It creates a cloned green environment on the matching AL2023 platform ARN, deploys the patched bundle, runs health and smoke checks against the green CNAME, and only on approval performs SwapEnvironmentCNAMEs. The old environment is kept for rollback.

**Killer example:** An agency owner says: 'AWS keeps emailing that our 9 client apps are on a retired platform. Move them all to the supported version without downtime, and I don't want to learn Beanstalk.' The AI lists 9 environments on 'PHP 8.1 running on 64bit Amazon Linux 2' and produces one risk table: 6 use amazon-linux-extras in .ebextensions, 3 override /etc/nginx/conf.d/elasticbeanstalk/*.conf (which must move to .platform/nginx/conf.d/elasticbeanstalk/), 2 need a PHP bump because AL2023 ships 8.2+, and 1 reads instance metadata without IMDSv2 tokens. It builds patched bundles, clones each environment as <name>-al2023, deploys, and runs each site's /health URL plus 5 recorded page checks. 8 pass and are CNAME-swapped one by one, with zero dropped requests. The ninth fails on a missing php-imagick package; the AI adds a dnf-based prebuild hook, re-deploys, passes, and swaps. The old blue environments stay up for 7 days for rollback, then get terminated on the owner's say-so.

**Integration path:** Elastic Beanstalk API / AWS CLI / eb CLI: DescribeEnvironments, DescribeConfigurationSettings, CreateConfigurationTemplate, ListPlatformVersions (filter AL2023 branches), CreateApplicationVersion (patched bundle uploaded to S3), CreateEnvironment (clone with new SolutionStackName/PlatformArn), DescribeEnvironmentHealth/DescribeEvents, SwapEnvironmentCNAMEs, TerminateEnvironment. Source bundles are plain zips in S3, so static analysis and rewriting are local file operations. General first-party agents (Amazon Q in console, AWS DevOps Agent) focus on troubleshooting, not bundle rewriting plus blue/green cutover; not verified exhaustively.

### 7. Gerrit Code Review: admin layer (project.config access sections, inherited ACLs, labels, submit requirements, groups) `open-source`

**Why it's powerful:** Gerrit is the code-review backbone for Android/AOSP, Chromium, Qt, Wikimedia, Eclipse and most automotive and telecom AOSP shops (Ericsson, Volvo, and others). Its permission model is very fine-grained: per-ref-pattern ACLs (refs/heads/release-*, refs/for/*, refs/meta/config) inherited down a project tree, with ALLOW/DENY/BLOCK and exclusive flags. It has custom voting labels with ranges and copy conditions, and since 3.7 it has submit requirements written in a query language (applicableIf/submittableIf/overrideIf) that replaced Prolog submit rules.

**Why people bounce off it:** Effective permission on a ref comes from inheritance across All-Projects, intermediate parent projects and the project itself. BLOCK beats ALLOW from below, exclusive flags cut off inheritance, and ref patterns can be regex. The Access UI shows one project's sections at a time and never the computed result for a given user. Labels and submit requirements live in a git config file on refs/meta/config, and the Prolog-to-submit-requirements migration left many orgs with rules nobody understands. In practice only 1-2 people per company dare to touch Gerrit ACLs, and every release-branch cut turns into a ticket to them.

**AI operator:** A 'Gerrit Steward' agent that loads the whole project hierarchy (parents, access sections, labels, submit requirements, groups) into a model. It answers plain-language questions about effective rights for any user and ref, and uses Gerrit's own check.access endpoint to confirm the answer. It turns policy requests into minimal diffs on project.config at the lowest correct level of the tree, labels, submit requirements and group changes. It shows a before/after table of effective permissions for affected users and pushes the change as a Gerrit change on refs/meta/config so it gets code-reviewed itself. It also translates leftover Prolog rules.pl files into submit requirements.

**Killer example:** A release manager says: 'Cut release-26.4 for every project under platform/. Only release-eng can push or submit there, it needs Code-Review+2 plus a new QA-Verified+1 label, and after Friday nobody else may even upload to it.' The AI finds the shared parent platform/Parent-Projects and adds one refs/heads/release-26.4 section there instead of editing 212 projects. It sets BLOCK push for Registered Users with an ALLOW for release-eng, defines the QA-Verified label with copyCondition on trivial rebases, and adds a submit requirement 'label:QA-Verified=MAX AND -label:QA-Verified=MIN' with applicableIf branch:release-26.4. It finds 3 projects that inherit from a different parent and would have silently escaped the policy, and patches those separately. It runs check.access for 5 sample users (a release-eng member, a regular dev, a bot account) and puts the effective-permission diff in the commit message of a refs/meta/config change for review. A follow-up change adding the refs/for BLOCK is queued for Friday. The release manager reviews one change instead of filing a ticket to the one Gerrit admin.

**Integration path:** Full REST API: GET/POST /projects/{name}/access (add/remove access sections), POST /projects/{name}/check.access, PUT/DELETE /projects/{name}/labels/{label}, /projects/{name}/submit_requirements (3.7+), /groups/ CRUD, /projects/{name}/parent. Also direct git fetch/push of refs/meta/config (project.config, groups file, rules.pl) as a change-for-review. The official gerrit-mcp-server (36 tools) covers only changes, reviews, comments and code-owners status, with no access, label, submit-requirement, group or project-config tools, so the admin layer is open.

**Demand 3/5 · Buildability 4/5**

### 8. Salesforce Quip (docs, spreadsheets, Quip for Salesforce): forced-exit operator before the 2027 retirement `closed`

**Why it's powerful:** Quip was the Salesforce-native office suite: docs, live spreadsheets with formulas, chat threads on every document, Data Mentions that show live Salesforce fields inline, and Quip templates attached to Opportunity and Account records through the Quip for Salesforce Lightning component. Sales teams kept account plans, mutual close plans and QBR docs there, tied to CRM records. Salesforce is retiring all Quip products. March 1, 2027 is the last renewal date. Each customer's own term end then starts a sequence: read-only (about 90 days), then blocked logins with no UI or API access (30 days per the cited Salesforce article), then permanent deletion. Salesforce says it will not move content for customers.

**Why people bounce off it:** The exit is the usability wall. Slack's official Quip-to-canvas converter works on one document at a time, says bulk conversion isn't available yet, and leaves the original read-only. A migration vendor says spreadsheets and Live Apps aren't guaranteed to come across, though Slack and Salesforce don't say so themselves. Bulk Export returns a ZIP named by thread ID with the folder tree flattened, so a separate JSON metadata pass is needed to rebuild folders and owners. Data Mentions export as blank or static text. Record-attached Quip templates have to be moved separately. Comments and message history only survive in DOCX/XLSX exports. Admins also face a different deadline per contract and rate limits of 50 requests/min per user and 600 per company. The vendors in this space are mostly services (ClonePartner) or a single destination (the Superhuman Docs/Coda self-serve importer).

**AI operator:** A 'Quip Exit Pilot' that inventories the whole Quip company through the Admin API. It classifies every thread as a plain doc, a spreadsheet, a doc with embedded spreadsheets (found by probing export/xlsx, which returns 400 on docs without one), a record-attached template, a Live App, a doc with Data Mentions, or dead content (no views in 12+ months). It then proposes an editable destination per class: Slack channel canvases for team docs, Word/Excel in SharePoint or Google Docs/Sheets for long-form docs and spreadsheets, and the Salesforce record page for account plans. It runs the move under the rate limits with checkpointing. Data Mentions become hyperlinks to the Salesforce record, or a note of the field value as of the export date. Spreadsheets get a cell-by-cell check of the exported XLSX against the values Quip renders, and any formula that failed to export is rebuilt. Folder shares are mapped to SharePoint, Drive or channel permissions. Every row of the change log links the old Quip URL to the new location. The countdown is per contract term, and the full export must finish before logins are blocked.

**Killer example:** A RevOps lead says: 'Our Quip term ends June 30 and Salesforce won't move anything for us. Get everything out. Account plans must still open from the Opportunity page, team wikis go to the matching Slack channels, and finance's forecast sheets go to SharePoint with working formulas.' The AI reports 18,400 threads: 1,212 account plans attached to Opportunities, 3,900 team docs, 640 spreadsheets (71 with formulas that need checking) and 9,800 not opened since 2024, which it recommends sending to a cold DOCX/PDF archive in SharePoint. It works out that at the 600 requests/min company limit the job needs about 4 days, and schedules it to finish 3 weeks before logins are blocked. It creates 3,900 channel canvases, writes the account plans to a SharePoint library with one folder per Opportunity ID, and adds a 'Plan' URL field to Opportunity because the Quip component will stop working. It exports the 640 sheets as XLSX and checks them cell by cell; 7 formulas exported as static values, and it rebuilds them. It ends with a redirect CSV mapping every Quip URL to its new home and a list of 23 Live App docs that need a person.

**Integration path:** Quip Admin API (ADMIN_READ scope) and Automation API: GET /1/threads/{id}, /1/folders/{id}, /1/threads/{id}/export/docx and /export/xlsx (Admin equivalents under /1/admin/threads/...), plus the async Bulk Export API at up to 36k docs/hour, which needs Quip Plus or Advanced. Destinations: Slack Web API conversations.canvases.create and canvases.create (markdown body; standalone canvases need a paid Slack plan; Tier 2 rate limit), plus canvases.access.set.
