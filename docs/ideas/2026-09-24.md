### 1. Salesforce Service Cloud — Entitlement Management & SLA milestones `closed`

**Why it's powerful:** Service Cloud is the most widely deployed enterprise support platform, and entitlement management is the machinery behind every paid support tier. Entitlements, Service Contracts and Contract Line Items define who is eligible for what; entitlement processes attach up to 10 milestones each; milestone time triggers can be static minutes or computed in Apex via `Support.MilestoneTriggerTimeCalculator`; and milestone actions fire success/warning/violation automations against business hours and holiday calendars. Around it sit case assignment rules, escalation rules, queues, Omni-Channel and the SLA dashboards executives actually read. Millions of support seats depend on it, and it is contractual — a mis-set milestone is a breached SLA with financial penalties, not a cosmetic glitch.

**Why people bounce off it:** The worst failure mode is silent non-existence. An entitlement process only runs if `Case.EntitlementId` is populated *and* the case matches process entry criteria — so if the Entitlement lookup isn't on the layout or isn't set by automation, no milestones are ever created, and the SLA report shows near-100% compliance because it is only measuring the cases that had milestones. Business hours exist in three layers (entitlement process, case, milestone) plus holidays, and which one wins is not visible on any screen. `Stopped`/`Stopped Since` pauses milestone clocks, but resume recalculation rarely matches what admins assumed. Entitlement processes are versioned and you cannot edit an active version's milestones — you clone to a new version, and every existing open case stays on the old version unless explicitly migrated, so orgs unknowingly run four concurrent SLA definitions. Assignment rules allow only one active rule per org, evaluate top-down with stop-processing semantics, and do not run for API/Flow-created cases unless the assignment rule header is set — so Email-to-Case, Web-to-Case and integration-created cases end up on different paths. Milestone actions are time-dependent actions that never fire if the milestone completes or violates first, and editing them mid-flight orphans already-queued actions. Observed workaround: "SLA implementation" consulting engagements in the $15–60k range, untouchable legacy Apex milestone calculators, and a very common capitulation where teams abandon entitlements entirely and rebuild SLA tracking in custom date fields plus scheduled Flows.

**AI operator:** Reads org config via Metadata + Tooling API (EntitlementProcess and all versions, EntitlementTemplate, MilestoneType, EntitlementSettings, BusinessHours/Holiday, AssignmentRules, EscalationRules, case record types and layouts) and profiles live data via SOQL: share of cases with null `EntitlementId`, milestone completion vs violation distribution, case counts by Origin, per-version open-case counts. The LLM emits an "SLA contract spec" — tiers, targets expressed in business vs calendar time, pause semantics, escalation ladder, notification targets — never XML. A deterministic builder renders that spec into a Metadata API package (EntitlementProcess with ordered milestones and time triggers, MilestoneType, BusinessHours entries, Holiday records, assignment/escalation rules) and deploys check-only first, then to sandbox, returning the component-level diff. Self-verification runs a synthetic-case harness in a scratch org: create cases per tier, advance statuses, cross a holiday boundary, exercise a Stopped interval, and assert actual milestone target/completion timestamps against the spec. It owns the null-entitlement blind spot, non-versioned edits, business-hours layering, origins that bypass assignment rules, and orphaned milestone actions.

**Killer example:** A support director says: *"Gold gets 1-hour first response and 8-hour resolution in business hours, Platinum is 24×7 at 30 minutes, and escalate to the duty manager at 75% of the clock."* The operator inspects the org and leads with the finding that **38% of last quarter's 12,400 cases had no Entitlement at all** — so the 99.2% SLA dashboard is describing 7,700 cases, not 12,400 — and that every case from the `support@` address skips the active assignment rule because an old workflow routes them first. It then emits version 3 of the process with four milestones (Gold First Response 60 business minutes, Platinum First Response 30 minutes against a new `Platinum_247` BusinessHours record it creates, Gold Resolution 480 business minutes, Platinum Resolution 1440), a warning action at 75% notifying the duty-manager queue, and reports three holiday conflicts including "Independence Day" existing twice with different dates in the calendar it was about to attach. The check-only deployment returns 0 errors — and it then refuses to activate until you choose what happens to the 4,700 open cases still on version 2, offering the batch that migrates them and the SOQL that proves the count.

**Integration path:** Salesforce Metadata API (`EntitlementProcess`, `MilestoneType`, `EntitlementSettings`, `BusinessHoursSettings`/`Holiday`, `AssignmentRules`, `EscalationRules`, `Queue`, plus `ServiceChannel`/`QueueRoutingConfig` for Omni-Channel), Tooling API for fast reads, REST/Bulk API for data profiling, and `sf` CLI for `deploy --dry-run` (check-only) validation and scratch orgs. Auth via a connected app with JWT bearer flow or OAuth on a free Developer Edition org / Trailhead playground. Entitlement Management and Omni-Channel are supported in Developer Edition, so the entire product can be built and demoed at zero cost — no partner program, no sales call. MVP: Node + jsforce + `sf` CLI, spec→package.xml renderer, and the synthetic-case harness as the self-verifier.

**Demand 5/5 · Buildability 5/5**

### 2. Microsoft Word — tracked-changes / redlining layer `closed app; fully open file format`

**Why it's powerful:** Word's revision layer is a change-attribution database living inside the file: every insertion, deletion, formatting change and move carries an author and timestamp, stored as nested `w:ins`/`w:del`/`w:rPrChange` runs that can be accepted or rejected individually. Around it sit Compare (produce a legal blackline from two versions), Combine (merge multiple reviewers), per-author markup filtering, the Reviewing Pane, threaded and resolvable comments, "restrict editing to tracked changes only", and Document Inspector for metadata scrubbing. This is the machinery through which essentially every commercial contract, NDA, MSA, lease, grant and HR policy on earth is negotiated — .docx is the lingua franca between counterparties who share no system. Install base: Word across 400M+ paid M365 seats, and near-100% penetration in legal, procurement and HR.

**Why people bounce off it:** "Simple Markup" is the default in modern Word, so it hides markup behind a thin change bar and people genuinely believe a document is clean and send it out — this is how the other side's earlier price, or your own internal comment, ships to the counterparty. "Accept All Changes" and "Accept All Changes and Stop Tracking" sit next to each other and silently differ in whether the next round is tracked at all. Formatting revisions ("Formatted: Font: 11 pt", style tweaks from a paste) flood the Reviewing Pane by the hundreds, so the rational move is Accept All just to read the text — which also accepts the substantive edits hiding inside those paragraphs. Compare produces a *third* document, attributes merged authorship as "Author", and quietly absorbs your unaccepted changes into their blackline. Accepting a change can orphan a comment anchor; moved text renders as move-from/move-to that many tools re-render as delete+insert, doubling the apparent diff. Accepting deletions renumbers clauses, and every cross-reference ("as set out in Section 9.2") stays stale until fields are updated, so the redline leaves a document that is internally inconsistent and nobody notices. Metadata — firm name, total editing time, prior authors, residual comments — survives unless Inspect Document is run, which is why "just PDF it before sending" is the standard workaround. What people actually do: buy Litera Compare / Draftable, print two versions side by side, keep an issues-list email that duplicates the document, or have a paralegal retype a clean copy.

**AI operator:** Context read is the revision graph itself, not the rendered text: each revision's id, author, timestamp, type, text, the containing paragraph, its style and heading path, plus the comment threads and defined-term index. The LLM emits a decision spec — a list of `{revisionIds, action: accept|reject|defer, riskTag, rationale}` grouped into semantic buckets (pure formatting/whitespace, defined-term consistency, drafting cleanup, numeric/commercial terms, liability & indemnity, deletion of protective language) plus any counter-edits it proposes as new tracked insertions under its own author identity. Application is deterministic OOXML surgery (accept = unwrap `w:ins`, reject = drop `w:del` content) via OpenXmlPowerTools' `RevisionAccepter`, or `TrackedChange.accept()/reject()` in the Word JS API when running in-app. Self-verification: re-run `WmlComparer` between pre- and post-state to show the user a redline *of its own actions*, assert the revision-count delta equals the decided set, assert zero bytes changed inside user-declared locked clauses, recompute cross-references and report stale ones. It owns the dangerous classes by construction — anything tagged commercial or liability is `defer`, never auto-accept — and a pre-send metadata gate runs Inspect-equivalent stripping.

**Killer example:** In-house counsel says: *"Take their markup on the MSA: accept anything that's just formatting or defined-term cleanup, reject anything touching the liability cap or payment terms, and tell me what they actually did."* The operator parses **318 revisions by 3 authors**, buckets 204 as formatting/whitespace/style and accepts them, then reports the 12 substantive edits hiding inside those formatting-heavy paragraphs: "net 30" changed to "net 60" in 5.2; the liability cap moved from USD 2,000,000 to "the greater of the fees paid in the preceding 12 months" (rejected, with a tracked re-insertion of the original figure); and — the one a human skims straight past — **the deletion of the single word "not" in 9.2, which inverts the indemnity**. It notes they renamed "Affiliate" in 4 of 6 places so the defined term is now inconsistent; that accepting their deletion of clause 11.3 renumbered Sections 11–14 and left 6 cross-references pointing at the wrong clause (listing each); and that the file they sent still contains an unresolved internal comment from their own reviewer reading *"we can live with 5m"* plus 43 minutes of their editing metadata — which it offers to strip before you return the document.

**Integration path:** Two complementary surfaces, both free. File path (source of truth, best MVP): .NET Open XML SDK + **OpenXmlPowerTools** (MIT) — `WmlComparer` to generate or normalize a redline between two .docx files, `RevisionAccepter` to apply accept decisions; or Python `lxml` over the unzipped `word/document.xml` for surgical accept/reject. In-app path (UI): an Office Add-in on **Word JS API 1.6+** — `Body.getTrackedChanges()`, `TrackedChange.accept()/reject()`, `TrackedChangeCollection.acceptAll()/rejectAll()`, `Document.changeTrackingMode`, plus the 1.4 comment APIs — scaffolded with `yo office`, sideloaded into Word on the web with any M365 account, no partner program or approval queue. Known office-js bugs argue for exactly this split: `getTrackedChanges()` can fail to sync when the document contains *moved* tracked changes, and deleted-type revisions sometimes return an empty `text` — so do the reasoning and mutation on the OOXML and use the add-in only as the conversational front end. Optional Graph `/drive/items/{id}/content` for round-tripping from SharePoint/OneDrive.

**Demand 5/5 · Buildability 4/5**

### 3. Excel + Google Sheets — conditional-formatting & data-validation rule engines `closed`

**Why it's powerful:** Conditional formatting is a real declarative rules engine bolted onto every spreadsheet: ~10 rule types (cell value, top/bottom N, above/below average, unique/duplicate, text/date occurring, color scale, data bar, icon set, and arbitrary custom formula), each with its own priority in an ordered stack, a "Stop If True" short-circuit, a partial-format payload (font, fill, border, number format — `dxf` records), and a multi-range "Applies to". Pair it with data validation (list-from-range, custom formula, input/error messages, dependent dropdowns) and sheet/range protection with per-range editors, and a plain grid becomes a small app with typed inputs, RAG dashboards, aging buckets and entry gating. This is the layer that makes shared trackers, budget templates and ops checklists usable by non-authors. Install base is essentially total: 400M+ paid Microsoft 365 commercial seats plus Google Workspace's billions of Sheets users — every business process document on earth has a rules layer someone wishes worked.

**Why people bounce off it:** The Rules Manager opens scoped to "Current Selection", so users look at a rule-laden sheet and conclude there are no rules. Custom-formula rules must be authored *relative to the top-left cell of the Applies-to range* with correct `$` anchoring — `$B2` vs `B$2` vs `B2` are three different products, and the wrong one doesn't error, it just colors the wrong cells. Then the fragmentation failure mode: copy/paste, row inserts, deletes and sorts shatter one rule into dozens or hundreds of near-duplicate rules with Applies-to strings like `$B$2:$B$7 $B$9:$B$14 $B$16`, until formatting visibly stops working and the file bloats — the recommended community fix is to defeat Excel's reference adjustment with `OFFSET()`. Overlapping rules resolve by priority order plus Stop If True with no preview of the resolved stack, so "why is this cell green" is unanswerable from the UI; there is no rules debugger and no way to distinguish a rule-driven fill from a manual one. Data validation isn't retroactive: adding a dropdown doesn't flag the 41 cells that already violate it. Dependent dropdowns need named ranges + `INDIRECT` (or a helper column of `FILTER`) because the UI has no concept of "options depend on column A". Observed workarounds: people manually recolor cells (destroying the rule they just paid for), install de-fragmenter VBA macros, keep a "how our tracker works" doc, or post a screenshot of the Applies-to string to r/excel and hope.

**AI operator:** Context read: used range, header row, sampled values with inferred column types, existing table/named ranges, and a full dump of current CF and DV rules (type, formula, priority, stopIfTrue, applies-to, format payload) plus theme colors. The LLM never writes A1 addresses — it emits a `RuleSpec` JSON keyed on *header names/table columns*: condition AST or formula template, format tokens resolved against the workbook theme, priority intent ("red wins over amber"), scope ("whole row" vs "cell"), and validation rules with error text. A deterministic compiler resolves targets to ranges, generates the formula with correct anchoring for the top-left cell, merges any existing duplicate rules with identical formula+format into one Applies-to, and applies as a single batch. Dry-run is real evaluation, not prose: it computes each condition over sampled rows itself and reports "will highlight 37 of 412 rows — here are 5 examples and 3 near-misses", and for DV it lists existing violating cells. It owns anchoring errors, priority/Stop-If-True conflicts, fragment consolidation, and never overwrites manual fills; post-apply it re-reads the rule set, asserts the expected count/hash, and keeps the pre-change rule snapshot for one-click revert.

**Killer example:** An ops lead says: *"Highlight any project row red if it's past due and not done, amber if it's due within 7 days, and stop finance typing anything but our 12 approved cost centres in column G."* The operator reads the sheet, finds **214 fragmented legacy rules** across 9 Applies-to fragments — two of which reference a helper column someone deleted, so they can never fire — and consolidates them to two rules: `=AND($E2<TODAY(),$F2<>"Done")` over `$A$2:$K$413` with Stop If True, and `=AND($E2>=TODAY(),$E2<=TODAY()+7,$F2<>"Done")` below it, explaining it set Stop If True because 18 rows satisfy both. It reports 6 rows whose due date is text ("Q3", "TBC") and will therefore never trigger under either rule, creates a hidden `_lists` sheet with a `CostCentres` named range, applies `=COUNTIF(CostCentres,G2)=1` as a custom DV rule with the error message "Use an approved cost centre (see _lists)" — and then flags what a human misses: **41 cells in G already hold unapproved codes that validation will not catch retroactively**, 12 of them a single typo variant of `OPS-1140`, which it offers to normalize.

**Integration path:** Google side (cleanest MVP): Sheets API v4 `batchUpdate` with `AddConditionalFormatRuleRequest`, `UpdateConditionalFormatRuleRequest`, `SetDataValidationRequest`, `AddProtectedRangeRequest` — free OAuth, no review needed for your own account/domain, and Apps Script gives an in-product sidebar with zero hosting. Microsoft side: Office Scripts (`ExcelScript.ConditionalFormat`, `ConditionalFormatRule`, `DataValidationRule`, `CustomDataValidation`) for Excel on the web plus Power Automate, or an Office Add-in on the Excel JS API (`range.conditionalFormats.add(Excel.ConditionalFormatType.custom)`, `Range.dataValidation`) scaffolded with `yo office` and sideloaded — no partner program. Graph's workbook endpoints don't cover CF fully, so for uploaded files use the file-format path: `openpyxl` (reads/writes `<conditionalFormatting>` rules, `dxfs`, and DV) or raw OOXML. MVP: Sheets add-on first (~2 weeks), then the Office Scripts port for Excel.

**Demand 4/5 · Buildability 5/5**

### 4. Razorpay — Offers, Subscriptions/mandates, Route split settlements `closed`

**Why it's powerful:** Razorpay is India's default online-payments and commerce-ops layer, used by 10M+ businesses, and for most Indian SMBs it *is* the checkout, the subscription biller, the invoicing tool and the marketplace payout engine at once. The configurable surface is large and genuinely commercial: an Offers engine (discount/cashback, card-network/issuer/method-scoped, min-amount, first-transaction-only, usage caps) that attaches to Orders, Subscriptions, Payment Links and Payment Pages; Subscriptions with Plans, Addons, trial/upfront handling, and UPI AutoPay / e-NACH / card mandates with their own max-amount and pre-debit-notification rules; **Route**, which splits one incoming payment across linked accounts with per-transfer settlement holds; Smart Collect virtual accounts for reconciliation; and Payment Pages/Links as no-code storefronts. All of it is fully API-driven with excellent docs and a public Postman workspace.

**Why people bounce off it:** Offers are the silent-failure showcase: an offer only applies if the **Order was created with that `offer_id`** (or `offer_force_offer` set) *and* the payment instrument matches the offer's issuer/network/method scope *and* the amount clears `min_amount` — so a merchant creates "10% off on HDFC credit cards", sees it listed as Active, and it applies to nobody, with no screen anywhere saying "0 of 4,000 payments matched this offer". Multiple active offers do not stack and do not deterministically pick the customer's best one, so three overlapping festive offers produce unpredictable discounts and angry customers. Subscriptions are the second wall: `total_count` counts *billing cycles including the upfront one*, addons attach to a subscription rather than a plan, `start_at` interacts with trials such that an off-by-one silently charges a customer on day 0 of a "7-day free trial", and UPI AutoPay/e-NACH mandate registration requires a max-amount that must exceed every future price change or renewals start failing months later — a revenue leak invisible until churn shows up. Route is the money-burner: transfers are specified as absolute paise amounts, not percentages, so any partner deal expressed as "15% to the vendor" must be computed per transaction including or excluding Razorpay's own fee and GST; get it wrong and you have over-transferred funds you cannot claw back without a reverse-transfer flow, and `on_hold` transfers left without `on_hold_until` sit frozen forever. Webhooks are the fourth: the whole system is eventually-consistent and merchants who don't wire `payment.captured` / `subscription.charged` / `transfer.processed` reconcile by eyeballing the dashboard. Observed workaround: SMBs hire a freelance developer for every pricing or split change, or abandon the advanced products entirely and take plain one-off payments with discounts applied manually over WhatsApp.

**AI operator:** Reads the merchant's current configuration and behaviour: `GET /v1/offers`, `/v1/plans`, `/v1/subscriptions`, `/v1/accounts` (Route linked accounts), `/v1/payments` for the last 90 days with `method`/`card.network`/`card.issuer`/amount distribution, `/v1/settlements`, and the registered webhook set. The LLM emits `{offers:[{scope, value, min_amount, usage_cap, applies_to[]}], plans:[...], subscription_ops:[...], route:[{split_rule: percent|flat, of: gross|net_of_fees, linked_account, on_hold_until}], webhooks[]}` — expressing splits as *rules*, which is the whole point, since the API only takes paise. The deterministic applier compiles percentage rules into a per-order transfer calculator (Razorpay fee + 18% GST handled explicitly, remainder-paise assigned to a designated account so splits always sum exactly to the captured amount), creates offers/plans idempotently, and registers the webhooks needed to make the rules fire. Dry-run replays the last 90 days of real payments through the proposed config and reports **match rate and rupee impact**. Self-verification runs a real Test-Mode payment end-to-end (test card + UPI), asserts the offer applied and the transfers landed at the expected amounts, then monitors the first 24h of live `payment.captured` events for a match rate of zero — the single most valuable alert in the product. Owned failures: zero-match offers, mandate ceilings below future prices, transfer rounding drift, missing webhooks, trial off-by-ones.

**Killer example:** A D2C skincare founder says: *"Launch a ₹1,199/quarter subscription with a 7-day free trial, 20% off the first billing for HDFC and ICICI cards only, and send 12% of every order to my dermatologist partner."* The AI builds the Plan, the trial-aware `start_at`, the two offers and the Route rule, then reports before applying: **(1)** a 7-day trial with `total_count: 4` bills four times over 12 months, not four times after the trial — you'd lose one quarter of revenue per customer; setting `total_count: 5` with `start_at` = +7 days. **(2)** The 20% first-billing offer only fires if each subscription is created with the offer_id attached *and* the customer pays with an HDFC or ICICI card — replaying the last 90 days, that's 31% of payments; the other 69% (mostly UPI) see full price. Cost difference: ₹58,000 vs ₹184,000 per 1,000 subscriptions. **(3)** The UPI AutoPay mandate would register at ₹1,199 — raise the price later and every existing mandate silently fails to renew, undiscovered for 90 days; registering at ₹2,500. **(4)** 12% of ₹1,199 is ₹143.88, the API takes whole paise, and 12% of *gross* means the founder eats the ₹28 gateway fee and GST out of their 88% — net-of-fees it's ₹140, with odd paise assigned to their own account so every split reconciles to the rupee. It then runs a Test Mode charge, confirms `offer_id` applied and the ₹140 transfer shows `processed`, and sets a 24-hour zero-match alarm on the live offer.

**Integration path:** Razorpay APIs (`api.razorpay.com/v1`) — Orders, Payments, **Offers**, Plans, **Subscriptions** + Addons, **Route** (`/accounts`, `/payments/{id}/transfers`, `/transfers/{id}/reversals`), Payment Links, Payment Pages, Smart Collect virtual accounts, Settlements, Webhooks; HTTP Basic auth with `key_id:key_secret`, official SDKs for Node/Python/PHP/Java/Ruby/.NET, public Postman workspace. Access reality: **Test Mode keys are generated instantly on signup with no KYC** and cover Orders/Payments/Offers/Subscriptions/Payment Links end-to-end with test cards and test UPI — the best solo-dev access on this list. Caveats: Route and some recurring methods (e-NACH, UPI AutoPay) require product activation on the account (dashboard request, live use after KYC; test-mode simulation available), and Razorpay's non-India entities expose a reduced surface — build for the India stack. Cleanest MVP: a read-only "offer forensics + split calculator" that replays 90 days of payments against active offers and reports match rate, zero-match offers and exact Route splits — pure `GET` scope, instantly credible, then add the writer.

**Demand 4/5 · Buildability 5/5**

### 5. Mercado Libre Seller — catalog competition, pricing & Mercado Envíos `closed`

**Why it's powerful:** Mercado Libre is Latin America's largest e-commerce platform — ~100M unique active buyers, ~1M active sellers, and the default commerce rail in Brazil, Mexico, Argentina, Chile and Colombia. The seller surface is unusually deep: per-category required/allowed attributes, variations via "User Products", four listing types with different exposure and commission, catalog listings where many sellers compete on one product page for a buy-box-style win, Mercado Envíos Flex/Full/Colecta fulfillment tiers, interest-free installment financing you can subsidize, price-automation rules, campaign/deal enrollment, and a reputation system (reputation color, claims rate, delayed-handling rate) that mechanically throttles exposure. Sellers routinely operate 5,000–50,000 SKUs across multiple country sites, and the API is genuinely open.

**Why people bounce off it:** The single most expensive thing on Mercado Libre is invisible on every screen: whether your catalog listing is actually *competing*. `/items/{id}/price_to_win` returns `winning | sharing_first_place | losing | listed`, and `listed` means "you are on the page but not in the auction at all" with a machine-readable `reason` — no Full shipping, no free shipping, reputation too low, no interest-free installments, item not in the catalog product — none of which the seller UI states as cause-and-effect. So sellers cut price repeatedly, watch nothing happen, and never learn the winner beat them on Mercado Envíos Full eligibility, not price. Listing creation is an attribute minefield: each `category_id` has its own required attributes with controlled value ids (not free text), and picking the wrong category silently kills catalog matching and search exposure while the listing still looks fine. Listing type (`gold_special` vs `gold_pro`) silently changes both your commission and whether you're financing installments out of your own margin. Variations moved to the User Products model, so the old "one item, many variations" mental model now maps to a parent/child structure sellers corrupt by editing the wrong level. Shipping is the other money pit: a wrong package dimension on a heavy item makes Mercado Envíos quote a shipping cost that eats the entire margin, and free-shipping thresholds differ per site and price band. Cross-site expansion (BR→MX) is not a copy — different categories, attributes, tax attributes and currencies. Observed workaround: sellers pay a Brazilian/Mexican hub agency or a repricer SaaS (Olist, Anymarket, Bling, Nubimetrics) 1–3% of GMV, mostly to have someone else watch `price_to_win`.

**AI operator:** Reads the seller's items via `/users/{id}/items/search`, then per item: `/items/{id}`, `/items/{id}/price_to_win`, `/items/{id}/shipping_options`, category `/categories/{id}/attributes` and `/categories/{id}/sale_price`, plus `/users/{id}/reputation` and item-level sales history. The LLM emits a change spec — `{item_id, ops:[{set_attribute}, {change_listing_type}, {set_price}, {enable_free_shipping}, {relist_under_category}], rationale, expected_effect}` — never raw HTTP. The deterministic applier validates every attribute value against the live category schema before sending (so "invalid value id" is caught locally, not as a 400 halfway through 400 items), and orders operations so category/attribute fixes precede catalog opt-in precedes pricing. Dry-run computes, per item, the *landed* effect: new commission at the target listing type, Mercado Envíos quote for the declared dimensions, installment subsidy cost, resulting net margin, and the projected `price_to_win` outcome — "you would win at R$X, netting R$Y" or "you cannot win at any profitable price; the blocker is shipping tier, not price". Self-verification re-polls `price_to_win` and item `status`/`health` after apply and rolls back price changes that didn't flip the status. Owned failures: category attribute rejections, catalog `reason` codes, currency/site mismatches, price floors that would sell below cost.

**Killer example:** A São Paulo housewares seller says: *"My air fryer basket isn't selling even though I'm the cheapest. Fix it and don't let me sell below R$42 net."* The AI pulls the listing, calls `price_to_win`, and answers: **"You're not losing on price — you're `listed`, reason `SHIPPING_TIER`. You are R$4 cheaper than the winner but you ship Flex from your address; the winner is on Envíos Full, and the algorithm won't put you in the auction at all. Cutting price further does nothing. Two viable paths: (a) move 120 units to Full — R$0.09/unit/day storage, you'd win at R$89,90 with R$47,20 net; (b) stay Flex and you cannot enter the auction at any price. Separately: you're on `gold_special`, so the 10× interest-free installments on this page are being paid by the winner, not you — switching to `gold_pro` would raise your commission from 11% to 16% and push net to R$38,40, under your floor, so I did not do that. Also, 6 of your other 14 listings are in category MLB-271126 which doesn't match this product — they're excluded from catalog entirely and have had 0 visits in 60 days."** It then applies the Full inbound plan and the 6 category corrections, and re-polls until status flips to `winning`.

### 8. Active Directory Certificate Services (AD CS) — enterprise PKI & certificate templates `closed`

**Why it's powerful:** AD CS is the PKI most enterprises actually run: it issues the certificates behind 802.1X wired/wireless auth, VPN, smartcard logon, domain controller LDAPS, SCCM/Intune client auth, internal TLS for every line-of-business app, code signing, S/MIME and EFS. A single enterprise CA can auto-enroll and auto-renew tens of thousands of machines and users with no user interaction via Group Policy, and supports schema v2–v4 templates with fine-grained EKUs, key archival/recovery, RA signature (approval) requirements and offline root/subordinate hierarchies. It ships in every Windows Server, is installed in the overwhelming majority of Windows domains — and is simultaneously the most common path to total domain compromise.

**Why people bounce off it:** Templates are AD objects whose behaviour is spread across bitmask attributes (`msPKI-Certificate-Name-Flag`, `msPKI-Enrollment-Flag`, `msPKI-Private-Key-Flag`, `msPKI-RA-Signature`, `pKIExtendedKeyUsage`, `msPKI-Certificate-Application-Policy`) *plus* an ACL of ExtendedRight GUIDs for Enroll/AutoEnroll — the GUI shows tabs, not semantics, and nothing tells you the combination you just ticked is catastrophic. Creating a template does nothing until the CA *publishes* it (the `certificateTemplates` attribute on the CA's `pKIEnrollmentService` object), so the first symptom is "I made the template and nobody can see it." Duplicating a template forces a compatibility/schema-version choice that silently changes which options exist and which key storage providers work, producing enrollment failures like `0x80094800 template not supported by this CA` that read as a CA problem rather than a schema problem. Autoenrollment needs four independent things to line up — GPO autoenrollment policy, AutoEnroll ACL, the publish/autoenroll enrollment flags, and correct supersedence — and misconfigured `supersedes` quietly archives working certificates. The hierarchy is a time bomb: CRL and AIA URLs are stamped into every issued cert and cannot be changed retroactively, so an offline root whose CRL is allowed to expire takes down 802.1X, VPN and smartcard logon *simultaneously and estate-wide*, and an LDAP-only CDP silently breaks every non-domain-joined client. Then the security semantics: `ENROLLEE_SUPPLIES_SUBJECT` + a client-auth EKU + no approval requirement + Domain Users/Authenticated Users in the enroll ACL (ESC1) means any user can mint a certificate claiming to be Domain Admin; write access on a template object is ESC4; NTLM relay to web enrollment is ESC8. What people do instead: because an appliance's CSR kept failing, an admin duplicates the `User` or `Computer` template, ticks "Supply in the request", grants Authenticated Users enroll and a 10-year validity with "Any Purpose" EKU, and ships it — literally the modal finding of every AD pentest. Others refuse to touch the CA at all, so certificates get issued by hand with `certreq` from an email thread and nobody knows what expires when.

**AI operator:** Reads the whole Public Key Services container over LDAP (templates with raw flag bitmasks and ACLs, `pKIEnrollmentService` objects showing which CA publishes what, CDP/AIA containers), `certutil -catemplates`/`-getreg`/`-crl` and the CA's issued-cert view for real issuance history, GPO autoenrollment settings, and a `PSPKIAudit`/`Certipy find` baseline so it starts from the estate's current ESC posture. The LLM emits a declarative template+publication spec (a JSON template definition of the kind `ADCSTemplate` consumes, plus enroll/autoenroll principal lists and CA publication targets) — never raw bitmask arithmetic; the applier computes flag values, writes via LDAP/`certutil`, and stages publication as a separate reviewed step. Plan/dry-run renders the security-relevant decode in plain English ("this template lets *any* holder specify their own subject and use it for client authentication"), diffed against the current object. Self-verification is a real test-enrollment loop: after applying it re-runs the ESC audit to prove no ESC1/2/3/4 was introduced, checks the template is actually published by the intended CA, and performs a genuine `certreq -enroll` as a scoped low-privilege test account to prove the happy path works *and* as a second account to prove the deny path fails — the two checks nobody ever does. Guardrails: refuse any spec combining enrollee-supplied subject with an authentication EKU unless manager approval (`msPKI-RA-Signature`) is set; refuse broad principals on authentication templates; never modify default `User`/`Machine`/`DomainController` templates in place; and continuously watch CRL `NextUpdate` with lead-time alerting, because that is the outage everyone eventually has.

**Killer example:** An admin says: *"Our new Aruba wireless controllers need certs for 802.1X, and the CSR keeps getting rejected — just make a template that works."* The AI reads the estate, sees the admin's in-progress duplicate of `Computer` already has "Supply in the request" enabled, and stops: decoding `msPKI-Certificate-Name-Flag` it shows that with `Client Authentication` in the EKU list, no RA signature, and `Domain Computers` holding Enroll, the template about to be published is textbook **ESC1** — any of the 3,140 domain-joined machines could request a certificate with `Administrator@corp.local` in the SAN and authenticate as Domain Admin in under a minute. Instead it produces a spec that solves the actual problem: subject built from AD (`SUBJECT_ALT_REQUIRE_DNS`) rather than from the request, a dedicated `wifi-infra` group holding Enroll and AutoEnroll, 2-year validity with a 6-week renewal window, RSA 2048 with a KSP matching the controllers' firmware, and schema version pinned to the level the CA supports — explaining that the `0x80094800` rejection was the Windows Server 2016 compatibility setting, not the CSR. Along the way it flags an unrelated live fusebox: **the offline root CA's CRL expires in 11 days and its CDP points at a decommissioned web server**, meaning in 11 days every 802.1X, VPN and smartcard authentication in the company fails revocation checking at once. Plan approved, it publishes the template, re-runs `Certipy find` (0 ESC findings, down from 3), test-enrolls as `svc-wifi-test` (success, subject from AD, SAN contains only the DNS name) and as `svc-nobody` (access denied, as intended), then opens a separate change for the CRL republish.

**Integration path:** LDAP writes to `CN=Certificate Templates,CN=Public Key Services,CN=Services,CN=Configuration` (all `msPKI-*` attributes + nTSecurityDescriptor), `certutil.exe` (`-catemplates`, `-dstemplate`, `-setreg`, `-crl`, `-view`, `-setcatemplates`), the `PSPKI` and `ADCSTemplate` PowerShell modules (the latter imports/exports templates as JSON — an actual declarative surface), `ICertAdmin2`/`ICertRequest` COM for issuing/denying pending requests, `certreq`/`Get-Certificate` for test enrollment, and `PSPKIAudit` (`Invoke-PKIAudit`) + `Certipy find`/`Certify.exe find /vulnerable` as the verifier. Access reality: free Windows Server 2022/2025 180-day eval ISO; a 2-VM lab (DC + CA) on a laptop reproduces every trap, and the security-audit tooling is open source. Cleanest MVP: a PowerShell-remoting agent + JSON template spec + PSPKIAudit/Certipy verification loop, positioned as "a PKI operator that cannot create an ESC1" — sells to MSPs and to anyone who just failed a pentest.

The LLM emits a typed change spec — board schema deltas, SLA matrix rows, agreement coverage rows, work-type/work-role mappings, member defaults — never raw HTTP. Dry-run is the differentiator: the applier **re-prices the historical time entries against the proposed mapping** and reports the billing delta plus the count of tickets whose SLA state would change, before a single write. Self-verification re-reads every mutated object and re-runs the pricing simulation post-apply; the layer owns rate-precedence collisions, deleting a status still referenced by a workflow rule or board default, and calendar/timezone mismatch on SLA clocks.

**Killer example:** An MSP owner types: *"We write off about 40 hours a month on the Acme managed agreement — figure out why and fix it."* The operator pulls 2,150 time entries from the last 90 days, finds 312 of them on work type "Remote Support" logged by members whose default work role is "Tier 2 Engineer" against an agreement addition that only covers "Tier 1 Engineer", and computes **41.5 h/month landing as covered-but-unbillable — roughly $6,200/month** at the agreement's rate. It proposes three agreement coverage rows, two member default-work-role corrections and one board default change, shows the re-priced 90-day delta, and then surfaces something nobody asked about: the "Managed Services" board's SLA is bound to the 24×7 calendar while the Acme agreement is 8×5, so the same after-hours entries are also generating **phantom SLA breaches in the client's QBR deck** — one root cause, two symptoms that had been treated as unrelated for a year.

**Integration path:** ConnectWise PSA REST API (`https://<region>.myconnectwise.net/v4_6_release/apis/3.0/...`), auth = public/private API key pair for an API Member plus a ClientID; OpenAPI schemas available, plus mature clients (`pyconnectwise`, `ConnectWiseManageAPI`). Access reality — **gated**: the ClientID requires registration on developer.connectwise.com, and documentation depth plus sandbox/test instance allocation is granted by integrator category under the ConnectWise Invent partner program (approval, not self-serve). Cleanest solo-dev MVP: get one friendly MSP to create a restricted-security-role API member on their live instance and ship read-only first — a "billing leakage + SLA calendar auditor" that needs only Inquire permissions and produces the re-pricing simulation — then add writes behind the dry-run gate once the simulation has been trusted for a few cycles.

**Demand 5/5 · Buildability 3/5**

### 11. Dynamics 365 Customer Service — Unified Routing `closed`

**Why it's powerful:** Dynamics 365 Customer Service is one of the two enterprise service platforms of record, and unified routing is now the routing engine Microsoft pushes all customers onto (also the engine inside Dynamics 365 Contact Center). It classifies and assigns work across channels — cases/records, chat, voice, messaging — through work streams, multiple ordered work classification rulesets (rule-based *and* ML models for sentiment, effort and intent), a route-to-queue ruleset, assignment methods (highest capacity, round robin, or custom rulesets), capacity profiles/units, and skill matching via characteristics plus rating models with exact/closest-match modes. It ships with diagnostics run traces and per-work-stream priority and overflow handling. Every D365 service tenant of any size configures this, and getting it wrong throttles the entire support organisation.

**Why people bounce off it:** The evaluation chain is long and almost entirely invisible: work stream → N classification rulesets in order → exactly one route-to-queue ruleset → queue assignment method → skill and capacity match. Nothing tells you which rule matched a given item unless you enabled the diagnostics feature *before* the item arrived, and then you read run traces after the fact. Rule order silently shadows: a loose earlier condition like `subject contains 'charge'` swallows every item your new precise rule was written for. Skill matching starves queues without alarms — if no agent holds the required characteristic at the required rating and you chose exact match, the item simply sits unassigned. Capacity profiles and capacity units are two parallel systems, and agents configured in units while the work stream uses profiles receive nothing at all, forever, with no error. Environment promotion is its own disaster: routing rules are solution-aware but the queues, users and teams they point at are not, so after a solution import you must remap every rule by hand, and Microsoft's docs warn you must export *all* internal entities including decision rulesets and contracts or work-stream import fails outright. Observed workaround: partners sell fixed-price "unified routing implementation" packages, admins keep the real configuration in Excel and rebuild it manually per environment, and Microsoft's own published guidance for multi-update routing problems is to contact Microsoft Support.

**AI operator:** Reads the tenant's routing graph from the Dataverse Web API — `msdyn_liveworkstream`, the routing/decision ruleset and rule-item tables, queues and queue members, `msdyn_capacityprofile`, the characteristic and rating-model/rating-value tables, and `msdyn_unifiedroutingrun`/setup-tracker diagnostics — plus agent skill coverage and 30 days of work-item history. The LLM emits a routing spec: work streams, ordered classification rules with conditions and output attributes, queue map, skill requirements with rating floors, capacity model, overflow and priority. A deterministic applier upserts those records inside a single solution and resolves every queue/user/team reference by name→GUID *in the target environment*, which is precisely what solution transport breaks. Dry-run replays the last 30 days of real work items through the proposed chain offline and reports, per item, which rule would match, the percentage that would land unassigned, and projected per-queue load; after apply it triggers diagnostics runs on a handful of test records and asserts the observed path equals the predicted one. It owns rule-order shadowing, rating floors with zero qualified agents, profile/unit mismatch, and unmapped references after environment moves.

**Killer example:** A service manager says: *"Route anything about chargebacks from premium customers to the payments team, only to people who've actually handled chargebacks, and don't swamp them."* The operator replays 30 days: 1,830 items match "chargeback", 412 of them premium — but **existing rule 3 (`subject contains 'charge'`) would shadow the new rule for 1,106 of them**, so it proposes inserting at position 2 and shows the before/after match table. It finds only 3 agents hold the `Chargebacks` characteristic at rating ≥ Proficient and computes that exact-match would leave ~41 items/day unassigned, so it proposes closest-match with a Basic floor plus a 15-minute overflow to `Payments_General`. It then catches the thing no human would: **6 of the payments team's 9 members are configured with capacity *units* while the target work stream uses the `Chat_Default` capacity *profile*, so those six would have received zero work regardless of the routing rules** — and it emits the corrected profile assignments plus a one-page diff for approval before a single record is written.

**Integration path:** Dataverse Web API (OData v4 at `/api/data/v9.2/`) against an Entra app registration using client credentials bound to a Dataverse application user; unified routing tables are documented in the D365 Customer Service developer entity reference; `pac cli` / Solutions API for packaging, and unified routing diagnostics as the post-apply verification oracle. Access is genuinely solo-dev friendly: a self-serve 30-day Dynamics 365 Customer Service Enterprise trial (unified routing must be provisioned from the Customer Service admin center) plus a free Power Platform developer environment for the pure-Dataverse work. MVP: Python/Node + MSAL, a spec→upsert applier with name-resolution, and an offline replay engine seeded from exported work-item history — the replay engine alone is demoable value before any write path exists.

**Demand 4/5 · Buildability 4/5**

### 12. Lightspeed Retail X-Series — price books & promotions `closed`

**Why it's powerful:** Lightspeed is one of the few truly global independent-retail POS platforms, at roughly 130,000+ customer locations across apparel, bike/outdoor, golf, pet, homeware and hospitality — the segment that is too big for Square and too small for an ERP. The back office is unusually capable for SMB retail: **Price Books** that override product prices scoped by customer group *and* by outlet with date ranges and loyalty amounts, a separate **Promotions** engine for in-store discounts and multi-buy offers, product variants/attributes, per-outlet inventory with reorder points and automatic purchase-order generation, consignments and transfers, customer groups, gift cards and store credit, and an accounting mapping layer. The API is real and actively versioned: `products`, `price_books`, `price_book_products`, `promotions`, `inventory`, `outlets`, `customers`, `sales`, `consignments` plus webhooks.

**Why people bounce off it:** Price books are a precedence engine with no precedence viewer. Multiple price books can cover the same product for the same outlet and customer group with overlapping date ranges, and the register resolves one winner — but nothing in the UI tells a retailer *which* book won or why, so the classic failure is a Christmas sale price book that never activated (wrong outlet scope, or a customer-group restriction the walk-in sale doesn't match) and staff selling at full price for three weeks while the owner insists the sale is live. The inverse is the money-burner: an old "Staff Pricing" or "Clearance" book left un-end-dated keeps discounting 400 SKUs forever, and because the discount is baked into the resolved price rather than shown as a markdown line, it looks like margin erosion with no cause. Promotions and price books are *different subsystems* that stack, so a 20%-off promotion applied on top of an already-price-booked item produces a price the owner never authorized. Multi-outlet is the second wall: inventory, reorder points and price books are all per-outlet, and a product added at head office simply doesn't exist sellably at outlet #3 until inventory and (if scoped) pricing are set there — a silent no-op with no warning. Variants multiply everything: a 6-colour × 5-size shoe is 30 rows that each need their own price book entry, so bulk pricing work is done in CSV exports that silently drop the price-book scoping columns. On top of this, Lightspeed is mid-migration from semantic API versions (0.9/2.0, now deprecated) to date-based versions like `2026-04`, and different resources live on different version paths. Observed workaround: retailers pay a Lightspeed implementation partner for setup and then never touch pricing structurally again — they discount manually at the register, which destroys reporting.

**AI operator:** Reads the full pricing graph — `GET /api/{version}/products` (with variants), `/price_books`, `/price_books/{id}/products`, `/promotions`, `/outlets`, `/customer_groups`, `/inventory` — and builds a deterministic **price resolver** that replicates Lightspeed's own winner-selection for any (product, outlet, customer group, date) tuple. The LLM emits `{intent, scope:{outlets[], customer_groups[], product_filter}, pricing:[{type: price_book|promotion, rule, start, end}], guards:{min_margin_pct, max_discount_pct}}`. The applier expands `product_filter` to concrete variant ids (so "all Nike trainers" becomes the 118 actual rows), creates the price book scoped correctly, and batch-`POST`s `price_book_products`. The dry-run is the differentiator: for every affected variant it prints the currently resolved price, the newly resolved price, which price book/promotion wins, gross margin after the change, and **stack collisions** ("this variant is also covered by 'Clearance 2024' which never ends and by a 20% storewide promotion — combined effective discount 62%, margin −£3.10"). Self-verification re-runs the resolver against freshly fetched data after apply and reconciles against the first real sales webhooks to confirm the register is charging the intended price. Owned failures: overlapping/never-ending books, outlet-scope no-ops, promotion×price-book stacking, variant expansion misses, version-path drift.

**Killer example:** A three-store bike shop owner says: *"Run 15% off all 2025 model-year road bikes at the Leeds and York shops from Friday to the end of the month, but never below what we paid."* The AI expands that to 214 variants, creates a date-bounded price book scoped to the two outlets, and reports before applying: **(1)** 31 of the 214 would go below cost at 15% — a Domane AL2 lands at £849 against £871 cost; those are capped at cost+8% and listed. **(2)** 62 of these bikes are already inside price book "Winter Clearance" which has no end date and wins over any new book with lower priority — the 15% would have been a no-op on those; it raises the new book's priority and sets an end date on Winter Clearance so it stops silently discounting in March. **(3)** The storewide "Locals 10%" promotion stacks on top of price books, so members would pay 23.5% off, not 15% — **£14,200 of extra margin across the month at last year's volume** — so it excludes this book from that promotion. **(4)** Leeds has 0 on-hand for 18 of these SKUs and no reorder point set, so the shop would be advertising bikes it can't sell there — offering a transfer from York, which has 41.

**Integration path:** Lightspeed Retail (X-Series) API at `https://{prefix}.retail.lightspeed.app/api/{version}/...` — date-based versions (`2026-01`, `2026-04`, `2026-07`), token auth via either a **Personal Token** (single retailer, ideal for MVP) or an OAuth Add-on (multi-retailer), plus webhooks for `sale.update` and inventory. Confirmed endpoints include `price_books`, `price_book_products`, `price_books/{id}/products`, `promotions`, `products`, `inventory`, `outlets`, `customers`, `consignments`. Access reality: developer account registration is self-serve and free, **but Lightspeed does not offer a sandbox** — you test against a free 14-day trial retail account (extendable by asking `x-series.api@lightspeedhq.com`), which is the main friction. Honest caveat: deprecated 0.9/2.0 paths are still required for a couple of write operations, so pin versions per-resource. Cleanest MVP: personal-token-only, single-tenant "pricing X-ray" that resolves effective price per variant/outlet and flags never-ending books and promotion stacking — read-only, immediately demo-able, then add the price-book writer.

**Demand 4/5 · Buildability 4/5**

## Notes on this run

**Strongest single pattern across all 12:** every winning operator concept is a *simulate-then-apply* loop where the dry-run output is itself the product. In seven of the twelve, the read-only diagnostic (the SLA blind-spot report, the offer-match forensics, the `price_to_win` auditor, the ESC1 audit, the billing-leakage re-pricing, the routing replay, the pricing X-ray) is independently sellable before any write path exists — which is also the cheapest path past the access gates on the gated platforms.

**Access reality, ranked best to worst:** Razorpay test-mode keys (instant, no KYC) → Salesforce Developer Edition and LINE (free, self-serve) → Google Sheets API / Word OOXML (free, no account gating) → Mercado Libre (free app + 10 test users) → M365 dev tenant for Shifts (free trial) → D365 Customer Service (30-day self-serve trial) → AD CS (free 180-day Windows Server eval, needs a 2-VM lab) → Lightspeed (self-serve dev account but **no sandbox**, 14-day trial only) → DATEV (sandbox self-serve, production needs **two approval meetings**) → ConnectWise (partner-program gated).

**Deliberately deprioritized:** several candidates scored higher on raw demand × buildability but were ranked out under the mainstream-install-base bias — NetBox, Checkmk, RabbitMQ, FreeIPA, Apache NiFi (all 4–5 × 4–5, but self-hosted OSS power-user tools), plus OpenUSD, ZBrush, MuseScore and TouchDesigner (specialist creative audiences). MECM/SCCM, IBM Maximo, TOTVS Protheus, Kyriba, SAP Ariba and Paychex all have demand 4–5 but buildability 2 from lab/licensing/partner gates. These remain unclaimed and are worth revisiting if the mainstream bias is relaxed.
