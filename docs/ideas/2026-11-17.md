### 1. Subtitle Edit (open-source subtitle editor plus seconv CLI), with Aegisub as a second connector `open-source`

**Why it's powerful:** Subtitle Edit is the de facto free subtitle workstation for freelance subtitlers, YouTubers, localization vendors and post houses. It reads and writes 300+ formats (SRT, ASS, WebVTT, TTML/IMSC, EBU STL, PAC, Netflix TTML), has waveform and spectrogram timing, shot-change detection, Whisper-based transcription, OCR of image-based subs (PGS/VobSub), batch Fix Common Errors, merge/split/balance lines, frame-rate and offset sync, and checks against Netflix-style rules. The Avalonia rewrite ships a headless `seconv` CLI with JSON settings profiles.

**Why people bounce off it:** The power sits behind dozens of dialogs whose rules interact: max characters per line, characters per second, minimum gap, minimum and maximum duration, shot-change snapping (frames before/after a cut) and line balancing all fight each other. Passing a broadcaster or Netflix Timed Text Style Guide QC means knowing which Fix Common Errors checkboxes to enable, in which order, with which thresholds per language. Sync problems (23.976 vs 25 fps drift, a cut in the edit) need visual or point sync, which most users never find. Format conversion quietly loses styling and positioning. Many people pay for EZTitles or OOONA, or deliver files that bounce at QC.

**AI operator:** 'Subtitle QC Operator' takes a subtitle file, the video (optional) and a target spec in plain words or a preset (Netflix English, Netflix Japanese, BBC, YouTube, CEA-608). It runs ffmpeg scene detection for shot changes, analyses violations (CPS, line length, gaps, durations, cut-crossing), and applies fixes through seconv with generated JSON fix profiles plus pysubs2 passes for things the CLI doesn't expose. The LLM handles the judgment edits no rule engine can: condensing a line to meet CPS without losing meaning, re-breaking at linguistic boundaries, stripping SDH tags for a non-SDH deliverable. Output is a QC report with before/after per cue.

**Killer example:** A freelancer pastes a rejection email: 'Netflix QC failed: 312 reading-speed errors, 97 cues crossing shot changes, wrong frame rate.' User: 'Here's the French SRT and the ProRes. Fix whatever they flagged, 25 fps, 42 chars, 17 CPS, 2-frame gap snapped to cuts, and give me IMSC TTML plus an SDH-free version.' The AI detects 1,184 shot changes and finds that the 97 cut-crossings come from a 23.976-to-25 drift that starts after reel 2. It re-syncs from that point, condenses 64 French lines ('Je ne sais vraiment pas ce que tu veux dire par là' becomes 'Je ne vois pas ce que tu veux dire'), re-breaks 140 lines at clause boundaries, removes [MUSIQUE]-style tags for the non-SDH file and exports both with seconv. It returns a QC table with 0 hard errors and 11 condensations flagged for a human read, each shown with the original and the new line.

**Integration path:** Fully headless and local. `seconv <input> <format> [options]` with --settings JSON for fix-common-errors profiles (Subtitle Edit 5.x, Avalonia), libse (.NET) for deeper access, pysubs2 for Python-side cue manipulation, ffmpeg scdet/scene filters for shot changes, faster-whisper for re-timing or transcription. Aegisub via Automation Lua scripts and ASS files for typesetting-heavy (anime/karaoke) work. No vendor API or account, so a CLI or desktop MVP is a few weeks of work. Confirm exact seconv option names per version.

**Verification:** Verified 2026-11-17: the `seconv` CLI is confirmed. Disclosure: Subtitle Edit already has a built-in Netflix quality check, updated to the current Timed Text Style Guides. Since v5.1 it also has an 'AI review' that proofreads through a local LLM (llama.cpp or Ollama) with an editable prompt. The edge is therefore the spec-driven loop (re-sync, cut snapping, condensing to a CPS target, QC report), not LLM access as such. Not re-checked: the built-in shot-change and Fix Common Errors tools.

**Demand 4/5 · Buildability 5/5**

### 2. Company email signatures across Gmail (Google Workspace) and Outlook (Microsoft 365), as an open alternative to Exclaimer/CodeTwo `closed`

**Why it's powerful:** Every employee sends thousands of emails, so the signature is the company's most-viewed brand surface: directory-driven title and phone, legal disclaimers per entity or country, campaign banners with UTM links, booking links, pronouns. Gmail exposes per-alias signatures through the Gmail API (users.settings.sendAs.patch with domain-wide delegation). Outlook supports add-in event-based activation (OnNewMessageCompose) to insert signatures client-side, and Exchange transport rules can append server-side.

**Why people bounce off it:** Signature HTML is fragile: table layouts, inline CSS, retina images, dark-mode inversion and Outlook desktop's Word renderer all break differently. Directory data is patchy. Microsoft Graph has no roaming-signature API, Set-MailboxMessageConfiguration -SignatureHTML stops working once roaming signatures are on, EWS is blocked by default from Oct 2026, and the classic-to-new Outlook switch lands in 2027. IT admins either pay per seat for Exclaimer/CodeTwo or let every employee hand-paste a broken JPG.

**AI operator:** A 'Signature Desk' operator for marketing or IT. It pulls attributes from Google Directory or Entra ID and flags missing or inconsistent fields, generates bulletproof table-based HTML from a brand description, previews it in Gmail, Outlook desktop, OWA, iOS and dark mode, and assigns variants by rule (department, country, legal entity). It deploys through the Gmail API for Workspace and an Outlook event-based add-in or transport-rule fallback for M365, and schedules campaign banners with start and end dates.

**Killer example:** Marketing: 'Everyone in Sales EMEA gets the new signature with the Web Summit banner until 14 November, German staff need the GmbH Handelsregister disclaimer, fix the all-caps titles, and nobody's phone should be missing +49.' The AI finds 212 users, shows a diff normalising 37 titles and 19 phone numbers, and renders previews in five clients. It catches that the banner turns into a white box on a black background in Outlook dark mode and swaps in a transparent PNG with a background-colour fallback. It pushes signatures to every Gmail send-as alias (including 14 shared-inbox aliases a hand rollout would miss) and to the Outlook add-in config, and schedules the banner removal for 14 November.

**Integration path:** Gmail API settings.sendAs (signature field) via a service account with domain-wide delegation, plus Admin SDK Directory for user data. Microsoft side: an Office.js add-in with event-based activation (OnNewMessageCompose / setSignatureAsync) reading signatures from the operator's backend, Graph /users for attributes, and an Exchange Online transport-rule disclaimer as fallback for mobile and third-party clients. Previews via headless Chromium plus dark-mode simulation. MVP: Gmail-only (fully API-driven). Phase 2: the Outlook add-in. Note: 'Gmail org-wide signatures' was a strong-but-cut runner-up on 2026-10-24; this broadens it to a cross-suite product.

**Verification:** Verified 2026-11-17: Gmail `users.settings.sendAs.patch` and its settings scopes are confirmed. Disclosure: Scribe sells a paid MCP that builds, audits and publishes signatures in plain English, though its page doesn't confirm Gmail or Outlook deployment. The ProSignature MCP is free but read-only. WiseStamp claims a prompt-based AI designer. Exclaimer shipped a screenshot-to-template converter on 2026-11-04. GAM can probably already bulk-set Gmail signatures (from memory, not checked), so a Gmail-only MVP is thin. The value is cross-suite, in the Outlook add-in. Not re-checked: Outlook `setSignatureAsync`.

### 3. Act! CRM (Act! Premium desktop / Act! Premium Cloud, with Act! Marketing Automation) `closed`

**Why it's powerful:** One of the oldest contact managers (since 1987), with a large, loyal SMB base that skews older and less technical: independent insurance agents, financial advisors, small manufacturers and distributors. It has deep contact history, groups and companies, dynamic groups driven by lookups, opportunity pipelines, custom tables, activity series (scheduled follow-up sequences), Outlook/Gmail integration and built-in email marketing automation (AMA).

**Why people bounce off it:** The UI is a 2000s-era Windows-style app (the web version mirrors it). The 'Lookup' and Advanced Query builder, dynamic groups versus static groups, custom tables, field properties/triggers, Activity Series templates and AMA's drip campaign editor are all hard for the non-technical small-business owners who are Act!'s core market. Many users only use Act! as an address book and pay consultants to build queries and campaigns.

**AI operator:** An 'Act! Assistant' that sits on top of the Act! Web API (OData v4 + REST, available for Premium Cloud and desktop Premium installs with the Web API enabled). It turns natural-language segments into OData $filter queries, then creates/updates contacts, groups, activities, opportunities and history entries. It builds Activity Series and follow-up schedules, and explains a contact's history in plain language. Skills cover Act!'s data model (contacts, companies, groups, custom tables) and common vertical playbooks such as insurance renewals and advisor client reviews.

**Killer example:** User (insurance agent) says: "Find everyone whose auto policy renews in the next 60 days and who I haven't talked to since spring. Put them in a 'Renewal push' group and schedule me a call for each, five a day starting Monday, with the oldest renewal first." AI queries contacts where Renewal Date is within 60 days and last call/meeting history is before 2026-06-01 (52 matches), creates a static 'Renewal push - Nov 2026' group, creates 52 call activities spread at 5 per weekday from 2026-11-23 sorted by renewal date, each with a regarding note listing the policy and premium, and replies: 'Done. 52 calls over 11 working days. 4 contacts have no phone number; want me to email them instead?'

**Integration path:** Act! Web API: OData v4 for reads/queries plus REST endpoints for creating/updating contacts, groups, activities, opportunities and history, authenticated with a bearer token from username/password/database. Swagger docs are available from Act!'s developer site. Works for Act! Premium Cloud and for on-prem installs that expose the Web API through IIS. AMA campaigns have more limited API coverage, so start with CRM records. A solo dev can get a trial license and build an MVP quickly. Distribution: Act! Marketplace and the Act! consultant/reseller network.

**Verification:** Verified 2026-11-17: Act!'s live Swagger lists `POST /api/contacts`, `POST /api/groups`, `PUT /api/groups/{id}/associated-contacts`, `POST /api/History` and `POST /api/ActivitySeries`. Not confirmed: POST on `/api/tasks`. Disclosure: Act!'s own AI does text writing and history summaries, and 'task automation' is on its 2026 roadmap. CData's free Act! MCP is read-only, but its paid version writes. Enrich Labs and Arahi sell agents for Act! 365.

### 4. bol.com Retailer API + Advertising API (Sponsored Products), the dominant Netherlands and Belgium marketplace `closed`

**Why it's powerful:** bol.com is the main marketplace in the Netherlands and Belgium, with more than 50,000 sellers. The Retailer API covers offers, pricing, stock, LVB (Logistics via bol) replenishments, shipments, returns and invoices. The separate Advertising API (v11) creates and updates Sponsored Products campaigns, ad groups, keywords, bids and targeting, and reports on performance.

**Why people bounce off it:** Sellers, most of them Dutch and Belgian SMBs, have to work across two different consoles: the seller dashboard for offers, LVB stock and returns, and the Sponsored Products advertising UI. Ads are managed keyword by keyword and bid by bid, with no cross-campaign bulk logic. Stock coverage, LVB replenishment and ad spend are never linked, so sellers keep paying to advertise SKUs that are about to run out at LVB. Most sellers handle this with spreadsheets or pay agencies.

**AI operator:** A seller operator that sees inventory, ads and margin together. It reads offers, LVB inventory, days of cover and margin from the Retailer API, and ad performance from the Advertising API. It then carries out instructions in plain Dutch or English: pause or reduce ads on low-stock SKUs, add search terms that convert as exact keywords and add wasting ones as negatives, raise bids on high-margin items, and draft LVB replenishment proposals. Every change set is previewed as a diff before it is applied.

**Killer example:** User says: "Zet advertenties op pauze voor alles met minder dan 10 dagen LVB-voorraad, verhoog biedingen met 20% op producten met marge boven 35% en ACoS onder 15%, en maak een aanvulzending voor de top 20 sellers." ("Pause ads on everything with under 10 days of LVB stock, raise bids 20% on products with margin above 35% and ACoS under 15%, and create a replenishment shipment for the top 20 sellers.") The AI finds 18 low-stock SKUs and pauses their ad groups. It raises bids on 42 keywords with a guardrail on the maximum bid. It drafts an LVB replenishment for 20 EANs with suggested quantities based on 30-day velocity. It then shows the complete diff before running anything.

**Integration path:** bol.com Retailer API v10/v11 (api.bol.com/retailer) with client-credentials JWT, covering offers, inventory, replenishments, shipments and returns. The Advertising API (Retailer-API v11 functional docs, advertising-api) uses the same authentication and supports campaign, ad group, keyword and bid create and update plus reports. Honest gaps: (1) Community MCPs already wrap the Retailer API (bol-mcp has 76 tools; Truto, Unified.to and AnythingMCP also offer connectors), but none was found for the Advertising API, and none links stock, margin and ad spend. That link is the product. (2) Partner AI ad-optimization tools exist in bol's ecosystem, so this needs a clear position. (3) Rate limits are strict, so batching and caching are mandatory.

**Verification:** Verified 2026-11-17: bol-mcp (76 tools) covers the Retailer API but explicitly not Advertising API v11. e-tailize says it is building an official bol MCP (private beta). Advertising API v11 campaign create and update is in bol's docs. The exact keyword and bid endpoints were seen only in search snippets this run. Not checked: whether bol has a built-in auto-bidding tool. Keyword harvesting alone repeats the 2026-10-04 Apple Ads card. The new part is linking LVB stock and margin to ad spend.

**Demand 3/5 · Buildability 4/5**

### 5. Hugin (open-source panorama stitcher, Panorama Tools CLI chain), with PTGui Pro as a second connector `open-source`

**Why it's powerful:** Hugin and its toolchain (pto_gen, cpfind, celeste_standalone, linefind, autooptimiser, pano_modify, nona, enblend/enfuse, verdandi) can stitch anything from a phone sweep to a multi-gigapixel bracketed HDR spherical: lens calibration, vignetting/EMoR photometric correction, masks for moving people, mosaic mode, every projection. PTGui Pro, the paid standard for virtual-tour and real-estate 360 shooters, has JSON .pts projects and -createproject / -stitchnogui batch.

**Why people bounce off it:** The GUI exposes the raw optimizer: lens a/b/c/d/e, yaw/pitch/roll/TrX, control-point pruning, 'optimize the vertical', anchor-incremental positions. A failed stitch (ghosting, broken horizon, nadir smear, wavy lines) has to be diagnosed from control-point error tables. HDR brackets need the right stack/exposure-layer settings or enfuse produces mush. Real-estate photographers, drone pilots and tour builders hit this wall and pay for PTGui or a cloud stitcher; even PTGui batch is fiddly.

**AI operator:** 'Pano Operator' ingests a folder, groups shots into panoramas and brackets from EXIF, generates the .pto through the CLI chain, chooses detector settings, optimizer variables and projection from intent, then iterates on control-point RMS: prunes bad points, adds vertical-line constraints with linefind, and masks ghosts found by a vision model on the preview. Renders via nona plus enblend/enfuse with nadir patching; batch-templated for whole-property shoots, with a PTGui connector writing .pts templates.

**Killer example:** User: 'Here are 47 drone shots from the farmhouse job, 3 brackets each. One 360 HDR equirect per hover point, fix the leaning horizon, patch the drone shadow, 8K JPEGs for Kuula.' The AI groups 5 panoramas by GPS and timestamp, builds stacks, runs cpfind --multirow plus linefind, sees pano 3 at 7.2 px RMS from a moving tractor, masks it and re-optimizes to 1.1 px, levels horizons, fills the nadir, renders with enfuse, and returns a per-pano quality table with one flagged for a reshoot.

**Integration path:** 100% scriptable: Hugin CLI tools on the plain-text .pto format; hugin_executor --stitching for the full render; Python via hpi/hsi plugins; ExifTool for grouping; libpano13 underneath. PTGui 13 exposes -createproject img... -output x.pts [-template t.pts] and -stitchnogui; .pts is strict JSON, so start from a PTGui-saved template. Local MVP: Hugin CLI wrapper with an LLM planner plus a vision check on downscaled previews.

**Verification:** Checked 2026-11-17 (one search, low confidence): no MCP server or AI assistant drives Hugin or PTGui. Nearby photo MCPs (darktable, PhotoFresco, photographi-mcp) don't stitch.

**Demand 3/5 · Buildability 4/5**

### 6. ArgyllCMS (open-source color-management engine) with DisplayCAL (community Python 3 fork) as the GUI layer `open-source`

**Why it's powerful:** The most capable color-calibration engine available, free or paid: display calibration and ICC/3D-LUT profiling (dispcal, dispread, colprof), printer and paper profiling from printed targets (targen, printtarg, chartread), device links and gamut mapping (collink), verification, spectral correction for wide-gamut OLED/QD panels, and 3D LUT output for DaVinci Resolve, madVR and hardware-calibrated monitors. DisplayCAL is maintained as a Python 3 community fork with ArgyllCMS 3.5 support.

**Why people bounce off it:** Color management is concept-dense and the tools speak in it: whitepoint, tone response (BT.1886 vs 2.2 vs sRGB vs PQ), black-point compensation, rendering intents, matrix vs XYZ LUT profiles, patch counts, colorimeter correction matrices per backlight, video-card gamma tables vs 3D LUTs. Photographers who print, small print shops and freelance colorists calibrate wrongly or pay $200-500 for single-probe vendor software. DisplayCAL exposes nearly every Argyll flag, which is exactly why people bounce off it.

**AI operator:** 'Color Operator' turns intent ('match my prints on Canson Platine', 'Rec.709 for broadcast on this LG OLED', 'consistent sRGB across 6 studio iMacs') into a full Argyll plan: targets, instrument correction for the detected panel, calibration targets and profile type. It runs the CLI chain step by step, tells the user when to place the probe or scan the chart, verifies with a delta E 2000 report, installs the profile, exports 3D LUTs, and explains the outcome plainly. Fleet mode keeps per-machine profiles and recalibration reminders.

**Killer example:** User: 'My prints from the Epson P900 on Hahnemuhle Photo Rag look darker and greener than my screen. Fix it.' The AI sees an i1Display Pro on a wide-gamut Dell, calibrates the screen to D50, 100 cd/m2, gamma 2.2 for print editing, generates a 1,000-patch target sized for the paper, tells the user to print with color management off and let it dry 24 hours, guides the chart read, builds an XYZ-LUT printer profile with a perceptual intent tuned for matte black, and sets up the Lightroom soft-proof. Verification: mean delta E 1.1 on screen plus a printed-vs-proof comparison chart.

**Integration path:** All CLI: ArgyllCMS binaries (dispcal, dispread, colprof, targen, printtarg, chartread, collink, colverify, ccxxmake) with text .ti1/.ti2/.ti3 files and standard ICC output; displaycal-py3 for its instrument database, verification charts and LUT export logic. Profile install via ColorSync, Windows WCS, or colord. LLM plus wizard UX on top; a hardware probe is needed for real calibration, though dry runs and profile analysis work without one. GPL/AGPL means shelling out to binaries rather than linking.

**Verification:** Checked 2026-11-17 (one search, low confidence): no MCP server or AI assistant drives ArgyllCMS or DisplayCAL. The nearest is a DDC/CI MCP that only changes monitor hardware settings.

**Demand 3/5 · Buildability 3/5**

### 7. Oracle JD Edwards EnterpriseOne (9.2, via the AIS Server) `closed`

**Why it's powerful:** A full mid-to-large ERP with GL, AP/AR, fixed assets, job cost, manufacturing, distribution and payroll, still running at thousands of companies. Every program accepts versions and processing options, Automatic Accounting Instructions (AAIs) drive the GL posting for every transaction, and User Defined Codes (UDCs) let customers reshape almost any list without writing code.

**Why people bounce off it:** The UI is a maze of cryptic program numbers (P4210 sales orders, P0411 vouchers, P0011 batches, P40950 distribution AAIs, P0004A UDCs, R09801 GL post). Behaviour is hidden in processing-option versions such as ZJDE0001 versus a custom version, and GL account selection runs through an AAI lookup hierarchy (company, then doc type, then GL class) that hardly anyone outside a CNC or finance consultant can follow. To find out why an order posted to a given account, a user needs to know which table, which AAI and which version are involved. Turnover in finance teams leaves companies paying consultants $150-250/hr for basic 'why/where/how do I' questions.

**AI operator:** 'JDE Navigator', an agent that knows the app-ID map, the AAI and UDC tables and the batch lifecycle. It answers questions by reading live data and does the work by driving the same forms a user would. It has three skills: (1) explain, which reads F0911, F4095 (AAIs), F0005 (UDCs) and F983051 (versions) through the dataservice and walks the posting logic in plain language; (2) do, which runs form actions through formservice (enter a voucher, approve a batch, add a UDC value, add an AAI row); (3) run, which launches UBEs such as R09801 or R03B551 where the AIS release supports it. Every write is shown first as a dry-run listing the form, the fields and the values, and runs only after the user confirms.

**Killer example:** User asks: 'Why did sales order 10452 hit COGS 1100.5100 instead of 5105, and fix it for GL class IN30 going forward.' The AI reads the F0911 lines for the order, looks up AAI 4220 in F4095 for company 00100, doc type SO and GL class IN30, and finds that no specific row exists, so the lookup fell through to the 00000/****/default row. It explains this in two sentences. It then proposes a new 4220 row (00100 / SO / IN30 to 1100.5105), shows the P40950 form payload, and adds the row through formservice once the user approves. It also lists the 37 other orders posted this month that the same gap affected.

**Integration path:** AIS Server REST, which is documented by Oracle: POST /jderest/v2/formservice runs any interactive form, fills fields and presses buttons (this is the write path, and it covers everything a user can do in the UI, including AAI and UDC maintenance); /v2/dataservice runs table and view queries; existing orchestrations are invoked at /jderest/orchestrator/{name}, and GET /discover plus the v3 open-api catalog list them. Caveat: orchestrations can only be authored in Orchestrator Studio (no create endpoint), so the operator must drive forms directly and not try to generate orchestrations. Authentication is a JDE user/role token, so security inherits from JDE row and form security.

**Verification:** Checked 2026-11-17: no Oracle-native JDE agent found, and the only JDE MCP (jde-e1-config-mcp) gives configuration advice without connecting to AIS. Disclosure: ERP Suites sells paid JDE 'digital workers' (Ledger, Payables). Forrester reports an Oracle configuration agent that reads JDE metadata. Not re-fetched this run: the AIS `formservice` reference, though Oracle documents AIS as JSON over REST for forms.

**Demand 4/5 · Buildability 2/5**
