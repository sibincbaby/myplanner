### 1. Matomo Analytics (self-hosted On-Premise and Cloud; includes Matomo Tag Manager) `open-source`

**Why it's powerful:** 1M+ sites, and the main destination for GA4 refugees who want raw, owned, unsampled data. Feature depth rivals GA4: 200+ report methods, unlimited saved segments, goals with revenue, funnels, custom reports (pivot any dimension x metric), custom dimensions (~50 per scope on-premise via console), full e-commerce reports (cart, product SKU/category, abandoned cart), roll-up of multiple sites, A/B tests, heatmaps/session recordings, plus a built-in Tag Manager with containers, triggers, variables, versions and publish workflow — all queryable over one HTTP API with a token.

**Why people bounce off it:** Every powerful feature demands the internal vocabulary. The segment editor is a raw dimension picker — a marketer has to know that 'people who came from a paid campaign and bought' is `referrerType==campaign;visitConverted==1`, that `;` is AND and `,` is OR, and that segments are slow unless browse-archiving/pre-processing is enabled on the server. Custom dimensions live in fixed index slots that must be provisioned before data arrives (and past data never backfills), goals need URL/pattern matching that fails silently on query strings, Custom Reports require choosing valid dimension combos, and Matomo Tag Manager is a whole second product (trigger -> variable -> tag -> version -> publish) that people abandon after their first mis-fired conversion tag. The typical Matomo user looks at Visitors Overview forever and touches none of it.

**AI operator:** A 'talk to your analytics' operator that both answers and configures. Read side: it composes the segment string + picks the right API module/method/period, fetches, and narrates with the numbers plus the exact segment definition it used (auditable, not a black box). Write side: it provisions the things people give up on — saved segments, goals, custom dimensions, custom reports, scheduled email reports, and Tag Manager tags/triggers/variables with a publish step. A killer sub-skill is 'GA4 migration mode': take a GA4 property's audiences/conversions/custom dimensions and re-create the equivalents in Matomo, reporting what doesn't translate. Since everything is one token-authenticated HTTP endpoint, this is the highest-leverage/lowest-risk build of the set.

**Killer example:** Marketer asks: 'Which paid campaigns brought buyers who came back within 30 days — and set up a goal for the newsletter signup on the checkout thank-you page.' The AI builds `referrerType==campaign;visitorType==returning;visitConverted==1`, pulls Referrers.getCampaigns + Ecommerce order revenue for 90 days, and answers: 'spring_sale drove EUR 41,300 from 212 repeat buyers at EUR 6.10 CPA; retargeting_broad looks great on first-touch but its repeat revenue is EUR 900 — you are overspending there by ~EUR 4k/mo.' It saves the segment as 'Paid repeat buyers' via SegmentEditor.add, creates the goal with Goals.addGoal (URL contains /checkout/thank-you, matching against the path only so the `?utm_` query string cannot silently break it), fires a synthetic tracking hit to prove the goal registers, and schedules a Monday email — then shows the exact segment string and API calls it used so the marketer can reuse them.

**Integration path:** Single Reporting HTTP API: GET/POST to /index.php?module=API&method=<Module.method>&format=JSON&token_auth=... covering 200+ read methods (VisitsSummary, Actions, Referrers, Goals, Ecommerce, CustomReports, MultiSites) and the write methods that matter — SegmentEditor.add/update, Goals.addGoal, CustomDimensions.configureNewCustomDimension, CustomReports.addCustomReport, ScheduledReports.addReport, and the TagManager.* family (createContainerTag/Trigger/Variable, createContainerVersion, publishContainerVersion). On-premise adds the `console` CLI (dimension slot expansion, archiving, plugin install) and a first-class plugin architecture for shipping the chat UI inside Matomo itself. Works unchanged against Matomo Cloud, so the same MVP serves both. Solo-dev MVP is days, not weeks: one API client + a skill file of method signatures + a segment-grammar validator.

**Demand 4/5 · Buildability 5/5**

### 2. Helm (charts, values.yaml, templates, releases) — the de facto Kubernetes package manager `open-source`

**Why it's powerful:** Helm is how essentially every third-party workload lands on Kubernetes — ingress-nginx, cert-manager, Prometheus stack, Postgres operators, internal apps. One `helm upgrade --install` templatizes hundreds of manifests, does atomic release upgrades with history and rollback, hooks for migrations, and dependency subcharts. Charts are the packaging unit the whole CNCF ecosystem publishes to.

**Why people bounce off it:** The interface between a user and a chart is a 1,500-line values.yaml of undocumented, deeply-nested knobs where the only way to know what a key does is to read the Go templates that consume it. Setting a value at the wrong nesting level (a subchart's values must be nested under the subchart's alias, and aliases differ per chart) silently does nothing — no error, just the default. Templates are Go text/template + Sprig with whitespace-chomping `{{- -}}`, `toYaml | nindent 8` indentation traps, and errors like `nil pointer evaluating interface {}.enabled` that point at a line in a template the user never wrote. Upgrades break on immutable fields (StatefulSet volumeClaimTemplates, Deployment selectors), CRD upgrades are explicitly not handled by Helm, and a failed upgrade leaves a `pending-upgrade` release that blocks all further deploys. Result: people fork charts they don't understand, pin ancient versions, and dread upgrades.

**AI operator:** A 'chart operator' that turns intent into verified values + diffs. It ingests the chart (values.yaml, values.schema.json, templates, README, subchart tree), builds an index of which values actually reach which rendered field, and then: (1) answers 'how do I do X with this chart' by pointing at the exact key path including subchart nesting; (2) generates a minimal values override, renders with `helm template`, and shows a rendered-manifest diff vs the currently installed release (helm-diff / `--dry-run=server`) rather than a values diff; (3) pre-flights the upgrade — detects immutable-field changes, missing CRD updates, deprecated apiVersions, PDB/resource-quota conflicts, and the `pending-upgrade` stuck-release state with the exact rollback command; (4) explains template errors in terms of the value the user set, and can author/patch a chart's templates + values.schema.json for internal charts.

**Killer example:** User says: 'On our kube-prometheus-stack release, give Prometheus 200Gi of gp3, keep 30 days, expose Grafana at grafana.acme.io with our cert, and turn off the etcd scraping that keeps paging us.' The AI resolves the four real key paths — including `prometheus.prometheusSpec.storageSpec.volumeClaimTemplate.spec.resources.requests.storage` (three levels deeper than the blog post the user copied, where the same key silently did nothing) and `kubeEtcd.enabled: false` under the subchart alias — renders the override and returns a 14-manifest diff, then blocks the deploy: 'STOP: volumeClaimTemplates is immutable; `helm upgrade` will fail and leave the release in pending-upgrade, which blocks every future deploy of this release. Safe path: (1) kubectl delete sts prometheus-k8s --cascade=orphan, (2) patch the PVCs to gp3, (3) upgrade — pods keep running throughout, zero metric loss. Also: your 30d retention at current ingest needs ~240Gi, not 200Gi — Prometheus will start evicting at day 26.' One approval runs the three steps and verifies the new release revision.

**Integration path:** Everything is local CLI + Go SDK: `helm template`, `helm get values/manifest`, `helm diff` plugin, `helm lint`, `--dry-run=server` (server-side apply validation), `helm history/rollback`, plus chart repo/OCI pulls for any public chart and `kubectl` for cluster state. MVP = a CLI/TUI or MCP server with a read-only kubeconfig context, a values<->template cross-reference built by parsing `.Values.*` references in the chart's templates, and a gated apply step that always renders a manifest diff first. Fits naturally into a PR flow (writes the values override + posts the rendered diff) which is also how it sells into ArgoCD/Flux shops without touching their GitOps model.

### 3. OpenTelemetry Collector (incl. the OTTL transform language and ocb custom-distribution builder) `open-source`

**Why it's powerful:** It is now the default vendor-neutral telemetry pipeline sitting in front of Datadog/Grafana/Splunk/New Relic in most orgs: 100+ receivers (OTLP, prometheus, filelog, kafka, hostmetrics, k8s events), processors that can batch, tail-sample traces by policy, redact PII, enrich with k8sattributes/resourcedetection, cut cardinality, and convert spans->metrics, and exporters that can fan out to multiple backends at once. Getting it right is directly worth money — a good pipeline config is the difference between a $40k and a $200k/yr observability bill, and it is the escape hatch from vendor lock-in.

**Why people bounce off it:** The whole product is one giant YAML file whose semantics are invisible: components must be both defined AND wired into a `service.pipelines` entry (defining a processor and forgetting to reference it silently does nothing), processor ORDER inside a pipeline changes behavior (memory_limiter must be first, batch after sampling), tail_sampling only works if all spans of a trace land on the same collector instance — which means a load-balancing exporter tier that nobody tells you about, and filtering/rewriting is done in OTTL, a bespoke expression language with its own context model (span vs datapoint vs resource) and functions like `set(attributes["x"], truncate_all(...))` that fails at startup with a parser error, or worse, matches nothing silently. Debugging is 'restart the collector, watch zpages / internal metrics, guess'. Most teams cargo-cult a config from a blog post, never touch it again, and keep paying for the data they meant to drop.

**AI operator:** A 'pipeline operator' that owns the collector config as a compiled artifact rather than hand-written YAML: it holds a component registry (every receiver/processor/exporter's config schema, scraped from the contrib repo), generates or edits config from natural language, and — critically — verifies before shipping: runs `otelcol validate`, then replays a captured sample of the user's real telemetry (OTLP file/otlpjsonfile receiver) through the candidate config in a local container and shows a before/after diff: spans dropped, attributes redacted, series count and estimated $/month per backend. Also does the reverse direction: 'why is this metric missing in Grafana?' -> traces the signal through the pipeline and names the exact processor that killed it. Plus cost-hunting mode: ingest an hour of data, propose filter/transform rules that cut N% of volume with the exact OTTL, ranked by savings.

**Killer example:** User says: 'Drop health-check spans, strip emails and card numbers from every attribute, keep 100% of errors and slow traces but 5% of the rest, traces to Datadog, metrics to our own Prometheus.' The AI emits the config — filter/healthcheck in OTTL, transform/pii regex replace_pattern, tail_sampling with three policies — and then does the thing no blog post does: it notices the user runs 6 collector replicas behind a Service, warns 'tail_sampling on replicas silently samples per-instance, so you would have been dropping ~83% of the spans in every error trace and never known', and inserts the loadbalancing-exporter tier that makes the policy correct. Then it replays the last 10 minutes of the user's real spans through both configs in a local container: 'health checks are 41% of your span volume; Datadog ingest 620M -> 180M spans/mo, about $18k/yr saved; 3 attributes still leak PII (user.email_hash, http.url query param `card`, db.statement) — here are the exact spans and the added OTTL rule.' Output is a PR against the OpenTelemetryCollector CRD.

**Integration path:** Fully local and scriptable: the collector is a single Go binary with `otelcol validate`, config via YAML/env, zpages + internal Prometheus self-metrics for runtime introspection, and `ocb` (builder) to produce custom distros. Component config schemas are extractable from the opentelemetry-collector-contrib source. MVP = CLI/VS Code extension + MCP server: config generate/edit, schema-validate, docker-run a shadow collector, replay fixtures, diff output. Kubernetes shops integrate via the OpenTelemetry Operator's OpenTelemetryCollector CRD (kubectl apply = deploy), so a GitOps-friendly PR-based apply path exists with zero custom infra.

**Demand 4/5 · Buildability 5/5**

### 4. Apple Shortcuts (iOS / iPadOS / macOS automation runtime) `closed`

**Why it's powerful:** Shortcuts is a full automation runtime pre-installed on ~1.5B Apple devices, with thousands of actions exposed by system apps and third-party apps (Mail, Calendar, Files, Numbers, Notes, Reminders, Health, Focus, Home, plus any app that ships App Intents). It can loop over lists, branch on conditions, call REST APIs via 'Get Contents of URL', parse JSON with dictionary actions, run Personal Automations on triggers (time, arrival, email received, app opened, NFC tag), and on macOS it can even shell out via 'Run Shell Script'. Functionally it is Zapier/Power Automate that runs locally, for free, on hardware people already own.

**Why people bounce off it:** The editor is a drag-and-drop block canvas with no text view, no search across your shortcuts, and no debugger. The wall is variables: 'Magic Variables' vs 'Set Variable' vs the implicit 'Shortcut Input' is genuinely confusing, and the moment a user needs Repeat with Each + a dictionary lookup + a Get Dictionary Value on a JSON key path, they stall. Actions are found only by scrolling a poorly-searchable action picker whose names ('Get Details of Calendar Events') do not match how users think. Reordering 40 blocks by dragging on a phone screen is miserable, errors surface as a single opaque red banner with no line number, and there is no copy/paste of shortcut source to share or ask for help with. Result: the overwhelming majority of users only ever run shortcuts other people built, from RoutineHub/Reddit, and never author one.

**AI operator:** A 'Shortcut Compiler' operator: a chat app (plus a macOS helper) that turns plain-English automation requests into a real, importable .shortcut file. The AI is pre-loaded with a skill pack containing the action identifier catalog (is.workflow.actions.*, plus scraped App Intents identifiers from installed third-party apps), the parameter schemas for each action, and the WFWorkflow plist grammar (WFWorkflowActions, WFWorkflowActionIdentifier, WFWorkflowActionParameters, UUID-linked magic variables via WFVariable/OutputUUID). It emits a binary plist with plistlib, signs it on macOS with `shortcuts sign -i in.shortcut -o out.shortcut --mode anyone`, validates it by actually executing `shortcuts run <name>` in a sandbox account, reads the failure, and self-repairs. Delivery to iPhone is a signed file download or an iCloud share link. Secondary mode: 'explain and fix' — user AirDrops a broken shortcut in, AI decompiles the plist to readable pseudo-code, finds the bad variable reference, and hands back a repaired signed file.

**Killer example:** A freelancer says: 'Every Friday at 5pm, take my calendar events from the past week with "client" in the title, total the hours per client, append a row per client to my Numbers timesheet in iCloud, then text my bookkeeper the total.' Building this by hand means ~30 dragged blocks, a Repeat with Each, a dictionary accumulator and three magic-variable references that most users never get right — it is a two-evening project that usually ends in the red error banner. The AI emits it as a signed .shortcut in 40 seconds: Friday 17:00 Personal Automation trigger, Find Calendar Events filtered on last-7-days + title contains 'client', a Repeat with Each accumulating Duration into a dictionary keyed by client, Get Dictionary Value per key, Append to the Numbers file, Format Number, Send Message. Before it hands it over it actually RUNS the thing under `shortcuts run` against a copy of the calendar, catches that Duration comes back in seconds not hours, inserts the divide-by-3600, re-runs, and returns a one-tap install link plus a plain-English map of every step so the user can edit it later.

**Integration path:** No official write API, but three real surfaces exist: (1) the .shortcut file format is a documented-by-reverse-engineering binary plist (open projects: shortcuts-toolkit, sebj/iOS-Shortcuts-Reference, Cherri language, zachary7829's format docs) so generation is plain plistlib; (2) macOS 12+ ships a first-party `shortcuts` CLI with list / run / sign / view, which gives you signing for distribution and a real execution loop for automated validation; (3) the Shortcuts SQLite store on macOS can be read to enumerate a user's existing shortcuts and the installed action catalog. Apple can change the format between OS releases, so the action catalog needs a per-OS-version regeneration job — that's the main maintenance tax.

**Demand 5/5 · Buildability 3/5**

### 5. ManageEngine ServiceDesk Plus (Cloud + on-premises) `closed`

**Why it's powerful:** It is the default ITSM/helpdesk for a huge slice of mid-market and education/government IT (ITIL incident/problem/change/release, asset & CMDB discovery, project module, multi-site service catalogs, SLAs with multi-tier escalation, request Life Cycles, Business Rules, Custom Triggers/Schedules, Deluge custom functions, and a full REST API v3 that covers nearly every entity). Feature-for-feature it does 80% of what ServiceNow does at 10% of the cost, and it can be self-hosted on-prem.

**Why people bounce off it:** The automation surface is fragmented across five different admin screens that all look like they do the same thing but fire at different moments: Business Rules (on create/edit), Request Life Cycle (a visual state machine with its own conditions/actions), Custom Triggers (time/field-based), Field & Form Rules (client-side JS), and Scheduled/Custom Functions (Deluge). A one-line ask like 'auto-assign P1 network tickets in the Bangalore site to the on-call network group, notify their Teams channel, and escalate to the manager if untouched in 30 minutes' requires knowing which of those five engines can see which fields, building a technician auto-assign rule, an SLA with escalation levels, a notification rule, and usually a Deluge custom function with a hand-built V3 JSON payload (`input_data={"request":{...}}`) because the UI action can't reach the outbound webhook. Admins are typically one-person IT teams with no scripting background; most give up and hand-triage tickets forever, and the config drifts into hundreds of half-working rules nobody dares delete.

**AI operator:** 'SDP Copilot' — an agent pre-loaded with skills for the SDP V3 REST API plus a compiled knowledge base of which automation engine can do what (the routing decision is the hard part, and it is deterministic enough to encode). The agent (a) introspects the live instance on connect — request templates, categories, sites, technician groups, SLAs, existing business rules/triggers/life cycles — and builds a config graph; (b) takes plain-language automation intents, picks the right engine(s), and generates the objects via API, including writing the Deluge custom function when a webhook/external call is needed; (c) simulates before applying: replays the last 90 days of tickets through the proposed rule and reports 'this would have matched 412 tickets, 37 of which you actually routed elsewhere'; (d) does config hygiene: finds dead rules, overlapping business rules that fight each other, SLAs nobody references; (e) answers ops questions in NL by composing V3 search criteria instead of the clunky filter builder.

**Killer example:** A one-person IT team types: 'During month-end close, anything from Finance mentioning SAP or payment run should be P1, go to the ERP group on a 2-hour SLA, post to #erp-escalation, and page the ERP manager if still unassigned after 30 minutes.' Done by hand that is four objects across four admin screens plus a Deluge function, and the usual outcome is a rule that fires on create but not on edit. The agent picks the engines for you — Business Rule (create+edit), SLA with one escalation level, Custom Trigger at +30min on unassigned, Deluge function posting the Teams Adaptive Card — writes the exact Deluge source, then backtests against the last 90 days before anything is saved: '118 tickets would have matched. 6 are false positives, all Concur expense tickets from Finance that say "payment" — want an exclusion? Also: your existing rule #34 "Finance -> Helpdesk L1" fires first and would have swallowed 41 of these; I will reorder it below the new rule.' That last line is the thing no human admin ever sees coming.

**Integration path:** REST API v3 over HTTPS with OAuth (Zoho OAuth for Cloud) or API key for on-prem; near-complete CRUD on requests, changes, problems, assets, technicians, SLAs, templates, plus admin metadata. Automation objects that are not fully API-creatable can be driven by the agent generating Deluge custom-function source the admin pastes once (agent supplies exact code), and by a headless browser fallback for the few config screens without endpoints. MVP: a desktop/web app + MCP server wrapping ~30 V3 endpoints, a config-introspection cache, a rule-backtester over the ticket export, and a plan/approve/apply loop. Free 30-day cloud trial and a free on-prem edition make solo-dev dogfooding trivial.

### 6. AWS Systems Manager (SSM) — Patch Manager, Automation runbooks, State Manager, Session Manager, Fleet Manager, Parameter Store `closed`

**Why it's powerful:** SSM is effectively the free fleet-management OS layer of AWS: it can patch thousands of EC2/on-prem/hybrid instances on a maintenance-window schedule, run parameterized Automation runbooks (300+ AWS-owned documents plus custom ones) to do things like AMI bake, EBS snapshot, instance restart with approval steps, keep config drift corrected with State Manager associations, give shell access without SSH/bastion via Session Manager, and store config/secrets in Parameter Store with hierarchy and KMS. Almost every non-trivial AWS org uses at least patching + Session Manager, and it replaces whole tools (Ansible cron-runs, bastion hosts, Landscape/WSUS).

**Why people bounce off it:** The console is a maze of five weakly-connected sub-products with different mental models. Getting a single patch cycle working means: attach an instance profile with AmazonSSMManagedInstanceCore, confirm the agent is registered (silent failure if the VPC lacks ssm/ssmmessages/ec2messages endpoints or NAT), create a Patch Baseline with approval rules expressed as 'auto-approve after N days by classification/severity' per OS product, tag instances into a Patch Group with the exact magic tag key `Patch Group`, create a Maintenance Window with cron/rate + duration + cutoff, register a target, register an `AWS-RunPatchBaseline` task with the right `Operation: Scan|Install`, concurrency and error thresholds, plus a service role. One wrong layer and everything reports 'no instances' with no explanation. Automation runbook authoring is raw YAML/JSON SSM Document schema with aws:executeAwsApi / aws:branch steps, jsonpath outputs, and no real debugger — you learn from failed executions. Result: teams use ~10% of SSM (Session Manager only) and pay for a third-party patching tool.

**AI operator:** An 'SSM Operator' — a chat/CLI agent with skills for the full SSM object graph (documents, associations, patch baselines/groups, maintenance windows, targets, tasks, parameters, inventory, compliance) that (1) diagnoses why nodes are not managed by walking IAM instance profile -> agent ping status -> VPC endpoint/NAT reachability -> platform support, and offers a one-click fix plan; (2) compiles plain-English patch policy into the whole baseline/tag/window/task stack as an idempotent plan, shown as a diff and an estimated blast radius before apply; (3) authors and dry-runs Automation runbooks from a description, validating each step's API shape against botocore's service model and running it first against a single tagged canary instance with automatic rollback step; (4) answers compliance questions from Inventory/Compliance APIs ('which prod boxes missed the last two cycles and why') instead of the user building Resource Data Sync + Athena.

**Killer example:** User says: 'Patch all prod Linux boxes tagged env=prod the second Tuesday of each month at 2am IST, security + critical only, auto-approve after 7 days, never more than 10% of the fleet at once, stop after 3 failures.' The AI builds the whole five-layer stack — baseline with per-product approval rules for AL2023/Ubuntu/RHEL, the magic `Patch Group` tag, `cron(0 20 ? * TUE#2 *)` converted to UTC with a 4h duration and 1h cutoff, the RunPatchBaseline Install task at MaxConcurrency 10% / MaxErrors 3, and the service role — then reports the thing the console would have hidden for a month: '212 instances targeted. 9 will silently never patch: 6 have no instance profile, 2 have a stopped agent, and — this is the one that bites everyone — your private subnet has no NAT and no ssm/ssmmessages/ec2messages VPC endpoints, so those 14 database hosts have been reporting "no instances" since March and have never received a security patch. Here is the endpoint Terraform and the IAM fix.' Apply is shown as a diff first, and exports to CloudFormation/Terraform if the team wants IaC.

**Integration path:** Pure API/SDK: boto3/AWS SDK covers every object (CreatePatchBaseline, RegisterTargetWithMaintenanceWindow, CreateAssociation, StartAutomationExecution, SendCommand, ListComplianceItems). Read-only mode is trivially enforced by an IAM role with only Describe*/List*/Get*. For MVP: an MCP server wrapping ~30 SSM calls + botocore service-model validation for runbook authoring + a plan/apply engine that renders changes as a diff (CloudFormation/Terraform export optional for teams that want IaC output). Session Manager streaming for live remediation is available via the SDK's StartSession + session-manager-plugin.

### 7. Recharge (subscription commerce for Shopify: plans, prepaid, bundles, dunning, retention/cancellation flows, customer portal) `closed`

**Why it's powerful:** The default subscription engine for DTC Shopify brands (tens of thousands of merchants, billions in processed subscription GMV). It runs recurring billing, per-customer charge queues and skip/swap, prepaid and gifted plans, bundle selections, dunning retry schedules, discount stacking on recurring orders, cancellation/retention offer flows, Flows automations, and a themable customer portal — i.e. it owns the brand's most valuable, most fragile revenue.

**Why people bounce off it:** The merchant's most common needs are *bulk changes to live subscribers*, and the UI only really supports one-subscriber-at-a-time editing. Changing a cadence, price, or product for an existing cohort means either a support ticket, a CSV request to Recharge, or an agency script. Layered on that: Recharge plans must stay in sync with Shopify selling plan groups (a change in one silently diverges from the other), prepaid vs pay-as-you-go behave differently on skip/swap, bundle_selections is a Pro-gated concept most merchants don't understand, dunning retry windows and failed-charge behaviour are buried settings that quietly leak MRR, and discounts applied to recurring charges follow different rules than one-time. Because every wrong click hits real charges and real customers, merchants freeze: they leave a bad cadence or a broken retention offer live for months rather than risk it.

**AI operator:** A subscription-ops copilot with a hard simulate-then-apply contract. Skills: cohort querying across subscriptions/charges/customers/orders; bulk cadence/price/product migrations; next-charge-date shifting; dunning and retry policy tuning; discount and retention-offer configuration; churn and MRR diagnostics ('which cohort churns after charge 3, and what did they all have in common'); and plan <-> Shopify selling-plan drift detection. Every mutating request first returns a dry-run: affected subscriber count, per-customer diff of next charge date and amount, projected MRR delta, and exclusions. Apply runs in rate-limit-aware batches with a persisted undo log so any batch can be reversed, and refuses to touch subscriptions with a charge queued inside a safety window.

**Killer example:** Founder says: 'Everyone on the 30-day coffee plan active 6+ months, move them to the 45-day cadence at the same price per bag, skip anyone charging in the next 3 days, and notify them.' This is the change every DTC brand wants and nobody dares make by hand — it is 1,842 subscriptions and each one is a real credit card. The dry run comes back before anything moves: '1,791 eligible, 51 deferred for imminent charges. Next charge dates shift +15d, unit price unchanged at 18.00, MRR -11% now but projected 12-month LTV +9% because your 30-day cohort churns hardest right after charge 3 — 34% of them cite "too much coffee" in cancellation reasons. Two blockers you did not ask about: 23 of these are prepaid 3-month plans where a cadence change silently strands the remaining prepaid charges, so I am excluding them; and your Shopify selling plan group still says 30 days, so new signups would diverge from migrated ones — I will patch both.' On approval it patches in throttled batches, re-reads every charge queue to verify, emits a Klaviyo event per customer, and returns one undo token that reverses the entire batch.

**Integration path:** Recharge Admin API version 2021-11 (REST, API-token with scoped permissions): subscriptions (create/update/change-address/skip/swap/cancel), charges, customers, addresses, onetimes, plans, and bundle_selections (Pro-gated — note 2021-11 removed total-count from GETs, so cohort work must cursor-paginate); plus webhooks for charge/subscription lifecycle, the Theme Engine for the customer portal, and Shopify Admin GraphQL for the selling-plan-group side of the sync. MVP path for a solo dev: a hosted chat app using a merchant-provided Recharge token + read-only cohort analytics first (zero risk, immediate value), then unlock writes behind dry-run + undo. Build and test on a Recharge partner/test store before touching live money.
