### 1. Salesforce sandbox post-refresh operator (Sandbox refresh plus SandboxPostCopy, Named Credentials, users, scheduled jobs, integrations) `closed`

**Why it's powerful:** Full, Partial and Developer sandboxes give every Salesforce team a production clone for UAT, training and integration testing, so most production changes are tested there first.

**Why people bounce off it:** A freshly refreshed sandbox is not usable straight away, and the cleanup is done by hand from a wiki checklist every time. User emails are masked with .invalid, so QA cannot log in or receive emails. Named Credentials and Remote Site Settings still point at production ERP and payment endpoints, so an integration test can charge real cards or post to the live ERP. Scheduled jobs and record-triggered Flows that call out can come back with the copy (sources disagree on which job types stay active after a refresh, so the operator inventories rather than assumes). Custom Settings and Custom Metadata hold production keys and URLs. Partial-copy sandboxes are missing the parent records test scripts need. Teams lose a day per refresh, and a missed step causes real incidents, such as customers receiving emails from UAT. The 'Salesforce release management' card covers sandbox-to-production deploys. This is the opposite direction (production to sandbox) and a different job.

**AI operator:** An operator that turns a plain-English description of the target sandbox state into an idempotent, replayable post-refresh plan. It inventories endpoint-bearing metadata (NamedCredential, ExternalCredential, RemoteSiteSetting, CSP trusted sites, Custom Settings/Custom Metadata values that look like URLs or keys), scheduled jobs (CronTrigger), active outbound Flows and Apex callouts, and connected-app integration users. It then proposes re-points and deactivations, unmasks the named test users, seeds anonymized fixture data, executes everything, and saves it as a reusable 'refresh recipe' that can also be generated as a SandboxPostCopy Apex class.

**Killer example:** User: 'Refresh UAT from prod tonight and make it safe and usable by 8am.' Before touching anything, the operator scans prod metadata and reports what a raw refresh would leave live: 3 Named Credentials pointing at api.stripe.com and the production NetSuite account, a Custom Metadata record holding the live Avalara URL, 12 scheduled jobs (one emails 4,000 renewal notices every Monday), and a 'Send renewal email' flow that fires on any Opportunity update. It triggers the refresh, polls SandboxProcess, and once IsSandbox = true it re-points the credentials to the Stripe test and NetSuite sandbox endpoints, aborts 11 of 12 CronTriggers (keeping lead scoring), deactivates the flow, unmasks the 14 QA users, and seeds 200 anonymized Accounts with open Opportunities in every stage. A smoke test charges a Stripe test card (200 OK, test mode). The whole run is saved as 'UAT-recipe-v1' and compiled into a SandboxPostCopy class, so next month's refresh fixes itself.

**Integration path:** Strong and documented: sf CLI (sf org create/refresh sandbox, sf project deploy/retrieve), Tooling API (SandboxInfo/SandboxProcess, CronTrigger queries, executeAnonymous for System.abortJob), Metadata API (NamedCredential, ExternalCredential, RemoteSiteSetting, Flow activation, CustomMetadata records), REST/Bulk API 2.0 for User updates and fixture seeding, and the SandboxPostCopy Apex interface to make the recipe run automatically on future refreshes. Safety rule: hard-refuse any write unless the org's IsSandbox = true (Organization object). Developer Edition orgs are enough for the MVP. Competitors (Gearset/Copado data seeding, Salesforce Data Mask & Seed) handle data but not the endpoint and job re-point checklist.

**Overlap check (2026-11-19):** no Salesforce or Agentforce feature found for post-refresh re-pointing. Third-party tools (Clientell's sandbox data-seeding agent, Blue Canvas, Gearset/Copado) cover seeding or checklists, not the endpoint/job/flow re-point plan.

**Demand 4/5 · Buildability 4/5**

### 2. Gmail: 'Check mail from other accounts' (POP fetch) and Gmailify retirement. A 'Mailbox Moving Day' operator that rebuilds the unified inbox before existing users lose it in January 2027. `closed`

**Why it's powerful:** For about 15 years Gmail has been the free universal inbox. POP fetch pulled in ISP, Yahoo, Outlook.com, university and cPanel-hosted mailboxes, Gmailify added Gmail spam filtering and categories to them, and Send-mail-as let people reply from the old address. Millions of people and small businesses run a legacy or domain address through Gmail this way. Google's help page (support.google.com/mail/answer/16604719) says new users lost the feature after Q1 2026 and existing users keep it only until January 2027.

**Why people bounce off it:** Google's only advice is to set up automatic forwarding from the other provider and check its documentation. That splits one Gmail setting across two systems: forwarding has to be configured inside each source provider (ISP webmail, cPanel forwarders, Outlook.com rules), and free Yahoo accounts lost automatic forwarding in 2021, so for them the documented fix doesn't exist. Then come the steps people get wrong: Gmail filters to relabel the forwarded mail, forwarded mail landing in spam because of SPF/DMARC alignment, Send-mail-as SMTP settings that break, and a gap of mail that arrived between the last POP fetch and the first forward. Users only find out when mail stops arriving.

**AI operator:** Reads the account through the Gmail API: external Send-as addresses (which show which mailboxes are linked), existing filters, and the labels POP-fetched mail lands in. Looks up each address's MX record to identify the provider and picks a route for each one: (a) Outlook.com or Microsoft 365: create a Graph messageRule with forwardTo; (b) cPanel or other hosts: UAPI Email::add_forwarder; (c) free Yahoo and other providers that can't forward: run a small IMAP-pull worker that copies new mail into Gmail with users.messages.import, replacing POP fetch; (d) web-only providers: a click-by-click checklist that the operator verifies itself. It then creates the deliveredto: filter (apply label, never send to spam), catches and confirms the forwarding-verification email, backfills the gap over IMAP with dedup by Message-ID and original dates kept, re-checks Send-mail-as, and finishes with a round-trip test message for each address.

**Killer example:** A shop owner says: 'Google is killing the thing that pulls my old Yahoo and my shop's email into Gmail. Make it keep working.' The operator finds 3 linked accounts: a free Yahoo address, info@shop.com on a cPanel host, and a 2009 Outlook.com address. It adds a cPanel forwarder for info@ and a Gmail filter that labels it 'Shop' and never sends it to spam, choosing a forwarder over an alias redirect because the host's SPF would fail on redirected mail. It adds a Graph forwarding rule on Outlook.com. It explains that free Yahoo can't forward and turns on an IMAP bridge instead. At cutover it backfills the 214 messages that arrived between the last POP fetch and the first forward, and skips 31 duplicates. Test emails from all three addresses arrive correctly labelled within 2 minutes, and replies still go out from the shop address.

**Integration path:** Gmail API: users.settings.sendAs, users.settings.filters.create, users.labels, users.settings.forwardingAddresses, users.messages.import. Microsoft Graph /me/mailFolders/inbox/messageRules, which works for personal Outlook.com accounts. cPanel UAPI Email::add_forwarder. Python imaplib for the backfill and the ongoing pull. DNS MX lookup for provider detection. Caveat: the import, insert and settings scopes are restricted, so a public SaaS needs Google OAuth verification and a CASA assessment. Ship the MVP as a self-hosted Docker or CLI tool where users bring their own OAuth client (no verification needed under 100 test users), then do CASA once demand is proven. The deadline is hard: January 2027.

**Date check (2026-11-19):** new POP/Gmailify setups ended after Q1 2026 (widely reported, Jan 2026 announcement). Early-2026 coverage said existing connections end 'later in 2026'; the most recent sources (Nov 2026) give January 2027. Re-check Google's help page before using the deadline in marketing.

**Demand 4/5 · Buildability 3/5**

### 3. PaperCut NG / PaperCut MF (print management: quotas, charging, shared accounts, secure release) `closed`

**Why it's powerful:** PaperCut is the default print-management server in K-12 schools, universities, councils and many enterprises. It handles per-user and per-group quotas on schedules, cost models per printer (paper size, colour, duplex discounts), shared accounts and cost centres, Find-Me queues with secure release, printer access groups, printer filters and restrictions, overdraft rules, card/ID lookup and environmental reporting. It runs self-hosted on Windows, Linux or Mac.

**Why people bounce off it:** The admin console is split across Users, Groups, Accounts, Printers, Devices and an Advanced Config Editor with hundreds of keys. Every term or new financial year an admin has to redo quota schedules for each group, fix cost models one printer at a time across 50 to 300 queues (queues added after imaging silently keep the default cost), wire up access groups and shared-account permissions, and guess what students will actually pay. Nothing lets you ask 'what happens if I change this', and nothing shows a diff of what changed since last term.

**AI operator:** Takes a snapshot of the current state over the XML-RPC Web Services API and server-command: list-printers, get-printer-property, get-printer-cost-simple, get-group-quota, list-printer-access-groups, listSharedAccounts. It compiles plain-language policy into a reviewable change plan, then simulates the plan by replaying last term's print log to show who runs out of credit and when. Once the admin approves, it applies the plan with set-printer-cost-simple, set-printer-property, set-group-quota, add-printer-access-group or set-printer-groups, addNewSharedAccount and set-user-account-balance-by-group, and can revert any change from the snapshot. A standing mode reports drift, such as new queues at default cost, groups with no quota, or disabled printers that still have access groups.

**Killer example:** An IT lead says: 'Autumn term: Years 7–11 get £5 a week, sixth form £10, staff unlimited. Colour costs 4× black and only works in the library and art room. Stop anyone sending 200-page PDFs to the art plotter.' The operator inventories 63 printers and finds 9 queues added over the summer that still charge the £0.10 default and have no access group. It sets the cost models, weekly group quota schedules and colour access groups, and adds a page-limit restriction to the plotter. It replays last term's 41,000 jobs and reports that 112 sixth-formers would have run out by week 3, nearly all from coursework PDFs printed to colour devices. It also finds that 12 users sent 3,400 pages to the plotter, and it lists those users. It asks whether to start sixth form at £15 for the first fortnight before applying the plan.

**Integration path:** PaperCut NG/MF XML-RPC Web Services API (/rpc/api/xmlrpc on the app server, with an auth token) plus the server-command CLI on the server. Both have documented write methods for printer cost, printer properties, group quotas, printer access groups and printer groups, users, groups and shared accounts. Print history comes from the print-log export or exportUserDataHistory for simulation. Everything is on-prem, so the MVP is a local agent or container next to the PaperCut server. Develop against the free 40-day NG trial. Check which advanced printer filter and restriction keys set-printer-property accepts on each version, and treat print scripts as copy-paste output, not API-written. 

**Overlap check (2026-11-19):** PaperCut demoed a partner-facing 'Intelligent Assistant' (knowledge base plus telemetry recommendations) at its June 2026 Partner Summit, with no sign it writes cost, quota or access config. The one community MCP (jpg486-ual/papercut-mcp, 1 star) is read-only (users, printers, balances). Re-check the assistant's scope when MF 26 ships.

**Demand 3/5 · Buildability 4/5**

### 4. Microsoft Word: multi-reviewer comment adjudication into a Comment Resolution Matrix (CRM), with Google Docs as the second connector `closed`

**Why it's powerful:** Word's threaded modern comments, resolve state, Combine Documents and tracked changes carry the formal review cycle in defence and aerospace (DoD-style CRMs), pharma regulatory writing, standards bodies (the ISO/IEC commenting template), government RFPs and engineering spec reviews. Every one of these reviews ends in a matrix of comment, category, proposed change, disposition and rationale.

**Why people bounce off it:** Eight reviewers each return their own copy. Combine merges only two files at a time and stalls on overlapping revisions. Word can't natively export comments with their anchor text, section path, page and reviewer into a spreadsheet, and the old VBA export macros broke with modern comments. Duplicate comments across reviewers have to be spotted by hand. After adjudication, someone spends days applying accepted edits, replying 'Accepted – see 4.2' in every thread and marking each one resolved. Comment-export add-ins exist (for example DocTools CommentManager), but none of them clusters, drafts dispositions or writes decisions back into the document.

**AI operator:** Takes in N .docx copies at the OOXML level: word/comments.xml, commentsExtended.xml (w15:done resolve state and threading through paraIdParent) and commentsIds.xml. It anchors each comment to its heading path, requirement ID and rendered page (LibreOffice headless for pagination). It clusters duplicates across reviewers, finds conflicting asks, classifies each item as Critical, Substantive or Administrative, and writes the CRM workbook in the org's template with draft dispositions. After the author edits dispositions in the sheet, it applies them to the master document: accepted editorial items become tracked changes, every original thread gets a reply carrying the disposition text and is marked resolved, and a closed-out CRM is produced for the record.

**Killer example:** A systems engineer says: 'Seven reviewers sent back the System Requirements Spec. Build me the CRM, merge duplicates, draft dispositions.' The operator parses 412 comments across the 7 copies and collapses them into 241 unique issues, 96 of which sit on the same 11 requirements. It flags that two reviewers ask for opposite changes to SHALL-117 (latency 50 ms vs 200 ms) and sends that to the chair as a conflict instead of drafting a disposition. It proposes 'Accept' with a ready-made tracked edit for 138 editorial items and writes CRM_SRS_revC.xlsx. Two days later it reads the edited sheet, applies 131 accepted edits as tracked changes, replies in and resolves every thread, and reports 7 comments whose anchor text was deleted in rev C. A human would miss those 7 because Word quietly re-anchors them to the next paragraph.

**Integration path:** File path for the MVP: python-docx plus lxml over comments.xml, commentsExtended.xml, commentsIds.xml and commentsExtensible.xml. OpenXmlPowerTools (MIT) to write tracked insertions and deletions. openpyxl for the matrix. LibreOffice headless for page numbers. In-app front end: an Office Add-in on the Word JS API (Comment.reply, Comment.resolved, getComments, the tracked-change APIs in 1.6+). Google Docs connector: Drive API comments.list and replies.create with action=resolve (the Docs API doesn't expose comments). Files round-trip through Graph or Drive. This is a different job from the 2026-09-24 tracked-changes card, which triages one counterparty's markup; this card adjudicates N reviewers' comments into a formal matrix.

**Overlap check (2026-11-19):** Copilot in Word and Claude for Word (beta) can read, reply to and act on comment threads in a single open document, which covers the apply-back half. Neither merges N reviewers' copies, de-duplicates across them, flags conflicts or produces a formal comment resolution matrix. DocTools CommentManager exports comments to Excel without any adjudication. The moat is the multi-copy matrix, so lead with it.

**Demand 3/5 · Buildability 4/5**

### 5. SAP CRM 7.0 (on-premise): customizing archaeology and exit planner, targeting SAP Sales/Service Cloud V2 or Salesforce `closed`

**Why it's powerful:** SAP CRM 7.0 still runs sales, service and marketing for thousands of large SAP shops. Its transaction types, item categories, partner determination, PPF actions, status profiles and BAdIs can model almost any process, and 15 years of consultants used all of it.

**Why people bounce off it:** Maintenance is ending (EhP 2-4 mainstream maintenance ends 2027, then customer-specific maintenance to 2030), and there is no lift-and-shift path. Every customer needs a re-implementation and must first work out what their CRM actually does. That knowledge sits in SPRO tables and Z-code written by consultants who left a decade ago. Discovery workshops alone cost SI fees in the hundreds of thousands, because no one can read 400 customized transaction types and partner determination rules.

**AI operator:** A read-only archaeology operator over the SAP CRM customizing and usage tables. It pulls configuration via RFC (e.g. CRMC_PROC_TYPE transaction types, item categories, partner determination procedures, PPF action profiles, status profiles, Z-BAdI implementations), joins it with usage counts from document tables, and explains each process in plain English ('ZQT1 is a quote type used 3,400 times last year; it auto-creates a follow-up ZOR1 order through action ZACT_ORDER'). It then produces a target design for the chosen platform. For Salesforce it emits Metadata API / sf CLI source (record types, Flows, validation rules) for a sandbox. For Sales Cloud V2 it emits an implementation worksheet. Unused config is flagged 'do not migrate'.

**Killer example:** User: 'Which of our CRM transaction types are actually used, and what happens automatically when a sales rep saves a ZQT1 quote?' The AI runs RFC reads plus document counts and reports that 38 of 212 transaction types were used in the last 24 months. For ZQT1 it walks the full on-save chain: partner determination pulls the account owner and the regional approver, action ZACT_APPR fires a workflow when discount is over 15%, and a Z-BAdI posts to ECC credit check. It then drafts the Salesforce equivalent (Quote record type, an approval process at >15%, a credit-check callout stub), deploys it to a sandbox, and lists the 4 behaviors it cannot map automatically.

**Integration path:** Read side: SAP RFC via pyrfc/node-rfc (RFC_READ_TABLE or a small read-only RFC wrapper), plus an optional SE16 table-export upload when RFC access is denied. Write side is the target system only: Salesforce Metadata API/sf CLI for a sandbox, or an implementation worksheet plus Sales Cloud V2's public APIs. Buildability is constrained by needing a real SAP CRM system (customer or partner access), and the sales motion runs through SAP SIs.

**Overlap check (2026-11-19):** no SAP or partner tool found that analyses CRM 7.0 customizing. SAP's migration assessment service and partners' AI conversion tools target Sales/Service Cloud V1 → V2, not CRM 7.0. EhP 2-4 mainstream maintenance ends in 2027 and there is no upgrade path (re-implementation only). Unlike the forced-exit cards for SMB CRMs (data and pipeline movers), this one's core is explaining enterprise customizing before a rebuild.

**Demand 3/5 · Buildability 2/5**
