### 1. Google Ads Performance Max (asset groups, retail listing-group partitions, audience signals) `closed`

**Why it's powerful:** One campaign serves Search, Shopping, YouTube, Display, Discover, Gmail and Maps. For retailers, Performance Max (PMax) is now the default Shopping vehicle. Results depend on how the Merchant Center catalog is split into asset groups, which assets each group gets, and which audience signals and search themes steer it.

**Why people bounce off it:** The product partition tree is the hardest part. It is a tree of `AssetGroupListingGroupFilter` subdivisions and units by brand, category or custom label, with a mandatory "everything else" node. Each asset group also has minimum asset counts and needs signals. The error messages are opaque, so most SMBs run a single "all products" asset group and leave money on the table.

**AI operator:** A "PMax structurer". It reads the Merchant Center catalog and margin labels, then proposes asset groups by margin, category or hero SKU. It builds valid listing-group trees, attaches headlines, images and logos, adds audience signals, and translates Google's errors into plain language. It also reports per-asset-group performance in plain language.

**Killer example:** "Split my PMax into three asset groups: high-margin products (custom_label_0 = high), Nike shoes, and everything else excluded." The AI creates the AssetGroups, builds the subdivision and unit nodes with "everything else" set to excluded, and links assets via AssetGroupAsset. It adds the remarketing list as a signal, all in one atomic `GoogleAdsService.Mutate`.

**Integration path:** Google Ads API `GoogleAdsService.Mutate` with `AssetGroupOperation`, `AssetGroupListingGroupFilterOperation`, `AssetGroupAssetOperation` and `AssetGroupSignalOperation` (developers.google.com/google-ads/api/performance-max/listing-groups). Gating: it needs a developer token with Basic or Standard access, and asset-group creation must be atomic. This is distinct from the broader Google Ads card already covered: it targets the PMax structure specifically.

**Demand 5/5 · Buildability 4/5**

### 2. FL Studio (Image-Line): piano-roll and MIDI-controller scripting `closed`

**Why it's powerful:** It is one of the most-used DAWs in the world, dominant in hip-hop, trap and EDM, with lifetime free updates and a huge bedroom-producer base. It has a Channel Rack and pattern workflow, a 125-insert mixer, and a strong piano roll.

**Why people bounce off it:** Two walls. First, music theory: chords, voicings, humanized drums and hi-hat rolls all have to be drawn note by note. Second, the routing model: Channel Rack, Patterns, Playlist and Mixer are four separate concepts that confuse beginners, and sidechaining is a classic tutorial search. The built-in "Gopher" assistant explains things but doesn't edit the project.

**AI operator:** "Producer's hands." The AI writes piano-roll scripts for musical content (progressions, basslines, drum patterns, arps) and drives the mixer, channels and patterns through a MIDI-script bridge, all from plain language. Every action stays undoable in FL's history.

**Killer example:** "Dark trap progression in F minor, 4 bars, then a hi-hat pattern with triplet rolls on bar 4, and route the 808 to its own mixer insert with a sidechain from the kick." The AI generates the chord notes in the piano roll and writes the hat pattern with 1/3-step rolls. It assigns the 808 and kick to new inserts, sets up the sidechain send, and names and colors everything.

**Integration path:** The Piano Roll Scripting API (`flpianoroll`, `.pyscript` files that create, modify and delete notes and markers) and the MIDI Controller Scripting API (Python modules `mixer`, `channels`, `patterns`, `playlist`, `plugins`, `transport`), both documented in the FL Studio online manual. Caveats: there is no full project-file write path, plugin-parameter coverage varies, and community FL Studio MCP servers already exist. Differentiate on music-theory skill depth and the routing operator, not raw API access.

**Demand 5/5 · Buildability 4/5**

### 3. Tailscale (ACL / grants policy file, tags, Tailscale SSH, autoApprovers) `partial OSS`

**Why it's powerful:** One HuJSON policy file controls who can reach which device and port across a whole tailnet. It covers app-capability grants, tag ownership, Tailscale SSH rules, subnet-route and exit-node auto-approval, device posture checks, and built-in policy `tests`. It replaces a VPN plus a firewall rulebook for millions of devices.

**Why people bounce off it:** Users hand-edit HuJSON with `src`/`dst` selectors (`tag:`, `group:`, `autogroup:member`, `host:port`). They confuse `acls` with `grants` and `tagOwners` with tags. The usual result is either everyone can reach everything or nobody can reach the database, and debugging means running `tailscale ping` and reading logs.

**AI operator:** A "network bouncer". It reads the current policy and device and tag inventory, writes a minimal diff for a plain-English access request, and adds `tests` that prove the intent. It runs the validate endpoint, explains the blast radius ("these 14 devices gain access"), and applies the change. It also answers "why can't Priya reach the staging DB?".

**Killer example:** "Contractors can SSH into staging boxes only, as the deploy user, and never touch prod or the DB." The AI creates `group:contractors`, an `ssh` rule to `tag:staging` with `users: ["deploy"]`, and a matching grant. It adds `tests` asserting that contractors are denied on `tag:prod:*` and `tag:db:5432`, validates, shows the diff, and POSTs the new policy.

**Integration path:** `GET`/`POST /api/v2/tailnet/{tailnet}/acl` writes the full policy, `POST /api/v2/tailnet/{tailnet}/acl/validate` validates it, `GET /api/v2/tailnet/{tailnet}/devices` lists devices, and `POST /api/v2/device/{id}/tags` sets tags (tailscale.com/api, tailscale.com/kb/1337/policy-syntax). The GitOps action and Terraform `tailscale_acl` resource are alternative delivery paths, and Headscale (OSS) speaks the same policy format.

**Demand 4/5 · Buildability 5/5**

### 4. Azure App Service (deployment slots, app settings & Key Vault references, VNet integration, access restrictions, auto-heal) `closed`

**Why it's powerful:** It hosts millions of .NET, Node, Java and Python web apps. It provides managed TLS and custom domains, staging slots with swap and sticky settings, VNet integration and private endpoints, access restrictions, health checks and auto-heal, autoscale, Easy Auth, and Key Vault references in app settings.

**Why people bounce off it:** Configuration is spread across dozens of portal panes. Users mix up which settings are slot-sticky and which swap. `@Microsoft.KeyVault(...)` references fail silently when the managed identity lacks access. VNet integration plus route-all plus private DNS is a maze, and access-restriction priorities are confusing. The classic complaints are "worked in staging, broke after swap" and "app can't reach the DB".

**AI operator:** A "web app concierge". It inspects site and slot config, explains in plain language what a swap will change, and diagnoses connectivity and secret-reference failures. It applies setting changes, identity grants and swaps from plain-language requests, always previewing the swap first.

**Killer example:** "Move the DB password into Key Vault, keep staging pointing at the staging DB after swaps, and auto-restart if memory goes over 1.5 GB." The AI enables a system-assigned identity, grants it Key Vault Secrets User, and sets `DbPassword=@Microsoft.KeyVault(SecretUri=...)`. It marks `DbConnection` as slot-sticky, adds an `autoHealRules` private-bytes trigger with a recycle action, and runs a preview swap showing the effective diff.

**Integration path:** ARM `PUT`/`PATCH Microsoft.Web/sites/{name}/config/web` (siteConfig, including `autoHealRules` and `ipSecurityRestrictions`), `.../config/appsettings`, `.../config/slotConfigNames`, `POST .../slots/{slot}/slotsswap`, and `.../networkConfig/virtualNetwork` (learn.microsoft.com/en-us/rest/api/appservice/web-apps). The `az webapp` CLI mirrors every step, including `deployment slot swap --action preview`.

**Demand 4/5 · Buildability 5/5**

### 5. Tableau Server / Tableau Cloud: permissions & locked-project default permissions `closed`

**Why it's powerful:** Permission rules work at the capability level on projects, workbooks, data sources, views, flows, virtual connections and collections. Locked projects push default permissions down to all content. Correctly configured, one Tableau site safely serves every department and external partner.

**Why people bounce off it:** It is a capability grid with templates, three-state Allow/Deny/Unspecified rules, and group-vs-user precedence where Deny wins. Admins can't easily answer "why can Bob download this?", and permission sprawl from years of one-off grants is a top Tableau admin complaint.

**AI operator:** A permissions agent. It computes effective access for any user and content pair and explains it in plain language. It finds risky grants (full-data download, direct user grants, unlocked projects) and applies requested changes as one reviewed diff.

**Killer example:** "Make the Finance project read-only for everyone except the FP&A group, and stop anyone downloading full data from those workbooks." The AI sets default workbook permissions on the project (FP&A = Editor, All Users = Viewer, ExportData = Deny). It locks the project and removes 6 conflicting user-level grants on existing workbooks, after listing each one for approval.

**Integration path:** REST API permissions methods. `PUT .../projects/{id}/permissions`, `PUT .../{workbooks|datasources|views|flows}/{id}/permissions`, `PUT .../projects/{id}/default-permissions/{type}`, and Delete Permission (help.tableau.com/current/api/rest_api/en-us/REST/rest_api_ref_permissions.htm). This is distinct from the broader Tableau card already covered: it targets governance.

**Demand 4/5 · Buildability 5/5**

### 6. AWS Backup (backup plans, resource selections, cross-region/cross-account copies, vault lock, restore testing) `closed`

**Why it's powerful:** One service centrally protects EC2/EBS, RDS/Aurora, DynamoDB, EFS, FSx, S3 and more. It handles lifecycle to cold storage, WORM vault lock, logically air-gapped vaults, cross-region and cross-account copies, and automated restore testing. That covers both ransomware recovery and audit requirements.

**Why people bounce off it:** Turning "hourly, 7-day, copied to another region" into config means combining cron rules, retention and cold-storage transitions (which have minimum-day constraints), and tag-based selections with IAM roles. Copy actions also need vault ARNs and KMS key policies. Compliance-mode vault lock is irreversible, and restore-testing plans are almost never set up. Many teams believe they're protected and aren't.

**AI operator:** A "backup auditor and builder". It lists resources that no plan covers and turns an RPO/RTO sentence into plans, selections, copy rules and restore tests. It shows a coverage diff before applying, and warns loudly (requiring typed confirmation) before any irreversible vault lock.

**Killer example:** "Every prod database: hourly backups kept 7 days, dailies kept 35 days and copied to us-west-2, monthlies for a year, and prove weekly that we can restore." The AI creates a three-rule backup plan; the daily rule gets a `CopyActions` target to the us-west-2 vault. It adds a selection on `env=prod` for RDS and DynamoDB and a weekly restore-testing plan with a validation window. It then reports the four prod databases that are missing the `env` tag and matched nothing.

**Integration path:** `CreateBackupPlan`/`UpdateBackupPlan`, `CreateBackupSelection`, `CreateBackupVault`, `PutBackupVaultLockConfiguration`, `CreateLogicallyAirGappedBackupVault`, `CreateRestoreTestingPlan`/`CreateRestoreTestingSelection`, `ListProtectedResources` (docs.aws.amazon.com/aws-backup/latest/devguide/api-reference.html). The `aws backup` CLI, CloudFormation `AWS::Backup::*` and Terraform are alternatives. Scope is account-level Backup. Org-wide backup *policies* go through AWS Organizations, which is already covered.

**Demand 4/5 · Buildability 5/5**

### 7. Google Classroom + Microsoft Teams Assignments (rubrics, grade categories, grading periods) `closed`

**Why it's powerful:** Google Classroom comes with Google Workspace for Education and Teams Assignments with Microsoft 365 Education, so between them they reach a very large share of K-12 and university classrooms. Both support rubrics, grade categories, grading periods, scheduled posting and per-student assignment.

**Why people bounce off it:** Teachers dread building rubrics (criteria × levels × points × descriptions) and setting up the gradebook. They have to do it again for every section, every term. It's tedious clicking for people with no admin support and no time.

**AI operator:** A teaching assistant that turns a lesson brief into fully configured assignments across a teacher's classes. It drafts the rubric text at the right grade level, schedules posting, files the assignment under the right category and grading period, and copies it to every section.

**Killer example:** "Post the persuasive essay to all three 9th-grade sections Monday 8am, due Friday, 20 points, rubric for thesis, evidence and grammar with 4 levels each, Writing category, Term 2." The AI creates the courseWork in 3 courses with `scheduledTime`, `gradeCategory` and `gradingPeriodId`. It then creates and attaches a 3×4 rubric to each assignment.

**Integration path:** Classroom API `courses.courseWork.create`, `courses.courseWork.rubrics.create`/`patch`, and `courses.update` (gradebookSettings) (developers.google.com/workspace/classroom/rubrics/getting-started). Gating: rubric writes need an Education Plus license, though Google's `V1_20260316_PREVIEW` version reportedly drops that requirement. Microsoft Graph Education: `POST /education/classes/{id}/assignments`, `POST /education/me/rubrics`, `PUT .../assignments/{id}/rubric/$ref`, and `POST .../publish`.

**Demand 4/5 · Buildability 4/5**

### 8. Shopify Markets + Shopify B2B (markets, catalogs, price lists, company locations, payment terms) `closed`

**Why it's powerful:** It's international selling and wholesale from one store. Markets gives per-country currencies, price lists, catalogs, domains and subfolders, and duties. B2B gives company accounts with multiple locations and buyers, location-specific catalogs and price lists, Net terms, and quantity rules.

**Why people bounce off it:** The object model is hard: markets → catalogs → price lists → publications → web presences, plus rounding and fixed-price overrides. B2B onboarding means company, locations, contacts, roles, catalog, price list and payment terms for **every** wholesale customer. Merchants expanding abroad or adding wholesale end up paying agencies.

**AI operator:** An "expansion and wholesale operator". The user names countries and a pricing policy, or forwards a wholesale customer's email or CSV. The AI builds the markets, catalogs, price lists, fixed prices and companies, then reports what changed and what each buyer will see.

**Killer example:** "Launch in Germany and France in EUR, prices 10% above US but the hero jacket fixed at €199, and hide the gift cards. Also add Acme Cafes (Boston + Austin), Net 30, 35% off, coffee only." The AI runs `marketCreate` ×2, `catalogCreate` + `priceListCreate` (+10%, EUR), `priceListFixedPricesAdd` and `publicationUpdate`. For Acme it runs `companyCreate`, `companyLocationCreate`, a location catalog with a −35% price list, and `companyLocationUpdate` with the Net 30 terms template.

**Integration path:** Admin GraphQL. Markets: `marketCreate`/`marketUpdate`, `catalogCreate`/`catalogUpdate`, `priceListCreate`/`priceListUpdate`, `priceListFixedPricesAdd`, `webPresenceCreate`. B2B: `companyCreate`, `companyLocationCreate`/`companyLocationUpdate`, `companyContactCreate`, `quantityRulesAdd` (shopify.dev/docs/apps/build/markets, shopify.dev/docs/apps/build/b2b). Gating: native B2B requires Shopify Plus. This is distinct from the Shopify core, Discount Functions and Metafields cards already covered.

**Demand 4/5 · Buildability 4/5**

### 9. Microsoft Teams Webinars & Town Halls (virtual events) `closed`

**Why it's powerful:** It's included with every Microsoft 365 business seat. It offers branded registration pages, custom registration questions, co-organizers and presenters, attendee caps, email notifications, attendance reports, and town halls for 10k+ attendees on Premium. Many companies already pay for it and still buy Zoom Webinars or ON24 because nobody can configure it.

**Why people bounce off it:** Event settings are split across the Teams client tabs, the meeting-options web page, admin meeting policies and the registration editor. Organizers routinely get lobby, presenter and registration settings wrong, and building custom questions is tedious.

**AI operator:** An "event producer". It turns a plain-language brief into a draft webinar with registration questions, co-organizers and meeting options. It previews, publishes on approval, and later summarizes registrants and attendance.

**Killer example:** "45-minute customer webinar next Thursday 4pm IST, registration required, ask company size (dropdown) and role, Priya co-organizes, no attendee emails." The AI POSTs a draft webinar with `isRegistrationRequired: true`, `coOrganizers` and `settings.isAttendeeEmailNotificationEnabled: false`. It adds two custom registration questions plus the predefined job-title question, sets lobby bypass on the underlying online meeting, and shows a preview before publishing.

**Integration path:** Microsoft Graph v1.0 `POST /solutions/virtualEvents/webinars` creates a draft webinar (verified 2026-10-18; delegated `VirtualEvent.ReadWrite` only, no app-only). `POST .../webinars/{id}/registrationConfiguration/questions` adds questions and `PATCH /me/onlineMeetings/{id}` sets lobby and presenter options. Caveats: breakout rooms and Q&A setup have no Graph write, and it runs as the signed-in organizer. This is distinct from the Teams admin center and Teams Shifts cards already covered.

**Demand 4/5 · Buildability 4/5**

### 10. ServiceNow Service Catalog (catalog items, variables, variable sets, catalog UI policies) `closed`

**Why it's powerful:** The catalog is the self-service front door for every IT, HR and facilities request in large enterprises. It provides dynamic forms, conditional variables, reference qualifiers, user criteria and fulfillment hooks.

**Why people bounce off it:** Building a single catalog item means Catalog Builder or half a dozen related lists: variables, variable types, reference qualifiers, UI policies and their actions, client scripts, categories and user criteria. Process owners queue for months behind scarce ServiceNow admins just to add a form.

**AI operator:** A "form builder by description". It turns a plain-language request form into a catalog item with variables, UI policies, category and visibility, all inside a named update set so the change promotes cleanly from dev to test to prod. It links existing fulfillment flows rather than authoring them.

**Killer example:** "New laptop request: pick Mac or Windows; if Mac show RAM 16/32; manager approval over $2k; only visible to employees." The AI inserts the `sc_cat_item` and its `item_option_new` variables. It adds a `catalog_ui_policy` with its action for the RAM field, applies the employee-only user criteria, and attaches the existing manager-approval flow. Everything is captured in the update set "Laptop request v1".

**Integration path:** Table API `POST /api/now/table/{table}` and `PATCH /api/now/table/{table}/{sys_id}` on `sc_cat_item`, `item_option_new`, `io_set_item`, `catalog_ui_policy`, `catalog_ui_policy_action` and `sc_cat_item_category`. Docs: servicenow.com/docs, Table API. Caveat: Flow Designer approval and fulfillment flows aren't practical to author via the Table API, so link existing ones. This is distinct from the ServiceNow ITSM/ITOM card already covered.

**Demand 4/5 · Buildability 4/5**

### 11. Pinterest Ads (Ads Manager + catalog Shopping campaigns, product groups, audiences) `closed`

**Why it's powerful:** It reaches roughly half a billion monthly users who are actively planning purchases. It has catalog-driven Shopping ads, product groups built from feed attributes, interest, keyword and "actalike" audiences, a conversion tag and CAPI, and the Performance+ automation. For home, fashion, beauty and DIY brands it is often the cheapest high-intent traffic available.

**Why people bounce off it:** Building Shopping campaigns is the hard part. Merchants have to split the catalog into product groups using nested `all_of`/`any_of` filters on `custom_label_0-4`, product-type levels and price ranges. They then have to wire those groups into ad groups with the right `targeting_spec`. Most SMB merchants stop at "boost a Pin".

**AI operator:** A "Pinterest shopping strategist". It reads catalog health first, then turns a plain-language brief into product groups, a campaign, ad groups with targeting and budget, and audiences. Everything is created paused for review, followed by a weekly plain-language performance summary.

**Killer example:** "Promote my fall sweaters under $80 to women 25–44 interested in cozy home decor, $40/day." The AI creates a product group (product_type contains "sweater", max price 80) and a conversions campaign. It adds an ad group with the interest, age and gender `targeting_spec` and the daily budget, attaches the product group as promoted, and leaves everything paused with a preview.

**Integration path:** Pinterest API v5. `POST /v5/catalogs/product_groups` creates product groups and `PATCH` updates them. `POST /v5/ad_accounts/{id}/campaigns`, `POST /v5/ad_accounts/{id}/ad_groups` (with `targeting_spec`) and `POST /v5/ad_accounts/{id}/audiences` create the rest (developers.pinterest.com/docs/work-with-catalogs/manage-product-groups/). Gating: it needs the `catalogs:write` and `ads:write` scopes, and the app has to move from Trial to Standard access through Pinterest review.

**Demand 4/5 · Buildability 4/5**

### 12. Xero Payroll (AU / UK / NZ: pay items, leave types, payroll calendars, pay runs) `closed`

**Why it's powerful:** Payroll is built into Xero for hundreds of thousands of SMBs in Australia, the UK and New Zealand. It covers earnings rates, deduction, reimbursement and leave types, superannuation and pension, payroll calendars and pay runs, and filing to the tax office: STP (Single Touch Payroll) in Australia and RTI (Real Time Information) in the UK.

**Why people bounce off it:** Owner-operators have to turn award or contract terms into pay items: ordinary vs. overtime multiples, allowances, STP reporting categories, and leave accrual rules. Then they have to run pay with per-employee adjustments. Getting the STP category or multiplier wrong means underpayment or mis-filed reports, which is a real compliance risk for a small business.

**AI operator:** A "payroll setup and run clerk". It configures pay items from plain-language award terms, drafts each pay run with that period's adjustments, and flags anything unusual against prior runs. It never files: it leaves a draft for the human to approve and file.

**Killer example:** "Add a Sunday rate at 1.75× ordinary and a $25/day tool allowance, then draft this fortnight's pay with Jake's 6 hours of Sunday work." The AI POSTs PayItems (an EarningsRate with `MultipleOfOrdinaryEarningsRate = 1.75` and the allowance with its STP category). It creates a draft PayRun, adds Jake's lines to his payslip, and shows gross and net changes against last fortnight.

**Integration path:** Xero Payroll AU v1 `POST payroll.xro/1.0/PayItems`, `/PayRuns`, `/Payslip/{id}`, `/Employees`, `/LeaveApplications` and `/PayrollCalendars`. UK and NZ use v2 (`payroll.xro/2.0/EarningsRates`, etc.). Docs: developer.xero.com/documentation/api/payrollau/payitems. It needs payroll OAuth scopes and is subject to Xero's API pricing tiers. This is distinct from the Xero bank-reconciliation card already covered.

**Demand 4/5 · Buildability 4/5**

## Checked and dropped this run (the API can't write the thing that is the usability wall)

Recorded here so future scouts don't re-propose these with invented endpoints:

- **Jira Automation rules** and **Salesforce Object Manager / validation rules / Dynamic Forms**: both have real write APIs (Automation `POST /rest/v1/rule` is GA), but they were dropped as **repeats**. The 2026-07-31 Jira and Salesforce Sales Cloud cards already pitched the same operators.

- **monday.com and Asana rules:** no rule-create API.
- **Help Scout Workflows:** list, status and run only.
- **Jira dashboard gadget config:** writes return 403 or 404 in practice.
- **Microsoft Loop, Microsoft Forms, Google AppSheet:** no authoring write API.
- **Calendly:** routing forms and workflows are not writable.
- **Gong, Clay, Creatio, LinkedIn Sales Navigator:** no authoring API, or partner-gated.
- **Salesforce Sales Engagement cadences:** `ActionCadence` create was removed.
- **Talend, Informatica mappings, Spotfire, Hex, Heap:** design surfaces are not writable.
- **Camtasia, Adobe Audition, Character Animator, Procreate:** no write surface. **Descript** was dropped because it already ships its own AI editing agent.
- **Paychex, Rippling, Kyriba:** partial or gated API access. **Carta** was dropped because it already ships a first-party AI integration.
