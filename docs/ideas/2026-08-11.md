### 1. Google Tag Manager (web + server-side containers) `closed`

**Why it's powerful:** GTM is the injection point for essentially every marketing tag on the web: roughly 43 million live sites per BuiltWith, 94.3% share among sites running any tag manager per W3Techs, and about 73.5% of the top one million sites. A container is a real programmable runtime — custom HTML tags, custom JavaScript variables, dataLayer variables, lookup and regex tables, trigger groups, tag sequencing, consent-mode gating, per-tag firing priority. Server-side containers add a second Node-based runtime with GA4 clients, custom templates and first-party cookie writing, which is how most teams now run Meta CAPI and Google Enhanced Conversions. API v2 exposes full CRUD over accounts, containers, workspaces, tags, triggers, variables, folders, environments and user permissions, plus versions.create and versions.publish — an operator can genuinely do everything a human does in the UI.

**Why people bounce off it:** The core model — tag fires on trigger, trigger reads variable, variable reads dataLayer — is four levels of indirection that marketers never internalise, so they cargo-cult containers full of dead tags. Trigger configuration is where people break: 'Some Pages' vs 'All Pages', Page URL vs Page Path vs Page Hostname, 'contains' vs 'matches RegEx' vs 'matches RegEx (ignore case)', and the fact that a Page View trigger never fires again in a single-page app after the first route. Consent Mode v2 added ad_storage, analytics_storage, ad_user_data and ad_personalization plus 'Additional consent checks' and 'Require additional consent for tag to fire' buried in Advanced Settings, and getting them wrong silently converts real conversions into cookieless pings. Preview mode shows a Tags Fired / Tags Not Fired split that requires you to already know which trigger condition failed. Version history is a flat list of numbered versions with a diff view nobody opens, so a regression from three weeks ago is effectively undiscoverable. Server-side adds a whole second mental model — clients, event data objects, template permissions, and the 'Permission not granted' error when a custom template lacks send_http. Workspaces add merge conflicts with a 'Workspace changes conflict with the current container version' banner. And the 2026 GTM/Google tag merge is currently shuffling where the Google tag settings actually live, which has broken people's mental map again.

**AI operator:** A GTM operator that connects with OAuth and is preloaded with skills for read-and-explain-container, diff-two-versions, build-a-conversion-tracking-setup, audit-consent-mode, find-dead-tags, and migrate-a-tag-across-N-containers. Every write goes into a fresh named workspace it creates itself, never the default workspace, and it renders a plain-English diff ('creating 1 trigger, modifying 2 tags, deleting 0') that the user approves before it calls versions.create and versions.publish. The second mode is a forensic auditor: point it at a container and it produces a ranked list of what is broken or wasteful — tags with no trigger, triggers referencing variables that no longer exist, duplicate GA4 config tags, custom HTML tags loading vendors nobody recognises, consent settings that will drop EU conversions. Multi-container fan-out falls out cheaply: one instruction applied across every country or brand container with a per-container preview. Rollback is a first-class verb because publish targets a version, so 'undo what you just did' is a real, safe operation.

**Killer example:** A performance marketer says: 'Google Ads conversions from checkout dropped about 40% starting Tuesday and nobody changed anything.' The operator pulls the container, lists versions, and diffs live version 87 against 86. On Tuesday someone replaced the Purchase tag's Custom Event trigger (event equals purchase) with a Page View trigger on Page Path matches RegEx /thank-you — which worked on the old checkout, but the site moved to a client-side routed checkout in June, so the pageview never fires on the confirmation route. It then reports something nobody asked about: the GA4 configuration tag's consent settings were switched so ad_storage is a required consent type with no update listener wired, meaning EU sessions that consent *after* the tag would have fired never send the conversion at all — which is why the drop is 40% rather than 100%. It proposes a workspace named fix-purchase-2026-08-11 with three changes (restore the Custom Event trigger, add a dataLayer variable for ecommerce.value with a fallback of 0, add an Additional Consent Checks update listener) and shows the diff. The user approves; it publishes version 88. Follow-up: 'do the same across our other twelve country containers.' The operator warns that the API is capped at 0.25 queries per second per project and 10,000 requests per project per day, so twelve containers will take minutes rather than seconds, and asks whether to publish each or leave them staged as unpublished workspaces for the local teams. The user picks staged, and it returns twelve workspace URLs.

**Integration path:** Tag Manager API v2 over OAuth 2.0 with tagmanager.edit.containers, tagmanager.edit.containerversions, tagmanager.publish and tagmanager.readonly scopes; the resource path is always accounts/{a}/containers/{c}/workspaces/{w}/{tags|triggers|variables}, so a workspace is mandatory for every write. The hard constraint is quota: 10,000 requests per project per day and 0.25 QPS per project (25 requests per 100-second window), returning HTTP 403 when exceeded — bulk fan-out must be queued and backed off, and a naive read-everything crawl of a large container burns quota fast. There is no diff endpoint, so version comparison has to be reconstructed client-side from full version payloads. Honest gap: Tag Assistant preview/debug output is not exposed via any public API, so the operator can reason about configuration but cannot watch a tag fire — pair it with a headless browser that loads the site with gtm_debug and reads the dataLayer directly.

**Competitive note:** Google's 2026 GTM updates ship AI-powered tag recommendations, AI-assisted trigger pattern suggestions, and a visual tagging beta (20 May 2026) for no-code purchase conversion setup in Google Ads. Those are suggestion surfaces bolted onto the existing UI: none of them read your live container, diff two versions to explain a regression, audit consent mode, or apply the same change across twelve containers.

### 2. Cloudflare (DNS, SSL/TLS, Rules engines, Email Routing, Zero Trust) `closed`

**Why it's powerful:** Cloudflare sits in front of roughly a fifth of all websites, and the free tier hands a non-engineer an enterprise control plane: authoritative DNS, a full reverse proxy and CDN, WAF with managed rulesets and wirefilter custom rules, rate limiting, five separate rule engines (Redirect, Transform, Configuration, Cache, Origin) plus legacy Page Rules, Workers, Email Routing, Tunnels and Zero Trust Access/Gateway. One dashboard controls a business's entire web presence: where the domain resolves, how TLS terminates, what gets cached, who is blocked, where email lands. The Rulesets API alone exposes ordered, phased rule lists that can rewrite headers, URLs, cache keys and origin selection per request. It is genuinely more powerful than most enterprise ADC stacks — and it is administered by whoever happened to sign up for the domain.

**Why people bounce off it:** The single most common self-inflicted outage is the SSL/TLS mode selector: Flexible plus an origin that redirects HTTP to HTTPS produces an infinite ERR_TOO_MANY_REDIRECTS loop, and the obvious 'fix' of switching to Full produces Error 525, or 526 under Full (strict) with a self-signed cert. Cloudflare's own community is full of people oscillating between the two for days. The error codes are opaque to a non-specialist: Error 1000 (DNS points to prohibited IP), 1014 (CNAME Cross-User Banned), 522 when the origin firewall silently drops Cloudflare's IP ranges, 1016 origin DNS error. Orange-clouding an MX record or the mail subdomain black-holes email because the proxy only handles HTTP/HTTPS, and nothing warns you. The rules surface is split across Page Rules, Redirect Rules, Transform Rules, Configuration Rules, Cache Rules, Origin Rules and Bulk Redirects, each with different capabilities and a different position in evaluation order — so 'add a redirect' has six wrong answers, and the query-string preservation toggle lives in exactly one of them. WAF custom rules require wirefilter expressions with operator-precedence traps. Zero Trust adds a third mental model: Access application vs Access policy vs Gateway network policy vs device posture, and a healthy Tunnel that still returns 502 because ingress points at localhost:8080 while the app listens on 3000. Finally there is no undo — zone settings apply globally in seconds and the only rollback is remembering what you changed.

**AI operator:** Preload skills for the whole zone surface: DNS record CRUD with proxy-status reasoning, SSL/TLS mode plus Always Use HTTPS and Automatic HTTPS Rewrites, authoring of Redirect/Transform/Configuration/Cache/Origin rules in wirefilter, WAF custom and rate-limiting rules, Email Routing with SPF/DKIM/DMARC generation, Zero Trust Access apps and policies, and Tunnel ingress mapping. Every mutation is preview-first: render a zone diff (records before/after, rule list with resulting evaluation order), then run an out-of-band probe — curl through Cloudflare and curl directly at the origin on 443 — and state the exact HTTP chain expected after the change. Apply takes an automatic snapshot (BIND export of DNS plus a captured copy of each ruleset) so a single 'revert' is real, not aspirational. The second mode is triage: the user pastes a screenshot or says 'my site is down', and the operator sweeps nameserver delegation, record proxy status, SSL mode, origin reachability, recent ruleset changes and analytics, then returns a ranked diagnosis with a one-tap fix. A read-only token drives the sweep; a separate write token unlocks only at apply time, so diagnosis cannot break anything.

**Killer example:** A shop owner says: 'Checkout has been redirecting in a loop since this morning and Gmail stopped receiving order notifications.' The operator finds SSL/TLS mode set to Flexible while a direct probe to the origin on port 80 returns 301 to https — the textbook loop — and verifies the origin already serves a valid Let's Encrypt cert on 443 expiring in 34 days, so Full (strict) is safe. It then notices what the user never asked about: the apex MX record and the mail A record are both orange-clouded, so the proxy is intercepting them and SMTP is being dropped, which is why order mail died at the same time someone was 'fixing' the site. Third problem: a Redirect Rule created three days ago matching http.host eq "shop.example.com" with query-string preservation off, stripping the ?session= parameter checkout depends on. The preview shows a three-line diff and the predicted chain (one 301, then 200 OK, redirect chain length 1). Unprompted, it also flags two separate v=spf1 TXT records — an SPF permerror — while _dmarc is p=reject, which is why the payment provider's receipts have been silently rejected for weeks. The user applies; the operator re-probes and confirms 200 OK, grey-clouded mail records, query string preserved. Follow-up: 'Will Full (strict) break my staging site?' It checks staging.example.com, finds a Cloudflare Origin CA certificate (which Full (strict) accepts), says no, and offers a Configuration Rule scoped to that hostname anyway. It closes by offering to merge the two SPF records and schedule a cert-expiry watch at 14 days.

**Integration path:** REST API v4 at api.cloudflare.com/client/v4 with scoped API tokens (Zone:DNS:Edit, Zone:Zone Settings:Edit, Zone:Firewall Services:Edit, account-scoped Tunnel and Zero Trust permissions), plus the official cloudflare-typescript and cloudflare-python SDKs. All rules engines go through the Rulesets API, where rules are ordered lists inside per-phase entrypoints (http_request_firewall_custom, http_request_transform, http_request_dynamic_redirect, http_request_cache_settings), so edits are read-modify-write on the whole ruleset and a naive full PUT clobbers concurrent changes — you need optimistic concurrency and per-rule patching. Snapshots are cheap: the DNS export endpoint returns a BIND zone file and rulesets can be captured verbatim. Honest gaps: no API can see the origin server's configuration, so half the diagnosis depends on an out-of-band HTTP probe the product runs itself; token permission groups are coarse, so a genuine read-only preview mode needs two tokens; and Zero Trust lives under account scope with its own permission set, which complicates onboarding for a one-domain small business.

**Competitive note:** Cloudflare ships a WAF Rule Builder Assistant (one rule expression inside the builder), an AI Assistant in Security Analytics (NL querying of HTTP/security events), and an official MCP server (January 2026) exposing 2,500+ endpoints via a search/execute Code Mode pattern. None of that is an operator for a non-engineer: the MCP requires an MCP client and a hand-scoped token, and offers no diagnosis, no preview diff and no rollback.

**Demand 5/5 · Buildability 4/5**

### 3. Microsoft Entra ID (Conditional Access, PIM, app registrations & consent, Access Reviews) `closed`

**Why it's powerful:** Entra ID is the authorization chokepoint in front of essentially every Microsoft 365 tenant, and M365 has north of 400 million paid seats — the same policy engine an accidental IT person half-configures is the one Microsoft runs at tens of billions of authentications per day. Conditional Access is a genuine rules engine: each policy is a JSON object with conditions (users, cloud apps, platforms, locations, client app types, sign-in and user risk, device filters), grantControls (MFA, compliant device, hybrid-joined, approved app, app protection policy, terms of use, with an AND/OR operator) and sessionControls (sign-in frequency, persistent browser, app-enforced restrictions, CAE). PIM turns standing admin roles into time-boxed eligible ones with approval, MFA and justification gates. Access Reviews recur over groups, app assignments and privileged roles and can auto-remove non-attested access. Critically for a builder: POST to /identity/conditionalAccess/policies is GA in Graph v1.0 — this is a fully writable control plane.

**Why people bounce off it:** The CA blade is an eight-level nested tree and nothing tells you the semantics: includes are ORed, excludes always win, and a nested group in an exclusion does not expand. The most consequential toggle is a tri-state at the bottom — Off / Report-only / On — and Microsoft ships a literal 'Don't lock yourself out!' warning because turning a policy On with no break-glass exclusion is unrecoverable without support. The grant-control radio, 'Require all the selected controls' versus 'Require one of the selected controls', is an AND/OR that people invert constantly and the summary text does not restate. Blocking legacy auth means finding 'Client apps' under Conditions, un-defaulting it, and knowing 'Exchange ActiveSync clients' and 'Other clients' are the POP/IMAP/SMTP AUTH bucket. The What If tool silently ignores sign-in risk and device state unless you set them, so it happily tells you a policy will not fire when it will. PIM splits the assignment (Eligible vs Active) from the enforcement, which lives in a completely separate per-role 'Role settings' pane. Access Reviews default 'Auto apply results to resource' to off, so the classic outcome is a year of reviews that removed nobody. And the failure surface is opaque codes in someone else's browser: AADSTS53003, AADSTS65001, AADSTS50105.

**AI operator:** Preload the full conditionalAccessPolicy schema, Microsoft's CA templates, the PIM unifiedRoleEligibilityScheduleRequest and unifiedRoleManagementPolicyRule shapes, the app-registration/consent object graph, and a lookup table mapping AADSTS codes to the specific condition that produces them. The user speaks in outcome language; the operator emits candidate policy JSON, then does the thing the portal refuses to do — blast-radius simulation. Because there is no GA Graph What If endpoint, it replays the tenant's last 30 days of auditLogs/signIns against the proposed conditions itself and reports exactly which named users, service principals and client-app types would have been blocked, with counts. It always writes state: enabledForReportingButNotEnforced first, snapshots the full prior JSON of every touched policy for one-command rollback, and hard-refuses to create any policy that does not exclude a verified break-glass account. Second mode is a standing hygiene auditor: CA coverage gaps (users matched by zero MFA policy), standing Global Administrators that should be PIM-eligible, app registrations with expiring secrets and over-broad delegated consent, stalled access reviews with auto-apply disabled.

**Killer example:** The user types: 'Block the old email protocols. Do not break the scanner in accounting or the billing system.' The operator queries auditLogs/signIns filtered on clientAppUsed in ('IMAP4','POP3','SMTP','Other clients') and reports: 224 users in the tenant, but only 6 principals used legacy auth in 30 days — 41 sign-ins from the Ricoh MFP at 10.14.2.30 via SMTP, 12 from a QuickBooks connector, and 3 from a former employee's iPhone that still has an ActiveSync partnership. It drafts a CA policy targeting All users, All cloud apps, client apps = Exchange ActiveSync + Other clients, grant = Block, with a named-location exclusion for the office IP and a group exclusion for the two service accounts. Then it volunteers something nobody asked for: the tenant's existing 'Require MFA for admins' policy has no break-glass exclusion, so the only account that could undo a lockout is itself covered — and separately, SMTP AUTH is enabled tenant-wide rather than per-mailbox, so the scanner exclusion is broader than it needs to be. It shows the preview as a table of who would have been blocked, not JSON. The user approves; it creates the policy in Report-only plus a second policy adding the break-glass exclusion. Twenty-four hours later it returns unprompted: report-only recorded 3 blocks, all from the ex-employee's device, and asks whether to flip to On. The user says 'yes, and kill that iPhone.' It PATCHes state to enabled, deletes the stale device object, revokes the user's refresh tokens, and hands over the exact What If arguments to confirm the next AADSTS53003.

**Integration path:** Microsoft Graph v1.0 is the whole surface: POST/PATCH /identity/conditionalAccess/policies (needs Policy.ReadWrite.ConditionalAccess plus Application.Read.All), /roleManagement/directory/roleEligibilityScheduleRequests and /roleManagementPolicies for PIM, /identityGovernance/accessReviews/definitions, /applications + /servicePrincipals + /oauth2PermissionGrants, and /auditLogs/signIns for the replay. Auth is a multi-tenant Entra app with admin consent, and the non-obvious constraint is that an app-only principal holding Policy.ReadWrite.ConditionalAccess still cannot write CA policies unless the service principal is also assigned the Conditional Access Administrator or Security Administrator directory role — this trips up almost every first implementation. PIM and Access Reviews require Entra ID P2, which most small tenants only have via Business Premium or an add-on, so degrade gracefully rather than 403. Use $batch (20 requests per call), honor Retry-After on 429, and note sign-in log retention is 30 days on P1/P2 and 7 days otherwise, which caps replay quality. Honest gap: there is no GA policy-simulation API and no server-side version history or rollback for CA policies, so the product must own snapshotting, diffing and restore — that is the actual moat, not the writes.

**Competitive note:** Security Copilot's Entra plugin investigates identities and summarizes risk, and the M365 admin agents answer questions, but none of them author or modify a Conditional Access policy — Microsoft ships templates and report-only mode as the safety story and stops there. Security Copilot also meters on Security Compute Units, which prices it out of exactly the small tenants that need this most.

### 4. Microsoft Intune (compliance, config profiles, Win32 apps, Autopilot, update rings) `closed`

**Why it's powerful:** Microsoft's own documentation states the Graph API for Intune 'performs the same Intune operations as those available through the portal', making it one of the few enterprise endpoint-management platforms that is completely automatable, across hundreds of millions of endpoints on Windows, macOS, iOS and Android. The Settings Catalog exposes effectively the entire Windows CSP and Apple payload surface — thousands of individually addressable settings — alongside compliance policies, security baselines, Win32 app deployment via .intunewin with detection and requirement rules, Autopilot zero-touch provisioning, Windows Update rings with deferrals and deadlines, proactive remediation scripts and Endpoint Privilege Management. It is bundled into M365 E3, E5 and Business Premium, so an enormous number of small companies already own it and have never configured anything beyond enrollment.

**Why people bounce off it:** Four different blades can set the same underlying CSP — Configuration profiles, Compliance policies, Security baselines, Endpoint security — and when two disagree Intune reports a device state of 'Conflict' with no indication of which profile won. Settings Catalog search for 'BitLocker' returns near-duplicate settings from an ADMX-ingested path and a native CSP path with identical display names and different behavior. Assignment is Include/Exclude groups plus a separate filter object with its own expression language, and filters are evaluated per-assignment, not globally, so an exclusion filter on one assignment does nothing to another. The canonical error a small-shop admin hits is profile status 'Error' with code -2016281112 / 0x87D1FDE8, official text 'Remediation failed', conveying precisely nothing. Autopilot profiles do not apply to already-enrolled hardware unless 'Convert all targeted devices to Autopilot' is toggled on. The Enrollment Status Page hangs on 'Identifying...' when a blocking app never reports success, and the fix is understanding that Win32 detection rules are what 'success' means — a bad detection rule produces an infinite reinstall loop rather than an error. Update rings layer quality deferral, feature deferral, deadline and grace period, and it is entirely possible to configure a 7-day deferral with a 2-day deadline and get behavior no one can explain. Microsoft's own docs warn the two Graph API families for Windows updates can silently overwrite each other with no visibility.

**AI operator:** Preload the deviceManagementConfigurationSettingDefinition catalog so it can resolve plain-English intent to exact setting IDs and CSP URIs, plus compliance/baseline templates, the Win32 detection and requirement rule grammar, Autopilot and ESP schemas, and a decoded table of Intune status codes including 0x87D1FDE8. The interaction is intent-in, diff-out: the user says what should be true of their fleet, and the operator returns a three-part preview — the exact settings it will write, every existing profile or baseline that already touches those same CSPs (the conflict map the portal never shows), and a resolved scope count like 'this lands on 187 of 214 Windows devices; here are the 27 excluded and why'. Only after confirmation does it POST, and it snapshots prior JSON for every touched profile and assignment so 'undo that' restores state. It stages risky changes to a pilot group and offers promotion after a soak window. Second mode is a standing fleet auditor: overlapping settings, orphaned assignments pointing at deleted groups, devices stuck in Error or Conflict, apps whose detection rules cause reinstall loops, update rings with contradictory deferral and deadline values.

**Killer example:** The user says: 'Every laptop should have BitLocker on and nothing should sit unpatched for more than a month.' The operator inventories 214 Windows devices, 187 corporate-owned, and reports that 34 are already covered by a Settings Catalog profile named 'Win10 Baseline - COPY' created in 2022 by a departed MSP, which sets BitLocker encryption to XTS-AES 128 while the assigned security baseline sets XTS-AES 256 — the reason 12 devices have been reporting 0x87D1FDE8 'Remediation failed' for eight months, because the two policies fight on every check-in. It proposes one consolidated disk-encryption policy with recovery-key escrow to Entra ID, marks the 2022 profile for retirement, and shows a before/after setting diff. Then, unprompted, it flags something else: the tenant has Windows Update rings configured through the Intune update APIs *and* a feature-update deployment created through the separate Windows Update for Business deployment service, which Microsoft documents as incompatible and capable of overwriting each other without visibility — explaining the 'deployments that cancel themselves' ticket filed with support in March and never resolved. It also notes the ring defers quality updates 7 days but sets a 2-day deadline, which is why some machines reboot before the deferral lapses. The user says 'fix the update thing, leave BitLocker for Monday.' It PATCHes the ring to a 7-day deferral with a 14-day deadline and 2-day grace period, deletes the orphaned deployment-service policy after showing which 9 devices it targeted, and leaves the encryption change staged with a named pilot group of 5 devices ready to fire.

**Integration path:** Microsoft Graph is the only surface and it is split awkwardly: /deviceManagement/deviceCompliancePolicies, /deviceConfigurations, /deviceAppManagement/mobileApps and /deviceManagement/managedDevices are GA in v1.0, but the Settings Catalog (deviceManagementConfigurationPolicy, deviceManagementConfigurationSettingDefinition) and Autopilot (windowsAutopilotDeploymentProfile) still live in beta — any serious operator must pin beta for its most important surface and absorb breaking changes. Permissions are DeviceManagementConfiguration.ReadWrite.All, DeviceManagementApps.ReadWrite.All and DeviceManagementManagedDevices.ReadWrite.All, app-only via an Entra app with admin consent; Intune RBAC roles and scope tags apply on top and silently narrow what the operator can see. Batch with $batch at 20 requests per call and back off on 429. Win32 app upload is not a simple POST — it is a multi-step mobileAppContentFile flow with Azure Storage SAS chunked upload and an encryption-info commit, the single most expensive integration to get right. Honest gap: no server-side simulation of 'what will this profile do to this device' and no policy version history or rollback, so scope resolution, conflict detection and undo all have to be re-implemented client-side against group membership and the assignment graph.

**Competitive note:** Security Copilot in Intune is explicitly a read surface — data exploration, policy and assignment lookup ('Why is PolicyA applying on DeviceB?'), device details, comparing a working versus non-working device — it does not create or change a policy, and it consumes metered Security Compute Units, pricing out the Business Premium tenants with the worst configuration debt. NinjaOne and PDQ sell around Intune rather than into it; MSP tooling like CIPP automates it via scripted templates with no natural-language layer.

**Demand 5/5 · Buildability 4/5**

### 5. Adobe Acrobat Pro (accessibility remediation, forms, Action Wizard, preflight) `closed`

**Why it's powerful:** Adobe reports over 500 million Acrobat users, more than 400 billion PDFs opened in Acrobat in the past year and 16 billion documents edited, with Document Cloud revenue around $3.2B. Acrobat Pro is not a viewer: it ships a full tagging engine for PDF/UA structure, an Accessibility Checker, Reading Order and Table Editor tools, form-field authoring with per-field JavaScript calculation and validation, Preflight with a profile tree that converts to PDF/A-1b through PDF/A-3, true redaction plus document sanitization, Bates numbering, Compare Documents, and Action Wizard for batch sequences over folders. Behind it sits Adobe PDF Services API, exposing OCR, Accessibility Auto-Tag, Extract, Document Generation, combine/split/compress/protect/linearize, electronic seal and HTML-to-PDF as cloud REST operations. The regulatory backdrop is unusually sharp: the European Accessibility Act became enforceable 28 June 2025 and pulls customer-facing PDFs into scope, the US DOJ Title II rule set an April 2026 date for large public entities, and outsourced manual remediation runs roughly $3–$20 per page. Almost every enterprise already owns the tool that can fix this and almost nobody knows how to drive it.

**Why people bounce off it:** Open the Accessibility Checker and you get a verdict list — 'Tagged PDF — Failed', 'Logical Reading Order — Needs manual check', 'Table headers — Failed', 'Alternate text — Failed' — with no instruction on how to resolve any of them. Fixing reading order means the Reading Order tool, where you drag rectangles over regions and pick a type from a floating palette, then drop into the Tags panel and hand-nest <Sect>, <TR>, <TH> and <TD> nodes, and use Table Editor to set Scope=Column on every header cell one at a time. Form authoring hides its power in Text Field Properties → Calculate, where you choose between 'Simplified field notation' and 'Custom calculation script', and tab order lives in a page-thumbnail right-click menu under Page Properties → Tab Order. Redaction is two disconnected steps — 'Redact Text & Images → Search & Remove Text' then a separate 'Sanitize Document' pass — and skipping the second leaves author names, tracked-change history and hidden layers in the file. Preflight is a tree of hundreds of profiles and Fixups whose failure report reads like a compiler dump, and the wrong PDF/A flavor silently rasterizes form fields. Action Wizard shows no intermediate output, so a 4,000-file batch either works or ruins 4,000 files. The whole toolset assumes a spec-reader's mental model of PDF internals, not an office worker's — so compliance work gets outsourced at $3–$20 a page by organizations that already paid for the software that does it.

**AI operator:** An Acrobat operator preloaded with skills for the five workflows people actually fail at: PDF/UA accessibility remediation, batch action authoring, fillable-form generation with calculation and validation scripts, pattern-based redaction plus sanitization, and PDF/A archival conversion. Point it at a folder, a SharePoint library or a Drive folder and describe the outcome — 'make these pass a PDF/UA audit', 'turn this into a fillable form where the total field sums lines 1-6 and rejects negatives', 'redact every account number, then sanitize'. It always previews on a stratified sample of three to five documents with a before/after Accessibility Checker report, a rendered tag-tree diff and a visual overlay of what will be redacted, then applies to the full corpus in checkpointed batches with per-file rollback. Every accessibility claim is independently verified against veraPDF or PAC rather than Adobe's own checker, so 'it passed' means something. Second mode is portfolio audit: crawl a document estate, score each file against PDF/UA and the EAA, cluster files by originating template, and produce a remediation queue with a cost-avoided estimate — plus fixes pushed upstream into the Word or InDesign template so future exports are born accessible.

**Killer example:** A city council has 4,120 public PDFs and an accessibility audit in six weeks. The clerk types: 'make everything on our rates and permits pages pass PDF/UA before the audit.' The operator runs Auto-Tag and reports 3,847 tagged cleanly, 273 failed — then surfaces two things nobody asked about. First, 68 of the failures are image-only scans with no text layer, so tagging them is theatre; they need OCR first, and the AI queues that as a prerequisite rather than shipping documents that pass a checker but are unreadable by a screen reader. Second, 41 of the 'documents' are byte-identical body content with different cover pages, all exported from one InDesign file, so it proposes fixing the source once instead of remediating 41 outputs. It then sets Scope=Column on roughly 1,900 table header cells, adds document titles and language metadata, and reports 'Tagged PDF — Failed' clear on all 4,120 while 'Logical Reading Order — Needs manual check' remains a human review queue of 12 multi-column newsletters it refuses to auto-approve. veraPDF confirms 4,108 files pass PDF/UA-1. Follow-up: 'why does the invoice template keep failing?' First: the nightly automation refreshing that DE has been erroring for nine days with 'Violation of PRIMARY KEY constraint' because someone added SubscriberKey to the DE without removing the old EmailAddress key, so the data is stale regardless. Second, and worse: the journey's email uses a Send Classification set to Transactional, which bypasses the publication list, and 1,900 of the contacts that did receive it had previously unsubscribed — a compliance exposure nobody knew existed. The marketer replies: 'fix it and send only to the people who missed out.' The operator creates journey version 2 with a properly typed Date field, switches the classification back to Commercial, builds an exclusion DE of the 812 already-sent SubscriberKeys, rewrites the query activity with Update semantics against the corrected primary key, and shows a dry run: 39,401 entries projected, 0 previously-unsubscribed contacts included. It stops there and asks for confirmation before publishing, showing the exact v1-to-v2 diff.

**Integration path:** REST at {subdomain}.rest.marketingcloudapis.com and SOAP at {subdomain}.soap.marketingcloudapis.com; both share OAuth2 client_credentials from an Installed Package created in Setup, requiring a user with 'Installed Package > Administer' and per-feature scopes (publishing a journey needs Automation | Interactions | Read). Journeys are real: POST /interaction/v1/interactions creates one, POST /interaction/v1/interactions/{id}/activities adds activities, there is a publish-by-id resource, and /interaction/v1/events is the entry point. Data rows go through /data/v1/customobjectdata/key/{key}/rowset, but Data Extension and QueryDefinition *definitions* still lean on SOAP objects, and Salesforce states outright that REST and SOAP do not have parity — so you need both clients. Hard constraints: Salesforce Support advises staying under 2,500 REST calls per minute, throttled accounts get HTTP 429 until pressure drops, and you must not request more than one access token per 20 minutes. Honest gap: several Automation Studio activity types and Journey Builder canvas features have no documented API representation and the Journey Spec is under-documented for custom activities — so the build needs a schema-probing layer that reads an existing working journey in the tenant and learns the shape by diff rather than trusting the docs.

**Competitive note:** Einstein for MCE is scoring, send-time optimization and engagement frequency — it does not build or debug anything. Agentforce campaign generation ships in Marketing Cloud Next / Growth and Advanced editions on the Agentforce 360 core platform, not in legacy MCE, and as of early 2026 Salesforce has not even shipped automated MCE-to-MCN content migration. That leaves the entire legacy MCE install base with a frozen, expert-only product and no vendor agent.

**Demand 5/5 · Buildability 4/5**

### 11. SQL Server Integration Services (SSIS + the SSISDB catalog) `closed`

**Why it's powerful:** SSIS has shipped in every non-Express SQL Server edition since 2005 and is still present in SQL Server 2025, making it the default ETL engine inside a very large share of on-prem enterprise data estates. It gives you a pipelined dataflow engine with ~30 transforms (Lookup with full/partial cache, Merge Join, SCD wizard, Fuzzy Lookup), a control flow with precedence constraints and checkpoint restart, distributed transactions, project/package parameters, environment references, Scale Out workers, and a .NET Script Task escape hatch. The SSISDB catalog adds versioned project deployment, parameterized executions and five logging levels with per-row event capture. The same .dtsx packages lift-and-shift unchanged onto the Azure-SSIS Integration Runtime, so the estate is portable but never actually gets rewritten.

**Why people bounce off it:** SSIS fails in hexadecimal. The most-searched string in the product is 0xC0202009 / DTS_E_OLEDBERROR with 'Invalid character value for cast specification', which can mean a type mismatch, a bad parameter cast, a truncation or a driver problem, and the message never says which column. Siblings 0xC020902A, 0xC0047062 and DTS_E_PROCESSINPUTFAILED are equally undiagnostic. Metadata drift produces 'The external columns for <component> are out of synchronization with the data source columns', and the three knobs that hide or expose it — DelayValidation, ValidateExternalMetadata, Run64BitRuntime — interact in ways nobody remembers, which is why the Excel/ACE path yields 'The Microsoft.ACE.OLEDB.12.0 provider is not registered on the local machine' on the server but not the developer's laptop. ProtectionLevel is its own tarpit: EncryptSensitiveWithUserKey plus a different service account gives 'Failed to decrypt protected XML node DTS:Password with error 0x8009000B'. Parameter binding requires knowing object_type 20 vs 30 vs 50 in catalog.set_execution_parameter_value. Every column has an independent error disposition (Fail component / Redirect row / Ignore failure), so a package can 'succeed' while silently dropping rows. And debugging means opening a 4,000-line .dtsx XML in the exactly-right SSDT/Visual Studio version, which the person on call usually does not have installed.

**AI operator:** An SSIS Operator preloaded with skills to (a) parse .dtsx/.dtproj XML into a semantic graph of connection managers, dataflow components, column mappings and error dispositions, (b) query the SSISDB catalog views for execution history, the parameter values actually used, and the event message stream, (c) map hex error codes plus surrounding messages to a ranked root-cause list, and (d) emit repairs as surgical .dtsx diffs. It never edits blind: every proposed change is shown as a before/after on the specific component, then validated by running the patched package against a restored copy of the target database via catalog.create_execution with logging level raised, and only promoted after the test execution is clean. Second mode is archaeology: point it at a folder of 200 packages and it produces a lineage map (which package writes which table, which connection managers are shared, which packages are dead), flags packages relying on DelayValidation to mask schema drift, and generates a costed port plan to Azure-SSIS IR or Fabric pipelines. A third, read-only posture exists for shops that will not let an agent execute anything: it produces the diff and diagnosis as a ticket.

**Killer example:** At 02:14 the nightly LoadClaims.dtsx fails and the analyst on rotation types 'the claims load died again, what now'. The agent queries catalog.executions for the last run, pulls catalog.event_messages, and finds 0xC0202009 with 'Invalid character value for cast specification' raised by the OLE DB Destination on the ClaimDate column. The source column changed from datetime to varchar(10) holding 'dd/MM/yyyy', and the package's Data Conversion component converts with LocaleID 1033, so every date past the 12th of the month now fails the cast — which is why the job survived the first eleven nights of the month and died on the twelfth. Unprompted, it surfaces the real diagnosis: the source change was made three weeks earlier during a vendor upgrade, and the package only tolerated it because ValidateExternalMetadata is False and DelayValidation is True, so SSIS skipped the check that would have caught it at design time. It then notes that 41 other packages bind the same shared connection manager and 6 of them read that same table, listing them. It proposes two diffs: the correct one (explicit CONVERT with style 103 in the source query plus a Data Conversion locale fix) and the one the analyst is about to ask for (Redirect Row on ClaimDate into an error table). The analyst replies 'just make it not fail tonight, we'll fix it properly Monday' — the agent applies the redirect variant, runs it against a restored copy, shows 1,104 rows would land in the error table, and asks for confirmation before touching production. It also files the Monday ticket with the permanent fix and the list of 6 sibling packages already attached.

**Integration path:** The real API is the SSISDB catalog over TDS: catalog.create_execution, catalog.set_execution_parameter_value and catalog.start_execution to run packages (including @object_type 20/30/50 and the LOGGING_LEVEL parameter), plus catalog.executions, catalog.execution_parameter_values and catalog.event_messages to read what happened; permissions need the ssis_admin database role or sysadmin. Packages themselves are XML on disk (.dtsx) and can be edited directly or through the Microsoft.SqlServer.Dts.Runtime managed object model on Windows, and dtexec covers file-system deployments. Deployment goes via ISDeploymentWizard or catalog.deploy_project against .ispac files. Honest gap: there is no REST API and no headless designer, the .dtsx XML carries layout and cached external metadata that is easy to corrupt, and Script Tasks are precompiled binaries embedded in the package that cannot be safely rewritten without Visual Studio build tooling — so the product must confine itself to surgical, schema-validated XML edits proven by a real test execution, and refuse to touch Script Task bodies.

**Competitive note:** Microsoft ships zero AI for SSIS: Copilot in Fabric Data Factory generates new Fabric pipelines and explains Fabric pipeline errors, but it does not read .dtsx or SSISDB. SQL Server 2025's SSIS changes are subtractive, which means the install base is frozen in place rather than shrinking — a large, painful, permanently unattended surface the vendor has clearly decided not to invest in.

**Demand 5/5 · Buildability 4/5**

### 12. Veeam Backup & Replication (v13) `closed`

**Why it's powerful:** Veeam is the data-protection market leader with a customer base the company puts at 550,000+, and Backup & Replication is the product most of them actually operate. It does image-level backup for VMware, Hyper-V, Proxmox and Nutanix AHV, agent-based backup for Windows and Linux, backup copy jobs with GFS retention, Scale-Out Backup Repositories tiering to S3/Azure/Wasabi, hardened immutable repositories, Instant VM Recovery, CDP, SureBackup automated restore verification and inline malware detection. The v13 REST API (x-api-version 1.3-rev1) exposes jobs, sessions, repositories, restore operations and encryption passwords, and v13.0.1 substantially expanded that surface. It is the piece of infrastructure that decides whether a small business survives ransomware — and it is usually run part-time by a generalist.

**Why people bounce off it:** The console is a Windows MMC-style application whose job wizard runs nine-plus pages, with the same effective setting reachable from three places (job, then Storage, then Advanced, then the Backup tab). Retention is stated as 'restore points to keep', which is not days, and its meaning changes completely between forward-incremental, forever-forward-incremental and reverse-incremental modes because those determine when synthetic fulls happen; GFS on a backup job behaves differently from GFS on a backup copy job. SOBR adds placement policy across Performance, Capacity and Archive tiers, Copy versus Move mode, and a 30-day operational restore window that people do not realize is the reason nothing has offloaded to cloud in a month. The failure strings that end up pasted into forums are unreadable: 'Cannot use CBT: Soap fault ... [vim.fault.FileFault]', 'Failed to create snapshot (Microsoft Software Shadow Copy provider 1.0)', 'Error: Access is denied. Failed to open storage for read access', 'All backup proxies are busy'. Immutability is the cruelest trap — it requires a hardened Linux repository with single-use credentials and XFS reflink, and if you get it wrong the job description still says immutable while nothing is actually protected. Application-aware processing silently degrades to crash-consistent without guest credentials, so SQL logs never truncate and the LDF quietly eats the volume. SureBackup, the one feature that would tell you whether restores work, requires an application group plus a virtual lab with a proxy appliance and masquerade IPs, so almost nobody configures it. The net effect is a huge population of environments that report green and cannot actually restore.

**AI operator:** Preload skills for reading and explaining job configuration in plain English ('you keep 14 restore points, which is roughly 14 business days, not 14 calendar days'), designing and creating jobs from a stated RPO/RTO and retention requirement, decoding failed sessions by joining session logs with guest and hypervisor events, configuring SOBR tiering, standing up a hardened repository with an immutability verifier that actually proves the setting took, and building a SureBackup application group and virtual lab. Proposed changes render as a plain-language contract — 'daily at 22:00, forever-forward-incremental, 30 restore points, weekly synthetic full Saturday, GFS 12 monthly to Wasabi, immutable 30 days' — alongside the exact JSON it will POST. Apply defaults to a safety mode: create the job disabled, run it once against a single VM, show the session result, then enable. Second mode is a restore drill and audit loop: weekly it checks every protection group against the stated policy, performs an Instant Recovery of one VM into an isolated lab, tears it down, and emits a one-page evidence report suitable for a cyber-insurance questionnaire or an auditor. That report is what the buyer actually pays for, because it converts an invisible obligation into a document.

**Killer example:** An MSP technician says: 'The Friday backup for the Hyper-V cluster keeps failing and I have no idea why.' The operator reads the last six sessions and finds four failures all pinned to the same VM, SQL01, with 'Failed to create snapshot (Microsoft Software Shadow Copy provider 1.0). Details: Writer SqlServerWriter is in state FAILED_AT_FREEZE'. It correlates with guest disk telemetry and finds the SQL01 volume at 4% free, below what VSS needs for shadow storage — the writer is failing at freeze because there is nowhere to put the shadow copy. That alone would be a good answer, but it keeps going and surfaces two things nobody asked about. First, the SOBR has not offloaded anything to the Wasabi capacity tier in 19 days, because the operational restore window is set to 30 days and the performance extent got sealed when it crossed 95% — so the cloud copy everyone assumes exists does not. Second, the job description says 'immutable 30 days' but the target repository is a plain SMB share, so the immutability setting was never applicable and nothing on that repository is protected from an attacker with domain credentials. It proposes: free 60GB on SQL01 or cap VSS shadow storage, shorten the operational restore window to 7 days so offload resumes, and rebuild the target as a hardened Linux repository with single-use credentials. Follow-up: 'We can't add disk to SQL01 this week.' The operator offers the interim path — switch SQL01 to crash-consistent processing with a separate SQL-native transaction log backup — shows exactly which job settings change, and warns explicitly that this stops log truncation so the LDF will grow, offering to add a maintenance plan and a disk-space alert at 10% free. It ends by noting that the immutability gap is the one item it will not let close silently and asks to schedule the hardened-repo build.

**Integration path:** The VBR REST API listens on port 9419, issues a bearer token from /api/oauth2/token, and requires an x-api-version header (1.3-rev1 for v13); it covers jobs, sessions, repositories, restore points, restore operations, encryption passwords and malware detection. Coverage of job creation is still incomplete for some workload types, so the Veeam.Backup.PowerShell module remains the necessary fallback for the long tail of wizard settings and for SureBackup application groups and virtual labs — build REST-first with a PowerShell escape hatch on the same connector. Enterprise Manager's REST API is the right entry point for multi-tenant MSP scenarios and self-service restore. Auth should use a dedicated Veeam account with an operator-scoped role rather than a full backup administrator, since Veeam's RBAC can genuinely constrain what a restore operator may do. Honest gaps: VBR is an on-prem Windows product so a local connector is mandatory, and the richest failure detail lives inside session log text that must be parsed heuristically rather than queried — which is where the real engineering effort goes.

**Competitive note:** Veeam Intelligence, embedded in VBR 13 and Veeam ONE, answers technical questions against the documentation and KB, gives some environment-specific insight, and generates PowerShell/REST/YARA code — but it is capped at 200 questions per 24 hours per license and it advises rather than executes. Community projects like BackupPaw show the appetite for an actual operator. The open gap is performing the change safely, verifying it took effect, and running recurring restore drills that produce evidence.
