### 1. MySQL / MariaDB query and index tuning (performance_schema, sys schema, slow query log, EXPLAIN ANALYZE; Percona Toolkit, RDS/Aurora MySQL, Cloud SQL for MySQL) `open-source`

**Why it's powerful:** MySQL is the most widely deployed OSS database. performance_schema, sys, invisible indexes and EXPLAIN ANALYZE already hold everything needed to find and prove a fix.

**Why people bounce off it:** Diagnosing a slow app means reading a raw slow log, normalizing queries by hand, interpreting EXPLAIN trees (type=ALL, filesort, temporary), and weighing composite-index column order against write cost, buffer pool sizing and lock waits. Non-DBA developers give up and buy a bigger instance. PMM and Workbench show numbers but not what to change. MySQL has its own idioms (no partial indexes, invisible indexes, ONLINE DDL limits, gh-ost/pt-osc for big tables).

**AI operator:** A read-mostly DBA copilot with skills: digest-slow-queries (events_statements_summary_by_digest, sys.statements_with_full_table_scans), explain-and-rewrite, propose-index (checks redundant/unused indexes first), and test-invisible-index (create INVISIBLE, compare EXPLAIN ANALYZE, then flip). Emits the exact ALTER TABLE ... ALGORITHM=INPLACE, LOCK=NONE statement or a gh-ost command for huge tables, plus a rollback statement. Writes run only after approval with a before/after plan diff.

**Killer example:** User: 'Checkout got slow after Tuesday's deploy. Find out why and fix it without locking orders.' AI diffs today's digest table against yesterday's baseline and finds a new query (WHERE customer_id=? AND status IN (...) ORDER BY created_at DESC) doing a filesort over 4M rows. It sees (customer_id, created_at) exists but (customer_id, status, created_at) does not, and creates the new index INVISIBLE. It shows EXPLAIN ANALYZE dropping from 2.1s to 3ms on that session, and finds two redundant indexes on the same table. Because orders is 180GB it refuses in-place DDL and prints a gh-ost command with a rollback. After the user approves, it flips visibility, drops the redundant indexes and reports p95 latency for the digest before and after.

**Integration path:** Pure SQL over a standard MySQL connection. performance_schema and sys are built in; EXPLAIN FORMAT=JSON and EXPLAIN ANALYZE (8.0.18+) give machine-readable plans. Managed variants add RDS Performance Insights and Cloud SQL Query Insights APIs. Optional shell-outs to pt-query-digest, pt-online-schema-change and gh-ost. Ship as an MCP server or CLI with a read-only user by default and a separate DDL role. No UI scraping.

**Demand 5/5 · Buildability 4/5**

### 2. Stirling-PDF (self-hosted open-source PDF toolkit with REST API and Pipeline automation) `open-source`

**Why it's powerful:** 50+ operations in one self-hostable app (merge, split, OCR, compress, convert, watermark, flatten, redact, QR split, passwords), a full OpenAPI REST API and a JSON Pipeline feature. It runs on-prem, which matters for confidential documents.

**Why people bounce off it:** A wall of tool tiles with no guidance on order. Page-selection syntax ('1,3-5,2n+1,last') is arcane. Order matters (OCR before compress, flatten before watermark) and a wrong order silently degrades output. Compression levels and DPI are guesswork when a portal says 'max 2 MB'. Pipelines are hand-written JSON, so most users repeat the same 5-click sequence daily. Bulk jobs over 200 files are practically manual.

**AI operator:** A PDF desk operator. The user describes the input pile and the desired output. The AI inspects the files (page counts, scanned vs digital, sizes, blank separators), builds the correct ordered pipeline, runs it, verifies the result against stated constraints (size, searchable text, page count), and saves the pipeline as a named reusable recipe.

**Killer example:** User: 'I have 60 scanned client files in this folder, each batch separated by a blank page. Split them per client, OCR them, get each under 4 MB for the tax portal, and name each file after the client name on page 1.' AI detects 38 blank-page separators and splits into 38 PDFs. It OCRs first, then compresses with escalating levels until each is under 4 MB, reporting that 3 files needed grayscale to fit. It reads the client name from page-1 text, renames the files, flags 2 where the name was ambiguous for a human check, verifies every output is searchable, and saves the 'Tax portal intake' recipe so next season is one sentence.

**Integration path:** REST API with a published OpenAPI spec (single Docker container), API-key auth and pipeline JSON, all headless. The operator is a thin planner that calls endpoints, inspects outputs with pypdf/PyMuPDF for verification, and loops until the constraint is met.

**Demand 4/5 · Buildability 5/5**

### 3. Excel / Google Sheets report bursting (split one master workbook into per-recipient files, then export and send) `closed`

**Why it's powerful:** Excel and Sheets hold the company's numbers, and the monthly 'send each regional manager only their slice' job runs in nearly every finance, sales-ops and HR team. Formatting, formulas, charts and PDF export are already in the file.

**Why people bounce off it:** Neither app has 'split by column value and send'. People filter, copy, paste values and re-fix column widths by hand 20 to 200 times a month. The shortcuts leak data: hidden sheets, pivot caches, external links and defined names still carry other regions' numbers, and one mis-sent file is a breach. The only automation is hand-written VBA or fragile Power Automate flows.

**AI operator:** Treats the master file as a template. Reads the structure, asks which column is the key and who receives each slice, then builds one self-contained file per recipient: formatting kept, formulas converted to values where needed, charts and pivots re-pointed. Strips hidden sheets, cached pivot data and links, runs a leak check (no other key value appears anywhere in the output), optionally exports PDF, and creates Outlook or Gmail drafts for review. Stores the 'burst recipe' so next month is one sentence.

**Killer example:** User: 'Take Q3_Sales_Master.xlsx, make one file per Region with only that region's rows on Detail and Summary, remove the Commission tab, PDF the Summary, and draft an email to each regional manager from the Contacts sheet.' AI creates 7 workbooks, deletes the Commission sheet and the hidden Raw sheet, converts cross-sheet formulas to values, scans each output (including pivot caches and defined names) for the other 6 region names and finds none, exports 7 PDFs, and creates 7 drafts with the right attachment. It reports 'West had 0 rows on Detail, so I skipped it, confirm?' and saves the recipe for October.

**Integration path:** Headless OOXML editing (openpyxl / Open XML SDK) plus Microsoft Graph (Excel API, OneDrive upload, Outlook createDraft); on the Google side the Sheets, Drive and Gmail APIs. LibreOffice headless for PDF. Office Script / Apps Script fallback. No UI automation needed.

**Demand 4/5 · Buildability 4/5**

### 4. Redis / Valkey (Redis OSS, ElastiCache, Memorystore, Azure Cache; Redis Insight as the UI) `open-source`

**Why it's powerful:** Nearly every engineering org runs Redis as cache, queue, session store and rate limiter, and the whole admin surface is one protocol (SCAN, MEMORY USAGE, SLOWLOG, INFO, CONFIG).

**Why people bounce off it:** Nobody knows what is in it. Incidents are unbounded keys with no TTL, big and hot keys blocking the single thread, a wrong maxmemory-policy causing OOM write errors, and KEYS * in production. Finding the culprit means chaining SCAN, MEMORY USAGE, OBJECT FREQ, SLOWLOG and LATENCY DOCTOR by hand, and Redis Insight only lists keys. The Redis to Valkey move is postponed because teams cannot tell which commands, modules and clients they depend on.

**AI operator:** A cache-hygiene and migration operator. Skills: keyspace-census (non-blocking SCAN sampling grouped by key prefix into count, bytes, TTL coverage, type), find-big-and-hot-keys, slowlog-explain (maps slow commands to the app code pattern), eviction-policy-advisor, safe-ttl-backfill (batched, rate-limited EXPIRE with a dry run), and valkey-readiness-check (COMMAND INFO, MODULE LIST, client versions). Destructive operations need explicit confirmation.

**Killer example:** User: 'Redis memory keeps climbing and we hit OOM twice this month. What is eating it and can you clean it safely?' AI samples the keyspace and reports that 61% of 14GB is session:* keys with no TTL (about 9M keys, mostly users inactive for 90+ days). It shows a plan to EXPIRE them at 30 days at 2k keys/s, recommends maxmemory-policy volatile-lru in place of noeviction, and flags a 380MB sorted set (leaderboard:global) as a latency risk. After approval it runs the backfill while polling INFO memory and reports the freed memory. It then confirms no Redis-Stack modules are in use, so the instance is Valkey-8-compatible, and prices the ElastiCache Valkey switch.

**Integration path:** Redis protocol only: redis-cli or any client for SCAN, MEMORY USAGE, OBJECT, SLOWLOG, LATENCY, INFO, CONFIG, EXPIRE. Cluster topology via the client. ElastiCache and Memorystore APIs for engine changes. Read-only ACL user by default, write user only after approval. Runs as an MCP server or CLI with no server-side install.

**Demand 4/5 · Buildability 4/5**

### 5. Google Cloud Run (services, revisions, jobs; Cloud Build and Artifact Registry alongside) `closed`

**Why it's powerful:** The default way to run containers on GCP with scale-to-zero, revisions, traffic splitting and a declarative knative-style spec, backed by full Admin, Logging, Monitoring and Recommender APIs.

**Why people bounce off it:** Marketed as 'just deploy a container', but production use needs a dozen interacting settings: CPU allocation, min/max instances, concurrency, startup CPU boost, gen1/gen2, VPC egress, Cloud SQL, Secret Manager mounts, invoker IAM vs allUsers, ingress, and revision-tag traffic splits. The console hides most of them, and errors ('container failed to start and listen on PORT', 403s, cold starts, min-instance bills) send users to Stack Overflow.

**AI operator:** A Cloud Run operator with skills: deploy, diagnose-startup-failure (Cloud Logging for the revision, PORT binding, OOM, missing secret permissions), wire-private-networking, canary-rollout (tag, split 5/95, watch error rate, promote or roll back), cost-tune (billable instance-seconds vs concurrency and min-instances), and iam-audit. Every change is shown as a gcloud/YAML diff first.

**Killer example:** User: 'Our API on Cloud Run times out on the first request after quiet periods and the bill doubled. Fix both.' AI reads the service spec and sees CPU throttled outside requests with min-instances=0, plus a Node app doing synchronous startup work. It also finds a second service with min-instances=10 sitting idle at night. It proposes startup-cpu-boost and min-instances=1 on the API and drops the other service to 1 with a Cloud Scheduler warm-up. It shows the monthly cost delta, deploys as a tagged no-traffic revision, runs a latency test against the tag URL, and shifts 100% of traffic after approval.

**Integration path:** Cloud Run Admin API v2 for CRUD on services, revisions, jobs and IAM; gcloud run services describe --format=export for the YAML spec; Cloud Logging, Monitoring and Recommender APIs for diagnosis. Scoped service-account auth (run.admin, logging.viewer). Ships as an MCP server or CLI plugin; Google's own MCP server is a thin wrapper with no diagnosis or cost reasoning.

**Demand 4/5 · Buildability 4/5**

### 6. imapsync (open-source IMAP mailbox migration CLI) for moving mailboxes between Gmail/Workspace, Microsoft 365, GoDaddy, cPanel, Zoho and similar hosts `open-source`

**Why it's powerful:** The standard tool for moving mail between any two IMAP servers: resumable, idempotent, handles hundreds of mailboxes, with folder mapping, regex renaming, size and date filters. It is the engine under many paid migration services.

**Why people bounce off it:** Over 150 flags and no UI. Real migrations need folder-name translation (Gmail's [Gmail]/Sent Mail vs INBOX.Sent vs Sent Items), Gmail's labels-as-folders duplication, provider rate limits, app passwords or OAuth, and attachment size rejections. Verifying nothing was lost means comparing counts folder by folder. MX cutover, SPF/DKIM, contacts and calendar live outside the tool. One wrong flag gives duplicated or missing mail.

**AI operator:** Interviews the user (hosts, mailbox list, cutover date), picks the right flag set for the provider pair, runs a dry run, then a throttled live pass and a delta sync at cutover. Produces a per-mailbox reconciliation report (folders, counts, size, skipped items with reasons) and drafts the DNS change list (MX, SPF, DKIM, DMARC) and a staff announcement.

**Killer example:** User: 'Move our 14 staff mailboxes from GoDaddy cPanel mail to Google Workspace this weekend. Keep folder structure, skip Spam and Trash.' AI reads the user CSV, tests logins, runs --dry on all 14, and flags that two mailboxes have 31 messages over the 25 MB limit. It maps INBOX.Sent to [Gmail]/Sent Mail, runs overnight with --maxbytespersecond, and does a delta pass Sunday morning. It reports '13 of 14 identical, 1 has 6 messages rejected as oversize, list attached' and outputs the exact MX and SPF records to publish.

**Integration path:** imapsync CLI with a CSV of host/user/password lines, headless, structured logs to parse. Optional Google Admin SDK and Microsoft Graph for target mailboxes and app passwords, registrar or Cloudflare DNS APIs for cutover. A thin Python or Node wrapper orchestrates runs and builds the reconciliation report.

**Demand 4/5 · Buildability 4/5**

### 7. Twenty CRM (twentyhq/twenty, open-source CRM) `open-source`

**Why it's powerful:** The fastest-growing open-source Salesforce/HubSpot alternative (self-hostable, Postgres) with custom objects, views, workflows, GraphQL and REST APIs and webhooks. Teams are leaving per-seat pricing.

**Why people bounce off it:** The wall is migration and data-model design. Moving from HubSpot, Pipedrive or Salesforce means recreating objects, properties, pipelines and relations by hand, mapping CSVs, deduping, and rebuilding views and workflows. The schema is flexible but unopinionated, so people stall at 'what should my objects be?' or import with wrong relation mappings. Re-running an import creates duplicates.

**AI operator:** A migration-and-setup operator. Reads an export or live API of the old CRM, proposes an equivalent Twenty data model, creates objects, fields and relations via the Metadata API, and imports records in dependency order with an idempotent external-ID key. Then generates saved views and workflows from a description. Keeps a reversible plan file and dry-run report.

**Killer example:** User: 'We're leaving Pipedrive. Here's the export zip and our API token. Keep deals, people, orgs and the Source and Plan Tier custom fields, and give me a Kanban of open deals per owner.' AI creates Company, Person and Opportunity with the two custom fields as SELECT types using the values it found. It imports 14k people deduped on lowercase email and reports 212 merged duplicates and 31 orphaned deals with no org. It builds the Kanban view and hands back an undo manifest of every created ID. Re-running the same import changes nothing.

**Integration path:** Documented Metadata GraphQL API for objects, fields and relations, Core GraphQL/REST for records, API keys, docker-compose self-host. Source CRMs have standard APIs (HubSpot CRM v3, Pipedrive, Salesforce describe). Solo MVP: local Twenty container plus CSV/JSON importer.

**Demand 4/5 · Buildability 4/5**

### 8. LeadSquared (India / SEA / MENA sales-execution CRM) `closed`

**Why it's powerful:** Widely used SMB and mid-market CRM in India, SEA and MENA for admissions, lending, insurance, real estate and healthcare. Lead capture, activity tracking, automation, telephony/WhatsApp and smart views, with an Execution API across leads, activities and opportunities.

**Why people bounce off it:** Large teams run on config the admin barely understands: stages and sub-statuses, custom activity types, assignment rules, Smart Views with nested AND/OR filters, automation cards and scoring. Counselors cannot build their own lists or reports. Automations are fragile and untouched. Duplicate and misrouted leads are rampant, and management asks for ad-hoc numbers that need an analyst.

**AI operator:** For reps and managers: ask for lead lists and pipeline numbers (lead search and advanced-search APIs) and bulk-update owner, stage or tags after a confirmation step. For admins: audit config, explain automations in plain language, flag conflicts and draft changes. Automation-card creation is mostly UI-only, so the admin side starts as read, explain and recommend.

**Killer example:** User (admissions manager): 'Show me everyone who applied via Facebook in the last 14 days, has no call logged, and is on Priya's team. Reassign the ones from Kerala to Arun and tag NeedsFollowup.' AI runs the search and finds 87 matches, shows the 23 from Kerala, and asks 'Reassign these 23 to Arun?'. On confirmation it updates the leads, saves a rollback list, and sends a one-line summary to the manager's WhatsApp.

**Integration path:** Documented REST Execution API with access and secret keys covering leads, activities, opportunities, tasks, users and search, plus webhooks and a Postman collection. WhatsApp/Telegram front end is the go-to-market wedge. Solo dev can build the data operator on a trial account.

**Demand 4/5 · Buildability 4/5**

### 9. OpenMetadata (with DataHub as a second connector) `open-source`

**Why it's powerful:** One catalog ingesting 80+ sources with column-level lineage, glossary, tags, data contracts, ownership, PII classification and a policy engine. Fully API-driven and Apache-2.0.

**Why people bounce off it:** A catalog is only as good as its curation, and curation is a thankless grind: writing descriptions, assigning owners and tags, linking glossary terms, writing ingestion YAML recipes. Most rollouts stall near 10 percent description coverage, so the catalog looks empty and analysts stop opening it.

**AI operator:** A chat operator wrapping the REST API and Python SDK: bulk PATCH of descriptions, owners, tags, glossary terms and tiers, ingestion pipeline creation, lineage edges and data contracts. Samples column values and reads dbt SQL and BI query history to draft descriptions and PII classifications. Always works through a review queue (proposed-changes diff) that a steward approves.

**Killer example:** User: 'Our finance dashboard revenue does not match the CFO's number. Find what feeds it, who owns each upstream table, and fill the missing descriptions on the gold layer.' AI walks column-level lineage from the dashboard to 3 upstream tables and finds a stale one with no owner. It drafts descriptions for 140 undocumented columns from dbt SQL and samples, tags 6 as PII, and suggests owners from the most frequent query authors. It opens a review batch of 150 proposed edits for one-click steward approval.

**Integration path:** Full REST API (OpenAPI, JWT bot tokens), openmetadata-ingestion Python SDK and CLI, Docker Compose self-host. DataHub offers GraphQL and acryl-datahub SDK. MVP is an MCP server with about 25 tools plus a proposed-change staging table.

**Demand 4/5 · Buildability 4/5**

### 10. ProPresenter 7 (Renewed Vision): live presentation and lyric software used by churches, venues and corporate AV teams `closed`

**Why it's powerful:** Drives multi-output live shows: lyrics, video backgrounds, countdowns, lower thirds, stage displays, NDI/SDI and cue-triggered macros. Used by tens of thousands of churches and venues.

**Why people bounce off it:** Run mostly by weekly volunteers. They juggle libraries vs playlists, themes, looks, macros, timers, stage layouts and CCLI lyric imports. Turning a bulletin into a correctly sequenced, themed show is hand-built every Sunday, and when the volunteer leaves nobody understands the setup.

**AI operator:** A 'Service Producer' that takes the week's plan (Planning Center order, a Google Doc or pasted bulletin), finds or imports lyrics, matches songs to library files, creates missing ones with house theme and line-break rules, assembles the playlist with looks, macros and timers, and writes operator notes. During the service it accepts live commands and keeps a rehearsal checklist.

**Killer example:** User: 'Sunday plan is in Planning Center. Build the playlist with 4 songs, the sermon title slide in the new series theme, a 5-minute pre-service countdown, and put the offering announcement on the lower-third look.' AI reads the plan, finds three songs in the library, creates the fourth from licensed lyrics with 2-line slide breaks, applies the 'Fall Series' theme, adds the timer, builds the playlist in order, and returns a run sheet with one warning (a missing background video).

**Integration path:** Documented local REST/HTTP API (playlists, presentations, looks, macros, timers, stage messages) plus WebSocket status. .pro files are protobuf with community schemas for headless slide authoring. Planning Center Services REST API for the plan. LAN-side connector plus chat UI; the API-vs-protobuf boundary is the main early risk.

**Demand 4/5 · Buildability 4/5**

### 11. Trendyol Seller Center (Marketplace Integration API), with Hepsiburada as a second connector `closed`

**Why it's powerful:** Turkey's dominant marketplace with 100k+ active sellers and an API covering products, price/stock, orders, shipment, claims and Q&A.

**Why people bounce off it:** Dynamic category attribute requirements, brand and barcode matching, commission and campaign tariffs, frequent listing rejections and Turkish-language content rules. Q&A and claims pile up in the Seller Center UI.

**AI operator:** Resolves each product from a Shopify, WooCommerce or Excel source to the correct Trendyol category, brand ID and required attributes, rewrites content in Turkish marketplace style, submits listings, diagnoses rejections, syncs price and stock, and drafts replies for the claims and Q&A queue.

**Killer example:** User (Turkish or English): 'Upload my 200 new sneakers, reject nothing, and answer today's customer questions about sizing.' AI maps each SKU to category and brand ID, fills required attributes (size, color, material), and submits. Of 12 rejections it fixes 9 (wrong barcode format, image ratio) and lists 3 for human input. It drafts sizing answers from each product's size chart and queues them for approval.

**Integration path:** Trendyol Seller REST API (Basic auth with seller ID, API key and secret) for brands, categories, attributes, products, price-inventory, orders, claims and Q&A. TS or Python service; Hepsiburada adapter later. MVP is the category-attribute resolver plus a rejection-explainer loop.

### 12. Outlook Contacts + Google Contacts + CardDAV address books (dedupe, normalization, groups and distribution lists) `closed`

**Why it's powerful:** The address book feeds mail merge, invites, distribution lists, CRM imports and phone sync, and for many small businesses it is the real customer database.

**Why people bounce off it:** Built-in tools do almost nothing: Outlook dedupes only exact emails at import, Google's 'Merge & fix' misses most real duplicates, merges are all-or-nothing. Phone and name formats diverge, groups and labels differ across systems, and there is no preview or real undo, so nobody dares bulk-edit.

**AI operator:** Pulls every source into one working set, builds fuzzy match clusters, shows each proposed merge with a field diff and confidence, normalizes phones to E.164, splits person and company records, rebuilds groups from plain-language definitions, and writes back with a full restore snapshot.

**Killer example:** User: 'My Outlook, Gmail and iPhone contacts are a mess. Merge duplicates, fix phone numbers to +44, and make a group called Wedding Guests from everyone with a note containing "wedding".' AI: 'Found 412 duplicate clusters. 380 are safe auto-merges, 32 need your eyes.' It shows the 32 diffs, applies approved merges, normalizes 1,140 numbers, creates the group in Outlook and a label in Google, and leaves a restore snapshot.

**Integration path:** Microsoft Graph contacts API, Google People API (contactGroups, batchUpdate), CardDAV (Radicale, Nextcloud, iCloud), vCard/CSV fallback. Local fuzzy-matching service with snapshot store. No UI automation.

**Demand 4/5 · Buildability 4/5**
