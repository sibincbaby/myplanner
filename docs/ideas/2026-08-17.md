### 1. PostgreSQL performance tuning and configuration `OSS`

**Why it's powerful:** Postgres is now the default database of the startup and mid-market world and increasingly of the enterprise, and it ships a diagnostic surface as rich as any commercial engine: `EXPLAIN (ANALYZE, BUFFERS)` with per-node actual-vs-estimated rows, `pg_stat_statements` ranking every normalized query by total and mean execution time and buffer traffic, `pg_stat_activity` with `wait_event_type`/`wait_event` and `pg_blocking_pids()` for blocking chains, `pg_stat_user_tables` for dead tuples and last-autovacuum times, `auto_explain` for capturing slow plans in production, and thirty-odd planner and memory knobs that routinely produce order-of-magnitude differences on identical hardware. Everything needed to fix a slow Postgres is already inside the database, reachable over the same connection the app uses.

**Why people bounce off it:** Postgres has no SSMS, no wizard, no opinion — the diagnostic surface is a set of catalog views a developer has to already know exists. The typical victim is a team with no DBA whose API "got slow this month": they can see the query, and they stop there. Reading an EXPLAIN plan means knowing that `rows=1 ... actual rows=1843000` is the whole story and that the fix is `ANALYZE` or a raised `default_statistics_target`, not an index; that a Nested Loop over a mis-estimated outer relation is a planner failure and not a query bug; that a Seq Scan is sometimes correct. The knobs are worse: `work_mem` is *per sort node per connection*, so the "obvious" fix of raising it globally is how teams OOM their instance; `shared_buffers` past ~40% of RAM makes things slower; `random_page_cost` still defaults to 4.0 as if the disk were spinning rust. And the silent killer is autovacuum — nothing in Postgres ever tells you `n_dead_tup` is at 60% of the table, that your index is bloated, or that `age(datfrozenxid)` is walking toward wraparound, until the day it does.

**AI operator:** A read-only-by-default companion that connects with a scoped login and carries skills for "why is it slow right now" triage (top `wait_event_type`, active longest-running queries, blocking tree via `pg_blocking_pids()`), regression hunting across `pg_stat_statements` snapshots, plan reading translated into plain-English root cause ("the planner expected 1 row and got 1.8 million because statistics on `orders.status` are stale"), index design that **de-duplicates against existing indexes** rather than stacking new ones, autovacuum and bloat health, and configuration review sized against the machine's actual RAM and core count. The safety model is the product: diagnostics run freely; every mutating suggestion is emitted as reviewable SQL with a before/after `EXPLAIN` cost comparison, `CREATE INDEX` is always `CONCURRENTLY` with the estimated build time and write-amplification cost stated, `ALTER SYSTEM` changes are shown with the required reload-versus-restart flag and a revert statement, and nothing is executed without explicit approval. A strict read-only mode makes it safe to hand to the application developers who caused the problem.

**Killer example:** User says: *"The orders dashboard used to load instantly and now it takes eight seconds — what happened?"* → AI pulls `pg_stat_statements` ordered by `total_exec_time`, isolates the dashboard's aggregate query at 7.9 s mean, runs `EXPLAIN (ANALYZE, BUFFERS)` and shows a Nested Loop whose outer estimate was 1 row against 1.8 million actual, traces it to `pg_stat_user_tables` showing `last_analyze` eleven weeks old on a table that has doubled since, runs `ANALYZE orders` (zero-risk, no lock), re-plans to a Hash Join at 240 ms, then separately proposes `CREATE INDEX CONCURRENTLY idx_orders_status_created ON orders (status, created_at) WHERE status <> 'archived'` as the durable fix — with the note that autovacuum is also 40 million dead tuples behind on the same table and a suggested per-table `autovacuum_vacuum_scale_factor = 0.02`.

**Integration path:** Plain SQL over any standard driver (psycopg/asyncpg/pgx) — `pg_stat_statements`, `pg_stat_activity`, `pg_stat_user_tables`, `pg_stat_user_indexes`, `pg_locks`, `pg_settings`, `EXPLAIN (FORMAT JSON)` for machine-readable plans — plus the `auto_explain` and `pgstattuple` extensions where installed, `ALTER SYSTEM` + `pg_reload_conf()` for configuration, and `psql`/`pg_dump` for anything else. Works unchanged against RDS, Aurora, Cloud SQL, Supabase and Neon (with `ALTER SYSTEM` swapped for the provider's parameter-group API). No vendor, no API key, no partner program, no approval — the highest-buildability idea in this batch, and the install base is effectively every company built after 2015.

**Demand 5/5 · Buildability 5/5**

### 2. Microsoft Power Apps + Dataverse (canvas apps, model-driven apps, security roles) `closed`

**Why it's powerful:** Power Apps ships inside most Microsoft 365 business tenants, which means tens of millions of seats already have it. Canvas apps give pixel-level UIs driven by Power Fx, a genuine Excel-derived functional language with delegation-aware data access; model-driven apps generate complete CRUD applications straight off the Dataverse schema with business rules, forms, views and workflow; Dataverse itself is a real relational platform with lookups, choice columns, calculated and rollup columns, row-level and field-level security, plugins, and audit. It is the fastest route from "we track this in a spreadsheet" to a governed internal application — and every artefact is source-controllable.

**Why people bounce off it:** Three specific walls, all of which stop non-developers cold. First, Power Fx errors are useless: `Name isn't valid. This identifier isn't recognized.` names neither the control nor the data source that broke, and the delegation warning — a small blue squiggle explaining that your filter will silently only consider the first 500 rows — is the single most common cause of an app that "works in testing and lies in production". Second, the Dataverse security model is a matrix of eight privileges (Create/Read/Write/Delete/Append/AppendTo/Assign/Share) crossed with five access levels (None/User/Business Unit/Parent-Child/Organization) per table, rendered as a grid of tiny concentric-circle icons; admins click until the app stops erroring, which means they land on Organization-level Read and quietly expose every row to everyone. Third, model-driven navigation lives in a completely separate Site Map designer most builders never discover, so apps ship with tables no one can reach. Layer on solution layering — managed versus unmanaged, and the "this component is managed by another solution" deploy failure — and the citizen developer the platform was sold to is stuck.

**AI operator:** An environment-connected operator that treats the app as source, not as a canvas. Pre-loaded with the Power Fx function surface and its delegation table per connector, the Dataverse metadata schema (`EntityDefinitions`, `Attributes`, relationships, option sets), the security-role privilege/access-level model, and solution packaging rules. It unpacks the `.msapp` to YAML with `pac canvas unpack`, edits formulas as text, repacks and reimports — which is what makes canvas-app authoring tractable at all — and drives Dataverse schema and roles through the OData Web API. Two skills carry the product: a **delegation auditor** that walks every formula in an app and flags each non-delegable filter against a table with more than 2,000 rows, with the rewritten delegable version; and a **security-role explainer** that answers "who can see this row and why" by resolving the user's roles, business unit and team memberships into a plain-English verdict. Schema and role writes render as a diff first — dropped columns and lowered access levels require typed confirmation — and everything deploys to a dev environment and exports as an unmanaged solution before anything touches production.

**Killer example:** User says: *"Our contract tracker only ever finds the first 500 vendors when Legal searches, and I need Legal to edit contracts but never see the Cost column."* → AI unpacks the app, finds `Filter(Contracts, StartsWith(Vendor, SearchBox.Text))` on a 14,000-row table, rewrites it to the delegable `Filter(Contracts, StartsWith(VendorName, SearchBox.Text))` against an indexed text column and flags two more non-delegable `Sort` calls it found on the way; then creates a Dataverse security role with Write at Business Unit scope on the Contracts table, creates a field-security profile masking `cst_cost`, assigns both to the Legal team via the Web API, and shows a before/after table of exactly which users gain and lose which access — then repacks the `.msapp` and imports it as solution version 1.4 into the dev environment for a smoke test before offering the production export.

**Integration path:** Dataverse Web API (OData v4 at `https://{org}.crm.dynamics.com/api/data/v9.2/` — `EntityDefinitions`, `Attributes`, `roles`, `roleprivilegescollection`, `AddPrivilegesRole`, `fieldsecurityprofiles`), Power Platform CLI (`pac canvas unpack/pack`, `pac solution export/import/pack`, `pac admin`), Power Platform Admin API for environments and DLP policies, and Entra ID app registration with a service principal for auth. The `.msapp` → YAML round trip is officially supported and is the crux of the whole build; the honest gap is that model-driven form and Site Map XML is fiddlier to generate cleanly than canvas YAML.

**Demand 5/5 · Buildability 4/5**

### 3. Apple App Store Connect + Google Play Console (release, signing and store compliance) `closed`

**Why it's powerful:** Between them these two consoles are the sole gate on every mobile app on earth. App Store Connect handles TestFlight internal and external groups, phased release percentages, per-locale metadata and screenshots, StoreKit in-app purchases and subscription groups, certificates, bundle IDs and provisioning profiles, and privacy declarations — all behind a well-designed REST API. Play Console handles internal/closed/open/production tracks with staged rollout fractions, Play App Signing, pre-launch reports run on real devices, Android vitals with per-release crash and ANR rates, the Data safety declaration, and target-API-level policy enforcement, behind the Android Publisher and Play Developer Reporting APIs. Getting a release out is a solved, automatable problem — for the teams that have already paid the tuition.

**Why people bounce off it:** Nobody bounces off shipping the happy path; they bounce off the rejection loop, and the rejections are deliberately vague. On Apple: `ITMS-91053: Missing API declaration` because a transitive SDK calls a required-reason API and the `PrivacyInfo.xcprivacy` manifest doesn't list `NSPrivacyAccessedAPICategoryUserDefaults`; `No profiles for 'com.acme.app' were found` because Xcode's Automatic signing and the profile store in App Store Connect disagree; the App Privacy questionnaire, a grid of data types crossed with collected / linked to identity / used for tracking, where one wrong checkbox is a multi-day resubmission. On Google: `Your app has policy issues: Permissions declaration form mismatch` with no line-level diff; a Data safety form of roughly thirty nested toggles that must agree exactly with what the manifest and the SDKs actually do or the app is suspended; and four testing tracks with different rollout semantics, where "closed testing" and "internal testing" are one dropdown apart from a production push. The pain is felt by literally every mobile team, and small teams pay it in whole days.

**AI operator:** One operator, both stores, because a release is one event. Pre-loaded with the App Store Connect and Android Publisher object graphs, the required-reason API list and `PrivacyInfo.xcprivacy` schema, the Play Data safety CSV column dialect, and a rejection-code knowledge base that maps ITMS and Play policy strings to concrete causes. Its highest-value skill runs **before** submission: it scans the built binary and Podfile/Gradle dependency graph, derives which data types are actually collected and which required-reason APIs are actually called, and generates both the privacy manifest and the Data safety CSV from evidence instead of from the developer's memory — then diffs them against what is currently declared in each console and reports every mismatch that would trigger a rejection. Around that sit release skills: promote a build to a TestFlight group with release notes generated from the git log, drive a staged Play rollout, and hold a **rollout watchdog** that polls Play Developer Reporting vitals and halts or rolls back if the crash-free rate breaches a stated floor. Every submit-for-review, `edits.commit`, and rollout increase is dry-run first as "here is exactly what will change" and requires explicit confirmation.

**Killer example:** User says: *"Get build 214 out to the beta testers, and if Apple is going to reject it again, tell me now."* → AI runs the pre-flight: parses the archive's linked SDKs, finds `UserDefaults` and file-timestamp required-reason API usage plus an ad SDK that collects IDFA, notices `PrivacyInfo.xcprivacy` declares neither, generates the corrected manifest entries and the matching Play Data safety CSV rows, and reports "this build would have failed with ITMS-91053"; after the fix, it uploads via Transporter, POSTs the build into the `Beta-iOS` betaGroup, PATCHes `betaBuildLocalizations` with release notes assembled from the 17 commits since tag `v3.8.0`, submits for beta review — then on the Android side uploads the AAB through `edits.insert` → `edits.bundles.upload` → `edits.tracks.update` at `userFraction: 0.1` on production, commits, and arms a watchdog that will roll back to 0% if the 24-hour crash-free rate drops below 99.2%.

**Integration path:** App Store Connect API (`api.appstoreconnect.apple.com/v1` — `builds`, `betaGroups`, `betaBuildLocalizations`, `appStoreVersions`, `reviewSubmissions`, `appStoreVersionPhasedReleases`, `profiles`, `certificates`, `inAppPurchases`) authenticated with an ES256 JWT signed by a `.p8` key (issuer ID + key ID), plus `xcrun altool`/Transporter for binaries and `xcodebuild -exportArchive` locally. Google Play Developer API (`androidpublisher/v3` — `edits.insert`, `edits.bundles.upload`, `edits.tracks.update`, `edits.commit`) with a service-account JSON key, plus the Play Developer Reporting API for vitals. Honest gap: the Play Data safety declaration has no write API — it is CSV import in the console — so the operator generates the CSV and hands it over rather than submitting it, and Apple's App Privacy answers are likewise console-side.

**Demand 5/5 · Buildability 4/5**

### 4. Firebase console (Security Rules, Remote Config, Crashlytics, App Distribution) `closed`

**Why it's powerful:** Firebase is the backend for a genuinely enormous population of mobile and web apps, most of them built by small teams with no backend engineer. Firestore and Realtime Database Security Rules are a real declarative authorization language with request context, resource shape, `get()`/`exists()` cross-document lookups and custom claims; Remote Config is server-driven feature flagging with conditional targeting by app version, audience, user property and percentage rollout, now with rollouts tied to health metrics; Crashlytics does stack-similarity crash grouping with velocity alerts; App Distribution handles pre-release builds. One console holds authorization, feature flags and production health for the whole app.

**Why people bounce off it:** Security Rules are the wall, and they fail in the single worst direction: silently open. The default template ships with a hard date-limited `allow read, write: if true;`, and when it expires the app breaks, so the overwhelmingly common fix is to put `if true` back permanently. The concepts that would prevent that are non-obvious — that rules are **not filters**, so a `list` query that doesn't itself constrain to the permitted subset is rejected wholesale with `Missing or insufficient permissions` and no indication of which clause failed; that `resource.data` is the existing document and `request.resource.data` is the incoming one, and confusing them is how a rule that looks like ownership enforcement lets anyone rewrite the `ownerId` field; that every `get()` in a rule costs a billed read and counts against a ten-lookup limit. The Rules Playground exists and almost nobody runs it. Remote Config compounds it: conditions are evaluated top-down with first-match-wins, so a broad condition placed above a narrow one silently swallows it, and there's no simulator showing which users get which value.

**AI operator:** A repo- and project-connected operator whose whole discipline is "never deploy a rule you haven't proven". Pre-loaded with the Rules language semantics, an over-permissive-pattern linter (`if true`, `if request.auth != null` as the sole guard, writes that don't pin the owner field, unbounded `list` rules), the Remote Config REST object model including ETag concurrency, and Crashlytics/BigQuery schema. It authors or repairs `firestore.rules` from a plain-English description of who may do what, then **proves it** by generating a `@firebase/rules-unit-testing` suite of allow-and-deny cases and running it against the local emulator before `firebase deploy --only firestore:rules` — a change that fails a deny case is never deployed. For flags it reorders and explains Remote Config conditions, shows the resolved value for a set of representative user profiles before publishing, and can drive percentage rollouts with an auto-rollback wired to a Crashlytics velocity threshold. Rules deploys and config publishes always require confirmation, and the operator refuses to deploy a ruleset that widens access without an explicit typed override.

**Killer example:** User says: *"Lock our orders collection down so a customer only ever sees their own orders and can't change who owns one — and make sure I haven't broken the support team's dashboard."* → AI writes `match /orders/{id} { allow read: if request.auth.uid == resource.data.ownerId || request.auth.token.support == true; allow create: if request.auth.uid == request.resource.data.ownerId; allow update: if request.auth.uid == resource.data.ownerId && request.resource.data.ownerId == resource.data.ownerId; }`, notices the support dashboard issues an unconstrained `collection('orders')` list query that the new rules will reject with `Missing or insufficient permissions`, generates the emulator test suite covering owner-read-allowed, stranger-read-denied, owner-cannot-reassign, and support-list-allowed, runs it, reports 11/12 passing with the support list failing, fixes the dashboard query to `.where('ownerId','==',uid)` for customers while the support path relies on the custom claim, re-runs green, and only then deploys.

**Integration path:** Firebase CLI (`firebase deploy --only firestore:rules`, `firebase emulators:exec`, `firebase appdistribution:distribute`), `@firebase/rules-unit-testing` plus the Firestore emulator for the proof step, the Security Rules Management API (`firebaserules.googleapis.com` — rulesets and releases, including a `TestRuleset` method), the Remote Config REST API (`firebaseremoteconfig.googleapis.com/v1/projects/{p}/remoteConfig`, ETag `If-Match` on publish), and the Firebase Admin SDK, all under a service account. Honest gap: Crashlytics has no public read API — issue data comes via the BigQuery export or Firebase Alerts through Cloud Functions — so the crash-health side of the watchdog needs BigQuery enabled.

**Demand 5/5 · Buildability 4/5**

### 5. Postman (collections, environments, scripts, mocks, monitors) `closed`

**Why it's powerful:** Postman is the default place an API is explored, documented and tested at nearly every backend, mobile and QA team on the planet — tens of millions of registered users. It carries collections with folder hierarchies and inherited auth, environments and variable scoping, a full JavaScript sandbox for pre-request and test scripts (`pm.test`, `pm.expect`, `pm.sendRequest`), the collection runner with data files, mock servers that respond from saved examples, scheduled monitors that turn a collection into uptime-and-contract checking, and Flows for chaining. Crucially the whole thing is addressable as JSON through a public API and runnable headless via Newman, so a machine can author it end to end.

**Why people bounce off it:** The QA analyst and the junior backend dev who live in Postman hit two exact walls. First, variable resolution order — local > data > environment > collection > global — is invisible, so a request that silently uses the wrong `{{baseUrl}}` produces a confusing 404 against staging rather than any error naming the culprit, and the newer Vault-versus-environment split for secrets means nobody in a shared team workspace can say where a credential actually lives. Second, `pm.test()` requires JavaScript, which is precisely the skill the person doing manual API testing does not have; so collections across the industry are thousands of saved requests with zero assertions, which means they document the API and verify nothing. Monitors and mock servers sit one tab away from all of it and go unused for the same reason: configuring them means understanding which environment a scheduled run will resolve against.

**AI operator:** A workspace-connected operator that authors the collection nobody has time to write. Pre-loaded with the Postman collection v2.1 schema, the `pm.*` sandbox API, variable-scope resolution rules, OpenAPI-to-collection mapping, and the monitor/mock configuration model. Core skills: generate a full collection with folders, examples and environments from an OpenAPI spec or from a handful of observed requests; **write assertions from plain language** ("status is 200, `userId` is present, response under 400 ms, and the schema matches the spec") into real `pm.test` blocks including JSON-schema validation; chain requests by capturing values into `pm.collectionVariables` so a login → create → fetch → delete flow actually runs unattended; trace which scope supplied a variable's value when a request misfires; and stand up a mock server plus a monitor on a schedule. It validates its own output by running the collection through Newman locally and reporting pass/fail before publishing, and any overwrite of an existing collection, environment or monitor schedule is shown as a diff and confirmed — with secrets never written into collection JSON, only referenced.

**Killer example:** User says: *"Take our OpenAPI file, make me a real test suite for the checkout flow, and ping me if it ever breaks in staging."* → AI imports the spec via the Postman API, builds a `Checkout` folder with the six endpoints and per-endpoint examples, writes a chained run — `POST /auth/login` capturing the token into a collection variable, `POST /carts`, `POST /carts/{id}/items`, `POST /checkout` — each with `pm.test` assertions for status, response-time budget and JSON-schema conformance against the spec's response schema, creates a `staging` environment with `baseUrl` and a Vault-referenced API key, runs the whole thing through Newman and reports 18/19 passing with one schema drift (`order.total` returns a string, spec says number), then creates a monitor on a 60-minute schedule against the staging environment with failure notifications.

**Integration path:** Postman API (`api.getpostman.com` — `/collections`, `/environments`, `/monitors`, `/mocks`, `/workspaces`, `POST /import/openapi`) with an API-key header, plus the Newman CLI for local and CI execution and the collection v2.1 JSON schema as the authoring format. No partner program, no approval, and the free tier is enough to build against — the main constraint is API rate limits on large workspaces.

**Demand 5/5 · Buildability 4/5**

### 6. Slack (Workflow Builder, custom steps, Enterprise Grid admin) `closed`

**Why it's powerful:** Slack is where a very large share of the working world's coordination happens, and underneath the chat it is a real automation and governance platform. Workflow Builder chains triggers (form submit, emoji reaction, channel join, schedule, webhook) to steps, and since the Deno-based automation platform arrived, developers can publish **custom steps** written in TypeScript that non-technical colleagues then drag into their own workflows. Enterprise Grid adds org-wide channel management, Information Barriers, SCIM provisioning, workspace-scoped policy, and an audit-logs API. Canvas puts structured, editable documents inside channels.

**Why people bounce off it:** Two distinct populations bounce for two distinct reasons. Ordinary users hit Workflow Builder's webhook and variable model: inbound JSON keys must be hand-declared into typed workflow variables in a bare schema editor with no sample-payload preview, so a mismatched key produces a workflow that simply doesn't run with nothing posted anywhere to say why, and multi-branch conditional logic renders as nested collapsible cards that are trivially easy to misorder. Admins hit the Grid split: settings live at org level *or* workspace level in `admin.slack.com` with no unified search, Information Barriers are configured against exact IDP group IDs typed by hand rather than picked from a list, and the difference between a channel converted to org-wide, a channel shared to another workspace, and a Slack Connect channel with an external org is three different blast radii behind similar-looking menu items. The result is that most teams use maybe 5% of the platform and the ones who try governance get it subtly wrong.

**AI operator:** A workspace- or org-connected operator with two personalities behind one interface. For end users it authors automation: pre-loaded with the Deno Slack SDK project structure, trigger types, and the workflow/function manifest schema, it scaffolds a real workflow app in TypeScript from a spoken description, deploys it with the `slack` CLI, and — the important part — publishes the result as a **custom step** so the requester's colleagues can reuse it from Workflow Builder without touching code. For admins it carries channel and usergroup lifecycle, Grid policy, SCIM provisioning, Slack Connect and external-sharing audit, and an "who can actually see this channel" resolver. Safety is asymmetric by design: authoring and read operations run freely; anything under `admin.*` — removing users, retargeting a channel's workspaces, creating barriers, changing sharing policy — renders as a diff of who gains and loses access and requires explicit confirmation, and destructive user operations are dry-run only until approved twice.

**Killer example:** User says: *"When someone reacts to a message with :bug:, open a ticket, post it back in the thread, and let the support team reuse this without bothering me."* → AI scaffolds a Deno workflow app with a reaction-added event trigger scoped to the `#support` channel, a custom function that reads the message text and permalink and calls the team's issue tracker, and a `chat.postMessage` step replying in-thread with the ticket link; deploys it with `slack deploy`, registers the trigger, tests it against a real message, then publishes the function as a custom step named "Create bug ticket" so anyone can drop it into their own Workflow Builder workflow — and reports the exact scopes the app requested so the admin can approve it once.

**Integration path:** Slack Web API (`conversations.*`, `chat.postMessage`, `usergroups.*`, `canvases.create`), the Deno Slack SDK plus the `slack` CLI for authoring and deploying workflow apps and custom steps, `admin.*` APIs and SCIM for Grid governance, the Audit Logs API for org monitoring, and Events API/Socket Mode for triggers — all over OAuth 2.0 with granular scopes, with `admin.*` requiring an Enterprise Grid org-admin token. Widely documented, generous developer sandbox, no partner approval for a workspace-scoped app.

**Demand 5/5 · Buildability 4/5**

### 7. Moodle LMS (roles and capabilities, restrict access, gradebook, cohorts) `OSS`

**Why it's powerful:** Moodle runs a very large share of the world's formal education and a good deal of corporate compliance training — universities, school systems, ministries and NGOs across every continent, self-hosted and free. Under the course pages sits a serious platform: a capability system with fine-grained permissions overridable at system, category, course, activity and block context; conditional availability trees that gate any activity on completion, grade, date, group or user profile field; a gradebook with weighted categories, aggregation strategies and grade letters; cohort-sync and self/manual/LTI enrolment methods; competency frameworks and learning plans; and a plugin ecosystem including H5P and BigBlueButton. Anything a course designer can imagine, Moodle can express.

**Why people bounce off it:** Moodle's power is expressed through screens designed for administrators in 2006. Define-roles is a matrix of more than eight hundred capabilities with four states each (Not set / Allow / Prevent / Prohibit), and the interaction between a course-level override and a system-level Prohibit is understood by approximately nobody, so institutions clone the Teacher role, tick things until the complaint stops, and end up with editing teachers who can see other courses' grades. The everyday teacher wall is Restrict access: the availability tree is an AND/OR nest of conditions with an eye icon that toggles whether a locked activity is *hidden* or merely *greyed out*, and the classic failure is a quiz gated on completion of an activity whose completion tracking was never enabled — so the gate never opens and thirty students are locked out on exam day with no error anywhere. Then the gradebook, where the difference between "Natural" weighting, "Simple weighted mean" and excluded-versus-empty grades quietly changes everyone's final mark.

**AI operator:** An operator that installs against any Moodle site through its own web-services layer, with skills for course and section building, enrolment and cohort management, availability-tree authoring, gradebook setup, role and capability diagnosis, and bulk activity edits. The two headline skills answer the questions Moodle refuses to: **"why can't this student see this?"** — which resolves the specific user against enrolment method, group membership, role assignments and the activity's availability JSON, and names the one condition that failed — and **"why is this grade wrong?"** — which walks the category aggregation and shows the arithmetic. It builds availability trees as the real JSON structure (`{"op":"&","c":[{"type":"completion","cm":412,"e":1},{"type":"date","d":">=","t":1789…}]}`) and, critically, checks that completion tracking is actually enabled on any activity it references before saving the gate. Writes run as a dry-run diff of affected users and activities; anything that could lock a cohort out of an assessment — availability changes, enrolment removals, role overrides — requires explicit confirmation and is reversible from a saved prior state.

**Killer example:** User says: *"Enrol the whole Fall Chemistry cohort in the Lab Safety module, but nobody sees the practical until they've passed the safety quiz with 80%, and Marta still can't open week 3 — find out why."* → AI calls `core_cohort_get_cohort_members` and `enrol_manual_enrol_users` to enrol 240 students with the Student role, sets the practical's availability to a grade condition on the safety quiz at `min: 80` combined with completion, notices that the quiz has completion tracking set to "None" and enables `completionpassgrade` first so the gate can ever open, then diagnoses Marta: she is in the cohort but her enrolment is suspended, *and* week 3 carries a group restriction to "Lab Group B" she isn't in — reporting both causes and offering to fix each separately.
