### 1. New Relic (observability platform: APM, infrastructure, logs, browser/mobile, synthetics, alerts) `closed`

**Why it's powerful:** Unifies APM traces, infra metrics, logs, browser/mobile RUM, and synthetics into one telemetry store (NRDB) queryable with NRQL, plus Applied Intelligence anomaly detection, dashboards, and alert workflows spanning the whole stack.

**Why people bounce off it:** NRQL is a SQL-like dialect but you must know which event type (Transaction, Span, Log, Metric) holds the data you want, plus FACET/TIMESERIES/percentile syntax quirks; alert conditions require choosing static vs baseline vs anomaly signal types and wiring policies to notification workflows/destinations correctly. Most engineers only ever click through pre-built dashboards and never write a custom NRQL query or alert condition, so most orgs run with stale, noisy, or missing alerts.

**AI operator:** A New Relic operator skill that turns plain-English observability requests into NerdGraph GraphQL calls: writes and runs NRQL, renders/edits dashboard widgets, creates alert conditions with correct thresholds/durations, and attaches notification workflows — plus a 'why did this fire' mode that chains NRQL queries across APM/infra/logs to explain an incident.

**Killer example:** 3am page fires. On-call says: 'why is checkout slow right now, and stop this from paging me again for the same thing.' AI runs NRQL across Transaction/Span/Log for the checkout service, finds a downstream payments-API latency spike is the root cause (not checkout itself), retargets the existing noisy alert condition to the actual payments service with a 2%/5-min threshold via alertsNrqlConditionStaticCreate, silences the mis-targeted one, and posts the trace evidence to the incident channel — all before the human finishes their coffee.

**Integration path:** NerdGraph (single documented GraphQL API) covers NRQL execution, dashboards, alert policies/conditions, and workflows with API-key auth; New Relic CLI (newrelic-cli) available for scripted setup.

**Demand 5/5 · Buildability 4/5**

### 2. Google Cloud Operations Suite (Cloud Monitoring + Cloud Logging: alerting policies, SLOs, log-based metrics, dashboards) `closed`

**Why it's powerful:** Unifies metrics, logs, traces, custom dashboards, alerting policies, and SLO/burn-rate monitoring across all GCP services (and hybrid workloads via the Ops Agent), with both MQL and PromQL query support.

**Why people bounce off it:** Alerting policies require navigating aggregation/alignment-period/trigger-type combinations or raw MQL; log-based metrics need Cloud Logging's filter query syntax that almost nobody memorizes; SLO setup (rolling vs calendar window, fast/slow burn-rate alerts) is notoriously confusing, so most teams build a dashboard once, never touch it again, and end up with alerts that are either silent or constantly noisy.

**AI operator:** An SRE operator that converts plain-English reliability requests into full AlertPolicy, LogMetric, Service, and ServiceLevelObjective API resources — including correct burn-rate alert wiring to an existing SLO and notification channel — and previews the exact conditions before creating them.

**Killer example:** A PM says: 'orders-api needs a real reliability contract — alert if p99 blows past 800ms for 10 minutes, and I want a 99.9% monthly SLO that pages fast if we're burning error budget too quickly.' AI creates the AlertPolicy (conditionThreshold on request_latencies, p99, service_name=orders-api, 800ms/600s), stands up a Service + ServiceLevelObjective (99.9%, 30-day rolling window), then layers a fast-burn AlertPolicy on top of that SLO wired to the existing on-call channel — a setup that normally takes an SRE half a day of MQL trial-and-error, done in one message.

**Integration path:** Cloud Monitoring API (REST/gRPC + client libraries) covers AlertPolicies, NotificationChannels, Services/SLOs, and Dashboards; Cloud Logging API covers log-based metrics — all mature, documented, service-account authenticated.

**Demand 5/5 · Buildability 4/5**

### 3. Close (close.com) `closed`

**Why it's powerful:** Close is built for high-velocity outbound sales — built-in power dialer, Smart Views (saved complex multi-condition segments across leads/contacts/activities), and branching multi-step Sequences with exit conditions — letting a small team run enterprise-grade outbound cadences without a separate sales-engagement tool.

**Why people bounce off it:** Smart Views require combining dozens of AND/OR filter conditions across custom fields, statuses, and activity history via a query-builder UI that most reps never master, so they fall back to basic keyword search and silently miss huge chunks of their own pipeline; Sequences with proper branch/exit logic and bulk enrollment likewise usually need API/CSV work that reps skip.

**AI operator:** An NL operator that compiles plain-English segment descriptions into Close's advanced search query JSON to build/save Smart Views, and enrolls matching leads/contacts into Sequences via the Sequence Subscription API — turning 'who should I call today' into a live, reusable view.

**Killer example:** A rep says: 'show me every $10k+ opportunity stuck in Demo for 14+ days with no contact activity, save it as my Monday hit-list, and drop their contacts into the Re-engagement sequence right now.' AI builds the nested Smart View filter (amount>=10000 AND status=Demo AND last_activity<14d ago) via the advanced-search endpoint, saves it as a named view the rep can reopen every week, and calls the Sequence Subscription endpoint to enroll every match on the spot — replacing a search-and-copy-paste ritual that used to eat 20 minutes each Monday.

**Integration path:** Close's well-documented REST API (api.close.com) with a rich advanced-search endpoint supporting nested filter logic, dedicated Sequences and Sequence Subscription endpoints, and Custom Activities API — straightforward API-key auth, no CLI needed, genuinely easy for a solo dev to integrate headlessly.

**Demand 4/5 · Buildability 5/5**

### 4. LaunchDarkly (feature flag & progressive delivery platform) `closed`

**Why it's powerful:** Multi-context targeting (users, devices, orgs), percentage rollouts, prerequisite flag hierarchies, guarded releases, and experimentation give teams safe progressive delivery across many environments and services.

**Why people bounce off it:** The targeting-rule builder (nested clauses across contexts, rollout bucket weights, prerequisite chains) becomes unmanageable once an org has hundreds of flags per project/environment; engineers routinely lose track of what's stale or which environment a rule applies to, and toggling the wrong environment causes real production incidents.

**AI operator:** An operator that reads current flag state via the API and executes natural-language flag operations — create flags, set per-environment/context targeting rules, schedule ramps — plus proactively surfaces stale flags (e.g. 100%-rollout flags untouched for 90+ days) for cleanup, always showing a JSON-patch diff before applying.

**Killer example:** Release manager says: 'ramp new-checkout-flow to 25% of EU users in prod, keep it fully off in staging, and tell me if any flags in this project have been sitting at 100% for months and can probably be deleted.' AI submits a JSON Patch adding the production targeting rule (segment=eu-users, 25/75 rollout) and forcing staging's environment off, shows the diff for a one-click confirm before it goes live, then scans the project and flags three forgotten 100%-rollout flags idle since Q1 as cleanup candidates — the exact kind of stale-flag incident risk that normally goes unnoticed until it causes an outage.

**Integration path:** Fully documented REST API (api.launchdarkly.com) using JSON Patch semantics for flag mutations, mirrored by LaunchDarkly's own Terraform provider — a ready reference for exactly which operations an agent needs to emit.

**Demand 4/5 · Buildability 4/5**

### 5. Zoho Books `closed`

**Why it's powerful:** Handles multi-currency revaluation, project/timesheet billing, recurring invoices with dunning, inventory costing (FIFO/weighted-avg), and jurisdiction-specific tax compliance (GST/VAT/US sales tax) across 180+ countries — genuinely enterprise-grade accounting for a fraction of NetSuite's price, with a real REST API v3 and an embedded scripting language (Deluge) for custom workflows.

**Why people bounce off it:** Getting tax compliance right (which tax authority, which nexus, when to file, how to configure GST/VAT rate schedules per state or country) is a maze that trips up most small-business owners doing their own books; writing a custom automation (auto-apply late fees, auto-flag anomalous vendor bills) means learning Deluge, Zoho's proprietary scripting language, which has almost no transferable skill outside the Zoho ecosystem.

**AI operator:** An operator layer with pre-built skills over the Books API v3 and a library of Deluge custom-function templates for the most common asks (auto tax-authority assignment by ship-to state, dunning-schedule automation, multi-currency revaluation at period close) — the user describes the business rule in plain language and the AI both configures the native Zoho automation and, where the API can't reach, writes and deploys the Deluge script.

**Killer example:** Owner says: 'every invoice shipped to California needs the right state+district sales tax, and anything overdue 30+ days should auto-tack on a 1.5% late fee and email the client — I don't want to think about this again.' AI configures the CA nexus/tax-authority mapping via the Books API, then generates and deploys a Deluge custom function bound to the invoice-overdue trigger that computes the late fee and fires the reminder — a rule that would otherwise require hiring a Zoho consultant fluent in Deluge just to write 15 lines of scripting logic.

**Integration path:** Zoho Books REST API v3 (OAuth2, full CRUD on invoices/bills/journals/tax authorities) plus the Deluge custom-functions API for workflow logic the REST surface can't express directly.

**Demand 4/5 · Buildability 4/5**

### 6. Redmine `open-source`

**Why it's powerful:** Free, self-hosted issue tracker/PM used by countless IT departments and dev teams: multiple issue trackers per project, per-role/per-tracker workflow state machines, unlimited custom fields, issue relations (blocks/precedes/duplicates), Gantt/roadmap, time tracking, and hierarchical sub-projects, all exposed through a REST API for issues/time entries/versions/memberships.

**Why people bounce off it:** The two screens that make Redmine actually usable well — the workflow transition matrix (tracker x role x from-status x to-status x field-permission grid) and custom field definitions — are HTML-form-only with zero REST write coverage (confirmed on Redmine's own tracker: issues #11159, #17760, #31186), so admins hand-edit an unreadable grid; meanwhile end users can't hand-construct correct REST filter queries (numeric custom_field_id, cf_X operators, IN/date-range syntax) so most staff give up on saved queries/bulk edits and just export to Excel.

**AI operator:** A chat layer in front of the REST API that resolves the natural-language request into correct cf_X / status_id[] / version_id parameters for bulk issue, time-entry, and membership operations, and — since the workflow matrix and custom-field admin panels aren't API-reachable — outputs a precise step-by-step admin checklist for those two instead of pretending to execute them.

**Killer example:** PM says: 'close every bug in Payments that's been Resolved for 2+ weeks and roll their story points into the next release.' AI resolves the numeric custom-field and version IDs behind the scenes, previews '14 issues, 37 points' for confirmation, then issues a single bulk PUT across issues.json to close them and reassign the version — the exact bulk operation that today forces admins to either script raw REST calls themselves or click through 14 issues one at a time.

**Integration path:** REST API (JSON/XML) for issues, time_entries, projects, versions, memberships, users, and saved queries; workflow/custom-field admin config has no core write API (UI-only, or requires the community redmine_workflow_api plugin where installed).

**Demand 4/5 · Buildability 4/5**

### 7. Coda `closed`

**Why it's powerful:** Coda blends documents, spreadsheets, and relational databases in one canvas — cross-table formulas, buttons that trigger automations, and Packs that pull in live Jira/Slack/Salesforce data — letting a team replace an entire tool stack with a single doc once mastered.

**Why people bounce off it:** The formula language looks like Excel but behaves like a database query language (lookups, relations, Filter(), WithName()), and buttons/automations require learning a mini-scripting model. Most users hit a wall trying to build even one linked-table view, so they end up using Coda as a glorified Google Doc and never touch the relational layer that justifies its price.

**AI operator:** A natural-language layer on the Coda REST API: the user describes the structure they want ("track vendor invoices linked to my Clients table, alert me when overdue"), and the AI creates the tables/columns/cross-table formulas/buttons and configures the automation rule via the API — no formula bar required.

**Killer example:** User says: 'I need a vendor-invoice tracker linked to my Clients table, and email me every Monday morning with anything overdue — I don't want to touch a formula bar.' AI calls the Coda API to create the Invoices table with a lookup relation into Clients, writes the overdue-days formula, and configures a scheduled Monday automation with an email action — delivering in one request the exact relational-database build that makes most Coda users bounce off the product entirely.

**Integration path:** Coda REST API v1 (fully documented, OAuth/token-based; full CRUD on docs/tables/rows/formulas/automations) plus the Coda Packs SDK for deeper custom actions — cloud-native, no desktop dependency, strong fit for a solo-dev MVP.

**Demand 3/5 · Buildability 5/5**

### 8. Backstage (Spotify/CNCF developer portal) `open-source`

**Why it's powerful:** Unifies a software catalog, TechDocs, and scaffolder-driven 'golden path' templates plus CI/CD, cost, and Kubernetes plugins into one org-wide developer portal, so any engineer can discover ownership, docs, and deploy status for any service.

**Why people bounce off it:** Onboarding a service means hand-authoring catalog-info.yaml with the right kind/entity-refs/annotations, understanding the System/Component/API/Resource relationship model, and running scaffolder templates that use Nunjucks templating with custom actions — most teams either skip registration entirely or copy a stale YAML file, leaving the catalog full of rot and orphaned entities.

**AI operator:** An operator that talks to Backstage's Catalog and Scaffolder REST APIs: given a plain-language service description it drafts a correct catalog-info.yaml, PRs and registers it, runs the matching scaffolder template with derived parameters, and can answer catalog-wide questions like 'which payments-team services have no TechDocs'.

**Killer example:** New hire says: 'register the fraud-detection service I just wrote — it's owned by the risk team, part of the payments system, and calls the accounts API.' AI drafts a correct catalog-info.yaml (kind: Component, spec.owner: group:risk, spec.system: payments, spec.dependsOn: [api:accounts-api]), opens a PR, and once merged calls POST /api/catalog/locations to register it — skipping the YAML-schema trial-and-error that causes most teams to just never register their services at all, leaving the catalog full of rot.

**Integration path:** Backstage backend exposes documented REST APIs for Catalog (entity CRUD/refresh) and Scaffolder (list/execute templates via POST /api/scaffolder/v2/tasks); self-hosted Node/Express backend with OpenAPI specs.

**Demand 4/5 · Buildability 3/5**

### 9. SAP Business One (SME/mid-market ERP) `closed`

**Why it's powerful:** Full double-entry financials plus integrated inventory, MRP, warehouse management, multi-currency, landed cost, and approval workflows in one system used by 75,000+ SMBs worldwide. Its 'Formatted Search' lets any field be driven by an embedded SQL query, and Crystal Reports/Query Generator give near-infinite reporting depth — but that same depth is the trap.

**Why people bounce off it:** Posting a journal entry correctly requires knowing G/L account determination rules, cost centers/distribution rules, and multi-level BOM/warehouse bins; building a usable report means writing raw SQL inside 'Formatted Search' or the Query Generator, a skill most bookkeepers and even many partners never master. Onboarding a new SME typically needs a paid SAP partner just to get the chart of accounts and approval procedures configured — this is the #1 complaint in SAP B1 partner forums.

**AI operator:** A natural-language layer preloaded with 'skills' for the Service Layer OData endpoints (JournalEntries, BusinessPartners, Invoices) plus a library of vetted Formatted-Search SQL snippets for common reports (aged AR, landed cost variance, BP reconciliation). The AI translates plain requests into correct Service Layer POST/PATCH payloads and Query Service SQL, respecting G/L determination and approval-procedure constraints instead of letting the user hand-edit them.

**Killer example:** User says: 'Post March rent as a recurring journal entry split 60/40 between the Warehouse and Admin cost centers, and show me which vendors haven't been paid in 45+ days.' AI does: creates the recurring JournalEntry template via Service Layer with correct cost-center distribution rules, then runs a saved Query Service SQL report against BusinessPartners/Invoices and returns the aged-payables list inline.

**Integration path:** SAP B1 Service Layer (REST/OData v4, session-cookie auth, 480+ business-object endpoints, native SQL query execution since FP2011) for real-time CRUD; DI API (COM/.NET) as fallback for legacy on-prem installs without Service Layer exposed.

**Demand 4/5 · Buildability 3/5**

### 10. Oracle Eloqua `closed`

**Why it's powerful:** Multi-step 'Program Canvas' flows (Decision/Action/Wait/Compare-field steps) drive nurture journeys across contacts and accounts; lead scoring & grading matrices combine fit + engagement; segments use nested AND/OR filter trees across contact fields plus full activity history (opens, clicks, form fills, custom data objects); dynamic content swaps by segment; App Cloud has 700+ integrations.

**Why people bounce off it:** Editing a Program Canvas requires understanding step semantics, shared-list dedup logic, and how a Segment differs from a Filter — one wrong branch or exit condition can silently strand thousands of leads in a program for months before anyone notices. Most marketing teams pay $150-300/hr consultants just to build or modify a single campaign flow because the risk of quietly breaking lead flow is so high.

**AI operator:** A natural-language operator layer that reads/writes Program Canvas objects, contact filters, and segments via the Eloqua REST/Bulk API, translates plain-English campaign requests into step graphs, and dry-runs the logic against a sample contact batch before publishing live so marketers can verify behavior without risking the whole program.

**Killer example:** User says: 'Move any contact who clicked our pricing email twice but hasn't booked a demo in 14 days into the Sales Ready segment and alert their rep.' AI queries Eloqua contact activity via the REST API, builds/updates the filter criteria and decision rule, adds or edits the Program Canvas step, wires the notification action, and publishes — reporting exactly how many contacts moved.

**Integration path:** Eloqua REST API 2.0 (contacts, segments, campaigns, programs) + Bulk API for activity/contact data, OAuth2 auth; fully documented, available to any licensed Eloqua instance without special partner gating.

**Demand 4/5 · Buildability 3/5**

### 11. ChannelAdvisor (now Rithum) `closed`

**Why it's powerful:** Single dashboard lists, prices, and syncs inventory across 200+ marketplaces (Amazon, Walmart, eBay, Google, Meta, TikTok Shop); a rule-based repricing engine adjusts prices per channel by cost/competitor/margin logic; inventory allocation rules route stock by warehouse/channel; attribute-mapping templates translate one product catalog into each marketplace's required taxonomy.

**Why people bounce off it:** The Rules Wizard for repricing and feed/attribute mapping uses a proprietary conditional-logic and priority-ranking system that differs per marketplace category, so sellers routinely mis-map required attributes and get dozens or hundreds of SKUs suppressed or rejected at once. Mastering it well enough to avoid mass listing failures effectively requires a certified partner agency.

**AI operator:** An AI layer that reads the product catalog and each marketplace's live attribute requirements via the ChannelAdvisor API, auto-generates or repairs mapping templates, and lets sellers define pricing/inventory rules conversationally instead of through the Rules Wizard.

**Killer example:** User says: 'Push all in-stock camping gear to Walmart and Google Shopping with a 12% markup, but never price below $19.99.' AI operator creates the pricing rule set and category attribute mapping via the ChannelAdvisor REST API, triggers the listing/feed export job, then reports back exactly which SKUs failed marketplace validation and why.

**Integration path:** ChannelAdvisor REST API (v2/v3, OAuth2, fully documented) exposing catalog, inventory, listing, and repricing-rule objects for programmatic create/update.

**Demand 4/5 · Buildability 3/5**

### 12. IBM Cognos Analytics `closed`

**Why it's powerful:** Enterprise-grade BI platform combining relational and OLAP reporting, dashboards, embedded forecasting/ML, and a governed semantic layer (Framework Manager packages / data modules) with scheduling and bursting to thousands of recipients — the default company-wide reporting backbone at large enterprises and governments.

**Why people bounce off it:** Building anything beyond a canned dashboard requires modeling a Framework Manager package or data module (joins, determinants, calculated members) and hand-crafting Report Studio/Cognos Analytics report specifications with nested queries, prompts, and conditional formatting — skills almost no business user has, so new-report or data-module requests queue for weeks with the BI team.

**AI operator:** An AI operator pre-loaded with the Cognos Analytics REST API (v1) and the target data module's metadata that turns a plain-language report/dashboard request into a generated report specification (XML/JSON), creates it via the API, wires up a schedule or burst list, and validates the output against live sample data before returning a link.

**Killer example:** User says 'Give me a dashboard of regional sales vs. quota by rep, refreshed every Monday morning, and email the underperformers list to their managers.' The AI inspects the data module for sales/quota/rep/manager fields via REST, builds a dashboard with a bar chart, creates a bursting report keyed on manager, schedules the weekly run, and returns the dashboard link.

**Integration path:** Cognos Analytics REST API (v1) for content-manager objects, report specs, schedules, and job execution; report/dashboard specs are generatable XML/JSON; Framework Manager model files provide schema context for grounding.

**Demand 4/5 · Buildability 3/5**
