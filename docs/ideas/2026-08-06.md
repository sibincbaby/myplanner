### 1. Google Apps Script (Google Workspace's built-in automation runtime) `closed`

**Why it's powerful:** Free with every Google account and it is the only real automation layer inside Workspace: full JS/V8 runtime with first-class bindings to Sheets, Gmail, Drive, Docs, Calendar, Forms and Admin SDK, plus time-driven/onEdit/onFormSubmit triggers, custom spreadsheet functions, sidebars, and deployable web apps. A 40-line script replaces a paid Zapier plan; it can send mail, mutate sheets, generate Docs from templates, and run on a cron - all inside the user's own account and quota.

**Why people bounce off it:** It is literally 'write JavaScript in a browser IDE' - the wall is not a bad UI, it is that the entry ticket is real programming plus Google's plumbing: appsscript.json manifest and OAuth scope selection, the 'Google hasn't verified this app / Advanced' authorization scare screen, container-bound vs standalone projects, installable vs simple triggers (simple triggers can't send email or call other services), 6-min execution limits and daily quotas, Stackdriver-only error visibility, and PropertiesService/LockService patterns nobody discovers. Business users who can build a pivot table stall permanently at 'Extensions > Apps Script'.

**AI operator:** A 'Workspace Automation Copilot': a chat app that owns the user's Apps Script projects programmatically. It authenticates with Drive + Apps Script API scopes, and for each request: (1) infers which sheets/labels/calendars are involved by actually reading their structure first, (2) generates the .gs source AND the appsscript.json with the minimal scope set, (3) pushes via script.projects.updateContent, (4) executes a dry run against a duplicated copy of the target sheet using script.scripts.run, (5) shows the user the concrete diff/sample output, (6) on approval installs the time-driven trigger by running a bootstrap installer function, and (7) reads execution logs back via the API to self-repair failures. Also runs in 'archaeologist' mode: inventory every existing script bound to a user's sheets, explain what each does, and flag broken/orphaned triggers.

**Killer example:** Office manager says: 'Every Friday at 5pm take the new rows in my Leads sheet, email each rep just their own leads as a formatted table, then move those rows to Leads Archive and mark them sent.' The operator reads the live header row (finds Owner Email in column F, not D, and that Status uses 'Sent'/'sent' inconsistently), writes the script with a lastProcessedRow watermark in PropertiesService so a re-run can't double-send, groups by owner, builds the HTML table, deletes source rows in reverse index order (the bug every beginner ships), and pins the manifest to gmail.send + spreadsheets.currentonly so the scary consent screen asks for two scopes instead of full Drive. Then it clones the sheet, runs against the copy, and returns the four actual emails - 'Priya: 11 leads, Marco: 6, Dana: 0 (she'd get no email - want a skip or a zero-state?)' - before installing the Friday 17:00 trigger. Second turn: 'what else is running in here?' -> 'Three bound scripts. One sends a daily digest to an ex-employee's address and has failed 41 times since March; one is dead code; one is the form handler you actually use.'

**Integration path:** Apps Script API REST (script.projects.create / getContent / updateContent / deployments) + script.scripts.run for execution (requires a shared Cloud project and OAuth consent), Drive API to locate and duplicate container files and to bind scripts to a spreadsheet, Sheets/Gmail APIs for pre-flight structure reading, Cloud Logging for execution logs. The open-source clasp CLI wraps the same endpoints for a local-first version. No scraping needed - it is a clean REST surface all the way down.

**Demand 5/5 · Buildability 4/5**

### 2. Google Merchant Center (Merchant API / Shopping feeds) `closed`

**Why it's powerful:** It is the gate to free Shopping listings, Shopping ads and Performance Max for essentially every online retailer. The feed spec carries 100+ attributes, plus supplemental feeds, feed rules (a full prefix/suffix/extract/lookup ETL engine), regional inventory and pricing, promotions, local inventory ads, automated item updates driven by on-page microdata, and per-item diagnostics. A well-tuned Merchant Center account is worth more revenue than most stores' entire paid social budget.

**Why people bounce off it:** The merchant is shown 1,200 rows of 'Disapproved: Missing value [gtin]', 'Mismatched value (page crawl): price', 'Image too small', 'Misrepresentation - account suspension in 7 days' and there is no path from any error string to an actual fix. Feed Rules are an ETL tool with no debugger or dry-run; supplemental feeds must be joined by offerId and silently no-op when the id doesn't match; account-level policy issues are described in generic policy prose with no diff of what changed. On top of that, the Content API for Shopping shuts down 18 Aug 2026 (12 days from today), so every custom/agency integration is being force-migrated to Merchant API v1 with new resource shapes (accounts/{account}/products, dataSources, productInputs vs products, long-running ops) - a second wall stacked on the first.

**AI operator:** 'Feed Doctor': an operator that OAuths into Merchant Center, pulls product-level issues + account issues, clusters thousands of disapprovals by ROOT CAUSE rather than by SKU, and then writes repairs into a dedicated AI-owned supplemental data source so the merchant's primary Shopify/Woo feed is never touched. It fetches the live landing page to compare structured data against the feed for price/availability mismatches, proposes the feed rule or schema.org patch, runs a preview diff, applies via productInputs.insert, and then re-checks after Google's next crawl, reporting which fixes landed. Second skill pack: automated Content API to Merchant API v1 migration of the merchant's existing integration code.

**Killer example:** Store owner pastes one line: 'Why are 1,240 of my products not showing on Google?' The operator pulls product statuses, throws away the SKU-by-SKU view Google gives you, and answers in four clusters with money attached: '900 handmade items fail on missing gtin - the fix is identifierExists=false, not buying barcodes. 260 are price mismatches because your landing page renders a logged-in member price and Google's crawler sees the higher one; that's ~GBP 14k/month of impressions you're paying nothing for and getting nothing from. 80 have images under 100x100. 80 are policy hits on knife blades over 15cm - I will not touch those, you need a human decision.' It then creates a supplemental data source called 'ai-fixes', pushes 1,160 productInputs so your Shopify feed is never edited (and your next Shopify sync can't undo the work), hands you a 6-line JSON-LD patch for the member-price bug, and sets a Pub/Sub watch that reports back in 72 hours: '1,102 re-approved, 58 still disapproved - Google now says image_link 404s on those; your CDN is rate-limiting their crawler.'

**Integration path:** Merchant API v1 (REST + gRPC, google.shopping.merchant.* client libraries) with standard OAuth2 - no partner/app review gate, just a GCP project and the merchant granting account access. Sub-APIs used: products/productInputs, dataSources, accounts + issues, promotions, and reports (Merchant Center query language, a SQL-ish surface ideal for an LLM). Pub/Sub notification subscriptions give real-time disapproval events for a monitoring loop. Optional headless fetch of product landing pages to diff microdata. Pair with Google Ads API for the Shopping/PMax spend side.

**Demand 5/5 · Buildability 4/5**

### 3. TallyPrime (Tally Solutions) `closed`

**Why it's powerful:** India's default SMB accounting engine - ~2.5M+ businesses. Full double-entry plus inventory with batches/godowns/BOM, GST returns (GSTR-1/3B/IMS reconciliation), TDS/TCS, payroll, cost centres, multi-company, multi-godown stock valuation, and TDL (Tally Definition Language) which lets you redefine reports, print formats and even data structures. Runs offline on a shop PC, one-time license, no per-seat SaaS bleed - which is exactly why nobody leaves it.

**Why people bounce off it:** It is a keyboard-driven DOS-lineage green screen where every capability is gated behind F11 (Company Features) and F12 (Configuration) toggles that exist at three different scopes (company / voucher type / report), and the toggles must be flipped BEFORE the voucher is entered or the fields simply don't appear. Want batch-wise tracking? Enable 'Maintain Batch-wise Details' + 'Use Expiry Dates'. Want to bill a different quantity than you shipped? 'Use separate Actual and Billed Quantity'. GST rates can be set at company, stock group, stock item, and ledger level with silent precedence rules, so a wrong rate at the wrong level produces a return that fails validation months later. The result: the owner or a junior clerk enters vouchers they don't understand, and every real question ('why is GSTR-1 showing 43 uncertain transactions?', 'why is my closing stock value wrong?') gets phoned to the CA or to a Tally partner who bills for a TDL customization. Millions of users are running an ERP-grade tool at 10% of its capability.

**AI operator:** 'Talk to Tally' - a Windows tray sidecar that speaks Tally's XML gateway on localhost:9000, preloaded with skill packs for (a) masters (ledgers, stock items, HSN/GST setup, GSTIN validation), (b) voucher entry incl. split settlements, bill-wise refs and stock allocations, (c) the F11/F12 configuration maze (it knows which toggles a requested behaviour requires and flips them with an explanation), (d) GST return hygiene - it reads the 'Uncertain Transactions' report and fixes causes, and (e) a TDL generator for custom reports/print layouts, with a diff preview. Front end is WhatsApp + voice in Hindi/Tamil/Gujarati, because the actual user is a shop owner, not a desktop-app person.

**Killer example:** Cement dealer sends a WhatsApp voice note from the shop counter: 'Sharma Traders ko aaj 12 bori cement 380 ka becha, aadha cash aadha udhaar, unka GSTIN 27ABCDE1234F1Z5 hai.' The operator creates the ledger under Sundry Debtors, reads state code 27 out of the GSTIN and sets Maharashtra so IGST vs CGST/SGST resolves correctly against the company's own state, confirms 'Cement 50kg' carries HSN 2523 at 28%, posts the Sales voucher with a split settlement (Rs 2,280 cash receipt, Rs 2,280 to the party with a bill-wise 'New Ref'), and replies with the invoice number and tax breakup in 20 seconds. The part no competitor does comes a month later: owner asks 'GSTR-1 mein 43 uncertain transactions kyun aa rahe hain?' - the operator reads the uncertain-transactions report, buckets them ('31 have no HSN on the stock item, 9 have a B2B invoice against a party with no GSTIN, 3 have a rate set at item level that contradicts the stock group'), explains that fixing the HSN needs 'Set/Alter GST Details' enabled at company level first, flips that F11 toggle with the consequence spelled out, patches the 31 items, re-runs the report, and sends back a screenshot: 'Uncertain transactions: 0. Return is ready to file.' That is the CA's Rs 8,000 monthly clean-up call, done from a voice note.

**Integration path:** Tally's XML-over-HTTP gateway is the real surface: enable HTTP Server in F1 -> Settings -> Advanced Configuration (default port 9000), then POST <ENVELOPE><HEADER><BODY><TALLYMESSAGE> documents. Export requests read any collection (Ledger, StockItem, Voucher, Company, plus any TDL-defined collection/report); Import requests write masters and every voucher type (Sales, Purchase, Payment, Receipt, Journal, Credit/Debit Note). ODBC driver gives a SQL read path for reporting. TDL is the plugin architecture for anything the stock XML surface doesn't expose. Real constraints to design around: synchronous only, no webhooks (poll on AlterID), no auth on the gateway (bind localhost, tunnel out), and Tally must be running with the company open - fine, since a large slice of the base already runs TallyPrime Server or Tally on a cloud VM. Distribution rides the existing ~28k Tally partner channel. Competitive note: TallyPrime 7.x ships 'TallyIra'/'Docs by Ira' (OCR document capture + Q&A), but that is read/capture oriented, requires the newest paid version + TSS, and the enormous 3.x-6.x installed base is untouched; write-through configuration and TDL authoring remain wide open.

**Demand 5/5 · Buildability 4/5**

### 4. monday.com `closed`

**Why it's powerful:** A general-purpose work OS: boards with 30+ typed columns (status, formula, mirror, connect-boards, dependency, time-tracking), cross-board connections, dashboards with 20+ widget types, workforms, docs, and an automation recipe catalogue - plus a full GraphQL API (api.monday.com/v2, date-versioned), apps framework, and monday code hosting. 225k+ orgs run real operations on it.

**Why people bounce off it:** The wall is BUILDING, not reading. Non-technical owners can add items fine, but designing a multi-board solution defeats them: connect-boards + mirror columns (mirrors are read-only and can't be filtered/automated on the way people expect), formula columns with monday's own non-Excel function set and no cross-item references, status label/color config buried in per-column JSON settings, and automation recipes that only exist as fixed templates - 'when X and Y but not Z, then A and B' usually has no recipe, so teams fake it with 5 chained recipes and a spare 'trigger' status column. The result: boards that look fine and silently stop working, and a cottage industry of monday 'partners' charging $5-15k to set one up.

**AI operator:** A 'board architect' operator embedded as a monday app (board view + item view panel) that owns the structural layer: it reads the whole account graph (boards, column types, connections, existing recipes) into a model, then takes plain-language descriptions of a process and emits the mutations - create_board, create_column with the correct settings_str JSON per column type, connect_boards + mirror wiring, formula bodies, dashboard widgets - with a diff-preview 'here's what I'll change' step and one-click rollback. Second half is an external automation engine: it subscribes webhooks and runs the conditional logic monday's recipe catalogue can't express, so the user never has to know which half is native.

**Killer example:** COO types: 'Client onboarding is a mess. Track every client through Legal -> Billing -> Implementation with an owner per stage, flag anything sitting more than 5 business days, and give leadership one board that's red/amber/green per client.' The operator first reads the account and pushes back with something a $10k partner would charge to discover: 'You already have three boards named Clients. Two are stale; the live one has 214 items and a mirror column pointing at a board that was deleted in March, which is why your renewal dashboard shows blanks.' Then it builds: an Onboarding board with per-stage groups, status columns whose labels and hex colors it writes through settings_str, a people column per stage, and a formula column computing business-days-in-stage (working around monday's lack of a native business-day function). It connect-boards to the real Clients board and mirrors contract value, builds a leadership dashboard with battery + chart widgets, and then handles the rule monday cannot express - 'stage unchanged 5 business days AND owner empty -> set RAG Red and DM the stage owner in Slack' - on its own webhook engine, so from the user's side it is just another automation. It shows all 14 changes as a preview diff first, and the rollback is one click.

**Integration path:** GraphQL API v2 with versioned API headers; OAuth app for multi-tenant install; webhooks for triggers; monday apps framework (iframe board/item views via monday SDK) so the chat panel lives inside monday, hosted on monday code. Note the competitive landscape: monday ships an official Platform MCP for item/column reads and writes - deliberately aim above it at structure/solution building and cross-board automation, which the MCP does not do.

**Demand 5/5 · Buildability 4/5**

### 5. Mailchimp `closed`

**Why it's powerful:** ~12M users, overwhelmingly non-technical SMBs. Under the friendly surface it has a genuinely deep engine: advanced segments with nested all/any condition trees over ~40 condition types (campaign activity, ecommerce purchase history, predicted demographics, signup source, API-set merge fields), variate (multivariate) campaigns with automatic winner selection, timewarp/send-time optimisation, automation flows, ecommerce store sync with product retargeting, conditional merge tags, and transactional sending.

**Why people bounce off it:** Two specific walls. (1) The audience/tags/groups/segments mental model - contacts existing in two audiences are billed twice, tags vs groups vs segments do overlapping jobs, and the advanced segment builder caps and nests conditions in ways that make 'why does my segment return 0 people' the single most common support thread. (2) Purchase-based and behavioural conditions only work if the store sync populated the right objects, which the merchant can't inspect from the UI. So the powerful half of Mailchimp - behavioural segmentation and multivariate testing - goes almost entirely unused, and people send blast-to-everyone campaigns instead.

**AI operator:** 'Talk to your list': NL -> segment condition JSON, with a member-count preview returned BEFORE anything is saved (the crucial trust loop the UI lacks), then campaign creation, content fill, variate/A-B configuration and scheduling in the same turn. Plus a diagnostic skill that inspects the ecommerce sync objects and explains exactly why a purchase-based segment is empty, and a post-send reporting skill that answers 'which subject line won and what should I do next time' from /reports.

**Killer example:** Shop owner: 'Email everyone who bought running shoes in the last 90 days but hasn't opened anything in 30 days - 15% off, send Thursday 9am their local time, A/B the subject line.' The operator builds the nested condition tree and comes back before saving anything: 'That's 812 of your 14,300 contacts. Heads up - it would have been 0 five minutes ago: your purchase conditions were matching nothing because the Shopify sync is writing product_title but no product category, so every category-based segment you've built since April has been silently empty. I've rewritten the condition to match on line-item title contains "running" instead, and here are 20 sample contacts so you can sanity-check it.' On approval it creates a variate campaign with two subject lines and open-rate winner criteria, drops in the promo template with the coupon merge tag, enables timewarp, schedules Thursday 09:00 local - and three days later, unprompted: 'Variant B won, 34% vs 22% open, 61 redemptions. The 30-day non-openers who still didn't open are now 402 people; want a re-engagement send or should I suppress them before they hurt your deliverability?'

**Integration path:** Marketing API v3: plain REST, API-key auth (no OAuth app review - the reason buildability is a 5), with full coverage of lists/members/tags, segments including the complete condition schema, campaigns + campaign-content + variate settings, /reports, /automations (classic), ecommerce stores/carts/orders, a /batches bulk endpoint, and webhooks. Honest gap to design around: the newer Automation flows / Customer Journeys canvas is NOT authorable via API - the API only exposes /customer-journeys/journeys/{id}/steps/{id}/actions/trigger to push a contact into a journey built in the UI. So either scope the MVP to segments + campaigns + ecommerce + reports (which is where the pain actually is), or add Playwright browser automation for journey authoring in v2.

**Demand 4/5 · Buildability 5/5**

### 6. Amazon Seller Central (SP-API + Amazon Ads API) `closed`

**Why it's powerful:** 1M+ active sellers run their whole P&L through it: listings with per-marketplace product-type JSON schemas, variation families, FBA inventory and replenishment, fee previews, A+ content, coupons/deals, hundreds of report types, and a separate Ads API for Sponsored Products/Brands/Display with placement multipliers, negative keyword mining and bid rules. Programmatically it can do things no seller can do by hand - 25,000 listing operations in one JSON_LISTINGS_FEED payload.

**Why people bounce off it:** Listing errors are numeric and untranslatable: '8541 The value for item_type_keyword is invalid', '90220 SKU is not eligible for this product type', 'Your listing is suppressed'. The required attribute set is not fixed - it's a dynamic JSON Schema per productType per marketplace, and Amazon rewrote attribute enums across many product types effective 27 Apr 2026, silently breaking working listings. Variation/parentage setup (parentage_level, child_parent_sku_relationship, variation_theme) is the single most-asked question in seller forums. Seller Central itself is ~20 nested menus, flat-file templates vs JSON feeds, and Buy Box loss with zero explanation. Sellers routinely pay agencies $2-5k/mo purely to translate these errors.

**AI operator:** A seller copilot with skills bound to Listings Items + Product Type Definitions + Feeds + Reports + Ads. The core trick: on any listing error it fetches the live productType JSON Schema, structurally validates the current listing against it, repairs the attribute payload, and re-submits - turning '8541' into a fixed listing instead of a forum search. Extends to 'why did I lose the Buy Box', 'what's my true margin after FBA fees on this SKU', and ads hygiene (mine 30-day search-term reports, propose negatives and bid moves, apply after confirmation).

**Killer example:** Seller: 'My Ceramic Mug 12oz family is a mess - the 3 colours aren't grouping and the blue one is suppressed.' The operator pulls the live MUG productType definition for the marketplace, structurally diffs all 4 SKUs against it, and reports in English: 'The parent has no variation_theme, the three children have no child_parent_sku_relationship, and Blue is suppressed because item_type_keyword still uses an enum Amazon retired on 27 Apr - that same retired value is on 61 of your other SKUs and they will suppress on their next re-crawl.' It builds the parent + 3 child patch set, dry-runs with mode=VALIDATION_PREVIEW so nothing hits the catalog until it validates clean, submits a JSON_LISTINGS_FEED, polls the processing report, and confirms: '3/3 accepted, suppression cleared, family live in 11 minutes.' Then the part the seller didn't ask for: 'You're losing the Buy Box on Blue - competitor is 4.5% cheaper with Prime. After FBA fees and your 22% target margin, GBP 18.40 wins it back; at GBP 17.95 you're selling below cost. Also, 30-day search terms show GBP 340 spent on "coffee mug personalised" with zero orders - want me to add it as a negative exact across the campaign?'

**Integration path:** SP-API: LWA OAuth (developer profile + registered app, roles requested per data set - keep MVP out of PII/restricted roles to skip the extra approval), endpoints Listings Items 2021-08-01, Product Type Definitions 2020-09-01, Feeds 2021-06-30, Reports 2021-06-30, Catalog Items 2022-04-01, FBA Inventory, Product Fees; sandbox available; per-operation rate limits require a queue. Amazon Ads API is a separate registration with its own profiles/auth. Ship as a hosted web app (sellers connect their account) rather than a CLI, because token handling and rate-limit backoff belong server-side.

**Demand 5/5 · Buildability 3/5**

### 7. Amazon CloudWatch (Alarms, Logs Insights, Dashboards) `closed`

**Why it's powerful:** Every AWS service emits into it for free, and it can do genuinely sophisticated things: metric math expressions, anomaly-detection bands, M-of-N evaluation, composite alarms combining many signals, Logs Insights ad-hoc queries over TB of logs, metric filters that turn log patterns into metrics, Contributor Insights, cross-account observability, and Synthetics canaries. Anything Datadog does for $$$ is technically expressible here.

**Why people bounce off it:** Three separate walls. (1) Discovery: you cannot graph anything until you already know the namespace + exact dimension set (finding that ALB latency is AWS/ApplicationELB > TargetResponseTime keyed by LoadBalancer=app/xyz/1a2b is archaeology through a 4-level console dropdown). (2) Alarm semantics footguns: TreatMissingData (notBreaching/missing/ignoring), evaluation periods vs datapoints-to-alarm, period vs statistic, alarms on sparse metrics that silently never fire, and composite alarm rules that are a raw string expression like ALARM(x) AND NOT ALARM(y). (3) Logs Insights is its own query language, and dashboards are hand-edited JSON blobs. The observable outcome everywhere: orgs with 200 alarms nobody trusts, plus the alarm that should have caught the outage was set to 'missing = breaching' and got muted six months ago.

**AI operator:** A 'CloudWatch operator' that plans, backtests, then applies. It auto-discovers the real metric/dimension inventory via ListMetrics + resource tags, translates plain English into alarm definitions and Logs Insights queries, and - the killer feature no console offers - BACKTESTS the proposal: replay the last 30 days through GetMetricData and report exactly how many times the proposed alarm would have fired, on which days, and whether it would have caught the known incidents. Then plan-then-apply via PutMetricAlarm / PutCompositeAlarm / PutDashboard, or emit equivalent Terraform/CDK for teams that require IaC. Second mode: 'alarm hygiene audit' - find alarms in INSUFFICIENT_DATA for 90 days, alarms with no SNS action, and duplicated alarms across accounts.

**Killer example:** On-call lead: 'Page me when checkout is actually broken, not when one pod hiccups - and don't wake me for a blip.' The operator discovers the checkout ALB and Lambda metrics by tag rather than making anyone hunt namespaces, proposes a composite alarm (p99 TargetResponseTime > 800ms for 3 of 5 datapoints AND 5XX rate > 1%, TreatMissingData=notBreaching), and then does the thing the console fundamentally cannot: it replays 30 days of real GetMetricData through the proposed rule and reports 'this would have fired 4 times, including 02:14 on Jul 22 - your actual outage - and would NOT have fired for the Jul 9 single-node blip that woke you at 3am.' Tuning is a conversation, not a redeploy: 'make it less twitchy' -> re-backtest in 8 seconds -> '2 fires, still catches Jul 22.' On approval it applies via PutCompositeAlarm, wires the existing prod-pager SNS topic, adds a saved Logs Insights query that pulls the correlated request IDs, and emits the equivalent Terraform so the platform team's IaC doesn't drift. Its unprompted closer: 'Separately - 31 of your 187 alarms have been INSUFFICIENT_DATA for 90+ days and 12 have no action attached at all. The one on payments-db free storage is among them.'

**Integration path:** Pure SDK - boto3/AWS SDK + aws CLI. Read path: cloudwatch:ListMetrics/GetMetricData/DescribeAlarms, logs:StartQuery/GetQueryResults, tagging API for resource naming. Write path: PutMetricAlarm, PutCompositeAlarm, PutDashboard, PutMetricFilter. Split into two IAM roles (read-only discovery role assumed by default, separate apply role behind explicit confirmation) via STS AssumeRole with an external ID. No UI automation or scraping needed anywhere; Terraform/CDK emit is a string-generation step.

**Demand 5/5 · Buildability 4/5**

### 8. Microsoft Excel macros - VBA (desktop) + Office Scripts (cloud), extended to Microsoft Access (.accdb) `closed`

**Why it's powerful:** VBA is a complete automation language over the whole Office object model and is the invisible backbone of finance/ops: it can reshape workbooks, build pivots, drive Outlook, print PDFs, and hit databases, and decades of live business logic already sit in .xlsm files. Office Scripts is its cloud successor (TypeScript over the Excel workbook object model) and can be scheduled unattended via Power Automate. The same COM/VBIDE surface reaches Microsoft Access, where an enormous amount of SMB operations still runs - relational engine plus bound forms, banded reports and VBA in one file. One agent covers both because it is one automation substrate.

**Why people bounce off it:** The VBA Editor is a 1998 UI with no usable IntelliSense over the object model, and the macro recorder emits brittle Select/Activate code with hardcoded Range("B2:H400") and sheet indexes; macro-security banners and org policies block .xlsm; and the typical user has inherited a macro nobody understands that now throws Run-time error 1004. Cloud-side, Office Scripts requires TypeScript and scheduling it means building a Power Automate flow - Graph still cannot trigger an Office Script directly. Access adds its own version of the same disease: SQL as a drag-and-drop QBE grid, DAO vs ADO, a form/report event model, and #Name? / 'Enter Parameter Value' errors with no pointer to the bad reference. The unifying fact: the person who wrote it left the company, there is no documentation, and a 20-minute change gets frozen for years or turned into a $40k rewrite quote.

**AI operator:** An Office 'macro mechanic': a local agent (plus a task-pane add-in for Excel on the web) that ingests the artifact before touching it - sheets, named ranges, ListObjects, every VBA module's full text, and for Access the whole app decompiled to text via SaveAsText (schema, every QueryDef's SQL, every form and report) - and builds a dependency graph. Then it explains inherited code in plain English, repairs it, rewrites recorder junk into range-safe code bound to tables and named ranges, authors new automation, and picks the right runtime (VBA for desktop/Outlook/filesystem work, Office Scripts when the workbook lives in OneDrive and needs scheduling, in which case it also creates the Power Automate flow). Every action runs against a timestamped sandbox copy first, with a before/after diff of affected ranges plus a rendered screenshot of the resulting report, and a rollback file - which is what makes non-technical users willing to press Run. The text-export path also gives Access users git-style diffs of forms, something Access has never offered.

**Killer example:** Finance analyst: 'The monthly report macro I inherited crashes since we changed the export layout - fix it, and have it build the pivot on a new sheet and email the PDF to my boss.' The operator extracts every module, traces the call graph, and names the two real causes in one sentence each: 'Line 41 hardcodes Range("B2:H400") - the export now has downloadable 517 rows, so 117 are silently excluded from every total you have sent for three months. Line 88 uses Sheets(3), which stopped being the data sheet when someone added a cover tab.' It rebinds both to a ListObject and a sheet resolved by name, adds PivotCache/PivotTable creation on a fresh sheet, appends ExportAsFixedFormat plus an Outlook MailItem, runs the whole thing against a duplicate of this month's file, and returns the produced PDF next to last month's so the analyst can see the 117 rows reappear - with a plain-English changelog and the original .xlsm untouched on disk. ### 9. Asana `closed`
