### 1. Penpot (open-source Figma alternative, self-hostable) `open-source`

**Why it's powerful:** A full design and prototyping suite built on open standards: SVG, real CSS Flex/Grid layout, components and variants, native W3C DTCG design tokens with sets and themes, shared libraries, inspect-to-code, and self-hosting. Enterprises, governments and agencies are moving to it for data sovereignty and to avoid Figma seat pricing.

**Why people bounce off it:** Teams coming from Figma hit a second learning curve. Penpot's Flex/Grid follows real CSS semantics (gap, align-self, grid tracks), and its token system (sets, themes, aliases, math expressions) behaves differently from Figma Variables. Building a themable library with tokens bound to every property takes hundreds of fiddly panel clicks. Most teams end up with half-tokenized files, detached components and hard-coded hex values everywhere.

**AI operator:** A 'Design-System Operator' built on Penpot's official MCP server and Plugin API, which can read and write tokens. Its skill pack can: audit a file for hard-coded values and rebind them to the nearest token; generate token sets and light/dark/brand themes from a brand brief; convert absolutely-positioned frames into Flex/Grid; build variant matrices (size x state x intent); and export tokens to Style Dictionary or Tailwind. Every change is shown first as a dry-run diff (node, property, old value, new value), with an undo checkpoint.

**Killer example:** User says: 'We just got acquired. Rebrand this 60-screen app file to the parent company's palette, add a dark mode, and make it all tokenized so we never do this by hand again.' The AI scans 2,300 layers and finds 41 distinct hex values and 27 off-grid spacings. It clusters them into 11 semantic tokens (surface, text/primary, accent, danger...) and snaps spacing to a 4px scale. It creates 'core', 'brand-parent' and 'theme-dark' token sets with aliases, then binds every fill, stroke, radius and gap to a token. It rebuilds 18 absolutely-positioned cards as Flex columns and shows a side-by-side light/dark preview of 5 key screens. It lists 4 layers it could not map confidently and offers to export the tokens as a Tailwind config for the dev team.

**Integration path:** Penpot's official MCP server, now in the main penpot repo under /mcp, connects over WebSocket to the Penpot MCP Plugin. Its execute_code tool runs JavaScript in the editor with the full Plugin API. The backend RPC API covers files, projects and exports, and self-hosting runs on Docker Compose. A solo developer can ship this as a skill library plus a plugin UI (diff preview, undo checkpoints) on top of the existing MCP server.

**Demand 4/5 · Buildability 5/5**

### 2. AWS WAF (wafv2) + AWS Firewall Manager `closed`

**Why it's powerful:** A layer-7 firewall in front of CloudFront, ALB, API Gateway, AppSync, Cognito, App Runner and Verified Access. It offers managed rule groups (Core, SQLi, Known Bad Inputs, Bot Control, ATP/ACFP), rate-based rules with custom aggregation keys, label-based rule chaining, CAPTCHA/Challenge actions, and org-wide rollout through Firewall Manager. It is the default WAF for a huge share of AWS workloads.

**Why people bounce off it:** The hard part is tuning, not setup. Teams turn on the Core rule set and the next day legitimate uploads get 403s from SizeRestrictions_BODY or CrossSiteScripting_BODY. Fixing that means reading rule labels, overriding one sub-rule to Count, and writing a scope-down or label-match rule in deeply nested JSON (AndStatement/NotStatement/LabelMatchStatement). Each fix has to fit a WCU budget and pass LockToken concurrency checks. Sampled requests keep only 3 hours and 100 samples, so real diagnosis means querying WAF logs by hand. Most teams leave everything in Count forever or switch the rule group off.

**AI operator:** A 'WAF Tuner'. It ingests the web ACL JSON plus WAF logs (CloudWatch Logs Insights or Athena over S3) and works in plain English. It explains which rule and label blocked a request and proposes the narrowest exception. It stages that exception as Count and watches the logs for N hours to confirm false positives drop without widening the attack surface, then flips it to Block. It also replays recent traffic to answer 'what if I enable Bot Control or tighten this rate limit' before anything goes live.

**Killer example:** User says: 'Customers can't upload PDFs to /api/documents since Tuesday. Fix it without weakening protection anywhere else, and while you're at it, tell me if a 100 req/5min per-IP limit on /login would hurt real users.' The AI queries the logs and finds 1,240 blocks from AWSManagedRulesCommonRuleSet with label SizeRestrictions_Body, all authenticated POSTs to /api/documents. It overrides only that sub-rule to Count and adds a follow-on rule: block if the label matches AND the URI does NOT start with /api/documents. CheckCapacity shows +3 WCU, and it applies the change with the LockToken. Replaying 7 days of /login traffic, it reports the proposed limit would have blocked 2 corporate NAT IPs (38 real users) and 1 credential-stuffing burst (41k requests). It suggests aggregating on IP plus the session header instead, and an hour later confirms 0 upload blocks with block counts on other paths unchanged.

**Integration path:** wafv2 API through boto3/CLI: GetWebACL/UpdateWebACL with LockToken, CheckCapacity, ListAvailableManagedRuleGroups, DescribeManagedRuleGroup (rule names and labels), GetSampledRequests and logging configuration. Logs come from CloudWatch Logs Insights or Athena, and Firewall Manager PutPolicy handles multi-account rollout. It can also emit Terraform aws_wafv2_web_acl diffs for GitOps shops. A safe MVP (read-only analysis plus PR output) fits a solo developer.

**Demand 4/5 · Buildability 4/5**

### 3. Amazon CloudFront (distributions, cache behaviors, cache/origin-request/response-headers policies, OAC, CloudFront Functions + KeyValueStore, Lambda@Edge, continuous deployment) `closed`

**Why it's powerful:** It is the CDN in front of a large share of AWS-hosted sites, SPAs, APIs and S3 media. It supports path-based behaviors to multiple origins, origin groups for failover, signed URLs and cookies, two kinds of edge compute, staging distributions for canary config changes, real-time logs, and per-behavior caching and header control.

**Why people bounce off it:** Every common failure has several possible causes. A low hit ratio usually means the cache key includes every query string, header or cookie. CORS fails because Origin isn't forwarded or there is no response headers policy. S3 returns 403 because of an OAC bucket-policy mismatch, and SPA deep links 404 without an error response or rewrite. Behaviors match first-come in precedence order. UpdateDistribution requires sending back the whole config with an If-Match ETag, so one hand edit can clobber unrelated settings. Three policy types interact confusingly, and each attempt takes minutes to propagate.

**AI operator:** A 'CDN Doctor'. It reads the distribution config, attached policies, origin bucket policy, functions, CloudWatch metrics and logs, and answers 'why is X slow, uncached or 403'. It applies minimal patches with a safe read-modify-write using the ETag. Each patch goes first to a continuous-deployment staging distribution with header-based traffic and is promoted only after hit-ratio and error metrics check out. Edge functions are unit-tested with TestFunction before publishing.

**Killer example:** User says: 'Since marketing launched the fall campaign our AWS bill jumped, the origin is melting, /app deep links 404 on refresh, and the new font CDN throws CORS errors in Safari. Fix all of it safely.' From the logs the AI sees the default behavior uses a legacy all-query-strings cache key, and UTM/fbclid params have fragmented the cache to an 18% hit ratio. It creates a cache policy that keys only on v and lang and passes the marketing params through an origin-request policy so analytics keep working. It adds a CloudFront Function on /app/* that rewrites extensionless paths to /app/index.html, unit-tested with TestFunction on 6 sample URLs. It attaches a response headers policy for CORS on /fonts/*. Everything ships to a staging distribution behind a test header, where curl confirms X-Cache: Hit, no 404s and correct Access-Control-Allow-Origin, and then it is promoted. The next day the hit ratio is 87% and origin requests are down 6x.

**Integration path:** CloudFront API through boto3/CLI: GetDistributionConfig/UpdateDistribution with ETag; Cache, OriginRequest and ResponseHeaders policies; CreateFunction/TestFunction/PublishFunction; the KeyValueStore API; CreateContinuousDeploymentPolicy; CreateInvalidation. Inputs include CloudWatch CacheHitRate and 4xx/5xx metrics, standard or real-time logs through Athena, and S3 GetBucketPolicy for OAC checks. It can also emit Terraform/CDK diffs.

**Demand 4/5 · Buildability 4/5**

### 4. AWS Organizations + AWS Control Tower (SCPs, RCPs, declarative policies, tag/backup policies, OUs, Account Factory, Control Tower controls) `closed`

**Why it's powerful:** It is the one place to set guardrails across every AWS account a company owns. SCPs and RCPs cap what any principal or resource can do, declarative policies enforce service config org-wide, and Control Tower adds hundreds of preventive, detective and proactive controls plus Account Factory and a landing zone. Nearly every org with more than a handful of AWS accounts runs it.

**Why people bounce off it:** An SCP is a deny ceiling that never grants anything, and it combines with OU inheritance, IAM, RCPs, permission boundaries and resource policies, so nobody can predict what a change will break. The IAM policy simulator doesn't fully model SCPs and RCPs. Policies are capped at 5,120 characters and 5 per OU, so teams hand-golf JSON with NotAction and conditions like aws:PrincipalOrgID and aws:CalledVia. When something breaks, CloudTrail only says 'explicit deny in a service control policy', without naming the policy. Platform teams are afraid to touch it, and app teams wait days for exceptions.

**AI operator:** A 'Guardrail Copilot'. It pulls the OU tree, attached SCPs, RCPs and declarative policies, and enabled Control Tower controls into a local model, then answers 'can account X do Y' by evaluating the full policy chain. It drafts changes, checks them with Access Analyzer ValidatePolicy plus size and quota limits, and replays 30 days of CloudTrail to list exactly who would have been denied. Rollout is a staged PR: a test OU first, then promotion. It also decodes any AccessDenied event back to the exact policy and statement that caused it.

**Killer example:** User says: 'Block every region except us-east-1 and eu-west-1 for all workload OUs, but don't break IAM, CloudFront, Route 53, Support or our break-glass role, and tell me who it would have hit last month.' The AI writes a region-deny SCP using NotAction for global services and an ArnNotLike exemption for the break-glass role, and checks it fits in 5,120 characters (3,980 used). Replaying org-trail CloudTrail across 84 accounts, it finds 3 principals in 2 accounts calling ap-southeast-2: a forgotten Lambda cron and a data-science SageMaker notebook. It also flags that the existing 'DenyLeaveOrg' SCP would push the Workloads OU past the 5-policy limit and proposes merging the two. It attaches the SCP to the Sandbox OU, opens the promote-to-Workloads PR, and drafts heads-up messages to the 2 account owners.

**Integration path:** Organizations API (ListRoots/ListOrganizationalUnitsForParent, ListPoliciesForTarget, CreatePolicy, AttachPolicy, DescribeEffectivePolicy), the Control Tower API (ListEnabledControls, EnableControl, GetLandingZone, EnableBaseline) and the Control Catalog API. Access Analyzer ValidatePolicy, CheckNoNewAccess and CheckAccessNotGranted handle policy checks, and CloudTrail Lake or Athena over the org trail handles replay. All of it is reachable from boto3 with a read-only management or delegated-admin role, and output can be a Terraform/CDK PR.

**Demand 5/5 · Buildability 3/5**

### 5. JMP Statistical Discovery (JMP / JMP Pro, plus JMP Live) `closed`

**Why it's powerful:** It is the standard analysis desktop in semiconductor, pharma, chemicals and manufacturing quality. Graph Builder, Fit Model (mixed models, REML), Custom DOE, Control Chart Builder, MSA/Gage R&R, reliability and Functional Data Explorer all come in one interactive tool. Every analysis is scriptable in JSL, and JMP 18+ also embeds Python.

**Why people bounce off it:** Most of the useful options are buried in nested red-triangle menus. Fit Model expects users to understand effect roles (nested, random, crossed), DOE needs factor and constraint setup, and control charts need phase and subgroup columns. Most engineers learn 2-3 platforms and push every question through them, with t-tests everywhere. Even when the numbers are right, interpreting a 6-panel report with REML variance components is a second hurdle.

**AI operator:** A JMP add-in with a docked chat panel. It reads the open table's schema (column names, modeling types, value labels) and has an LLM choose the right statistical approach and generate JSL from a vetted per-platform template library. The add-in runs the JSL in a sandboxed namespace, then walks the report display tree to extract estimates, p-values, variance components and capability indices. It returns a plain-language verdict with assumption checks and saves the JSL to the table so the analysis can be reproduced.

**Killer example:** User says: 'Yield dropped on line 3 last month. Is it the new chamber, the new resist lot, or just noise? And if it's real, design me the smallest experiment to fix it.' The AI fits Yield ~ Chamber + Resist Lot (random) + Shift with REML, adds Tukey HSD and residual checks, and runs a control chart with a phase column at the changeover date. It reports: 'Chamber C is 2.1 points lower (p<0.001); resist lot explains only 6% of variance; the shift appeared on Sept 9, the day C's RF generator was swapped. Ppk for C is 0.82 vs 1.4 for A/B.' It then builds a 12-run Custom Design on RF power, pressure and gas flow for chamber C, with randomization and blocking by day. Both scripts are saved to the table as 'Line 3 yield study' and 'Chamber C DOE'.

**Integration path:** JSL covers every platform, and launch/report scripts can be recorded with 'Save Script to Data Table', which makes it easy to build few-shot examples. Add-ins (.jmpaddin) are a documented format. HTTP Request() or the embedded Python can call an LLM endpoint. JMP Live has a REST API for publishing results. MVP: a chat add-in, a schema extractor, JSL templates for about 10 platforms, and a report-tree summarizer.

**Demand 4/5 · Buildability 4/5**

### 6. XWiki (Standard + structured apps, App Within Minutes, LiveData, Velocity/Groovy scripting) `open-source`

**Why it's powerful:** An LGPL, self-hostable enterprise wiki that doubles as an app platform. Pages can hold typed objects defined by classes, App Within Minutes builds CRUD apps with no code, LiveData tables query structured data, rights inherit through nested spaces, and there are 900+ extensions, including a Confluence migrator. It is the knowledge component of Germany's sovereign openDesk suite and a leading landing spot for teams leaving Atlassian Data Center before its March 2029 end of life.

**Why people bounce off it:** Anything beyond plain pages means learning several separate concepts. Structured data uses a 4-part pattern (classes, objects, sheets, templates). Rights mix allow and deny across wiki, space and page levels plus groups. Dynamic content needs Velocity or HQL inside {{velocity}} macros. The Confluence migration leaves unconverted macros and broken links to fix page by page. Most teams end up with a flat Confluence clone and never use the structured features they chose XWiki for.

**AI operator:** 'XWiki Architect'. The user describes a process, dataset or permission intent, and the operator turns it into XWiki artifacts: classes, sheets, templates, AWM apps, LiveData macros and rights entries. It also cleans up after a Confluence import by mapping leftover macros to XWiki equivalents, fixing links and rebuilding page-tree permissions. It shows a dry-run diff of every page and object it will touch, applies changes over REST, and records a revertible page version for each one.

**Killer example:** User says: 'We just migrated 6,000 Confluence pages. Fix the broken stuff in the Engineering space, then turn our 40 loose decision pages into a real decision log: status, owner, date, linked ADR, a create form, a table on the space home showing accepted decisions from the last 90 days, and only architects can edit.' The AI scans the space and finds 312 unconverted macros. It maps 290 of them (jira, expand, status, info panels) to XWiki equivalents and lists 22 that need human review. It repairs 148 broken links. It then creates the Decision class, sheet, template and 'New decision' button, extracts fields from the 40 existing pages into objects, adds a LiveData table with the HQL filter to the space home, and sets edit rights for XWiki.ArchitectsGroup only. A one-page diff summary lets the admin approve or revert each batch.

**Integration path:** XWiki REST API (/xwiki/rest) for pages, objects, classes, attachments, tags and search, plus rights objects (XWiki.XWikiRights). Anything REST can't reach is handled by pushing a small Groovy/Velocity script page and running it as an admin. Confluence import uses the filter-stream / Confluence Migrator extensions. MVP: an MCP server wrapping REST plus a validator that renders each page and checks for macro errors.

**Demand 4/5 · Buildability 4/5**

### 7. Medusa v2 (open-source headless commerce; Saleor and Sylius 2 as additional connectors) `open-source`

**Why it's powerful:** An MIT-licensed Node/TypeScript commerce engine (~30k GitHub stars) with a modular architecture. It supports regions with per-region currencies and tax/payment providers, sales channels, multi-warehouse stock locations and fulfillment sets, price lists with customer-group and quantity rules, and a v2 Promotion module (buy-get, tiered, campaigns with budgets), plus returns, exchanges and claims. Saleor (GraphQL) and Sylius 2 (Symfony/API Platform, popular with EU agencies) offer comparable depth with channels, zones, catalog and cart promotions.

**Why people bounce off it:** Agencies build the store and hand the admin to merchants. Wiring a region to tax, payment and fulfillment providers, setting shipping options per service zone and location, layering price lists over promotions, and modelling 'buy 2 get 1' with target and buy rules all require a mental model of the module graph. Some configuration is available only through the API. Merchants end up paying the agency for every operational change, and the 'it's for developers' reputation blocks non-technical store owners. Sylius has the same problem with zones, shipping categories and promotion priority and exclusivity.

**AI operator:** An 'Admin Copilot' plugin: a Medusa admin widget plus a backend route that reads the live configuration (regions, channels, locations, providers, price lists, promotions) and runs multi-step admin workflows from chat. It always shows a dry-run plan of the API calls first. Skills include onboarding a new market, building promotions, restocking and transferring inventory, bulk CSV price updates, and order exceptions. A config audit catches problems like 'region with no shipping option' or 'variant not in any sales channel'. Saleor and Sylius connectors map the same skills onto their APIs.

**Killer example:** User says: 'Start selling in Canada Monday: CAD prices at USD x 1.36 rounded to .99, ship from Toronto with flat $12 or free over $150, Wholesale B2B gets 15% off, and run a buy-2-get-1 on socks for launch week only.' The AI creates the Canada region with CAD, GST/HST tax and the payment provider. It links the Toronto location to a fulfillment set and service zone and creates two shipping options, the free one with a cart-total rule. It bulk-sets 1,840 CAD variant prices and flags 12 that would round below cost. It adds a B2B price list scoped to the customer group and channel, and a buy-get promotion in a dated campaign. Its audit finds 37 sock variants not in the Canada sales channel and offers to fix them. It finishes with a checklist and three test-cart quotes (retail under $150, retail over $150, B2B).

**Integration path:** Medusa's Admin REST API and JS SDK (@medusajs/js-sdk). Admin widgets and UI routes host the chat panel, custom API routes and Workflows SDK steps give compensating (rollback-able) multi-step operations, and the operator ships as an installable Medusa plugin. Saleor uses GraphQL plus its Apps framework. Sylius 2 uses an API Platform Admin API with Twig hooks for an in-admin panel. Solo MVP: one Medusa plugin with about 15 tool calls, tested against a local create-medusa-app.

**Demand 3/5 · Buildability 5/5**

### 8. commercetools Composable Commerce (Merchant Center + Cart/Product Discount predicates, Product Types, Price Selection, Stores/Channels) `closed`

**Why it's powerful:** The API-first enterprise commerce engine behind many large retailers. It supports any product-type schema, price scoping by currency, country, customer group, channel and validity window, multi-store and multi-channel inventory, and a full promotion engine (stackable cart and product discounts, discount codes, discount groups, multi-buy) defined in a boolean predicate language.

**Why people bounce off it:** Merchandisers have to write promotions in a predicate DSL, e.g. lineItemCount(sku in ("A","B")) >= 2 and customer.customerGroup.key = "vip", target line items with a second predicate, and get stacking mode and sortOrder right across dozens of live discounts. The Merchant Center builder only handles simple cases, so complex promotions become developer tickets. Precedence between product and cart discounts confuses even implementers, and a wrong sortOrder can silently double-discount or block a campaign.

**AI operator:** A 'Promo and Catalog Operator' that knows the project's product types, categories, customer groups, stores and existing discounts. It turns a promotion brief into CartDiscount or ProductDiscount drafts with valid predicates, targets, stacking mode and sortOrder. It simulates real carts through the Carts API in a staging store to show exactly which discounts fire, and explains 'why didn't promo X apply to cart Y' predicate by predicate. It bulk-edits prices and attributes through the Import API. Every write is diffed and can be rolled back.

**Killer example:** User says: 'Black Friday: VIPs in the DE store get 20% off winter jackets, buy-3-cheapest-free on socks for everyone, neither stacks with the employee discount, Friday 00:00 to Monday 23:59 Berlin time. Also, last year's campaign double-discounted some carts; make sure that can't happen.' The AI audits the 31 live discounts and finds the cause: last year's jacket promo sat below a sitewide 10% code with stackingMode=Stacking. It creates two CartDiscounts (customer.customerGroup.key="vip" with a category target, and multiBuyLineItems for socks) with StopAfterThisDiscount and a sortOrder above the employee discount. It converts the times to UTC and scopes both discounts to the DE store. It then runs 5 test carts (VIP with jackets, non-VIP, employee, VIP with the 10% code, mixed socks) and shows each total next to which discounts fired, before asking 'Publish?'

**Integration path:** A documented HTTP API with official TypeScript, Java and Python SDKs, OAuth2 client credentials with narrowly scoped keys (e.g. manage_cart_discounts only), an Import API and GraphQL. Free trial projects are available for development. It ships as a Merchant Center Custom Application so it sits inside the UI merchandisers already use. commercetools' own Commerce MCP covers generic CRUD, not promotion simulation and explanation.

**Demand 4/5 · Buildability 3/5**

### 9. Microsoft Dynamics GP (Great Plains), on-premises mid-market ERP `closed`

**Why it's powerful:** Decades of depth: multi-company, Analytical Accounting, Fixed Assets, Project Accounting, Multicurrency, Manufacturing, SOP/POP, payroll and 1099s. It runs on a SQL Server schema (GL00100, PM00200, SOP10100...) that tens of thousands of companies have customized with Dexterity, SmartList Builder and Management Reporter, often with 15+ years of history.

**Why people bounce off it:** The UI is a 1990s Dexterity client with modal windows and a Routines/Utilities/Maintenance menu maze. Period-end steps (year-end close, 1099 edits, reconcile utilities, batch recovery) are risky, and often only one 'GP person' knows them. Table names are opaque. Microsoft has stopped selling GP to new customers and ends support on 2029-12-31, with security updates until 2031-04-30. Experts are retiring while thousands of companies must keep GP running and also plan a migration.

**AI operator:** 'GP Whisperer'. It is a natural-language operator that reads the GP SQL schema and writes only through eConnect or Integration Manager. It is preloaded with a GP table/field dictionary and period-end runbooks. It answers plain-language cross-module reports, guides year-end and 1099 checklists with pre-flight checks (unposted batches, stuck SY00500 batches, AA mismatches), and handles bulk master-data fixes through eConnect XML. A migration-readiness mode profiles data quality, maps GP segments to a Business Central dimension design, and lists dead customizations.

**Killer example:** Controller says: 'Before we run 1099s, find every vendor we paid over $600 with no Tax ID or the wrong 1099 type, fix the ones whose W-9 says LLC taxed as S-corp, and show me the rest.' The AI joins PM00200, PM30200 and PM00202 and finds 37 vendors. It cross-checks W-9 attachment metadata and stages eConnect taUpdateCreateVendorRcd updates for the 18 exempt vendors. It lists the 19 with missing TINs and drafts a W-9 request email. Nothing posts until the controller approves.

**Integration path:** Reads go directly against the GP SQL Server database, whose schema is well documented, so the read path alone is a valuable MVP. Writes go through eConnect's XML business-logic procedures (taCreateVendor, taSopHdrIvcInsert...), so GP validation is never bypassed. Deploy as an on-prem Windows agent next to SQL Server with an LLM endpoint the customer chooses. Sell through the GP VAR network, which is looking for new services before the sunset.

### 11. Workday Adaptive Planning (FP&A: budgeting, forecasting, workforce and revenue planning) `closed`

**Why it's powerful:** One of the most widely deployed cloud FP&A platforms. It offers standard, cube and modeled sheets (workforce, capex, revenue), version management (actuals, budget, forecasts, what-if), level hierarchies with dimensions and attributes, account formulas, OfficeConnect, and Adaptive Integration loaders.

**Why people bounce off it:** Budget owners see a grid and can't tell why a number is what it is. Account formulas (ACCT.Revenue[time=this-12], ASSUM references) are readable only by the model admin. Adding a cost center, a hire or a scenario version means knowing which sheet type owns the data and how levels roll up. Most companies have 1-2 Adaptive admins who become a bottleneck every forecast cycle.

**AI operator:** 'Forecast Copilot'. It explains any number by walking the formula and rollup chain. It performs scenario edits from plain English as cube or modeled-sheet imports into a target version, and authors account formulas through updateAccount with a dry-run diff. It drafts monthly variance commentary from exportData and runs model-hygiene checks for orphan levels and broken assumptions.

**Killer example:** VP Finance says: 'In the Downside version, push engineering hires after July to January, cut paid marketing 20% from Q3 but keep events flat, and tell me EBITDA and runway by region.' ### 12. ONLYOFFICE Docs (Document/Spreadsheet/Presentation Editors, Document Builder, DocSpace) `open-source`

**Why it's powerful:** A full OOXML-native, self-hostable office suite embedded in Nextcloud, Seafile, Moodle, Odoo and others. It has 450+ spreadsheet functions, pivots, role-based PDF forms and real-time co-editing. One JS Office API runs in three places: in-editor macros, plugins, and the headless Document Builder engine.

**Why people bounce off it:** Automation is developer-oriented. Macros use ONLYOFFICE's own JS API, not VBA, so imported VBA macros break and Excel recipes from the web don't work. Mail merge, role-based form templates and bulk document generation all need Document Builder scripts or deep menus. Admins who leave Microsoft find their users can no longer automate anything, and the bundled AI plugin rewrites text rather than performing editor actions.

**AI operator:** An ONLYOFFICE plugin side panel plus a headless worker. An LLM loaded with the Office JS API reference and tested macro snippets turns requests into JS macros, previews them in plain language, and runs them through callCommand in the open document. Batch jobs become .docbuilder scripts run on the server. It also converts legacy VBA macros to ONLYOFFICE JS.

Result: '142 certificates generated, 9 rows flagged.'

**Integration path:** Plugins API (callCommand/executeMethod) for the live document, macros on the same Office JS API, open-source Document Builder (CLI plus Python/.NET/C++ bindings) for headless docx/xlsx/pptx/pdf, the Docs and Conversion APIs on the self-hosted Document Server, and the DocSpace REST API. MVP: a plugin plus a small Node service calling the LLM and docbuilder.
