### 1. Adobe Bridge: batch asset management, XMP/IPTC metadata and renaming for Creative Cloud (with a headless ExifTool path) `closed`

**Why it's powerful:** Bridge ships free with every Creative Cloud seat. It offers Batch Rename with sequence and metadata tokens, XMP/IPTC Core and Extension metadata templates, keyword hierarchies, Smart Collections, PDF contact sheets and web galleries, Photoshop batch processing (Image Processor), stacks, and ExtendScript automation with full XMP read/write.

**Why people bounce off it:** Most designers and photographers only use Bridge as a thumbnail browser. Batch Rename's token builder, IPTC templates, hierarchical keyword import and Smart Collection criteria are buried and unintuitive. Rights metadata (IPTC usage terms, model releases, creator contact) matters legally for agencies and stock submissions, yet almost nobody fills it in consistently. Delivering 2,000 assets to a client with correct names, keywords, descriptions and copyright takes a day of clicking.

**AI operator:** 'Asset Librarian' agent. It drives Bridge through ExtendScript or writes XMP directly with ExifTool. A vision model looks at each image or video and writes descriptions, alt text and keywords from the studio's controlled vocabulary. The agent applies the right IPTC rights template per client, batch-renames to the client's naming spec, builds Smart Collections, and hands deliverable exports to Photoshop Image Processor or Media Encoder. It can also audit a folder tree for missing rights fields, duplicate names and colour-profile mismatches.

**Killer example:** A photographer says: 'Acme's Q3 shoot goes out Friday. Rename everything ACME_2026Q3_<shot>_<###>, stamp our copyright and Acme's 2-year web-only usage terms, keyword it from Acme's product taxonomy, write alt text, export 2400px sRGB JPEGs, and make a contact sheet.' The AI tags 1,140 images with vision plus the taxonomy and sends 38 low-confidence ones to a quick review grid. It writes IPTC Core, IPTC Extension and hierarchical keywords to XMP and shows a before/after rename table for approval. It runs the exports and builds the PDF contact sheet. It also stops the delivery on one real risk: 17 frames show identifiable people but have no model-release ID, and it puts them in a 'Blocked – needs release' Smart Collection. A full day of clicking takes about 20 minutes of review.

**Integration path:** Bridge ExtendScript/JavaScript scripting (Bridge DOM: app.document, Thumbnail, Metadata, XMPScript), startup scripts for custom menu commands, and BridgeTalk to send jobs to Photoshop and Media Encoder. The headless path writes XMP sidecars and embedded metadata with ExifTool, so Bridge doesn't have to be running. MVP: an ExifTool plus vision-LLM CLI or desktop app, with an optional Bridge script panel for in-app commands.

**Demand 4/5 · Buildability 5/5**

### 2. Amazon ECS (Elastic Container Service) on Fargate/EC2: task definitions, services, capacity providers, ALB target groups, Service Connect, deployment circuit breaker, autoscaling `closed`

**Why it's powerful:** ECS is the default container platform for a large share of AWS shops that don't want to run Kubernetes. It gives serverless Fargate or EC2 capacity, IAM task roles, native ALB/NLB integration, Service Connect and Cloud Map discovery, blue/green and rolling deploys with automatic rollback, Spot capacity providers, secrets from SSM and Secrets Manager, and FireLens log routing, with no control plane to run.

**Why people bounce off it:** One working service touches a dozen resources across several consoles. The task definition alone has pitfalls: valid Fargate cpu/memory pairs, awsvpc networking, executionRoleArn vs taskRoleArn, secrets ARNs and logConfiguration. Then come the service (subnets, security groups, assignPublicIp, health-check grace period), the ALB target group (ip target type, health-check path, deregistration delay), autoscaling policies and IAM roles. Failures are opaque: CannotPullContainerError, 'ResourceInitializationError: unable to pull secrets', tasks stuck in PROVISIONING, and restart loops from failed health checks all mean digging through stopped-task reasons, VPC endpoints and security group rules.

**AI operator:** 'ECS Pilot' has four skills. (1) It generates or patches task definitions and services from an intent spec, checking Fargate cpu/memory pairs and IAM policies. (2) It debugs stopped tasks by pulling stoppedReason, CloudWatch logs, target-group health, SG/NACL paths, VPC endpoints and IAM policy-simulation results into one diagnosis with a fix. (3) It deploys safely: registers a revision, updates the service with the circuit breaker on, watches the rollout, and rolls back automatically. (4) It cuts cost with Spot weights, rightsizing from Container Insights, and scheduled scale-to-zero for non-prod environments.

**Killer example:** An on-call engineer at 2am says: 'orders-api has been flapping since the 11pm deploy, fix it.' The AI reads the last 20 stopped tasks, which all failed ELB health checks. It then finds three causes the console would never connect. The target group checks '/', but the logs show the app serves /healthz on 8080. Warm-up takes about 85 seconds while the grace period is 30. The new revision also moved to port 8080, and alb-sg has no ingress rule to task-sg on that port. It proposes a 3-line fix as a Terraform diff plus a live-apply option. After one 'yes', it applies the fix, forces a new deployment, watches until 4/4 tasks are healthy, and writes a 5-line incident summary with timeline and root cause into Slack. Diagnosis takes minutes instead of an hour of console-hopping.

**Integration path:** AWS SDK/CLI (ecs, elbv2, application-autoscaling, ec2, iam simulate-principal-policy, logs, cloudwatch), fully headless: a read-only IAM role for diagnosis and a scoped write role for changes. It can emit CDK, Terraform or CloudFormation diffs for IaC-managed stacks and checks drift before any live change. Competitive note: the awslabs ECS MCP server covers containerize and deploy helpers. The gap is failure diagnosis across ECS, ELB, VPC and IAM, plus safe change orchestration.

**Demand 4/5 · Buildability 4/5**

### 3. AWS Security Hub (+ Security Hub CSPM, GuardDuty, Inspector, AWS Config conformance packs) across AWS Organizations `closed`

**Why it's powerful:** It is the central AWS security aggregator. It pulls findings from GuardDuty, Inspector, Macie, IAM Access Analyzer, Config rules and CSPM standards (FSBP, CIS, PCI DSS, NIST 800-53) across every account and region, normalizes them (ASFF/OCSF), and supports automation rules, central configuration policies and EventBridge-driven remediation. Nearly every AWS-heavy org has it on because of audit requirements.

**Why people bounce off it:** A typical org gets tens of thousands of findings, and the console only offers filter-chip triage. The same issue shows up as duplicates across standards, accounts and regions. Doing useful work means knowing control IDs (EC2.19, S3.8), delegated-admin and home-region aggregation, per-OU central configuration policies, automation-rule criteria syntax, the suppression workflow, and which Config rule backs which control. Remediation is manual per resource or needs hand-built SSM/EventBridge pipelines, so teams export to spreadsheets and the posture score stays stuck.

**AI operator:** 'Posture Operator' queries findings, groups them by root cause instead of by control, and ranks them by real exploitability: internet exposure plus a known CVE plus a privileged role. It writes automation rules (suppress or re-severity, with justification), per-OU central configuration policies and SSM Automation remediations, and previews each one before applying. It keeps an exceptions register for auditors. Asked 'why is this account at 62%?', it answers with the five changes that would raise the score the most.

**Killer example:** A platform lead says: 'We have 14,000 findings and an audit in 3 weeks. What actually matters, and make the noise go away honestly.' The AI collapses 14,000 findings into 41 root causes. 11,200 come from the Sandbox OU, and 1,900 are CIS controls that duplicate FSBP. Three items go to the top: 9 internet-facing EC2 instances with critical Inspector CVEs and an admin instance role. It drafts a Sandbox suppression rule with a written justification, a central config policy that removes the duplicate CIS controls, and an EventBridge-to-SSM auto-fix for public S3 buckets that excludes the static-site account. It previews each change with counts and applies them after approval. It then produces an auditor-ready exceptions register plus a 10-line owner-tagged remediation plan. Projected score: 58% to 91%.

**Integration path:** AWS SDK/CLI, all headless: securityhub (get-findings, batch-update-findings, create-automation-rule, create-configuration-policy), guardduty, inspector2, config, organizations, events and ssm. It runs from the delegated-admin account with a read-only role by default and a separate, approval-gated remediation role. MVP: a CLI or Slack bot plus a small web UI. Wiz and Orca overlap but are expensive separate platforms. This is a thin NL operator on native Security Hub for teams that already pay for it.

**Demand 4/5 · Buildability 4/5**

### 4. Zoho Analytics (Cloud + On-Premise edition) `closed`

**Why it's powerful:** It is the default BI tool for the large Zoho One and SMB installed base, especially in India, the Middle East and LATAM. It has 500+ connectors (Zoho CRM, Books and Desk, QuickBooks, Google Ads, databases), SQL Query Tables, formula and aggregate-formula columns, lookup-column data modelling, pivots, KPI widgets, dashboards, row-level sharing filters, scheduled emails and white-label embedding. An On-Premise edition exists for self-hosting.

**Why people bounce off it:** Business users hit a wall as soon as data comes from two sources. They need to understand lookup columns (Zoho's join model), Formula Columns vs Aggregate Formulas, when to write a Query Table instead, and why a chart double-counts after a join. Row-level security through 'Share with criteria filters' and per-user dashboard permissions is a maze. Most orgs end up with one 'Zoho Analytics person' who gets asked for every new report.

**AI operator:** 'Zoho Analytics Analyst' is a side panel or Cliq/Slack bot. It reads workspace metadata (tables, columns, lookups, existing views) and turns plain-language requests into Query Tables (SQL), formula columns and report or dashboard definitions, which it creates through the API. It warns about join and double-counting risks before committing, and sets criteria-filtered sharing per user or role. It also audits the workspace for orphaned or duplicate reports, broken lookups and sync failures.

**Killer example:** A sales head says: 'Show monthly revenue per rep: CRM closed-won next to Books invoices actually paid, India only. Each rep sees only their own numbers, and I get it every Monday at 9.' The AI finds there is no lookup between CRM Deals.Owner and Books Invoices.Salesperson and proposes one. It warns that joining at deal level would double-count split invoices, so it aggregates first. It writes the Query Table, a combo chart and a pivot, builds a 'Rep Performance' dashboard, shares it to 23 reps with Owner = ${LOGINUSER}, and schedules the Monday email. It closes with: 'Rahul's closed-won is ₹18L but only ₹6L is paid. 3 invoices have no salesperson and are listed here.' The one-week 'Zoho person' queue becomes a two-minute request.

**Integration path:** Zoho Analytics REST API v2 (OAuth2) covers workspace, table and view metadata, data import/export, Query Table and formula-column creation, report creation, sharing and permissions, and scheduled email/export. SQL export queries let the AI check numbers. The On-Premise edition exposes the same API. Distribute through the Zoho Marketplace or as a standalone web app with a Zoho OAuth client. Zoho's Zia answers questions but doesn't build models or sharing.

**Demand 4/5 · Buildability 4/5**

### 5. Frame.io (Adobe) V4: review, approval and media-asset hub `closed`

**Why it's powerful:** Frame.io is the default review-and-approval layer for most video studios and agencies, and for a growing share of design and photo teams. It offers frame-accurate comments, version stacks, custom metadata fields, collections, Camera-to-Cloud ingest, permissioned share links, and deep Premiere, After Effects and Resolve integration. V4 turned it into a metadata-driven asset manager.

**Why people bounce off it:** Producers get lost in V4's metadata model of custom fields, filter-based collections and field-level views. On a 40-deliverable campaign, nobody knows which versions are approved, which comments are still open across the stacks, or which share links expose what to which client. Triage is manual: reading 300 time-coded comments, merging duplicates and turning them into an editor task list takes hours every round. Most teams keep a spreadsheet next to Frame.io.

**AI operator:** 'Review Producer' reads the whole project graph through the V4 API: assets, version stacks, time-coded comments, metadata fields and share links. For feedback it clusters and de-duplicates comments, flags conflicting notes between reviewers, and exports an editor to-do list or Premiere/Resolve markers. For status it bulk-sets approval fields, builds collections, and creates or expires share links. For audits it reports public links, unapproved assets and silent reviewers. Custom Actions add right-click commands inside Frame.io.

**Killer example:** A producer says: 'Round 3 notes on the Nike spring campaign. What's still open, where do the brand team and our CD contradict each other, and give the editor a fix list he can drop straight into Premiere. Also lock down any public links older than two weeks.' The AI reads 312 comments across 14 latest versions and collapses them to 23 unique fixes. It flags 3 real conflicts, such as brand's 'music louder' against the CD's 'music down under VO' at 00:14 on the 30s cut, and drafts one clarifying question per conflict for the producer to send. It exports a Premiere marker XML per cut, sets Status to 'Changes requested' on 9 assets and 'Approved' on 5, and expires 9 stale public links after showing the list. A three-hour notes session takes about ten minutes.

**Integration path:** Frame.io V4 REST API via Adobe Developer Console (OAuth server-to-server or user auth): accounts, workspaces, projects, folders, files, version stacks, comments, metadata fields and shares. Webhooks for comment.created and file.ready, and Custom Actions for in-app triggers. Comments export to Premiere/Resolve markers (EDL/XML). MVP: a web app plus an MCP server over the V4 endpoints.

**Demand 4/5 · Buildability 4/5**

### 6. Graylog (Graylog Open, self-hosted; plus Enterprise/Security editions) `open-source`

**Why it's powerful:** A widely deployed self-hosted log platform and a common Splunk or ELK alternative for mid-size engineering, IT and MSP teams. It has GELF/Syslog/Beats inputs, real-time routing streams, a pipeline-rule processing language, per-stream index sets with rotation and retention, lookup tables (CSV, threat intel, GeoIP), event definitions with aggregation and correlation, notifications, content packs, and Sidecar-managed collectors.

**Why people bounce off it:** Getting value means stitching together five concepts: inputs, then pipeline rules (a custom when/then DSL with grok() and parse_json(), where stage order matters), then stream rules, then index sets (retention and rotation math), then event definitions (filter plus aggregation plus grace period). A pipeline not connected to the right stream silently does nothing. Grok patterns fail without explanation, and retention settings fill the OpenSearch disk. Many installs never get past 'raw syslog in, full-text search', and alerting stays unused.

**AI operator:** 'Graylog Operator' knows the pipeline-rule grammar and function reference, the grok pattern library, stream and index-set semantics, and event-definition schemas. Given sample messages and a plain-language goal, it writes parsing rules and tests them against real messages with the pipeline simulator. It then sets up routing and retention, creates alerts, explains why a message didn't match, and generates Sidecar configs for new hosts.

**Killer example:** An SRE says: 'Parse our nginx logs, keep payments traffic for 90 days separately, and alert me if payments 5xx goes above 50 in 5 minutes.' The AI pulls 20 live messages and writes a grok pipeline rule. The simulator shows 18/20 parse, and the 2 failures are IPv6 client addresses, so it fixes the pattern and re-tests to 20/20. It creates a 'payments-nginx' stream with its own 90-day index set, sized at about 140 GB against 400 GB free disk. It wires the pipeline to the correct stream and stage, which is the step people usually miss, and creates the 5xx event definition with a Slack notification. It replays the last 24 hours and shows the alert would have fired twice, both during yesterday's 14:05 deploy. Setup takes one prompt instead of an afternoon of silent misconfiguration.

**Integration path:** Full REST API that the web UI itself uses (Swagger at /api/api-browser). It covers inputs, streams, pipelines, rules and connections, the rule simulator, index sets, event definitions, notifications, lookup tables, sidecars and search. Auth is by API token. It runs locally with docker-compose (graylog + opensearch + mongodb), and content packs let generated configs be exported and shared. A Wazuh or OpenSearch Security Analytics connector could come later. Realistic solo MVP.

**Demand 3/5 · Buildability 5/5**

### 7. Grist (grist-core, open-source relational spreadsheet with Python formulas; Grist Labs) `open-source`

**Why it's powerful:** Grist looks like a spreadsheet but is a relational database underneath. Formulas are full Python with rec/$column references, and it has Reference and Reference List columns, summary tables (live pivots), linked widgets for dashboard pages, form views, webhooks, and row- and column-level Access Rules. It is a self-hostable, free replacement for Airtable, Smartsheet and emailed Excel files.

**Why people bounce off it:** There are three walls. (1) Access Rules need thinking in rule order, table and column resources, user.Access, rec.Owner == user.Email, newRec and default rules. A wrong order either leaks data or locks everyone out, and Grist's own docs call it the hardest feature. (2) Data modelling: Reference vs Reference List vs lookupRecords, and how summary tables group. (3) Linked-widget 'select by' wiring is unintuitive. Users fall back to one giant flat table that everyone can see.

**AI operator:** 'Grist Architect' connects through the REST API, reads the schema from the _grist_Tables and _grist_Tables_column metadata, and turns requests into Grist user actions: AddTable, AddColumn with Python formulas, ModifyColumn to a Ref type, and AddRecord in _grist_ACLRules and _grist_ACLResources. It also generates summary-table pages. Before applying, it simulates access by impersonating each role ('View as') and shows a matrix of who can see and edit what. The existing formula assistant only covers single formulas; this operator also covers schema, pages and permissions.

**Killer example:** An ops manager says: 'Turn this Projects sheet into a proper tracker. Clients get their own table, each PM sees and edits only their own projects, Finance sees everything but can only edit Budget, and add a page with total budget per client.' The AI splits 212 free-text client names into a Clients table, merging 'Acme Inc' and 'ACME' after confirming. It converts Projects.Client to a Ref column and adds PM as Ref:Team. It writes three ACL rules in the correct order and builds a SUM($group.Budget) summary page with a linked chart. Before committing, it shows a permission matrix: 'Alice (PM) sees 14 rows, can edit 14. Bob (Finance) sees 212, can edit the Budget column only. Guest link sees 0.' It also catches that the existing public share link would have exposed Budget and offers to fix it. The feature Grist's docs call the hardest becomes a checked, previewed one-liner.

**Integration path:** Grist REST API (/api/docs/{docId}/tables, /records, /columns and /apply for raw user actions, including the ACL metadata tables) with API keys, plus the /sql endpoint for reads. Self-hosted grist-core runs as a Docker image. Ships as a Grist custom widget (iframe plugin API: grist.docApi.applyUserActions) inside the document, or as an MCP server.

**Demand 3/5 · Buildability 4/5**

### 8. Sieve mail filtering (RFC 5228 plus extensions), used by Fastmail, Proton Mail, mailbox.org, Posteo, Dovecot Pigeonhole/Roundcube, Stalwart and cPanel-hosted mailboxes `open-source`

**Why it's powerful:** Sieve is the standard, portable language for server-side mail filtering and does far more than click-built rules. Extensions include regex, variables, date and relational tests, vacation with :days, notify, fileinto :create, spamtest, header editing, include for shared libraries, and envelope and subaddress routing. Rules run on the server, so they apply on every device and move between providers.

**Why people bounce off it:** It is a real programming language that punishes mistakes. require lines must declare the right extensions, 'stop' semantics are easy to get wrong, :contains vs :matches vs :regex behave differently, and header vs address vs envelope tests trip people up. Every provider supports a different set of extensions, and there is no dry-run. Anything beyond simple rules drops users into a raw editor where one syntax error can quietly stop all filtering, so most people never touch filters.

**AI operator:** 'Mailwright for Sieve' samples real mail headers over IMAP or JMAP, clusters senders and patterns, and writes a provider-aware script using only the extensions listed in the ManageSieve or JMAP capability list. It validates the script with Pigeonhole's sieve-test or a JS/Python parser and dry-runs it against the last N messages to show exactly what would move where. Deploys are versioned with one-click rollback. It can also explain and refactor an inherited script in plain English.

**Killer example:** A freelancer says: 'Receipts and invoices go to Finance/2026, anything from my accountant also goes to my wife, auto-reply to work mail on weekends saying I'll answer Monday, and get newsletters out of my inbox.' The AI scans 5,000 recent headers, finds 43 receipt senders plus subject patterns like 'Invoice #', and identifies 61 newsletter senders by List-Unsubscribe headers. It writes the script with redirect :copy for the accountant and a vacation block guarded by currentdate weekday. It says plainly that 'haven't opened in 60 days' can't be expressed in Sieve and offers a scheduled IMAP sweep instead. The dry-run table reads '312 would move: 188 Finance, 124 Newsletters; 0 errors'. It also warns that the 'Invoice' rule would catch 2 client project threads and adds an exception for those senders. It activates the script through ManageSieve, keeping v1 for one-click rollback.

**Integration path:** ManageSieve (RFC 5804, port 4190) on Dovecot, Stalwart, mailbox.org, Posteo and many cPanel hosts. JMAP for Sieve Scripts (RFC 9661) on Fastmail and Stalwart. IMAP/JMAP for header sampling and dry-runs. Validation with Pigeonhole sieve-test or an open-source JS/Python Sieve parser. For Proton, which has no filter API, it produces a validated script to copy and paste. Ships as a web app or CLI plus an MCP server.

**Demand 3/5 · Buildability 4/5**

### 9. Epicor Kinetic (formerly Epicor ERP 10) `closed`

**Why it's powerful:** It covers job costing, MRP and scheduling, multi-plant inventory and GL posting rules, and it is highly extensible. BAQs (Business Activity Queries) work as a query engine, BPMs (Method and Data Directives) as business rules, Epicor Functions as server logic, and Application Studio for UI layers. Small manufacturers depend on one overloaded 'Epicor person' or pay consultants $175+/hr per report or rule. Epicor's own AI (Prism, Grow) targets insight and agents, not authoring customizations.

**AI operator:** 'BAQ & BPM Operator' turns plain-language questions into BAQs and checks them by executing them through BaqSvc against live data before saving. It turns plain-language rules into BPM Data or Method Directives, or Epicor Functions, exported as solution packages for testing in Pilot. It also explains in plain English what an existing BPM or BAQ does.

**Killer example:** A plant manager says: 'Stop anyone releasing a job when any material is under 50% on hand and the customer is on credit hold, and give me a dashboard of jobs at risk this week.' The AI writes a Method Directive on JobEntry.Update that checks JobMtl against PartWhse on-hand quantity and the customer's credit hold, with a clear error message. It deploys it to Pilot and tests it on job 12045, which is blocked as expected. It then builds a 'Jobs_At_Risk_Week' BAQ joining JobHead, JobMtl, PartWhse and Customer, and adds it to a dashboard. A consultant ticket that would have cost about $1,500 is done in one conversation.

**Integration path:** Kinetic REST API v2 (OData for every business-object service; API keys plus basic or token auth). BaqSvc and BaqDesignerSvc create and execute BAQs. BpMethodSvc and Solution Workbench export/import handle BPM deployment. Epicor Functions are callable over REST. All changes go to Pilot/Test first and are promoted only after approval.

### 10. Znuny (community fork of OTRS; Request Tracker as a second connector) `open-source`

**Why it's powerful:** A full ITIL-capable self-hosted helpdesk. It has queues, roles and groups with fine-grained permissions, ACLs that change which fields and actions each agent sees, a BPMN-style Process Management engine, GenericAgent for bulk and scheduled actions, Postmaster regex email routing, escalation and SLA calendars, dynamic fields, and a GenericInterface web-service layer. Thousands of European public-sector, university and mid-market IT teams moved to it after OTRS dropped its Community Edition.

**Why people bounce off it:** Admins give up in AdminACL, Process Management and SysConfig. An ACL is a nested Properties/PropertiesDatabase/Possible/PossibleNot/PossibleAdd matrix where one wrong key silently hides a ticket type from everyone, with no preview. A process means Activities, Activity Dialogs, Transitions and Transition Actions on a fragile canvas. SysConfig has 2,000+ cryptically named settings, and the GenericAgent form has 100+ fields. Most installs end up with a few Postmaster regexes and one person who dares to touch the ACLs.

**AI operator:** 'Znuny Admin Copilot' turns plain-language policy into ACL YAML, process YAML, GenericAgent jobs, Postmaster filters, queues, SLAs, groups and SysConfig changes. Before import, it lists which agents, queues and ticket types are affected. It answers questions like 'why can't Maria close this ticket?' and keeps a pre-change YAML export for one-click rollback. Ticket-level bulk requests go through GenericInterface TicketSearch/TicketUpdate.

**Killer example:** User says: 'Hardware requests over 2,000 EUR need the department head's approval before Procurement. 1st-Level can't close them, and anything pending approval for 3 business days re-pings the head.' The AI creates the ApprovalStatus and Amount dynamic fields and a 3-activity process YAML (Request → Dept-Head Approval → Procurement) with transitions on Amount > 2000. It writes an ACL that removes 'closed successful' for the 1st-Level role while approval is pending, and an hourly GenericAgent reminder job that uses the SLA calendar. It shows a dry-run table of who can do what at each step before importing.

**Integration path:** GenericInterface web services (REST/SOAP) for ticket CRUD and search. The Perl Console (Admin::Queue/Group/Role/SLA::Add, Admin::Config::Update, Maint::GenericAgent::Run, Maint::Config::Rebuild). Native YAML import/export for ACLs and processes, plus SysConfig export/import. A read-only DB connection helps simulate effects. MVP: a sidecar container with console access plus a web chat, or an OPM package with an admin chat panel. The RT connector would use REST2, TicketSQL and generated Scrip/Lifecycle JSON.

**Demand 3/5 · Buildability 4/5**

### 11. Lightdash (open-source BI on top of dbt) `open-source`

**Why it's powerful:** The most popular open-source 'Looker alternative' for dbt shops (MIT, self-hostable via Docker or Helm). Metrics and dimensions are defined in dbt YAML, and business users get a governed Explore UI, dashboards, scheduled deliveries, and charts-as-code through the CLI.

**Why people bounce off it:** Business users can only explore what already exists in YAML. A new metric, join, custom dimension or time grain means asking an analytics engineer to edit dbt model YAML (meta.metrics, joins, additional_dimensions) and redeploy. Engineers in turn fight YAML sprawl, duplicate metrics, and hundreds of charts that break when a field is renamed. Lightdash's own AI answers questions over existing metrics but doesn't safely change the semantic layer.

**AI operator:** 'Lightdash Semantic Steward' has two modes. For business users, it answers questions, and when a metric is missing it drafts the dbt YAML change as a PR with a preview chart in a 'lightdash preview' project. For analytics engineers, it does bulk refactors: renaming or merging duplicate metrics and rewriting every affected chart through lightdash download/upload so dashboards don't break, followed by validation runs.

**Killer example:** User says: 'I need net revenue retention by signup cohort, monthly, excluding internal test accounts, on the Board dashboard.' The AI finds no NRR metric. It writes the YAML: a subscriptions join, an nrr metric built on the existing mrr metrics, and a default filter is_internal = false.
