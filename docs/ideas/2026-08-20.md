### 1. GoDaddy Domains & DNS `closed`

**Why it's powerful:** GoDaddy is the registrar of record for more domains than any competitor, which makes its DNS manager one of the most-used admin surfaces on the internet. It is a full authoritative DNS host: A/AAAA/CNAME/MX/TXT/SRV/NS records, TTLs down to 600 seconds, DNSSEC, nameserver delegation, domain forwarding, and WHOIS privacy. It ties directly into GoDaddy-resold Microsoft 365 and Google Workspace mail plans, cPanel hosting zones, and SSL issuance driven by domain-validation records. For agencies and resellers there is bulk portfolio management across hundreds of domains with auto-renewal, transfer and registrar-lock controls. Everything that matters is reachable through a clean REST API with a real sandbox.

**Why people bounce off it:** The single most common wall is that a user cannot add any DNS record at all because the domain is delegated to external nameservers — and the fix lives on a completely different screen than the one throwing the failure, with no pointer to it. MX setup is the next trap: pre-existing MX records must be deleted first or mail silently breaks, and the Priority field (lower number wins) produces misconfigured failover that generates no error, just undelivered mail. GoDaddy's own documentation concedes propagation can take 24–48 hours, so business owners routinely decide a correct change "didn't work" and re-break it mid-propagation. Connecting Google Workspace or Microsoft 365 means getting SPF (TXT), DKIM (CNAME) and MX right across two vendors' UIs simultaneously, and no screen anywhere confirms "email will now work end to end." The API has its own landmine that mirrors the UI's: a `PUT` to `/records/{type}` replaces *every* record of that type, so a naive automation that meant to add one MX record silently deletes the rest.

**AI operator:** A domain-health operator with four skill packs. **Zone reader** pulls the full record set and, critically, verifies GoDaddy is actually authoritative before attempting any write — enforcing the precondition that traps most real users. **Mail wiring** diffs the current zone against known-good templates (Google Workspace MX set, Microsoft 365 MX + SPF + DKIM set) and produces a plain-English diff, so the user just says "connect my domain to Google Workspace." **Record surgery** handles adds and edits, defaulting to additive `PATCH` semantics and never using replace-by-type `PUT` without showing exactly which records would be destroyed. **Verification** does a post-change resolver lookup rather than declaring success on a 200. Safety model: GET-snapshot the prior record set before any write so it can be replayed as rollback; never touch NS or SOA without explicit typed confirmation; refuse to guess MX priority values. What makes it more than a chat wrapper is that it encodes GoDaddy's replace-by-type semantics and the nameserver precondition — the two things that turn a five-minute task into two days of broken email.

**Killer example:** User says: *"Point my email to Google Workspace and keep my website working."* → AI calls `GET /v1/domains/{domain}/nameservers` to confirm GoDaddy is authoritative and stops with an explanation if it is not, `GET /v1/domains/{domain}/records` to snapshot the current zone, computes a diff against Google's required MX set (five hosts with priorities 1/5/5/10/10) plus the SPF TXT record, shows the user exactly which existing MX records will be replaced and confirms the A record for the website is untouched, then on confirm calls `PUT /v1/domains/{domain}/records/MX` with the full replacement array and follows up with a live resolver lookup to verify.

**Integration path:** REST at `https://api.godaddy.com`, with a real sandbox at `https://api.ote-godaddy.com`. Endpoint families: `/v1/domains/{domain}/records` (GET, PUT replace-by-type, PATCH add), `/v1/domains/{domain}/records/{type}/{name}`, `/v1/domains/{domain}/nameservers`, plus domain availability and purchase endpoints. Auth is a Personal Access Token passed as `Authorization: sso-key {key}:{secret}`. There is no first-party CLI or SDK — only thin community wrappers — so the operator talks REST directly, which is fine given how small the surface is. Honest gaps: API keys are account-scoped rather than per-domain, so a multi-tenant product needs its own scoping and consent layer; and DNS propagation delay is physics, not an API limitation, so the operator can verify but cannot accelerate.

**Demand 5/5 · Buildability 5/5**

### 2. Sage Intacct `closed`

**Why it's powerful:** Intacct is a genuinely multi-entity, multi-dimensional general ledger built by accountants for accountants, and the AICPA's preferred provider. Its differentiator is dimensions — department, location, class, project, customer, vendor, employee — so one GL line carries six-plus analysis axes instead of forcing a bloated chart of accounts. It handles multi-currency consolidation, automated revenue recognition, and structured month-end close workflows for thousands of mid-market and nonprofit organisations. Smart Rules attach validation logic to almost any object via Add/Set/Delete triggers. Platform Services adds custom objects, custom reports and workflow, so finance teams effectively build applications on top of the ledger. REST API v1 exposes full CRUD over accounts, vendors, customers, items, dimensions, bills, invoices and journal entries.

**Why people bounce off it:** Users describe navigation as the worst part of the product — "getting used to navigating the menus was the worst part," and it "still feels cumbersome" even after learning it. Error messages are reported as confusing and typically carry a code the user cannot decode without support. Reports are called "really hard to understand," taking "hours and hours to figure things out." The most expensive trap is structural and irreversible: Intacct does not allow promoting an object from the entity level to the top level once it has been created, so a wrong dimension-level choice at setup takes substantial work to unwind and can require Sage engineering to perform a manual data fix. Smart Rules compound it — configuring one means picking from an Owner Object dropdown spanning dozens of objects and choosing among three trigger types, with no guidance about which combination actually fires when.

**AI operator:** Four skill packs. **Close the books** runs recurring journal entries, exercises Smart Rule validation, and generates dimension-sliced financial statements. **Fix a dimension mistake safely** produces a dry-run diff of every transaction that would be re-classed — and specifically refuses to walk into the one-way entity-to-top-level promotion trap, explaining the constraint instead. **Build this report** turns "spend by project and vendor last quarter" into the correct dimension-structure configuration rather than making the controller reverse-engineer the report writer. **Enter this transaction** handles vendor bills and journal entries from natural language. Safety model: every write shows a before/after balance diff and requires explicit confirmation; because posted GL entries are effectively immutable, "rollback" means auto-generating a reversing journal entry and handing back its reference number, which is how accountants actually undo things. The differentiator over a chat wrapper is encoded tacit expertise — Smart Rule owner-object semantics and the irreversible promotion trap are exactly what a generic assistant would cheerfully walk a controller straight into.

**Killer example:** User says: *"Reclass all August marketing spend from the Digital-Ads department to Growth-Paid."* → AI issues a GET against the journal-entry-line object filtered by `department = Digital-Ads` and period `2026-08`, presents a line-by-line diff with the dollar totals per account, and on confirm POSTs reclassing journal entries through the general-ledger journal-entry object — never mutating the original lines — then returns the reversing-entry number that would undo it.

**Integration path:** REST v1 at `https://api.intacct.com/ia/api/v1`, with the legacy XML Gateway still required for objects REST has not reached parity on. Auth is OAuth 2.0 authorization-code (Client ID/Secret from the Sage Developer Portal, `/oauth2/authorize`) *plus* a Sender ID — the Intacct Web Services License Key — baked into every request, which is an extra credential beyond standard OAuth that surprises most integrators. JWT bearer tokens; Postman collection and OpenAPI spec published on developer.sage.com. Honest gaps: the Sender ID must be requested from Sage support before an app can go live, so this is not purely self-serve, and several Platform Services features still require the older XML API.

**Demand 5/5 · Buildability 4/5**

### 3. BILL (Bill.com) `closed`

**Why it's powerful:** BILL is the largest independent SMB and mid-market AP/AR automation platform, and it sits as the payables layer across the QuickBooks Online, Xero and Sage Intacct ecosystems — a very large share of US bookkeepers and accountants already have a login. It covers bill capture with OCR, configurable multi-step approval routing, payment execution over ACH, check and virtual card, a vendor e-invoicing network, AP cards, and budgets. The v3 API exposes a broad object model: Bill, Recurring Bill, Vendor, Vendor Credit, Bill Approval, Invoice, Recurring Invoice, Customer, Credit Memo, Received Payment, Bank Account, Card Account, Budget, Reimbursement, plus Network Connection and Webhook Subscription objects.

**Why people bounce off it:** Reviewers call the platform confusing, with issues that are hard to resolve without long support waits. The most-cited concrete complaint is that there are "too many steps involved in getting a submitted invoice approved for payment" — and worse, approval and payment are bundled into a single approve-to-pay motion that blurs two genuinely distinct decisions. An AP clerk approves something and does not realise they have also queued the money to move. Configuring approval workflows and integrations is reported as taking real time to understand, with "a lot of options to explore" that "can feel overwhelming at first." The API itself shows the platform's age: authentication is session-based, `POST /v3/login` with username, password, organizationId and devKey returning a sessionId that expires after 35 minutes — not OAuth, not a static key — so any operator has to manage session lifecycle explicitly.

**AI operator:** Four skill packs, and the first one is the whole pitch. **Approve without paying** sets bill-approval status only and explicitly does not touch payment scheduling, directly dissolving the approve/pay blur that is the platform's top complaint. **Chase overdue bills** reconciles due dates against approval state and drafts vendor follow-ups. **Build an approval chain** turns "anything over $5k needs Dana, anything over $25k needs Dana and the CFO" into the multi-step routing config that otherwise takes an afternoon of clicking. **Network reconciliation** matches BILL Network invoices against recorded bills. Safety model is deliberately asymmetric: any payment-triggering action requires an explicit, separately-worded confirmation naming the amount, vendor and date — "this will schedule $12,400 to Acme Supply on 2026-08-27" — that is structurally distinct from approval confirmations; every write is preceded by a GET-based preview of the resulting object; and every money-moving POST is logged with its BILL transaction ID for audit. AP fraud and mis-payment risk is precisely why the approve/pay distinction deserves a hard gate rather than a chat wrapper's best intentions.

**Killer example:** User says: *"Approve all vendor bills under $500 from our top five recurring vendors, hold everything else."* → AI lists matching bills via the Bill list endpoint filtered by vendor and amount, presents the set as a checklist showing each vendor, amount and due date, and on confirm calls the Bill Approval endpoint for each one — while explicitly reporting that no Payment objects were created and no money will move until separately instructed.

**Integration path:** Sandbox at `https://gateway.stage.bill.com/connect/v3/`, production at `gateway.bill.com`. Auth is session-based via `/v3/login` returning a sessionId reused per devKey, with 35-minute expiry. BILL publishes a machine-readable endpoint index at `developer.bill.com/llms.txt`, and ships an official Postman collection; there is no first-party language SDK. Honest gap: a production devKey for a multi-tenant operator acting across many customers' BILL organisations requires BILL partner-program approval rather than self-serve signup, so single-tenant deployments are the fast path to a first customer.

**Demand 5/5 · Buildability 4/5**

### 4. Procore `closed`

**Why it's powerful:** Procore is the dominant construction project management platform, and it unifies genuinely distinct disciplines in one system: Project Management with RFIs, Submittals and Daily Log; Drawings and Sheet management with version control and markup; Financial Management with Change Orders and Commitments; Bidding; and Quality & Safety observations and inspections. The value is that one drawing set drives the RFIs, submittals and punch lists hanging off it, rather than four disconnected trackers. It supports company-level and project-level permission templates, custom fields, and a shared directory, plus a 400-plus-integration marketplace. General contractors standardise on it despite the cost precisely because nothing else spans preconstruction through closeout.

**Why people bounce off it:** Reviewers say plainly that "project setup is too difficult." Permissions must be configured per item and per document at *both* company and project level, and a directory has to be built at both levels before anyone can even receive emails or documents through the platform — a two-tier model that is invisible until something silently fails to reach someone. Users describe the modules as "confusing" and say they "don't work well with each other," which is a symptom of the same problem: each tool has its own permission surface. The sheer tool count overwhelms non-power users during onboarding, and G2/Capterra reviewers describe training as "overwhelming," often taking weeks, with a large fraction of features never discovered. The population here is project engineers and superintendents, not software people.

**AI operator:** Five skill packs. **RFI intake** turns a field note or photo caption into a correctly-routed RFI with the right ball-in-court assignment. **Submittal routing** builds and advances submittal workflows. **Daily log entry** captures weather, manpower and notes from a spoken end-of-day summary. **Change-order drafting** assembles the commitment and change-order records with the right cost codes. **Directory and permission setup** is the highest-leverage one — it clones a known-good project's permission templates and directory onto a new project, which is the exact task reviewers say is too difficult. Safety model: every write is staged as a diff against current Procore state and requires explicit confirmation before the POST or PATCH; permission-template and directory changes get an extra confirmation because they govern who can see financial data; a rollback pack re-applies the prior JSON snapshot. It beats a chat wrapper by holding the OAuth session, `company_id`, `project_id` and permission-template state across a whole multi-step setup instead of one disconnected call at a time.

**Killer example:** User says: *"Set up the Riverside project the same way as Main St — same permission templates, directory and RFI workflow."* → AI calls `GET /rest/v1.0/companies/{company_id}/permission_templates` plus the Main St project directory, diffs both against the empty Riverside project, shows exactly which templates and which twenty-three directory contacts will be created and at which level, then on confirm calls `POST /rest/v1.0/projects/{project_id}/permission_templates` and the directory and RFI configuration endpoints to replicate the setup.

**Integration path:** REST v1.0 JSON at `api.procore.com`, documented at developers.procore.com, with OAuth 2.0 in both authorization-code and client-credentials flavours via `login.procore.com/oauth`; access tokens expire in 1.5 hours so refresh handling is mandatory. Sandbox companies are free and self-serve, which is unusually generous for this category and materially de-risks a build. Endpoint families cover projects, RFIs, submittals, drawings, daily logs, change orders, commitments, users and permission templates. Honest gap: a public Marketplace listing requires a formal Certification Assessment and Marketplace Requirements review; private/internal apps appear not to need it, but Procore's docs do not state this explicitly, so a commercial build should confirm with their partner team before committing to a go-to-market that depends on the marketplace.

**Demand 5/5 · Buildability 4/5**

### 5. Ubiquiti UniFi Network `closed`

**Why it's powerful:** UniFi Network puts enterprise-grade routing, multi-AP WiFi, managed switching, VLANs and firewalling under a single controller — either a self-hosted UniFi OS Console or Ubiquiti's hosted Site Manager. It does Layer 3 VLAN segmentation, WireGuard and OpenVPN site-to-site tunnels, deep-packet-inspection traffic identification, adaptive WiFi tuning, zone-based firewalling on newer gateways, and per-client and per-VLAN QoS. The same console optionally runs Protect for cameras, Access for door control and Talk for phones, converging infrastructure that used to need three separate enterprise vendors. Millions of UniFi devices are deployed, and it is the default recommendation in SMB and prosumer IT circles because the feature set rivals Cisco- and Aruba-class gear at a fraction of the price.

**Why people bounce off it:** Ubiquiti's own help centre has to publish an article titled "Traffic and Firewall Rules" because the console exposes two overlapping rule systems — simplified Traffic Rules layered on top of the legacy granular Firewall Rules — and running both produces contradictory blocking behaviour with no unified "why is this device blocked" view anywhere. VLAN and firewall interaction is the single largest source of community forum threads: a misconfigured port profile silently drops traffic, surfacing nothing in the UI and diagnosable only from device-level logs. Gateways that have moved to the newer zone-based firewall present a third paradigm, and the available guides do not agree on how to migrate. The people hitting this are the ones who bought UniFi precisely because it was affordable enterprise gear — small-office owners and accidental IT admins trial-and-erroring their way through two rule systems at once.

**AI operator:** A network operator with three skill packs. **Rule authoring** encodes UniFi's actual precedence — Traffic Rules versus Firewall Rules, legacy versus zone-based mode detection — so "block guest WiFi from seeing the office printer" produces one correctly-scoped rule instead of a conflicting stack. **Segmentation setup** creates VLANs, SSIDs and port profiles as a coherent set rather than four disconnected settings pages. **Connectivity tracing** walks the client → port profile → VLAN → rule chain end to end to answer "why can't this device reach that one," which is the question the console cannot answer. Safety model: every mutating call is preceded by a dry-run that fetches current rules and renders a plain-language diff with an explicit confirm; rollback uses UniFi's native rule `enabled` toggle rather than deletion, so nothing is destroyed and a bad change is one flag away from reverted; changes that could sever the admin's own management path are refused outright. This is more than a chat wrapper because it resolves the cross-layer confusion Ubiquiti's own documentation acknowledges, using live controller state rather than general networking advice.

**Killer example:** User says: *"Keep guests off the office network but let them use the internet."* → AI lists existing networks and VLANs via the Integration API, creates an isolated guest VLAN and SSID if none exists, applies a Traffic Rule blocking guest-VLAN→LAN while permitting guest-VLAN→WAN, checks for pre-existing Firewall Rules that would conflict with it, and then verifies by pulling the client list and confirming no guest-VLAN device can reach the printer's IP.

**Integration path:** The official UniFi API exposes `/v1/...` REST endpoints per site for devices, clients and WiFi configuration, reachable either against the local controller or through Ubiquiti's cloud Site Manager API at `api.ui.com`, authenticated with an `X-API-KEY` header. The legacy local-controller surface at `/api/s/{site}/...` with session-cookie auth still underlies most third-party tooling and remains necessary for rule types the official API has not yet reached. Honest gap: an operator must bridge both API generations because coverage is not at parity, and self-hosted controllers mean per-customer network reachability is a deployment concern, not just an auth one.

**Demand 4/5 · Buildability 5/5**

### 6. Buildium `closed`

**Why it's powerful:** Buildium is a mainstream property-management platform, now part of RealPage, spanning Rentals (properties and units), Leases with renewals and recurring transaction schedules, tenant and owner portals, full double-entry accounting with GL entries, bank reconciliation and bill pay, work-order and task management, applicant screening, and owner distributions. What makes it unusually attractive as an operator target is that its Open API is genuinely self-serve REST — credentials are generated in account settings, with no partner-approval gate — which is rare in property management where Yardi and AppFolio both require partner programs. One integration can drive leasing, maintenance and accounting together.

**Why people bounce off it:** Reviewers say payment setup is "slow and confusing" with unclear fee structures, and rent collection is "cumbersome" specifically around prepaid rent, legal notices, and associating a payment with the right month — a bookkeeping ambiguity that produces wrong ledgers rather than errors. Security-deposit handling and rent-change workflows are described as clunky. Admin security and access-control screens are confusing. And the accounting story has a structural hole: Buildium does not sync with QuickBooks, so anyone running both is doing manual reconciliation forever. The user here is a property manager or a small landlord, not an accountant and definitely not a developer, being asked to operate a double-entry ledger correctly.

**AI operator:** Five skill packs. **Lease renewal** handles the renew-plus-rent-increase-plus-update-recurring-charge sequence that today spans three screens. **Recurring transaction setup** builds the charge schedules correctly the first time. **GL entry and bank reconciliation** posts and matches, in the user's language rather than in debits and credits. **Work-order dispatch** creates and assigns maintenance tasks. **Security-deposit disposition** walks the itemisation and return. Safety model: financial writes generate a draft GL entry rendered as a before/after ledger diff and gated on confirm; rollback is offered as a same-session reversal entry rather than deletion of a posted transaction, which is both how accountants actually undo mistakes and what an audit trail requires. It beats a chat wrapper by holding lease, unit and GL-account IDs across a multi-step task the UI deliberately spreads across separate screens.

**Killer example:** User says: *"Renew the Maple Ave unit 3 lease for another year at $50 more rent and update the recurring charge."* → AI calls `GET /v1/leases/{leaseId}` to read the current term and rent, posts a lease renewal with the new end date, then updates the lease's recurring-transaction resource so next month's charge reflects the increase — showing the before/after monthly charge and the new lease end date, and flagging that the prior recurring charge would otherwise have kept billing the old amount.

**Integration path:** REST/JSON at `https://api.buildium.com/v1`, authenticated with `x-buildium-client-id` and `x-buildium-client-secret` headers generated self-serve in account settings — no partner approval required. Endpoint families: Rentals, Leases, GLEntries, GLAccounts, Bills, Vendors, Tasks, Applicants, Owners and Bank Accounts, plus webhooks. Honest gaps: the GL endpoints require exact `accountingbasis` and date-range parameters that are easy to misuse and will silently return the wrong slice rather than error, and some UI reversal flows are not fully mirrored in the API, so the operator's reversal path needs testing against real ledgers before it can be trusted.

**Demand 4/5 · Buildability 5/5**

### 7. Semrush `closed`

**Why it's powerful:** Semrush bundles 55-plus SEO and marketing tools into one platform — Position Tracking, Site Audit, Backlink Analytics, Keyword Gap, Listing Management, Map Rank Tracker, the Content Marketing Toolkit and Traffic Analytics — and agencies run dozens of client projects in it simultaneously. Its keyword and backlink databases are among the largest commercially available, feeding both organic and paid competitive research from the same corpus. Projects act as persistent containers that continuously re-run Position Tracking and Site Audit crawls over time, so it functions as monitoring infrastructure rather than a one-off research tool. It is the closest thing the industry has to a standard SEO suite.

**Why people bounce off it:** A Capterra reviewer wrote that you need "a degree in semrush" to fully utilise it, and G2 reviews consistently cite the learning curve as a barrier for teams without dedicated SEO expertise — 55-plus tools produce a dense interface where beginners cannot tell which tool answers their question. The purchasing journey is separately confusing and upsells expensive add-ons with automatic plan renewal unless manually toggled off. The API compounds all of it with an opaque metered economy: unit cost varies roughly a hundred-fold by endpoint, from about 1 unit per row for a basic traffic overview to 100 units per row for historical paid-search data, and the Business tier enables API access while shipping with zero API units, so you must buy separate unit packages before executing a single call.

**AI operator:** An SEO project manager with three skill packs. **Audit triage** pulls Site Audit diffs overnight and prioritises fixes in plain language, ranked by traffic at risk rather than by Semrush's own severity labels. **Rank monitoring** manages Position Tracking keyword and competitor lists. **Competitive research** routes a question to whichever of the 55 tools actually answers it, which is the core discovery problem. The distinctive safety feature here is unit budgeting: because cost varies 100× by endpoint and is invisible until spent, the operator shows an estimate — "this pull will cost roughly 12,000 units, approve?" — before firing any bulk or historical query. That is spend protection for a metered API, structurally the same discipline an ads operator needs for budget. It beats a chat wrapper because knowing *which* endpoint answers a question is most of the value, and because no chat wrapper will warn you before burning a unit package.

**Killer example:** User says: *"Show me every keyword where we dropped out of the top 10 this week and draft content briefs for our three biggest traffic losses."* → AI calls the Position Tracking report endpoint to diff week-over-week rankings, quotes the unit cost of the follow-up pulls before proceeding, then calls Keyword Overview and Keyword Gap on the losers, ranks them by estimated traffic lost rather than by position delta, and drafts the three briefs.

**Integration path:** Two surfaces — the Standard/Analytics reporting API at `https://api.semrush.com` with key-based auth via query parameter, and the newer v4 API at `https://api.semrush.com/apis/v4/...` covering Projects, Position Tracking, Site Audit, Listing Management and Map Rank Tracker, using an API key plus OAuth 2.0 for some resources. No official CLI or SDK; community wrappers only. Honest gaps: most of the toolkit is read and report-pull, with a narrower write surface for managing Projects and campaigns, so this operator is heavily weighted toward analysis-and-recommend rather than take-action — and every call, read or write, spends the same opaque unit currency.

**Demand 5/5 · Buildability 4/5**

### 8. Genesys Cloud CX `closed`

**Why it's powerful:** Genesys Cloud CX is an enterprise contact centre covering the full stack: Architect, a visual designer for IVR and flows across voice, chat, email, SMS, social and bot channels; ACD omnichannel routing; Workforce Engagement Management with forecasting, scheduling and quality management; Predictive Engagement and Journey Orchestration; Data Actions for calling external systems from inside a flow; predictive routing and agent copilot; and deep interaction, queue and agent analytics. It has passed 2 million platform users and 500,000-plus agents across 3,100-plus customers at roughly $1.2B ARR, making it one of the most widely deployed contact-centre platforms in the enterprise.

**Why people bounce off it:** G2 reviewers name "steep learning curve" as the dominant negative, with onboarding for new admins commonly cited at four to eight weeks even with formal training. Editing even a simple IVR prompt requires understanding Architect's nested flow modules — menu flows, task flows, bot flows — plus Data Actions, and when a Data Action fails for a missing OAuth scope the error is vague enough to force trial-and-error debugging. Presence and routing configuration hides a genuine silent failure: if an organisation's default unavailable code is not explicitly mapped to a Presence Status, agent status stops syncing between the agent console and Omni-Channel, so agents appear available when they are not, and nothing throws. Diagnosing a single routing problem routinely means bouncing between Architect, Admin and Analytics, which reviewers describe as fragmented.

**AI operator:** Four skill packs. **Flow builder** drafts Architect flow definitions and Data Action payloads from plain language. **Routing and queue configurator** creates and edits queues, skills and routing rules. **Presence and capacity admin** owns the mapping layer, and specifically audits the unavailable-code-to-Presence-Status mapping that produces the silent desync. **Reporting digest** assembles the cross-screen answer to "why is this queue backing up." Safety model: diff the flow or queue JSON before publish; require explicit confirmation for anything touching live queues or presence mappings; dry-run new flow logic through Architect's flow-testing harness against sample interactions before it goes live; roll back via Architect's built-in flow version history, which is a real native safety net rather than a bolted-on one. The reason this beats a chat wrapper is that the leverage is in constructing flow, queue and routing objects through the Platform API under a scoped OAuth client — not in narrating which buttons to click in Architect.

**Killer example:** User says: *"Route all chats mentioning 'refund' to the billing skill queue with high priority, and alert a supervisor if wait exceeds three minutes."* → AI drafts an inbound chat Architect flow with a transcript-match decision block, creates the routing configuration via `POST /api/v2/routing/queues`, adds an SLA notification task wired to a Data Action, checks that the billing skill has agents whose routing profile actually includes the queue, renders the flow diff, and on confirm calls the Architect publish API.

**Integration path:** Platform REST at `https://api.<region>.pure.cloud` (for example `api.mypurecloud.com`) with OAuth 2.0 client-credentials. Endpoint families include `/api/v2/routing/queues`, `/api/v2/architect/flows`, `/api/v2/presence/definitions` and `/api/v2/users`. There is an official `gc` CLI, a Terraform provider (`MyPureCloud/genesyscloud`, marketed as CX-as-Code), and SDKs for Python, Node, Java and .NET. Honest gap and the reason buildability is 3 rather than 4: Architect's flow-authoring JSON is a proprietary and only partially documented grammar, so constructing flows via raw API rather than through the visual designer or CX-as-Code YAML is genuinely nontrivial engineering — the pragmatic build targets CX-as-Code as the emission format rather than raw flow JSON.

**Demand 5/5 · Buildability 3/5**

### 9. Synology DSM `closed`

**Why it's powerful:** DSM turns a Synology box into a small-business data centre. Btrfs snapshots give point-in-time rollback; Hyper Backup and Active Backup for Business provide agentless backup of servers, Microsoft 365 and Google Workspace; Synology Drive handles team file sync; and there is a VPN Server, Surveillance Station NVR, Container Manager and a built-in reverse proxy, all on top of layered ACL permissions over standard SMB, NFS and AFP shares. It supports RAID and SHR pooling, iSCSI targets, and a package ecosystem that includes Directory Server as an Active Directory alternative. Clinics, schools and small offices deploy it specifically because it undercuts a real SAN-plus-backup-vendor stack by an order of magnitude.

**Why people bounce off it:** DSM layers Windows-style share permissions on top of its own ACL system, and a detailed admin write-up notes the built-in permission-checking tool is misleadingly named — "perhaps 'Privilege Viewer' would be a more consistent name" — because it does not show effective combined permissions the way admins expect. Forum threads document the resulting nightmare: an admin grants Read/Write, verifies the box is ticked, and the user is still denied, with the real cause being mismatched numeric UID/GID values between DSM and the connecting client, surfaced only as the user showing "unknown" and never as an actionable message. Separately, limited accounts routinely cannot access their own home share until an admin enables the User Home service and re-applies permissions — a two-step dependency the user-creation wizard never mentions. None of these produce an error a non-technical admin would connect to the actual cause.

**AI operator:** Three skill packs. **Permission grants** encode the real model — DSM ACL versus legacy Unix-style versus share-level Windows ACL, plus the User Home service dependency — so "give Priya read-write to Accounting but nobody else" produces a correct minimal grant instead of an overbroad Everyone share. **Effective-permission explainer** computes what a given user actually gets on a given path, including UID/GID mismatch detection, which is the thing DSM's own tool refuses to do. **Backup policy** creates and verifies scheduled tasks with sane retention. Safety model: every permission or backup change is dry-run against live permission state and shown as an explicit before/after grant list requiring confirmation; because DSM has no native permission undo, the operator replays its pre-change snapshot to roll back; backup tasks verify target reachability and retention sanity before scheduling rather than discovering the problem at 2am on restore night.

**Killer example:** User says: *"Back up our QuickBooks server and email me if it ever fails."* → AI calls the Active Backup Web API to create a scheduled task targeting the server, sets a retention policy, wires a notification rule to task-failure status, then triggers a manual test run through the API and confirms it completed successfully before reporting done — rather than declaring victory on a created-but-never-executed job.

**Integration path:** DSM Web API at `https://{nas}:5001/webapi/entry.cgi`, which is self-describing through `SYNO.API.Info`. Session auth via `SYNO.API.Auth` (account and password exchanged for a `sid` token, with 2FA support). Documented API families include `SYNO.Core.*`, `SYNO.ActiveBackup.*` and `SYNO.FileStation.*`, published in Synology's official Developer Guide PDFs. SSH additionally exposes Linux-level CLI tooling (`synouser`, `synoshare`, `synogroup`) for anything the Web API misses. Honest gap: API coverage and documentation quality vary considerably by package and DSM version, so an operator needs version detection and graceful degradation rather than assuming a uniform surface.

**Demand 4/5 · Buildability 4/5**

### 10. Qualtrics XM `closed`

**Why it's powerful:** Qualtrics is the enterprise standard for advanced survey research. Multi-level Loop & Merge repeats blocks over a data table; Embedded Data variables thread state through an entire survey; the Survey Flow canvas composes Randomizer and Branch Logic elements into real experimental designs; real-time Quotas gate or redirect respondents mid-field; piped text personalises question wording; and the XM Directory panel layer supports longitudinal multi-wave studies. It powers CX, employee-experience and academic research at Fortune 500 and R1-university scale, and the people building these surveys are researchers, HR partners and marketers — not engineers.

**Why people bounce off it:** Qualtrics does not let Display Logic reference loop fields directly. The documented workaround is injecting custom JavaScript into the first question of a loop to copy the loop value into an Embedded Data field, and then basing Display Logic and Quotas on that field instead — which means a competent researcher is blocked until they write JavaScript. Deleting an Embedded Data element that a Display Logic condition depends on is worse: the system will not warn you, and the logic simply stops matching, silently, mid-field. Randomizer and Branch interaction is a third trap — a Branch placed loosely under a Randomizer can misfire onto the wrong element after a block completes unless it is nested inside a Group within the Randomizer. Every one of these produces bad data rather than an error message, and bad data in a fielded study is often unrecoverable.

**AI operator:** Three skill packs. **Survey flow build** assembles Block, Branch, Randomizer and Embedded Data elements from a described study design, including the correct nesting that keeps Branches from misfiring. **Quota wiring** translates "200 US and 200 non-US completes, stop when both are full" into correctly scoped Quotas — and applies the loop-and-merge JavaScript workaround automatically when the design needs it, removing the JavaScript prerequisite entirely. **Logic audit** scans for Display and Skip Logic referencing deleted or renamed Embedded Data before it silently breaks, which is a check the platform itself does not offer. Safety model is shaped by the API: the flow endpoint takes the entire JSON tree with no partial-patch semantics, so every edit is a whole-object round trip and a bad write is catastrophic. The operator therefore always GETs current flow, shows a structured before/after diff, and pushes to a *duplicated* survey by default unless the user explicitly says apply-live, with one-click revert to the cached prior flow.

**Killer example:** User says: *"Cap this survey at 150 completes from Enterprise-tier and 150 from SMB, and end it early once both are full."* → AI GETs `https://{datacenter}.qualtrics.com/API/v3/surveys/{surveyId}`, adds an Embedded Data element carrying tier, creates two Quota objects via `POST /API/v3/surveys/{surveyId}/quotas` scoped to it, wires flow termination via `PUT /API/v3/surveys/{surveyId}/flow`, and shows the full flow JSON diff before pushing — flagging that this is a whole-tree replacement, not a patch.

**Integration path:** REST v3 at `https://{yourdatacenterid}.qualtrics.com/API/v3/`, auth via an `X-API-TOKEN` header. Endpoint families: `/surveys`, `/surveys/{id}/flow`, `/surveys/{id}/quotas`, `/distributions`, `/mailinglists`, `/responseexports`. There is an official Postman collection and mature community Python and Node wrappers, but no first-party CLI. Honest gap already noted and material: `/flow` has no partial-patch semantics, so any automated edit must round-trip the entire flow object, which raises the blast radius of a bad write and is exactly why the duplicate-by-default safety posture is non-negotiable here.

**Demand 4/5 · Buildability 4/5**

### 11. Miro `closed`

**Why it's powerful:** Miro is the mainstream infinite-canvas whiteboard for product, design and operations teams — workshops, retros, mind maps, kanban and diagramming — with hundreds of professional templates, Frames for structuring board sections, dedicated mind-map and flowchart tooling, sticky-note clustering and voting widgets, Talktrack recorded walkthroughs, and a Miro Apps and Miroverse ecosystem for embedding custom mini-apps directly on the canvas. Enterprise administrators get organisation, team and content-export management at scale through dedicated Enterprise endpoints. The REST v2 API is genuinely complete for content manipulation, and there is also a Web/Apps SDK for in-canvas JavaScript and a Miro MCP server.

**Why people bounce off it:** Reviewers report an "overwhelming amount of options and features," and specifically that users "spend too much time deciding how to arrange their setup versus simply arranging it" — hundreds of templates producing decision paralysis rather than a starting point. Onboarding non-Miro participants into a live workshop is slow, and boards get visually cluttered fast with several people editing simultaneously. The sharpest concrete trap is that item nesting inside Frames is invisible in the UI, so a select-all-and-move silently drags unrelated content along with it. The API's own history reflects the underlying complexity: Miro renamed widgets to items in v2 and split one polymorphic endpoint into per-type endpoints for sticky_note, shape, text, card, frame and connector, which the developer community had to relearn.

**AI operator:** Four skill packs. **Workshop setup** builds frames and stickies from a written agenda. **Retro synthesis** clusters and tallies stickies into themes and action items. **Diagram-from-text** turns a written process into shapes and connectors with sane layout. **Template picker** chooses and prefills the right template from a brief, which directly attacks the decision-paralysis complaint. Safety model: every action is staged as a diff — a preview list of items to create, move or delete with board coordinates — approved before the real POSTs fire; bulk destructive edits require explicit confirmation and are preceded by an API-duplicated board snapshot for one-click rollback. What it adds over a chat wrapper is a maintained frame/item parent-child model that the raw flat item list does not expose, which is exactly the invisible-nesting trap that catches humans doing select-and-move.

**Killer example:** User says: *"Turn my rough retro bullets into a board with Went Well / Didn't Go Well / Action Items columns, coloured stickies, and cluster the duplicates."* → AI calls `POST /v2/boards`, creates three frames via `POST /v2/boards/{id}/frames` for the columns, creates one sticky per bullet via `POST /v2/boards/{id}/sticky_notes` with position mapped inside the correct frame and `style.fillColor` set by category, then groups likely duplicates via `POST /v2/boards/{id}/items/bulk` after showing the diff.

**Integration path:** REST v2 at `https://api.miro.com/v2/*` with OAuth 2.0 (authorize at `https://miro.com/oauth/authorize`, bearer token per call). Endpoint families cover boards, frames, sticky_notes, shapes, texts, cards, connectors, tags and webhooks; there is also the Web/Apps SDK for in-canvas JavaScript and an official Miro MCP server, which shortens the build considerably. Honest gap: live multi-cursor presence and Talktrack recording are UI and SDK-only, so the REST API can create and edit content but cannot see or drive a live walkthrough — the operator is a board author, not a facilitator.

**Demand 5/5 · Buildability 5/5**

### 12. ADP Workforce Now `closed`

**Why it's powerful:** ADP Workforce Now is one of the largest US payroll and HCM platforms, running payroll, tax filing, benefits administration, time and attendance, and talent management for hundreds of thousands of employers. Its real moat is the compliance engine — multi-state and local tax, garnishments, ACA — which competitors struggle to match. The HCM API v2 is event-based rather than field-based REST: worker lifecycle changes are expressed as events such as `worker.birth-name.change`, work-assignment changes go through `/events/hr/v1/worker.work-assignment.modify`, and there is an Associate Certifications API v2 for credential tracking.

**Why people bounce off it:** Users report the platform "can sometimes be confusing to navigate when trying to find information about payroll and pay stubs," and implementation is described as complex for anyone unfamiliar with the system. The far more serious complaint is about consequences: reviewers cite "issues with tax compliance and long turnaround times to resolve problems, with errors often taking months or even years to correct." That asymmetry — easy to misconfigure, extraordinarily slow to unwind — is what makes this a high-value operator target rather than a convenience play. Mobile access is reported as slow and not user-friendly. The integration path is itself a wall: ADP's OAuth requires client-certificate mutual TLS on top of standard OAuth credentials, a materially higher bar than a typical bearer-token API.

**AI operator:** Three skill packs. **Run this pay period** walks a pre-close validation pass before submission, catching the classifications and rate changes that produce corrections later. **Why did this employee's pay change** diffs work-assignment and pay-rate events against the current pay statement and explains the delta in plain language — the single most common HR-generalist question and one the UI answers poorly. **Update this worker** constructs the correct event object rather than attempting a raw field edit. Safety model, sized to the stakes: every write is staged as a specific typed event, shown as a diff against current state, and requires explicit confirmation; the operator refuses outright to touch anything inside an already-processed or locked pay run rather than attempting a silent fix, because that is precisely how a small mistake becomes a multi-year correction. It beats a chat wrapper because it encodes ADP's event model — a naive "just update this field" approach does not map to how ADP actually processes changes, and a wrapper that assumes otherwise produces writes that appear to succeed and do nothing.

**Killer example:** User says: *"Sarah Chen moved from Marketing to Product last week, update her department."* → AI constructs a `worker.work-assignment.modify` event with the new department and cost centre, shows the diff against her current assignment including the effective date and which pay period it lands in, warns if that date falls inside an already-processed run, and on confirm POSTs to `/events/hr/v1/worker.work-assignment.modify`.

**Integration path:** REST under `api.adp.com` via ADP's Developer/Marketplace portal; HCM API v2 is event-based. Auth is OAuth 2.0 with client-certificate mutual TLS, with certificates requested through the ADP partner self-service portal and 60-day advance rotation notices. Honest gap, and the reason buildability is 2: credentials are issued only to ADP clients for their own data, or to vendors approved into the ADP Marketplace partner program, and that approval takes weeks rather than minutes. There is no self-serve path. A realistic build starts as a single-employer internal tool for a customer who already has ADP credentials, and only pursues Marketplace listing once the operator is proven.

**Demand 5/5 · Buildability 2/5**
