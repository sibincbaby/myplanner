### 1. Salesforce release management: Change Sets, DevOps Center, Metadata API and the sf CLI (moving config from sandbox to production) `closed`

**Why it's powerful:** More than 150k Salesforce orgs ship their admin changes (fields, flows, validation rules, permission sets, Lightning pages, profiles) through it. The Metadata API and sf CLI can retrieve, diff, validate, quick-deploy and roll back almost any part of an org's configuration.

**Why people bounce off it:** Change Sets make you hand-pick every component from paged lists, and they don't reliably pull in dependencies. A deploy fails on the first missing field, record type or picklist value, and one Flow can depend on a dozen components. Profiles only deploy partially. Production validation runs every Apex test and returns cryptic errors such as 'Field X does not exist on line 0'. Sandboxes drift from prod and there's no way to see what changed. DevOps Center expects Git and work items, which accidental admins don't understand. Many SMB admins end up rebuilding changes by hand in prod.

**AI operator:** A 'Release Butler' on top of the sf CLI and Metadata API. It retrieves the source and target orgs and builds a dependency graph from Tooling API MetadataComponentDependency plus parsing of Flow and FlexiPage XML. From that it computes the smallest package.xml that includes every dependency. It runs a check-only deploy with RunRelevantTests, explains each failure in plain language and adds missing dependencies automatically. It writes a readable release note and a rollback package, and quick-deploys once a human approves. A 'what drifted?' mode diffs sandbox against prod component by component.

**Killer example:** An accidental admin at 4:45pm on a Friday says: 'Push the new Renewal Risk field, the flow that sets it and the updated Opportunity page to prod tonight. Leave out the half-finished Quote changes. Last time I did this by hand it took 3 failed deploys.' The AI diffs both orgs and finds two dependencies the admin didn't list: the Risk_Level__c global value set and a new picklist value on the Enterprise record type. It also spots that the Opportunity page references a Quote LWC that isn't in prod. It removes that component from the page in a scoped copy, leaves out the 4 Quote components, and runs a validation deploy (212 relevant tests pass in 6 minutes). It reports: '9 components, 0 profile overwrites, validation ID 0Af... ready for quick deploy, rollback package saved to git tag pre-renewal-risk.' It schedules the quick deploy for 11pm and posts the release note in Slack.

**Integration path:** The sf CLI (project retrieve/deploy start --dry-run, project deploy quick), the Metadata API, and the Tooling API (MetadataComponentDependency, and SourceMember for change tracking). Auth uses OAuth web flow or JWT connected apps. Everything runs headless and can be scripted. The MVP is a local agent wrapping the sf CLI, with a git working copy as the diff and rollback store.

**Demand 5/5 · Buildability 4/5**

### 2. Microsoft Excel: Python in Excel (=PY cells running pandas, matplotlib, seaborn and statsmodels on Microsoft's cloud runtime) `closed`

**Why it's powerful:** It ships inside the Excel that hundreds of millions of people already use. Anaconda Python runs directly in cells. xl("Table1[#All]", headers=True) turns a range into a DataFrame, so pandas groupby, merge and pivot, regression, clustering and seaborn charts all work without leaving the workbook or installing anything. Results come back as Python objects or spill as Excel values, and they recalculate with the workbook.

**Why people bounce off it:** The office users who would benefit don't know Python, and Python users find the cell model strange. Cells run in row-major order across sheets, so a reference to a cell that comes later in the workbook is silently stale. Each cell needs a choice between Python Object and Excel Value output. There's no pip, only the curated Anaconda packages. Errors (#PYTHON!, #BUSY!, #CALC!) show up as opaque tracebacks in a side pane. Users also need xl() range syntax, run into compute-quota limits, and can only get external data through Power Query. Most people enable it, look at an empty =PY cell and close it.

**AI operator:** An Office.js task-pane add-in. Add-ins can write and read PY(). The operator reads the workbook schema (tables, headers, sample rows, named ranges) and writes a correctly ordered chain of =PY cells: load, clean, analysis and chart, each with a comment. It picks Object or Value output for each step and writes final results into native Excel tables and charts so colleagues who don't use Python can work with them. It reads #PYTHON! tracebacks and rewrites the cell to fix them. Skills include cohort retention, RFM segmentation, statsmodels ETS forecasting, outlier flags, fuzzy de-duplication and 'explain this workbook's Python'. It is restricted to the Anaconda package allowlist.

**Killer example:** A finance analyst who has never written Python, with a 40k-row Orders table, says: 'Build a monthly cohort retention heatmap by first-purchase month, forecast next quarter's revenue with a confidence band, and tell me which cohort churned worst and why.' The AI adds a 'Cohorts' sheet with 4 ordered =PY cells. The first loads Orders through xl(). The second derives first_month and pivots a retention matrix, spilled as a real Excel table. The third renders a seaborn heatmap image in the cell. The fourth fits a statsmodels ETS forecast. The first draft hits a #PYTHON! error on mixed date formats, which the AI reads and fixes on its own. A1 then says: 'Mar-2026 cohort retained 18% at month 3 vs 31% average; 62% of its customers came from the spring discount campaign. Q4 forecast: $1.21M (±$90k).' The analyst can refresh all of it.

**Integration path:** An Office.js Excel add-in (task pane plus an LLM backend). It writes cells with range.formulas = [["=PY(\"...\",1)"]] and reads them back. Workbook context comes from the Tables and Range APIs. It works in Excel for Windows, Mac and web for Microsoft 365 users with Python in Excel enabled, distributed through AppSource.

**Demand 4/5 · Buildability 4/5**

### 3. Amazon Cognito (User Pools, app clients, Managed Login, Lambda triggers, Identity Pools) `closed`

**Why it's powerful:** It's the default auth backend for a huge number of AWS-hosted apps. One managed service covers sign-up and sign-in, MFA, social and SAML/OIDC federation, custom auth flows via Lambda triggers (pre-signup, pre-token-generation, migrate-user), Managed Login branding, threat protection, M2M client-credentials, and Identity Pools that exchange user tokens for scoped IAM credentials.

**Why people bounce off it:** Developers often name it as their most-hated AWS service. Key settings, such as username vs. email alias and required attributes, can't be changed after the pool is created. People confuse pools with identity pools, and app clients with resource servers and scopes. Hosted-UI callback and logout URLs mismatch. Lambda trigger event shapes are barely documented, and federated IdP attribute mapping fails silently. Errors like 'invalid_grant' or 'redirect_mismatch' say almost nothing. Teams move to Auth0 or Clerk mainly to escape the setup pain.

**AI operator:** A 'Cognito Concierge'. It reads pools, clients, IdPs, triggers and domains through the AWS SDK and explains the current setup in plain words. It turns auth requirements described in plain language into a reviewed plan covering the pool, app clients, scopes, IdPs, attribute mappings, and Lambda trigger code with tests. It warns before any choice that can't be undone after creation. It diagnoses login failures by replaying the OAuth flow and correlating CloudTrail with the trigger's CloudWatch logs. Everything can be exported as CDK or Terraform.

**Killer example:** A startup CTO, two days before an enterprise pilot, says: 'Acme uses Okta. Let their people SSO in, auto-link to the email accounts they already made, put them in an "enterprise" group, add tenant_id to the access token, and figure out why our staging login throws redirect_mismatch.' The AI first diagnoses staging: the app client's callback list has 'https://staging.app.io/callback' but the SPA sends a trailing slash. It then adds an Okta SAML IdP with email and tenant attribute mappings. It writes a pre-signup Lambda that calls AdminLinkProviderForUser for existing emails, and a pre-token-generation V2 trigger that injects tenant_id and the group. It warns that the pool's case-sensitive usernames will make 3 existing users fail to link, and lists them. It shows a diff, applies it after approval, runs a test login, and displays the decoded JWT with tenant_id=acme. Finally it emits the matching CDK.

**Integration path:** The AWS SDK and CLI (cognito-idp, cognito-identity, lambda, logs, cloudtrail), using a read-only IAM role by default and writing only after a diff is approved. CDK and Terraform export support GitOps. It can run as a local MCP server or as SaaS assuming a cross-account role.

**Demand 4/5 · Buildability 4/5**

### 4. GitHub Projects (v2): org/user project boards with custom fields, iterations, views, built-in workflows, sub-issues and issue types `closed`

**Why it's powerful:** It's the free planning layer on top of repos millions of teams already use. It has typed custom fields, table, board and roadmap layouts, a filter language, Group by, Slice by and Sum, Insights charts, built-in workflows, sub-issues, issue types, and aggregation across repos and orgs. Configured well, it can replace Jira for many engineering orgs.

**Why people bounce off it:** Every project starts empty. Teams rebuild Status, Priority, Size, Iteration and Estimate fields and 5-10 views by hand, with hand-written filter strings. Iteration breaks need setting up too. Automation beyond the built-in toggles, such as parent rollup or iteration carry-over, needs GitHub Actions against GraphQL with node IDs and field option IDs, which is notoriously painful. Bulk edits, iteration rollover and 'what slipped' reports are all manual, so PMs give up and go back to spreadsheets or Jira.

**AI operator:** 'Projects Pilot', a GitHub App plus chat (Slack, web or MCP). It scaffolds projects from templates, translates plain English into the filter language and saved views, and bulk triages and edits items. It also rolls iterations over with carry-over reports, generates status rollups and burn-up charts from item history, and writes the GitHub Actions workflows the built-in automation can't handle. Every bulk write starts as a dry-run diff.

**Killer example:** An EM on Monday morning says: 'Roll Sprint 14 into Sprint 15. Carry over anything not Done, but flag items that have now slipped twice. Make a "Slipped" view. Size the 47 untriaged platform issues from their descriptions. Then tell me in one paragraph what slipped and why.' The AI moves 23 unfinished items to the new iteration. It tags 6 that also slipped from Sprint 13 and creates a view with the filter `iteration:@current label:slipped-2x -status:Done` grouped by assignee. It proposes S/M/L/XL sizes for the untriaged issues for one-click approval. Its summary reads: '5 of 6 double-slips are blocked on the infra/terraform-upgrade sub-issues owned by one person; consider splitting.' It also opens a PR adding `.github/workflows/rollup-parent.yml` so parents close automatically when their sub-issues do.

**Integration path:** The GraphQL API (ProjectV2, ProjectV2Field, ProjectV2ItemFieldValue, addProjectV2ItemById, updateProjectV2ItemFieldValue), the Projects REST API (Sept 2025), which has CRUD for projects, items, fields and views with filters, and the `gh project` CLI. It uses GitHub App auth and projects_v2_item webhooks. Some built-in workflow toggles may still need UI deep-links.

**Demand 4/5 · Buildability 4/5**

### 5. Tempo (Timesheets + Planner + Cost Tracker/Financial Manager) for Jira Cloud and Data Center `closed`

**Why it's powerful:** It's the de facto time, capacity and cost layer of the Atlassian ecosystem, used by tens of thousands of Jira customers and nearly every consultancy and agency that bills from Jira. It covers worklogs with work attributes, Accounts and Customers, Teams, approvals, workload and holiday schemes, Planner allocations, and cost and revenue tracking against budgets.

**Why people bounce off it:** End users hate logging time. They rebuild the week on Friday from memory, pick the wrong Account, or miss required attributes and get rejected. Admins deal with interlocking settings: Accounts linked to projects, mandatory attributes, workload and holiday schemes, approval periods, Planner capacity versus allocations, and cost rates. Answering 'why is project X 30% over budget?' means joining reports by hand. Existing Tempo MCPs only fill worklogs.

**AI operator:** 'Tempo Copilot' has three skill packs. (1) Timesheet autopilot drafts worklogs from Jira activity, commits, PRs and calendar events, using the right Account and attributes. (2) The manager and approver pack finds under-logged timesheets against workload schemes, bulk-approves clean ones and flags anomalies. (3) The admin and finance pack provisions Accounts, assigns schemes, creates Planner allocations, and answers budget-burn questions by joining Tempo with Jira data. Every write is staged as a changeset.

**Killer example:** An agency delivery lead on the last day of the month says: 'Who on Payments is under 90% of their workload? Nudge them with a pre-filled draft. Approve everyone whose time is all on billable accounts. And tell me why ACME-2026 burned 140 hours over plan before I call the client.' The AI finds 3 people under target. It DMs each in Slack with a draft week built from their Jira transitions, PRs and calendar ('Tue: 3h PAY-412 code review, 1h ACME sync'), each one a single click to submit. It bulk-approves 9 timesheets and holds 2 with non-billable entries on a billable account. It then reports: '92 of the 140 extra hours are 4 bug issues logged to ACME-2026 after the Sep 12 scope change (PAY-388 alone: 41h). These map to change request CR-7 in Confluence, which was never added to the budget, so they're likely billable as a change order.'

**Integration path:** Tempo REST API v4 (worklogs, accounts, customers, teams, plans, allocations, workload and holiday schemes, approvals, work attributes) with a PAT or OAuth, plus the Data Center endpoints. It pairs with the Jira REST API, Google or Microsoft Graph calendars, and Slack. It can ship as a Forge app or a web app plus MCP server.

### 6. Atlassian Opsgenie (on-call schedules, escalation policies, routing rules, alert policies, integrations, heartbeats), as a forced-exit operator to JSM Operations / Compass / PagerDuty / incident.io / Grafana IRM `closed`

**Why it's powerful:** Opsgenie runs paging for thousands of engineering orgs: layered rotations with restrictions and overrides, multi-step escalations, team routing rules, alert dedup and enrichment policies, and hundreds of inbound and outbound integrations.

**Why people bounce off it:** Atlassian ended sales in June 2025 and shuts Opsgenie down on April 5, 2027, deleting any data that hasn't been migrated. That is under six months away. Atlassian's tool moves data into JSM or Compass, but teams still have to choose a destination, re-point every monitoring webhook and API key, check that rotations, escalations and policies behave the same, and map concepts by hand for non-Atlassian targets. Nobody fully understands years of accumulated routing rules, and people are afraid of breaking paging.

**AI operator:** An 'On-call Migration Copilot'. It exports the full Opsgenie config and builds a plain-language model of who gets paged for what, and when. It flags dead config: rules that never fire, empty schedules and departed users. It generates the equivalent config on the target, checks equivalence by replaying historical alerts through both, and builds a checklist for re-pointing integrations by finding the webhook senders in Datadog, CloudWatch, Alertmanager and similar tools through their APIs. It runs test pages before cutover.

**Killer example:** A platform lead says: 'Move us to PagerDuty, merge the three platform rotations into one follow-the-sun schedule, and prove nobody loses coverage.' The AI reads 14 schedules and 9 escalation policies. It finds a Sunday 02:00 to 06:00 UTC gap and an escalation pointing at a deactivated user. It builds the PagerDuty schedules and escalation policies and renders a side-by-side coverage heatmap. It replays 200 historical alerts through both configs, with 197 matching responders and the 3 differences explained. It lists 23 Datadog and CloudWatch endpoints to switch, with diffs.

**Integration path:** Opsgenie REST API v2 (schedules, rotations, overrides, escalations, teams, routing rules, policies, integrations, alert history). Target APIs are PagerDuty REST and Event Orchestration, JSM Operations and Compass, incident.io, and Grafana OnCall/IRM, plus the monitoring tools' webhook APIs. It is time-boxed to the migration wave through April 2027 and can continue afterward as an 'on-call config hygiene' product.

### 7. Salesforce Experience Cloud (customer/partner portals: sites, sharing sets, guest-user access, audiences) `closed`

**Why it's powerful:** It turns a Salesforce org into authenticated customer, partner and dealer portals, with record access, case deflection, knowledge, PRM deal registration and audience personalization. It's widely deployed by Salesforce customers who need to give outsiders access to CRM data.

**Why people bounce off it:** External access stacks its own sharing model (external OWDs, sharing sets, share groups, partner role hierarchies, the guest-user profile and sharing rules) on top of Experience Builder pages, audiences and site settings. Admins either lock users out or accidentally expose records to the public guest user, which is how the well-known Salesforce community data leaks happened. Nobody can answer 'what can a partner user at Acme actually see?' without logging in as them.

**AI operator:** A 'Portal Access Operator'. It models a site's effective guest and external visibility from OWDs, sharing sets, share groups, profiles and permission sets using the Metadata and Tooling APIs, plus SOQL run as the user. It answers 'who can see X?', flags objects and fields exposed to guests, and generates least-privilege fixes as a deployable package with a before/after access diff. Positioning note: an earlier idea already covers internal Sharing & Visibility, so this one is limited to the external, guest and site-config surface.

**Killer example:** A security reviewer asks: 'Before our SOC 2 audit, prove anonymous visitors can only see published FAQ articles and partners only see opportunities they registered.' The AI audits the site. The guest profile has Read on Case and Contact, and an unauthenticated API call returns 1,412 Case records. The partner sharing set maps Account.Id on Opportunity without a registrant condition, so 3 sample partner users can see a competitor-partner's deals. It proposes removing guest Case/Contact access, adding a partner sharing rule on Registered_By__c, and limiting guest Knowledge to the FAQ data category. It shows a before/after visibility matrix and deploys after approval with a rollback package.

**Integration path:** The Metadata API (Network, ExperienceBundle, SharingSet, SharingRules, Profile/PermissionSet, Audience), the Tooling API, and the Connect REST API through the sf CLI. Effective-access checks use queries run as test external users and UserRecordAccess. Changes ship as validated deploys with rollback.

### 8. Adobe Substance 3D Designer (with the Substance 3D Automation ToolKit) `closed`

**Why it's powerful:** It's the industry-standard procedural material tool behind most AAA game, VFX and archviz texture libraries. Node graphs produce resolution-independent, parameterized materials that can be exposed as sliders and cooked to .sbsar files for Painter, Unreal, Unity, Blender and Houdini.

**Why people bounce off it:** It's node-graph programming in disguise. One convincing material takes 50 to 300 nodes and knowledge of about 400 library filters (Tile Sampler vs Splatter Circular, Slope Blur, Non-uniform Directional Warp), plus grayscale vs color inputs, output formats and bit depth, and $size inheritance. Painter users bounce off it, so studios depend on 1 or 2 material TDs and everyone else buys stock .sbsar files they can't customize.

**AI operator:** A 'Material TD in a box'. It has a library of vetted sub-graph recipes (cobblestone layout, moss driven by AO and curvature, edge wear, tiling breakup, brick bonds) that the LLM composes into a real .sbs through pysbs. It wires exposed parameters, cooks with sbscooker and renders previews with sbsrender. A vision model critiques the preview and the operator iterates. It can also explain an existing .sbs in plain English or add parameters to it.

**Killer example:** An environment artist says: 'Make a wet mossy cobblestone with irregular stones about 20 cm, moss only in the cracks and on upward-facing edges. Expose moss amount and wetness as sliders, and give me 4 seed variations at 2K as Unreal ORM-packed maps.' The AI builds a Tile Sampler stone layout, a crack mask, moss masked by slope plus cavity, and a wetness pass that lowers roughness and darkens albedo. It exposes moss_amount and wetness, cooks the .sbsar and batch-renders 4 seeds to BaseColor, Normal and ORM PNGs. It shows a contact sheet, and after self-critique it fixes visible tiling repetition with a breakup pass.

**Integration path:** Headless: pysbs (Automation ToolKit) builds and edits .sbs graphs, sbscooker produces .sbsar, sbsrender renders with overrides and seeds, and sbsmutator generates variations. Interactive: Designer's in-app Python API (the sd.* module), through a plugin that exposes an MCP or socket for live graph edits.

**Demand 4/5 · Buildability 3/5**

### 9. Scribus: open-source desktop publishing, the free alternative to InDesign and Publisher `open-source`

**Why it's powerful:** It produces professional print output: PDF/X-1a, X-3 and X-4 export, CMYK and spot colors, ICC color management, bleeds and crop marks, master pages, linked text frames, styles and tables. It's GPL, cross-platform and free. Scribus 1.6 has a full Python 3 Scripter API and can run headless (scribus -g -py), which makes it a self-hostable engine for newsletters, brochures and catalogs.

**Why people bounce off it:** It's notoriously hostile to people coming from Word or Publisher. Text only goes into frames you create and link by hand. Styles, master pages, colors and PDF/X presets each live in separate dialogs. Preflight output is cryptic, and units and DPI are confusing. Schools, churches, NGOs and print shops want to leave Publisher, which Microsoft retires in Oct 2026, but they give up on Scribus within an hour.

**AI operator:** A chat panel or MCP server that drives Scribus through the Python Scripter, either in-app or headless under xvfb. It generates layouts from a brief with master pages and a style set, flows DOCX or Markdown into linked frames and fixes overflow, and places and fits images with warnings when effective DPI is under 300. It converts RGB to CMYK, runs preflight and turns each error into a fix, and exports PDF/X with bleed for the print shop. It also adds CSV data merge (catalogs, badges), which Scribus doesn't have natively, and a Publisher-to-Scribus rebuild path through libmspub.

**Killer example:** A parish volunteer says: 'Make a 4-page A4 newsletter from this week.docx using last month's masthead. Put the events in a two-column box on page 3, use our dark green as a spot color, and give the printer a PDF/X-4 with 3mm bleed.' The AI loads last month's .sla, flows the DOCX into linked frames with the correct styles, builds the events box and adds the spot color. Preflight finds 2 images at 150 DPI, which it flags with suggested replacements. It then exports newsletter_PDFX4.pdf with bleed and crop marks.

**Integration path:** The Scribus 1.6 Python Scripter API (newDocument, createText, linkTextFrames, createParagraphStyle, loadImage, setColor, PDFfile export), run in-app or headless with `scribus -g -ns -py script.py` under xvfb-run. The .sla files are XML, so they can be diffed. It ships as a startup script plus a local MCP server or Docker image, fully self-hostable.

**Demand 3/5 · Buildability 4/5**

### 12. Google Cloud Billing + FinOps surfaces (Cloud Billing detailed export to BigQuery, Budgets API, Recommender, CUDs/Spend-based commitments, FinOps Hub, labels) `closed`

**Why it's powerful:** GCP billing data is very detailed. The BigQuery export has resource-level cost with labels, credits, SKU pricing and the folder hierarchy. On top of that there are programmatic budgets with Pub/Sub alerts and Recommender APIs for idle VMs, rightsizing, orphaned disks and CUD purchases.

**Why people bounce off it:** The console reports are shallow. Real answers need the detailed export plus tricky BigQuery SQL over nested credits and labels arrays and project.ancestors. Budgets are set up one by one with Pub/Sub plumbing, recommendations are scattered across projects, and CUD math needs a spreadsheet. GCP-heavy startups mostly have no tooling.

**AI operator:** A 'GCP Spend Analyst'. It checks or enables the detailed export, learns the org's label and folder conventions, and answers cost questions by generating correct BigQuery SQL that accounts for credits and net cost. It aggregates Recommender insights across projects with the savings attached, applies safe fixes after approval (orphaned disks, idle VMs, budgets with Slack alerts), and models CUD purchases against usage.

**Killer example:** A CTO asks: 'Why did our bill jump 40% last week, and stop it happening again?' The AI queries the export by service, SKU, project and label. 72% of the jump is BigQuery on-demand analysis in analytics-prod, from one scheduled query with no partition filter. It shows the job ID and owner from INFORMATION_SCHEMA.JOBS. It proposes a custom query quota per project and a 50/90/100% budget with Slack alerts, and creates both on approval.

**Integration path:** The BigQuery API over the billing export, the Cloud Billing and Budgets APIs, the Recommender API, Cloud Asset Inventory, the Compute and Resource Manager APIs, and Pub/Sub. It uses a service account with billing viewer plus scoped write roles and ships as SaaS or an MCP server.
