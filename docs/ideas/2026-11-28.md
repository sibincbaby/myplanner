### 1. Microsoft Planner + To Do + Outlook flagged-mail tasks (basic Planner via Microsoft Graph) `closed`

**Why it's powerful:** Planner ships with every Microsoft 365 tenant and sits behind Teams channels, with buckets, 25 labels, checklists, assignments and progress charts. To Do and Outlook flags feed the same Graph task model.

**Why people bounce off it:** No bulk edit, no import (Excel export only, one way), no dependencies and no cross-plan view. Tasks cannot be moved or copied between plans, label names are per plan, and checklists and descriptions are edited one card at a time. A 60-task kickoff takes about 45 minutes of clicking, and teams end up with 14 half-used plans and no view of what is overdue.

**AI operator:** A Graph-driven agent with skills for plans, buckets, tasks, taskDetails (checklist and description), label names and To Do lists. It handles ETag/If-Match and throttling itself. It does bulk create, reassign, relabel and re-bucket from plain language or a pasted Excel/Word list, and builds a cross-plan overdue and workload digest. Every bulk change goes in a plan-level undo log.

**Killer example:** User pastes the onboarding spreadsheet: 'Build a plan called New Hire - Priya, buckets by week, IT items to Sam and HR items to Joy, the Steps column as card checklists, Priority 1 items labelled Red. Then show every overdue task across all my plans grouped by person, and move done tasks older than 30 days to an Archive bucket.' The AI creates 1 plan, 5 buckets and 38 tasks with checklists and labels in one pass. It replies with a per-person overdue table, archives 17 old cards by copy plus delete (Planner cannot change a task's planId), and lists the 3 cards it could not edit because of throttling or permissions. One command ('undo the archive') restores them.

**Integration path:** Microsoft Graph REST: /planner/plans, /buckets, /tasks, /tasks/{id}/details (PATCH needs If-Match ETags), /me/todo/lists/{id}/tasks and flagged mail via /me/messages. Delegated OAuth, so each user only touches their own plans. Solo-dev build with a small MCP server, no desktop app needed. Overlap to check before building: Microsoft's Copilot-licensed Planner agent can already generate plans from a prompt (not verified here), so the wedge is bulk edits on existing plans, Excel/Word import and the cross-plan view for tenants without Copilot.

**Demand 4/5 · Buildability 4/5**

### 2. Salesforce Account Hierarchy and relationship graph (ParentId, Ultimate Parent, Account-Contact Relations, Opportunity Contact Roles); HubSpot company associations and Dynamics parentaccountid as later connectors `closed`

**Why it's powerful:** A correct account hierarchy powers ABM, territory assignment, rolled-up pipeline, account plans and renewals at the parent-company level. ParentId, Account Contact Relation and OpportunityContactRole are all writable through the standard REST and Bulk APIs.

**Why people bounce off it:** The native tool only displays a hierarchy someone has already built. Parent Account is edited one record at a time, with no bulk builder and no ultimate-parent logic. Real orgs hold 'IBM', 'IBM Corp.' and 'International Business Machines' as separate unlinked accounts across territories and owners. Vendors sell paid products around this. A bad parent link silently misroutes leads and rolls revenue up to the wrong company, so teams keep an untrusted Data Loader spreadsheet.

**AI operator:** Pulls Accounts with domains, addresses, DUNS or firmographic IDs and existing parent links. It proposes parent-child and ultimate-parent links with a confidence score and evidence (same registered domain, DUNS, legal-suffix normalisation, shared billing address). The user reviews by confidence band. Approved links are written via Bulk API 2.0 with a before-snapshot CSV for rollback. It then computes Ultimate Parent, flags cross-owner conflicts, and optionally fills Account Contact Relations and missing Opportunity Contact Roles. Dry-run diff is the default.

**Killer example:** RevOps lead: 'Marketing wants ABM by parent company, but half our enterprise accounts are not linked. Build the hierarchy for Strategic and Enterprise and tell me whose territories change.' The operator reads 38,400 accounts and proposes 1,126 links: 811 high-confidence (same domain or DUNS), 240 medium (name plus country), 75 ambiguous (for example 'Delta' the airline versus 'Delta Controls'). The lead approves the 811. The operator writes them, recalculates Ultimate Parent on 2,950 accounts, and lists the 63 subsidiaries owned by different reps than their parent, with a suggested resolution for each. A snapshot lets the whole batch be reverted.

**Integration path:** Salesforce REST and Bulk API 2.0 for Account, Contact, AccountContactRelation and OpportunityContactRole. SOQL for names, domains and ParentId. A Developer Edition org is enough to build. Metadata API only to add an Ultimate_Parent__c field. OAuth connected app is the only setup burden. HubSpot association API and Dataverse parentaccountid are straightforward later connectors.

**Demand 4/5 · Buildability 4/5**

### 3. Rotki (open-source, self-hosted crypto portfolio, accounting and tax reporting), with BittyTax and Koinly CSVs as sibling inputs `open-source`

**Why it's powerful:** Rotki is a local-first, privacy-preserving crypto accountant (AGPL, Python backend, Vue UI, documented REST API). It decodes on-chain transactions across many EVM chains and exchanges, applies cost-basis methods, and produces PnL and tax reports without sending data to a cloud.

**Why people bounce off it:** Accurate output needs a human to repair the event stream: unmatched transfers between own wallets that look like disposals, missing acquisitions with zero cost basis, spam airdrops, and wrongly decoded DeFi events (LP deposits, bridges, wrapped tokens). Cost-basis rules have recently become stricter (US per-wallet tracking, 1099-DA reporting, fair-value accounting). Users face thousands of red warnings and give up or fall back to a paid tool they do not trust.

**AI operator:** A Ledger Repair Operator talking to a local Rotki instance over its REST API. It lists report warnings, clusters them by root cause and proposes fixes: link transfer pairs between own accounts, add manual or customized events, ignore spam assets, re-run decoding. It regenerates the PnL report and shows how each fix changed gain/loss. Every edit is a proposed diff applied only on approval. It never files anything.

**Killer example:** User: 'My 2025 report shows 41k of gains and I think half is fake. Fix it.' The AI pulls the report and finds 63 'missing acquisition' warnings. 47 are ETH moves between the user's own Ledger and Binance withdrawals (matched by amount, timestamp and fee). 9 are spam airdrop tokens. 7 are real missing buys from a closed exchange account. It proposes 47 transfer links and 9 ignores, and asks for the exchange CSV for the last 7. After applying, the regenerated report drops gains to 12.8k and warnings to 7, with a before/after per-asset table and the reasoning for each change.

**Integration path:** Rotki's documented local REST API (history events, reports, assets, ignored assets, manual balances, exchange and blockchain accounts), headless in Docker or as the Electron backend. Repairs map directly to API calls. BittyTax (Python CLI over transaction CSV) is a simpler second backend. Local-only operation makes the privacy pitch easy. Risk is tax-law correctness, so reasoning must be shown.

**Demand 4/5 · Buildability 4/5**

### 4. Amazon Redshift (provisioned clusters + Serverless): performance and cost tuning `closed`

**Why it's powerful:** Redshift is the most widely deployed AWS data warehouse. Distribution and sort keys, encodings, WLM and Serverless RPU limits all have real effect on speed and bill.

**Why people bounce off it:** Performance depends on distribution style and keys, sort keys, encodings, VACUUM/ANALYZE state, WLM configuration, materialized view refresh and Serverless RPU capacity. The signal is scattered across system tables (SYS_QUERY_HISTORY, SVV_TABLE_INFO, SVL_QUERY_REPORT) that need hand-written SQL. Teams live with 40-minute queries and over-provisioned clusters because nobody can read the plan, spot DS_BCAST_INNER or DS_DIST_BOTH, or tell which table's distkey is wrong.

**AI operator:** Skills for the Redshift Data API, system-view diagnostics, EXPLAIN reading and the management API (parameter groups, WLM JSON, resize, Serverless limits). It diagnoses slow queries (broadcast joins, spills, skew, stale stats), recommends key and encoding changes from real access patterns, generates ALTER or deep-copy SQL with a lock and storage-headroom estimate, tunes WLM or max RPU against queue wait and spend, and verifies improvement by rerunning the query. Never DROPs; always asks approval.

**Killer example:** User: 'The daily revenue dashboard went from 4 minutes to 40 since March. Find out why and fix it without a maintenance window.' The AI reads the query's step summary, sees a DS_BCAST_INNER on a 900M-row fact table because orders.customer_id changed from KEY to EVEN after an unrelated CTAS rebuild, and checks SVV_TABLE_INFO (skew, 38% unsorted). It estimates a deep copy would need 210 GB of the 600 GB free, proposes the online ALTER DISTSTYLE KEY DISTKEY customer_id plus a scheduled VACUUM SORT, runs it in the approved window, and reruns the dashboard query: 38 seconds.

**Integration path:** Headless SQL plus AWS APIs: Redshift Data API (IAM auth, no JDBC or VPC access needed), boto3/aws-cli for ModifyClusterParameterGroup, ModifyWorkgroup, snapshots and resize. System views are read-only SQL. MVP is a read-only diagnoser with 25-30 curated queries and plan heuristics, then a gated DDL path.

**Demand 4/5 · Buildability 4/5**

### 5. Float / Runn / Forecast (resource and capacity planning for project teams) `closed`

**Why it's powerful:** These tools hold the source of truth for who is booked on what, at what rate, with leave, holidays and role skills. They can predict overbooking and hiring needs weeks ahead and tie staffing to project budgets.

**Why people bounce off it:** The allocation grid is drag-and-drop, one person-week at a time. A single reshuffle (a project slips two weeks, someone goes on leave, scope is added) means editing dozens of cells across projects. There is no what-if mode and no cross-project conflict view. PMs go back to spreadsheets, the tool goes stale and nobody trusts utilization numbers.

**AI operator:** A staffing-scenario operator that reads people, roles, allocations, time off and phases through the API. It proposes a minimal-change reshuffle that respects skills, maximum utilization and leave, shows a diff table (who moves, which weeks, utilization before and after), and writes only after PM approval. Scenario drafts live in the operator, so 'what if Beta slips a month' never touches live data.

**Killer example:** User: 'Beta's QA hand-off slips to Jan 19. Keep everyone under 100% and don't take anyone off Acme.' The AI finds 3 people over-allocated in January, moves Priya's 12 hours on Beta forward two weeks, covers Acme's gap with Tom (same role tag, free capacity), and shows 14 allocation edits in one diff table with utilization before and after. On approval it applies them and posts a summary to the Beta channel.

**Integration path:** Float REST API v3 (people, projects, allocations, time off, roles, clients), Runn REST API with API key, Harvest Forecast less documented. Writes are plain POST/PUT/DELETE, so no GUI automation. Solo dev can ship an MCP server with a scenario-diff layer and a plan/approve/apply loop. Risks: rate limits and part-day or repeating allocations.

**Demand 4/5 · Buildability 4/5**

### 6. Linux systemd + journald (units, timers, drop-ins, cgroup limits, sandboxing) on RHEL/Ubuntu/Debian/Amazon Linux fleets `open-source`

**Why it's powerful:** systemd runs essentially every Linux server. It offers dependency ordering, restart semantics, cgroup v2 limits, timers, socket activation and 100+ sandboxing directives with a built-in exposure score (systemd-analyze security).

**Why people bounce off it:** It is deep but the interface is arcane: systemctl status truncates, journalctl has dozens of filters, ordering cycles and 'start request repeated too quickly' are opaque, and hardening a service is trial and error on ProtectSystem, CapabilityBoundingSet and SystemCallFilter. Developers copy StackOverflow snippets and edit vendor unit files directly, so changes vanish on package upgrade.

**AI operator:** A Unit Doctor over SSH with skills for systemctl, systemd-analyze, journalctl, systemd-run and cgroup inspection. It diagnoses failures and flapping (exit status, OOM kills, ordering), writes fixes as drop-ins (never touching vendor files), converts cron jobs and nohup processes into services or timers, and hardens iteratively. It applies one directive at a time in a transient trial, watches the journal for EACCES/EPERM, keeps what works, and reports the exposure score before and after.

**Killer example:** User: 'report-exporter.service dies every night around 02:10. Make it restart sanely, run weekdays at 02:00, and lock it down.' The AI reads 14 nights of journal, finds the kernel OOM kill (cgroup memory 1.9G) and writes a drop-in with MemoryHigh=1.5G, MemoryMax=2G, Restart=on-failure. It replaces the cron line with a timer (OnCalendar=Mon..Fri 02:00, Persistent=true, validated with systemd-analyze calendar), then hardens step by step and drops SystemCallFilter after it breaks the exporter. Exposure goes from 9.2 UNSAFE to 3.1 OK, and it prints an Ansible snippet for the other 12 hosts.

**Integration path:** Pure CLI and file-based: systemctl, systemd-analyze, journalctl -o json, systemd-run, drop-ins under /etc/systemd/system/*.d/. Reach hosts via SSH or an Ansible inventory and emit drop-ins plus a playbook. MVP is a CLI/MCP tool with a command allowlist, transient-trial mode and mandatory diff and approval. Generic AI-over-SSH tools exist, so the differentiator is the verified hardening loop and journal forensics.

**Demand 4/5 · Buildability 5/5**

### 7. Aseprite (Igara Studio): sprite pipeline, palette and export automation `open-source`

**Why it's powerful:** Aseprite is the default pixel-art tool for indie game studios, with tags, slices, cels, palettes and a full Lua scripting API plus a rich CLI for batch work.

**Why people bounce off it:** The wall is the export and production pipeline. Sprite-sheet export has dozens of CLI flag combinations (--sheet, --data, --split-tags, --split-layers, --trim, --sheet-pack). Common pains are engine-ready layouts for Godot, Unity or Phaser, recolouring a sprite set to a new palette, and normalising 200 sprites. Many artists never touch Lua and redo the export by hand after every art tweak.

**AI operator:** A Sprite Pipeline Operator that audits a folder of .aseprite files (tags, frame durations, palette use, canvas sizes), then fixes and exports them by writing and running CLI commands or Lua scripts for palette remap, retiming, trimming, packing and per-tag sheet export, and emitting engine-ready JSON. It dry-runs on copies and reports what changed.

**Killer example:** User: 'All enemy sprites in /art/enemies need the 16-colour Sweetie palette, walk at 100ms per frame, idle at 200ms, packed into one 512-wide sheet with 1px padding, plus Godot-friendly JSON.' The AI runs a Lua batch script that remaps colours to the nearest palette entries and sets tag durations, then calls the CLI with --sheet, --data and --sheet-pack. It writes enemies.png and enemies.json and reports: '23 sprites processed, 2 had colours with no close palette match (list attached), sheet is 512x384.'

**Integration path:** Official CLI (--batch, --script, --sheet, --data, --split-tags, --list-tags) and Lua API with read and write access, fully headless on local files. Dry-run-on-copy safety model. Some app.command calls (for example ExportSpriteSheet) behave differently in batch mode, so prefer CLI flags and verify output.

**Demand 3/5 · Buildability 5/5**

### 8. Octopus Deploy (Server self-hosted + Octopus Cloud): variable scoping and release-process sprawl `closed`

**Why it's powerful:** Octopus is the release orchestrator for a large base of .NET and enterprise shops, with lifecycles, step templates, tenants, runbooks and a variable system scoped by environment, role, target, tenant, channel and step.

**Why people bounce off it:** After a few years a project has 400+ variables with overlapping scopes. Nobody can answer what DB_CONNECTION resolves to for tenant X deploying to Prod-EU via the Hotfix channel, because Variable Preview resolves one scope combination at a time. Duplicated step templates, stale lifecycles and library variable sets shared across 60 projects make every change feel dangerous.

**AI operator:** A Release Process Doctor with skills for the REST API, the octopus CLI and Config-as-Code OCL files. It resolves and explains effective variable values for any scope combination, finds scope conflicts, shadowing, unused variables and plain-text secrets, and writes changes as a diff applied only after approval, snapshotting the variable set revision first. It also reads task logs to explain failed deployments.

**Killer example:** User: 'Why did tenant Contoso-UK get the staging SMTP host in Production last Thursday? Fix it without touching the other 40 tenants.' The AI reads the deployment's variable snapshot and shows that SMTP_HOST had a role=web value outranking the tenant-scoped one because of an unscoped duplicate in a library variable set. It proposes one tenant-and-environment-scoped value, previews resolution for all 41 tenants x 3 environments (only Contoso-UK changes), and applies it after approval.

**Integration path:** REST API with an OpenAPI spec at /api (variables, projects, processes, lifecycles, tenants, runbooks, tasks and logs), the octopus CLI, Terraform provider, and OCL in git for a PR path. Variable editing is a documented PUT. Ship a read-only explainer and conflict linter first against a trial instance, then add the write path with revision snapshot and rollback.

**Demand 3/5 · Buildability 4/5**
