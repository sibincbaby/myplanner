*Ranking note: ranked by demand × buildability × strength-of-fit, where fit means both "the person blocked by the UI is not an engineer" and "the API can actually write the thing that is the wall." That second clause did most of the work this round. **Etsy outranks YouTube Studio despite a lower buildability score** because Etsy's blocked user is a solo maker with no alternative, while YouTube's wall is closer to tedium than to a cliff. The same clause demoted or killed a lot of otherwise-excellent candidates: **Braze** (demand 5/5, the Liquid learning curve is the single most-cited complaint in its category) cannot create campaigns, Canvases or segments via REST at all — the entire authoring surface is UI-only, and browser automation against an enterprise SSO dashboard is not a product. The same defect, in milder form, sank a whole cluster in project/ticketing: **Trello** has no Butler API, **Freshservice** has no Workflow Automator API, **Front** exposes rules strictly read-only, **Wrike** has no automation-rule or request-form endpoints, and **Intercom** has no Workflow authoring API — in every case the automation builder that *is* the usability wall is precisely the thing you cannot write. Two of that cluster survive elsewhere in spirit: **Aha! Roadmaps** is the rare product whose workflows and custom fields genuinely are API-writable, and **Front**'s read-only rules still support the highest-value half (a rule-execution tracer, which Front itself does not ship). Also checked and dropped on the Looker Studio precedent from 2026-08-20: **Amplitude/Mixpanel** (chart APIs are read-only; writes are limited to annotations and governance metadata), **Domo** (card creation effectively undocumented), **Sigma Computing** (createWorkbook returns an empty shell; Workbooks-as-Code is private beta), and **Anaplan** (Bulk API can only run actions a human built in Blueprint first — a superb runner, but it cannot build). **CapCut** was the most painful cut: 5/5 demand and hundreds of millions of installs, but v6+ encrypts `draft_content.json`, so the only known integration path covers legacy versions and could be closed by ByteDance at any time. Deliberately excluded as failing the mainstream test: Pro Tools, Adobe Audition, Procreate, Affinity (JS scripting API still pre-alpha), Spotify for Artists, and Sage 100 (COM-only, no web API).*

### 1. Etsy Seller (Shop Manager) `closed`

**Why it's powerful:** Etsy carries roughly 9 million active sellers, and Shop Manager is the whole business in one console: listings with full variation and inventory matrices (price, quantity, SKU and visibility per combination), personalization fields, production partners, shipping profiles, digital downloads, coupons and sales, Star Seller metrics, and both Etsy Ads and Offsite Ads. The listing's SEO surface — title, thirteen tags, attributes, category — is effectively the entire ranking algorithm, which means small text edits move real revenue in a way that is rare for a settings screen.

**Why people bounce off it:** The variations and inventory editor is the single most-cursed screen on the platform: a full combinatorial matrix that has to be re-entered by hand every time a size or colourway changes. SEO is a thirteen-tag guessing game with no diagnostics anywhere — nothing tells a seller which tag is dead weight. Etsy Ads is worse than unhelpful: sellers report the in-ads tag-editing path breaking outright, showing "This listing doesn't have related tags" instead of the usual adjustment button, and others report losing targeted-keyword data entirely, "showing only 2 of 16 previously displayed targeted words." Shipping profiles versus listing-level overrides regularly charge the wrong rate, which shows up as a margin problem months later rather than an error. The population here is the purest expression of this thesis — a solo maker who is expert at the craft and has no operational alternative.

**AI operator:** Five skill packs. **SEO Rewriter** regenerates title, tags, attributes and description per listing from Etsy's own taxonomy plus the shop's actual stats. **Variation Builder** turns "S/M/L in four colours, plus three dollars for XL" into the complete products-and-offerings matrix in one call. **Repricer and Sales Runner** orchestrates price, sale and coupon together. **Order Ops Desk** handles receipts, shipment and tracking creation, and message templates. **Listing Launcher** takes a draft from images through digital files to publish. Safety model: every write lands as `state: draft` with a rendered preview and a per-listing diff table requiring approval before publish; every write stores a pre-image so "undo the SEO rewrite on those forty listings" is one command; and a rate-budget manager keeps the account under the 10,000-per-day and 10-per-second ceilings so a bulk job never bricks the key. It beats a chat wrapper because it holds shop-wide state — which listings are in which experiment, what the naming convention is — and can schedule a views-and-favourites re-check to measure whether its own rewrite worked.

**Killer example:** User says: *"My linen apron listings are dying — rewrite their SEO and add a plus-size variant at four dollars more."* → AI calls `GET /application/shops/{shop_id}/listings/active` plus listing stats, generates new titles, thirteen tags and attributes, `PATCH`es each as a draft for review, then `PUT /application/shops/{shop_id}/listings/{listing_id}/inventory` adding a 2XL property value at base plus four with inherited quantity, and schedules a re-check in fourteen days.

**Integration path:** Etsy Open API v3 at `https://openapi.etsy.com/v3/application/...`, OAuth 2.0 authorization-code with PKCE, scopes `listings_r/w`, `shops_r/w`, `transactions_r/w`, `billing_r`, `email_r`. Rate limits are 10,000/day and 10/sec per key on a sliding window, raisable by request. Honest gaps, and they shape the go-to-market: app access is tiered as **Seller App** (your own shop only, approved in minutes), **Personal App** (deeper manual review), and **Commercial Access** (required to serve other sellers, and only requestable *after* a Personal App is approved) — so the MVP is a single-seller Seller App and the multi-tenant version is a second, slower approval. There is **no Etsy Ads API at all**, so the ads half must be advisory or browser-driven. No sandbox either; you test against a live shop using drafts.

**Demand 5/5 · Buildability 4/5**

### 2. YouTube Studio `closed`

**Why it's powerful:** Studio is the control plane for a creator's entire business — metadata, playlists, end screens and cards, captions in dozens of languages, monetization and ad-break placement, copyright claims and disputes, memberships, and an analytics stack with retention curves, traffic sources and an impressions-to-CTR funnel that rivals a BI tool. Every lever that moves views and revenue lives there, and most of it is genuinely predictive if you know how to read it.

**Why people bounce off it:** Bulk editing is crippled. The native Edit action on the Videos tab covers only a handful of fields, and end screens and cards must be re-applied video by video — which is exactly why TubeBuddy sells a Bulk End Screen Editor as a headline feature and pitches it as replacing "days of manual work." Analytics has the opposite problem: Advanced Mode is a full pivot interface with period comparison, grouping by geography and subscriber status, and custom groups, and most creators never open it. Meanwhile the screens that carry real money — copyright claim triage, mid-roll ad-break placement, the made-for-kids audience setting — are error-prone and unforgiving. Playlist ordering across a 500-video library is manual drag-and-drop.

**AI operator:** Five skill packs. **Library Ops** does bulk metadata rewrites, tag and description templating with per-video variables, thumbnail swaps and playlist re-sectioning. **Localization** pushes captions and localized titles and descriptions across N languages in one instruction. **Analytics Interrogator** turns the Analytics API into answers — "which of my last forty videos lost people before thirty seconds, and what do their hooks share." **Monetization Hygiene** covers ad-break placement, made-for-kids audit and claim triage. **Release Runbook** chains scheduled publish, playlist add, pinned comment and community post. Safety model: every mutation is two-phase — plan, then a diff preview showing all forty-seven old and new descriptions, then apply — with a full pre-change snapshot of each `videos.list` payload stored for one-click revert. Critically it also runs a quota budgeter: the default is 10,000 units/day and `videos.update` costs 50, so roughly 200 edits per day, and the agent must batch, schedule across days, and warn rather than fail halfway through a library. That quota arithmetic is exactly the kind of thing a chat wrapper gets wrong and a stateful operator gets right.

**Killer example:** User says: *"All my 2023 tutorials still point to my old course link and have the wrong end card. Fix the links, add them to the 'Beginner Path' playlist in view-count order, and translate the titles to Spanish and Portuguese."* → AI runs `search.list` and `playlistItems.list` to scope, `videos.list(part=snippet,localizations)` to snapshot, `videos.update` per item with the rewritten description plus `localizations.es` and `.pt`, `playlistItems.insert` ordered by `videos.list(part=statistics)`, and flags end screens as API-unsupported, offering a guided click-through instead of silently skipping them.

**Integration path:** YouTube Data API v3 (`videos.update`, `playlists`, `playlistItems`, `captions.insert`, `thumbnails.set`, `commentThreads`), YouTube Analytics API v2 and the Reporting API for bulk reports; OAuth 2.0 with the `youtube.force-ssl` scope; official client libraries in Python, JS, Java and Go. Honest gaps: there is **no API for end screens, cards, or most monetization settings** — the operator must degrade to a guided walkthrough for those; the 10,000 unit/day default quota needs a formal increase application with an audit; and a public app using sensitive scopes requires Google OAuth verification and a security assessment. No sandbox — you test against a real channel.

**Demand 5/5 · Buildability 5/5**

### 3. Salesforce CPQ (SBQQ) / Revenue Cloud `closed`

**Why it's powerful:** CPQ is a distinct managed package from Sales Cloud with its own object model, its own certification track and its own calculation engine. It handles bundles with option constraints and dependency rules, Price Rules driven by lookup queries, tiered and volume discount schedules, contracted pricing, multi-dimensional quoting, amendment and renewal quotes with proration maths, Advanced Approvals, and quote document generation. In effect it encodes an entire enterprise's pricing policy as declarative metadata.

**Why people bounce off it:** The Price Rule model. An admin must pick an evaluation event (Load, On Initialization, Before Calculate, On Calculate, After Calculate) *and* a scope (Calculator versus Configurator), then wire `SBQQ__PriceCondition__c` records against a Lookup Object, then `SBQQ__PriceAction__c` records writing to twin fields — and the failure mode is silent. The quote simply calculates the wrong number, or the Quote Line Editor hangs on "Calculating…". Salesforce maintains a troubleshooting knowledge article that exists solely to answer "why didn't my price rule fire." Reviewers consistently report setup as complex and time-consuming and rules becoming unmaintainable as products and bundles scale. The practical consequence is economic: most orgs cannot deploy or change CPQ without a systems integrator on retainer, which means every pricing experiment carries a consulting invoice.

**AI operator:** Five skill packs. **Pricing Rule Author** turns an English pricing policy into the PriceRule, PriceCondition and PriceAction record graph with the correct evaluation event. **Bundle Configurator** handles products, options, option constraints and feature min/max. **Quote Doctor** traces why a given quote line priced the way it did by replaying the calculator and diffing field by field. **Amendment and Renewal Runner** handles mid-term changes. **Config Migrator** promotes sandbox to production. The safety model is the product: nothing lands in production directly. Changes are emitted as sfdx source, committed to git, deployed validation-only first, then the operator runs the Calculate Quote API against three to five real quotes in the sandbox and prints a **before/after price delta table** for human sign-off. Every quote-level write stores a Read Quote JSON snapshot for restore. That price-delta simulator is what makes this more than a chat wrapper — it is a CPQ regression harness with a language front-end, and regression is precisely what the SI retainer is currently buying.

**Killer example:** User says: *"Give reps 15% off the base SKU whenever total ACV is over $250k, but never let it stack with the partner discount."* → AI creates `SBQQ__PriceRule__c` (Evaluation Event = On Calculate, Scope = Calculator), a `SBQQ__PriceCondition__c` on `SBQQ__QuoteLine__c.SBQQ__NetTotal__c > 250000`, a second condition requiring `SBQQ__PartnerDiscount__c` to be null, and a `SBQQ__PriceAction__c` setting `SBQQ__AdditionalDiscount__c = 15`; deploys via Metadata API to sandbox; POSTs to `/services/apexrest/SBQQ/ServiceRouter?loader=SBQQ.QuoteAPI.QuoteCalculator` against three live quotes; and shows the deltas before promoting.

**Integration path:** Standard Salesforce REST, Bulk, Tooling and Metadata APIs — CPQ config objects are just custom objects, so they are fully CRUD-able — plus the CPQ-specific `SBQQ.ServiceRouter` Apex REST with `read`/`load`/`save` loaders (QuoteReader, QuoteCalculator, ProductLoader, ProductSaver) and the Calculate Quote API. Auth is a connected app with OAuth2 JWT bearer; tooling is mature (sfdx CLI, jsforce, simple-salesforce). Honest gaps: a free Developer Edition org **does not ship the CPQ managed package**, so you need a CPQ-enabled sandbox or partner org to build against at all; and Salesforce is migrating customers to **Revenue Cloud Advanced**, which has a different object model — so the target moves and a build should plan for two backends.

**Demand 5/5 · Buildability 4/5**

### 4. Apollo.io `closed`

**Why it's powerful:** A 200-million-plus contact database with 65-plus search filters spanning technographics, funding, job postings and buying intent, plus sequences with email, call and LinkedIn steps, a dialer, an inbound router and meeting scheduler, deal pipeline, CSV enrichment and cleanse, and a Chrome extension. The free tier and low price give it an enormous install base skewed toward SMB and startup — which is exactly where there is *no* sales ops person at all to absorb the complexity.

**Why people bounce off it:** Three concrete traps. First, the filter stack: nobody can reconstruct which combination of intent topic, technology, headcount and score produced a given list, so lists are not reproducible month to month. Second, the credit model — export versus reveal credits, consumed per unique record per twelve-month window — where teams burn a month's credits in an afternoon and only find out afterward, because the spend is invisible until it has happened. Third, sequence setup that fails silently on mailbox connection, warmup and daily send limits, so a rep believes they are sending 500 emails a day and are actually sending 40. Data-accuracy triage is left entirely to the user with no tooling for it.

**AI operator:** Five skill packs. **ICP Search Composer** turns a plain-English ideal customer profile into a search payload and shows a **count preview before any credit is spent**. **Credit Governor** attaches a per-action cost estimate, a budget ceiling, and a mandatory confirm above a threshold. **Sequence Builder and Copy Rewriter** handles the outbound. **List Hygiene** dedupes against CRM via bulk match, applies suppression lists and predicts bounces. **Pipeline Reporter** closes the loop. The safety model follows directly from the wall: credits are literally money, so the operator's core primitive is estimate-then-approve, not act-then-report. Every enrollment is staged into a named list so a single "unenroll all" reverses it, and an append-only run log stores every search payload so any list is reproducible months later — which is the reproducibility the product itself does not offer.

**Killer example:** User says: *"Find 300 US SaaS companies, Series B–C, 50–500 people, using Snowflake; get the VP Data and Head of Analytics at each; dedupe against Salesforce; enroll them in Data Stack Outbound starting Tuesday."* → AI calls `POST /api/v1/mixed_companies/search` with technology, headcount and funding-stage filters, `POST /api/v1/mixed_people/search` for the titles, `POST /api/v1/people/bulk_match` to enrich, dedupes against CRM, `POST /api/v1/contacts` to create, then `POST /api/v1/emailer_campaigns/{sequence_id}/add_contact_ids` with `send_email_from_email_account_id` and a scheduled start — quoting the credit cost and waiting for approval before the enrich step.

**Integration path:** REST at `https://api.apollo.io/api/v1` with an `X-Api-Key` header and a well-documented public reference. Honest gaps that matter: adding contacts to a sequence requires a **master API key** (403 without it) and is capped at 600 calls/hour; there is **no OAuth for multi-tenant third-party apps**, so every customer must mint and paste their own key — awkward, but workable for a per-tenant operator; API access is plan-gated; and there is **no sandbox**, so every test call burns real credits against real data, which makes the Credit Governor a development requirement, not just a feature.

**Demand 5/5 · Buildability 4/5**

### 5. Amazon VPC — network connectivity `closed`

**Why it's powerful:** A full software-defined network: multi-AZ subnetting, stateful security groups that can reference other security groups, stateless NACLs, prefix lists, transit gateways with route-table propagation and association, PrivateLink endpoints and flow logs. Crucially it also ships two analysis services most users have never opened — Reachability Analyzer, which performs static configuration analysis between any two resources and, when unreachable, names the blocking component with a hop-by-hop path; and Network Access Analyzer, which sweeps security groups, NACLs, ENIs, transit gateways, NAT and internet gateways, endpoints and peering to find unintended exposure paths.

**Why people bounce off it:** Connectivity is decided by five independent objects on three different console pages, and every failure presents identically as a TCP timeout. As one practitioner guide puts it, if you spend thirty minutes checking security groups when the real problem is a missing route, you are just as stuck at the end. The canonical traps are all silent: security groups are stateful but you still need the inbound rule on the destination, while NACLs are stateless so you need *both* directions — people add only the inbound NACL rule and the ephemeral-port return traffic on 1024–65535 is dropped. A "public" subnet that is not public because the main route table was edited instead of the associated one. A NAT gateway placed in a private subnet. A VPC endpoint created without DNS hostnames enabled, so calls quietly go out the NAT and get billed. A transit gateway attachment that is associated but not propagated. Deleting a security group that other groups reference. Every one of these produces a thirty-second timeout as its only symptom.

**AI operator:** Five skill packs. **Reachability Doctor** takes "my Lambda can't reach RDS," builds a NetworkInsightsPath, reads the blocking component and proposes the *single* minimal change. **Safe Subnet Architect** creates a compliant three-tier VPC from a sentence, with explicit route-table associations and never the main route table. **Exposure Sweep** runs Network Access Analyzer scopes on a schedule and diffs findings. **SG Hygiene** finds unused groups, 0.0.0.0/0 on 22 and 3389, and rules referencing deleted groups. **Egress Cost Detective** correlates flow logs with missing VPC endpoints to find traffic paying NAT charges. The safety model is unusually well-equipped because AWS provides the primitives: every mutating EC2 call is first issued with `DryRun=true`, which is free; a hard guard refuses any change that would remove the rule or route currently carrying the caller's own SSH or SSM session, or the bastion and VPN CIDR, and refuses to delete the last route to an IGW or NAT serving a subnet with running instances. After applying, it **re-runs Reachability Analyzer to prove the fix** rather than declaring success on a 200.

**Killer example:** User says: *"The app servers in prod can't reach the new Aurora cluster on 5432."* → AI calls `ec2:CreateNetworkInsightsPath` (source the app ENI, destination the Aurora ENI, protocol tcp, port 5432), `ec2:StartNetworkInsightsAnalysis`, polls `ec2:DescribeNetworkInsightsAnalyses`; the result names the DB security group's missing inbound rule; the AI proposes `ec2:AuthorizeSecurityGroupIngress` on the DB group with `ReferencedGroupId` set to the app group rather than a CIDR, runs it with `DryRun=true`, applies on approval, and re-runs the analysis to show `NetworkPathFound: true` with the full hop list.

**Integration path:** EC2 API — `CreateNetworkInsightsPath`, `StartNetworkInsightsAnalysis`, `DescribeNetworkInsightsAnalyses`, `CreateNetworkInsightsAccessScope`, plus `DescribeRouteTables`, `DescribeNetworkAcls`, `AuthorizeSecurityGroupIngress`/`Revoke...`, `CreateRoute`, `ReplaceRouteTableAssociation` and the transit-gateway route-table calls. Auth via IAM role assumption and STS, ideally cross-account read-only plus a scoped write role. boto3 and the JS/Go SDKs cover everything. Honest gaps: Reachability Analyzer costs about ten cents per analysis and is **static-configuration only** — it will not catch OS firewalls, DNS failures, TLS or application-layer problems, so the operator must be explicit about what it did not test; coverage is incomplete for some cross-account and on-premises/VPN destinations; Network Access Analyzer is region-scoped, so org-wide sweeps need fan-out; and the cost-detective pack needs flow logs already enabled.

**Demand 5/5 · Buildability 4/5**

### 6. Google Cloud IAM + Organization Policy `closed`

**Why it's powerful:** Policy-as-data access control across the org, folder, project and resource hierarchy, with over 1,700 predefined roles, custom roles, IAM Conditions expressed as CEL over time, resource and tags, Deny Policies that override allows, workload identity federation, and Organization Policy constraints plus custom constraints that hard-block resource configurations org-wide. Policy Intelligence adds three things almost nobody uses: Policy Simulator, which replays ninety days of real access against a proposed policy; Policy Troubleshooter; and the IAM Recommender, which computes least-privilege downgrades from actual usage. Cloud Asset Inventory can search every IAM policy across an entire org in one call.

**Why people bounce off it:** The IAM page shows principals against roles as a flat grid that hides inheritance, so you cannot tell from the project page that a binding actually came from a folder. The recurring complaint is figuring out which permission is missing and at which level to grant it — one developer built an entire permissions-search web app because the official documentation was too slow to navigate. The silent failure modes compound: granting `roles/viewer` at project level to fix one access-denied quietly over-permissions two hundred resources; IAM changes take up to about seven minutes to propagate, so people re-grant broader roles believing the narrow one failed; a Deny Policy at folder scope overrides every allow below it with an error naming neither the policy nor the folder; an inherited `constraints/iam.allowedPolicyMemberDomains` makes an external-user grant appear to succeed and then vanish; and service-account impersonation needs `roles/iam.serviceAccountTokenCreator` on the service-account *resource*, not the project, which lives on a different page entirely. The universal escape hatch — grant Owner — is exactly the outcome the product exists to prevent.

**AI operator:** Five skill packs. **Access Forensics** takes a pasted 403 and calls Policy Troubleshooter plus the resource ancestry to name the exact missing permission at the exact scope. **Least-Privilege Grant** turns "let the CI service account deploy to Cloud Run in staging" into a minimal role set with an IAM Condition, runs Policy Simulator first, and shows the diff of who gains and loses access. **Org Guardrails** authors and dry-runs custom constraints. **Privilege Cleanup** pulls IAM Recommender findings org-wide and stages batched downgrades with per-principal blast radius. **Ancestry Explainer** answers "who can read this bucket and why." Safety model: every mutation is preceded by a Policy Simulator run and **blocked if the simulated delta removes access for the invoking principal or for any organization admin** — do not sever your own admin path. All writes use etag-based read-modify-write with the prior policy JSON stored for a one-command `setIamPolicy` rollback, and because propagation is asynchronous, verification is a poll rather than an assert. The simulate-diff-apply-verify loop is the whole product; no chat UI does it.

**Killer example:** User says: *"Our GitHub Actions deployer keeps getting permission denied pushing to Artifact Registry in prod — just make it work, but don't give it owner."* → AI calls `policytroubleshooter.googleapis.com/v3/iam:troubleshoot` with the workload-identity principal and `artifactregistry.repositories.uploadArtifacts` on the repo resource, confirms via `cloudasset.assets.analyzeIamPolicy` that no folder-level grant exists, runs a Policy Simulator replay with a proposed `roles/artifactregistry.writer` binding scoped to the single repository plus a `resource.name.startsWith(...)` condition, reports "0 principals lose access, 1 gains 3 permissions," and only then calls `setIamPolicy` with the current etag — storing the pre-change policy for rollback.

**Integration path:** `iam.googleapis.com` v1/v2 for roles and deny policies, `cloudresourcemanager.googleapis.com` v3 for get/set IAM policy with etags, `orgpolicy.googleapis.com` v2 for constraints, `policysimulator.googleapis.com` v1 for Replay, `policytroubleshooter.googleapis.com/v3`, `recommender.googleapis.com`, and `cloudasset.googleapis.com` v1 for `searchAllIamPolicies` and `analyzeIamPolicy`. Auth is best done as workload identity plus user-delegated OAuth, so the operator inherits the human's own privileges rather than exceeding them. Official Python, Go and Node libraries. Honest gaps: there is **no true sandbox** — you need a real organization; **Policy Simulator needs ninety days of Cloud Audit Logs to be meaningful**, so it is useless on new projects and the demo story has to account for that; custom constraints support only a subset of resource types; and some Security Command Center and Access Context Manager surfaces are console-only.

**Demand 5/5 · Buildability 4/5**

### 7. Acumatica Cloud ERP `closed`

**Why it's powerful:** A full mid-market ERP — general ledger with sub-accounts and multi-branch, multi-entity structure, AP and AR with document-level approval maps, project accounting with WIP and revenue recognition, inventory with landed cost and lot/serial tracking — plus two things that make it unusually good as an operator target. Generic Inquiries are a user-buildable query and view layer over any data access class, and the licensing is unlimited-user, which means non-finance staff genuinely touch the system rather than emailing a controller.

**Why people bounce off it:** Everything is a screen ID, and knowing which one is folklore — GL301000 for Journal Transactions, AP301000 for Bills and Adjustments, SM207060 for Web Service Endpoints. Learning curve is flagged as a con in roughly 191 G2 reviews, with reviewers calling out specifically that Generic Inquiries "are powerful but have a steep learning curve" and that advanced reports and the Report Designer need real training; others report disjointed navigation and a need for in-depth end-user training. The concrete error modes are the usual accounting traps plus some Acumatica-specific ones: releasing a batch that is out of balance, sub-account segment validation failures, a Generic Inquiry that returns nothing because the join type or the Relations tab is wrong, and — the one that bites integrators — a custom GI being completely invisible to the API until someone extends an endpoint.

**AI operator:** Five skill packs. **Screen Navigator** maps plain language to the correct screen ID with fields prefilled. **GI Author** builds and extends Generic Inquiries from a question, including joins, conditions, and exposure to the endpoint — a genuine schema-aware builder, not a template filler. **AP/AR Clerk** enters bills, applies payments, runs checks and handles vendor holds and retainage. **Close Agent** covers recurring entries, allocations, reclass batches and period validation. **Approval Router** handles assignment maps and escalation. Safety model follows accounting practice rather than software convention: rollback is a **reversing batch** via Acumatica's native Reverse action on a released batch, or unrelease-and-delete while still on hold, and the operator always reports the reversing batch number rather than claiming a deletion. What lifts it above a chat wrapper is the GI Author — turning "show me projects where committed cost exceeds budget" into a persisted, reusable inquiry object plus the endpoint extension that makes it queryable forever.

**Killer example:** User says: *"Reclass $12k of the ACME rent bill from Marketing to Sales for August."* → AI GETs `/entity/Default/24.200.001/Bill` to fetch the source document, PUTs a new `JournalTransaction` batch debiting Sales rent and crediting Marketing rent in the August period, releases it, and returns the batch number alongside a one-click Reverse.

**Integration path:** Contract-based REST at `/entity/Default/{version}/{Entity}`, with versioned endpoint contracts configured on screen SM207060; OAuth 2.0 with `api`, `api:concurrent_access` and `api:offline_access` scopes plus legacy cookie auth; OData exposure of Generic Inquiries for reads; and a screen-based SOAP API for anything the contract does not cover. Free developer and trial instances are available, and Acumatica runs an open developer training track covering web services — unusually generous for mid-market ERP and a material de-risker. Honest gaps: custom Generic Inquiries **are not exposed by default** — you must build a custom endpoint or extend an existing one per tenant, which is real per-customer setup work; multi-tenant ISV distribution goes through the Acumatica marketplace and ISV program; and endpoint-contract version drift across the 23R/24R/25R releases is ongoing maintenance.

**Demand 4/5 · Buildability 5/5**

### 8. BigCommerce `closed`

**Why it's powerful:** BigCommerce ships natively what competitors charge for: multi-storefront and multi-channel management across Amazon, eBay, Walmart, Meta, TikTok and Google, customer-group pricing via Price Lists, a cart-level promotions engine, real-time shipping quotes and advanced faceted filtering. Product modelling handles variants, modifiers and complex rules with per-variant pricing, images and inventory without a third-party app, and Stencil themes plus a GraphQL Storefront API support headless builds.

**Why people bounce off it:** Reviewers say the admin panel "feels cluttered compared to Shopify's stripped-down interface" and that BigCommerce is accessible for non-developers but far more complex than beginner-oriented builders, concluding bluntly that "unless you are comfortable with code or ready to hire a Stencil developer, you will hit walls quickly." Two screens do most of the damage. The first is the Variations versus Modifiers versus Complex Rules split — three overlapping ways to model the same option, with different pricing semantics, and no guidance on which to pick. The second is the Price List assignment matrix: a list bound to the wrong channel-by-customer-group combination silently shows the wrong price on one storefront, with no error surfaced anywhere. You find out from a customer.

**AI operator:** Five skill packs. **Catalog Surgeon** does bulk product, variant and modifier edits, custom fields and image hygiene. **Pricing Strategist** builds price lists, records and channel/customer-group assignments with a dry-run diff of the **effective price per SKU per channel** — the view the admin UI refuses to give you. **Promotion Composer** turns natural language into promotions rules JSON plus coupon codes, verified against a simulated cart. **Channel and Listing Manager** handles the marketplace surfaces. **Storefront Health** covers redirects, metafields and webhooks. Safety model: every changeset is applied to a **free developer sandbox store first** and replayed to production only on approval; per-entity pre-image snapshots give exact revert; price writes are capped by maximum percentage delta and per-run SKU count; and promotions are created disabled with a scheduled enable requiring sign-off. Beyond a wrapper, it keeps a local mirror of catalog and price lists so it can answer "what does this SKU cost a Wholesale buyer on the TikTok channel?" *before* writing anything.

**Killer example:** User says: *"Give wholesale customers 20% off all Nike SKUs on the B2B storefront only, starting Monday."* → AI resolves the brand, calls `GET /v3/catalog/products?brand_id=`, `POST /v3/pricelists`, bulk `PUT /v3/pricelists/{id}/records` with computed price and sale price per variant, then `POST /v3/pricelists/{id}/assignments` binding both `customer_group_id` = Wholesale **and** `channel_id` = the B2B storefront, sets `date_from`, and returns a per-SKU before/after table plus a rollback token.

**Integration path:** REST Management API v3/v2 at `https://api.bigcommerce.com/stores/{store_hash}/v3/...` with an `X-Auth-Token` header from a store-level API account, or an OAuth app install with per-resource scopes for multi-tenant; GraphQL Admin and Storefront APIs; store webhooks; free developer sandbox stores; official Node and PHP SDKs. Honest gaps: theme and design work is a separate file-based `stencil` CLI workflow rather than REST, so visual changes need a git-backed path outside the API; payment gateway configuration, tax setup and parts of channel onboarding are UI-only; and API rate limits are plan-tiered, with Enterprise far higher — which constrains bulk operations for exactly the smaller merchants who most need them.

### 9. Adobe Analytics (Analysis Workspace) `closed`

**Why it's powerful:** eVars and props with per-variable allocation and expiration, unlimited segmentation with hit, visit and visitor containers and sequential "then" and "within N" logic, calculated and segmented metrics, Attribution IQ with ten models including algorithmic, fallout, flow, cohort and journey panels, virtual report suites with component curation, and Data Warehouse and Data Feeds for raw export. It is the analytics system of record for most of the Fortune 500's digital estate.

**Why people bounce off it:** The failure mode is silent wrong numbers, not error dialogs — which is the most expensive kind. Container scope in the segment builder (hit versus visit versus visitor) changes the answer by multiples with no warning. eVar allocation and expiration settings — linear, original, most recent — silently attribute conversion to the wrong dimension. Unique visitors are non-additive across date ranges, so summed rows never tie out and nobody can explain why. Data Warehouse and Workspace totals routinely disagree, to the point that "causes of data discrepancies between Data Warehouse and Workspace" is a standing Experience League thread topic. Adobe's own trainers say segmentation is typically the hardest part of an Analytics class because users can add so much to a segment and use so many operators that it becomes overwhelming; community idea threads complain about "the number of inefficiencies that continue to make using Analysis Workspace a frustrating experience," specifically in the segment and metric builders, which "completely hide the underlying page."

**AI operator:** Five skill packs. **Segment Architect** does scope-aware container construction, sequential segments and exclusion nesting. **Metric Foundry** builds calculated and segmented metrics with allocation-aware definitions. **Workspace Builder** clones a template project and patches the project-definition JSON. **Discrepancy Doctor** is the wedge: it answers every question three ways — Workspace report, segmented metric, and Data Warehouse — and **refuses to deliver a number until they reconcile**, naming the container or allocation setting responsible when they do not. **Governance** covers virtual report suite curation, component naming and annotations. Safety model: artifacts are created unshared, owned by a service user, tagged `operator-run`, previewed as a JSON diff, and reversible by `DELETE /segments/{id}` or `/calculatedmetrics/{id}`. The reconciliation gate is what makes this more than a chat wrapper — it catches the exact class of error that quietly costs companies real money, and a chat wrapper would cheerfully return the first plausible number.

**Killer example:** User says: *"First-time mobile buyers who used search but never opened the wishlist, last 90 days — and make it a dashboard I can rerun."* → AI `POST /segments` with a visitor-scoped container wrapping a hit-scoped exclusion, `POST /calculatedmetrics` for search-assisted revenue as a segmented metric, `POST /reports` to validate row counts against an unsegmented control, clones the template project and `PUT /projects/{id}` with the new panel definition, then `POST /annotations` to mark the release date on the trend.

**Integration path:** Base `https://analytics.adobe.io/api/{GLOBAL_COMPANY_ID}`, OAuth 2.0 server-to-server plus an `x-api-key` header. Documented write endpoints cover `/segments`, `/calculatedmetrics`, `/annotations` and `/reports`; the community Python SDK `aanalytics2` is mature. Honest gaps: the `/projects` endpoint documents GET, PUT, DELETE and a `/validate` POST, but **Workspace panel authoring from scratch is not a supported API** — Adobe's own guidance is to create a template project in the UI and have your application change only small portions of the project definition, and some fields such as tags cannot be POSTed at all. The project JSON is a large, undocumented but stable blob. No sandbox — this needs a live report suite. Customer Journey Analytics customers get a cleaner projects API, which is the better long-term target.

### 10. Microsoft Purview (Data Lifecycle Management / DLP) `closed`

**Why it's powerful:** Tenant-wide retention policies and retention labels with auto-apply driven by trainable classifiers, sensitive information types or KQL; adaptive scopes; disposition review; DLP across Exchange, SharePoint, OneDrive, Teams and Endpoint; sensitivity labels with encryption; eDiscovery Premium with holds, searches and review sets; communication compliance and unified audit. The decisive fact is commercial rather than technical: **every Microsoft 365 E3 and E5 tenant already pays for this**, and almost none of them have it configured correctly.

**Why people bounce off it:** The failure modes are documented by Microsoft itself, which is the tell. Retention policies show a status of "(Error)" whose official remedy is to re-run `Set-RetentionCompliancePolicy` to retry distribution — an admin is expected to know that. The "principle of retention" (retain beats delete) surprises admins who believed they had configured deletion, and they only discover otherwise during a disposition review. Hard ceilings bite silently: 10,000 policies per tenant, 1,000 retention labels, and 25 retention policies per mailbox recommended against 50 supported. DLP rules never fire because of instance-count and confidence thresholds buried three dialogs deep. And static versus adaptive scope must be chosen before anyone understands the difference between them. The person operating this is usually a generalist IT admin at a mid-sized firm with a compliance obligation and no compliance specialist.

**AI operator:** Five skill packs. **Policy Author** turns a plain-language records schedule into retention policies, labels, label policies and auto-apply rules. **DLP Rule Compiler** handles sensitive information types, confidence, instance counts and exceptions — always born in simulation mode. **Conflict and Limits Analyst** resolves precedence, counts per-mailbox policies, checks scope overlap and validates against the ceilings *before* creating anything. **eDiscovery Runner** drives case, hold, search, statistics and export. **Health Doctor** finds distribution errors, retries them, and reports label publish status. Safety model is the strictest on this list, because several actions here are irreversible by design: every change is emitted as a reviewable PowerShell change-set run against a dev tenant first; **DLP always starts as `-Mode TestWithoutNotifications`**; retention policies are created `-Enabled $false` and enabled only after impact review; a JSON snapshot of every policy and rule supports restore; and there is a hard block on preservation lock and on retention-scope shrink, both of which cannot be undone.

**Killer example:** User says: *"Keep everything in Finance SharePoint sites for 7 years from last modified then delete after review, and stop anyone emailing files with 10 or more credit card numbers — but test it first."* → AI runs `Connect-IPPSSession`, then `New-RetentionCompliancePolicy -SharePointLocation <adaptive scope>`, `New-RetentionComplianceRule -RetentionDuration 2555 -RetentionComplianceAction KeepAndDelete -ExpirationDateOption ModificationAgeInDays`, and `New-DlpCompliancePolicy` plus `New-DlpComplianceRule -ContentContainsSensitiveInformation @(Name="Credit Card Number"; mincount="10") -Mode TestWithoutNotifications` — reporting the affected item counts before anything enforces.

**Integration path:** **Security and Compliance PowerShell** is the real automation surface — `Connect-IPPSSession` with certificate-based app-only auth, then `New/Set/Get-RetentionCompliancePolicy`, `-RetentionComplianceRule`, `-DlpCompliancePolicy`, `-DlpComplianceRule`, `New-Label`, `New-LabelPolicy` and `New-ComplianceSearch`. Graph covers eDiscovery at `/security/cases/ediscoveryCases` and reading sensitivity labels. A free Microsoft 365 E5 developer tenant is a genuine sandbox. Honest gaps, and they set the buildability score: there are **no supported Graph REST endpoints for creating retention or DLP policies** — PowerShell only, so the backend needs a PowerShell 7 execution host with app-only certificate auth rather than being pure SaaS; policy distribution is asynchronous and can take **one to seven days** to take effect, so verification must be a patient poll rather than a synchronous assert, which materially shapes the product's UX; and preservation lock and non-modifiable retention are irreversible.

**Demand 5/5 · Buildability 3/5**

**Why it's powerful:** Thirty-five-plus modules in one tenant — CRM with smart process automation, Tasks with Scrum, Gantt, checklists and time tracking, a full BPM engine with business processes and CRM automation robots, telephony and omnichannel Open Channels, HR absence calendars, Drive, and a website and landing builder. The BPM designer can model approval chains, conditional branching and cross-module triggers that would otherwise need Jira plus Zapier plus a CRM. **Killer example:** User says: *"When a deal hits Contract Sent, give legal 2 days to approve; if approved, create a project with our standard 12-task install checklist and assign the crew; if rejected, kick it back to Negotiation and DM the rep."* → AI calls `crm.category.stage.list` to resolve stage IDs, `bizproc.workflow.template.add` to install an approval template bound to the deal document type, wires the stage robot to `bizproc.workflow.start`, then on approval calls `sonet_group.create` plus a loop of `tasks.task.add` with `UF_CRM_TASK` linking each task back to the deal, and `im.message.add` for the rejection DM — all wrapped in a single `batch` call.

Honest gaps: Bitrix24 is mid-migration to "REST 3.0" with a different call path and response format, and 3.0 currently covers only basic task operations — so you straddle two API generations; on-premise and cloud method availability diverge; some newer CRM automation-rule types do not round-trip cleanly through `bizproc.*`; and rate limits are per-portal and not documented in exact numbers.

### 12. Microsoft Bookings `closed`

**Why it's powerful:** Bookings ships inside Microsoft 365, so nearly every business already owns it without knowing. It supports services with duration, pre- and post-buffers, price and per-service staff; staff availability derived live from Outlook free/busy; custom intake questions; scheduling policies covering minimum lead time, cancellation window and time increments; email and SMS reminders; automatic Teams meeting creation; and multiple booking pages per business alongside personal "Bookings with me" pages. For a clinic, a salon or a consultancy it is a complete scheduling product they are already paying for.

**Why people bounce off it:** It is admin-hostile in the specific Microsoft 365 way, where the fix is always on a different surface than the failure. Enablement runs through Exchange PowerShell (`Set-OrganizationConfig -BookingsEnabled`), so the very common "You don't have permission to create a booking calendar" wall has its remedy in a tenant policy no small-business owner will ever find. The booking calendar is a hidden mailbox object, so it does not appear where owners look for it. And staff availability comes silently from Outlook free/busy — so slots simply "disappear" and nobody knows why. On top of that: buffer time versus minimum lead time confusion, publish/unpublish interacting with self-service scope, and round-robin behaviour across multiple staff that is not explained anywhere in the UI.

**AI operator:** Five skill packs. **Business Bootstrapper** sets up the business, hours, branding and policies. **Service and Staff Modeler** handles durations, buffers, roles and round-robin. **Intake Questions** creates custom questions and maps them downstream. **Availability Doctor** is the killer pack and the reason this ranks: it diagnoses "why is no slot showing?" by walking staff mailbox free/busy, working hours, scheduling policy, lead time and time zones, and **names the one blocking factor** — the question the product cannot answer about itself. **Ops** handles bulk reschedule, cancel with reason, and reminder cadence. Safety model: configuration is mirrored to a staging booking business first, a full JSON snapshot is taken before edits, and anything customer-visible — publishing a page, cancelling appointments, sending reminders — requires explicit confirmation with the affected-customer count shown, because the blast radius here is other people's calendars.

**Killer example:** User says: *"Add 'Dental Cleaning, 45 min' with a 15-minute buffer, only Tue/Thu 9–3, Dr. Lee and Dr. Patel round-robin, ask for insurance ID, and no same-day booking."* → AI calls `POST /solutions/bookingBusinesses`, `POST /{id}/staffMembers`, then `POST /{id}/services` with `defaultDuration: PT45M`, `postBuffer: PT15M`, `schedulingPolicy.minimumLeadTime: P1D` and both staff member IDs, adds the intake question via `POST /{id}/customQuestions`, and finishes with `POST /{id}/publish`.

**Integration path:** Microsoft Graph v1.0 at `/solutions/bookingBusinesses` with sub-collections for `services`, `staffMembers`, `customQuestions`, `appointments` and `customers`; MSAL plus the Graph SDKs for JS, .NET and Python; a free Microsoft 365 developer tenant as a real sandbox. Honest gaps, and they are important architecturally: application (app-only) permissions support read **and** write only for `bookingCustomer` and `bookingAppointment` — `bookingBusiness`, `bookingService`, `bookingStaffMember` and `bookingCustomQuestion` are **read-only app-only**, so the entire configuration half of the operator must run **delegated** on behalf of an admin rather than as a daemon. Separately, `Bookings.ReadWrite.All` explicitly cannot create, delete or publish a booking business — that requires `Bookings.Manage.All`. And tenant enablement is Exchange Online PowerShell, not Graph, so the operator needs a PowerShell path for the single most common first-run blocker.

**Demand 4/5 · Buildability 4/5**
