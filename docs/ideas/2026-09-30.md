### 1. Renovate (Mend Renovate: self-hosted CLI, GitHub App or GitLab runner; configured through renovate.json and shared presets) `open-source`

**Why it's powerful:** It supports 90+ package managers (npm, Maven, Gradle, Docker, Helm, Terraform, GitHub Actions, and regex managers for any file). It can group updates, run on schedules, automerge, pin digests, raise vulnerability alerts, handle monorepos, share presets across an org, and keep a Dependency Dashboard issue. It can replace Dependabot and does much more.

**Why people bounce off it:** The only way to configure it is a large JSON schema with hundreds of options, and most real behavior depends on the order of packageRules. Rules match on matchPackageNames, matchDepTypes, matchUpdateTypes, matchManagers and matchFileNames, later rules override earlier ones, and several options were renamed recently (matchPackagePatterns was folded into matchPackageNames). Nothing shows which rule applied to which dependency. Teams either get flooded with PRs on day one or write a config that quietly never opens a PR, and then turn Renovate off. Custom regex managers are hard to write without a debugger.

**AI operator:** 'Renovate Whisperer' reads the repo (lockfiles, manifests, CI files), runs `renovate --platform=local --dry-run=full` and `renovate-config-validator`, and turns a plain-language policy into a validated renovate.json or org preset. It explains any existing config in plain English. It answers 'why did or didn't this dependency get a PR?' by parsing Renovate's debug log (packageFiles, branches, matched rules). It writes customManagers regexes and tests them against real file contents, and it forecasts PR volume before the config change is merged.

**Killer example:** A platform lead says: 'We have 120 repos drowning in 900 open Renovate PRs. Make one org preset: group AWS SDK and Terraform providers into a Monday-morning PR, automerge devDependency patches once CI is green, never go past Node 20, ignore our @acme/* packages, and tell me why the payments repo hasn't had a single PR in 3 months.' The AI writes the preset (groupName, schedule ['before 9am on monday'], automerge for devDependencies patch updates, allowedVersions '<21' for node and node Docker images, enabled:false for @acme/**) and dry-runs it across 5 sample repos: '43 PRs per week drop to 7.' It parses the payments repo's debug log. The cause is a stale ignorePaths ['**/src/**'] that hides the only package.json, so 61 updates are silently skipped. It then opens one PR on the config repo and one on payments, each with a plain-English explanation.

**Integration path:** Renovate is an open-source Node CLI that runs headless (`npx renovate`, with `--platform=local` for dry runs on a checkout). It ships a JSON schema and a config validator, and its structured JSON debug logs show which rules matched each dependency. The GitHub and GitLab REST APIs let the agent read the Dependency Dashboard issue and open config PRs. It can ship as an MCP server, a GitHub App or a CLI companion.

**Demand 4/5 · Buildability 5/5**

### 2. Salesforce Reports & Dashboards (custom report types, joined reports, cross filters, bucket fields, row-level and summary formulas, dynamic dashboards, subscriptions) `closed`

**Why it's powerful:** It is the analytics layer that sales managers, VPs and RevOps staff in every Salesforce org work in. It runs on live CRM data with no ETL and supports cross-object 'with/without' filters, historical trending, bucketing, formula columns and conditional highlighting. Dashboards can run as the viewing user and be emailed across the org.

**Why people bounce off it:** The data a user wants is usually not reachable from the standard report types. They need an admin to build a Custom Report Type with the right object relationships ('A with or without B') and don't know which one applies. Cross filters, summary formulas such as PARENTGROUPVAL and PREVGROUPVAL, joined reports, the 3-grouping limit and the 2,000-row display cap all trip up end users. The result is an admin backlog of 'can you build me a report' tickets and hundreds of near-duplicate reports.

**AI operator:** 'Ask-the-Pipeline Report Builder' indexes the org's describe metadata (objects, fields, relationships, existing report types) and how existing reports are used. It turns plain-language questions into Analytics REST API reportMetadata: reportType, detailColumns, groupingsDown and groupingsAcross, reportFilters with a boolean filter string, aggregates, custom summary formulas and crossFilters. It picks an existing report type, or creates a Metadata API ReportType when none fits. It runs the report and shows the answer inline, then saves it to the user's private folder and can pin it to a dashboard. Before creating anything, it checks whether an existing report already answers the question.

**Killer example:** A sales VP types: 'Which enterprise deals slipped their close date more than twice this quarter? Group by rep, show what share of each rep's pipeline has slipped, and email it to my directors every Monday.' The AI first finds 3 near-duplicate 'slipped deals' reports and shows why none of them fits: all three miss the push count. It picks the 'Opportunities with Field History' report type, filters CloseDate changes in the current fiscal quarter, adds a row-level push count, filters for more than 2 pushes and Segment='Enterprise', groups by owner, and adds a PARENTGROUPVAL formula for the slipped share. The inline answer is '$4.1M across 23 deals; Dana's pipeline is 38% slipped vs a 9% team median.' It saves 'Slipped Enterprise Opps (QTD)', adds it to the Sales Leadership dashboard, and sets a Monday 8am subscription for the Sales Directors group. The whole thing takes one message instead of an admin ticket.

**Integration path:** Salesforce Analytics REST API (/analytics/reports with POST and PATCH reportMetadata, /describe, and sync and async runs), the Dashboards REST API, and Metadata API deploys for ReportType, Report and Dashboard. Describe calls keep the model grounded in real fields and relationships. OAuth runs as the end user, so sharing rules apply automatically. It can ship as a Lightning web component or utility-bar chat panel (AppExchange-style), or as an external web app or MCP server.

**Demand 5/5 · Buildability 4/5**

### 3. Azure Policy (with Initiatives, Remediation, Exemptions and Defender for Cloud regulatory compliance) `closed`

**Why it's powerful:** It is the enforcement engine for all of Azure. The Deny, Audit, Modify, Append, DeployIfNotExists and DenyAction effects can enforce tagging, allowed SKUs and regions, private endpoints, diagnostic settings, encryption and Kubernetes (Gatekeeper) policy across the whole management-group hierarchy. It ships thousands of built-in policies and compliance initiatives (CIS, NIST, ISO, MCSB), runs automatic remediation, and feeds the Defender for Cloud secure score.

**Why people bounce off it:** Policies are written in a JSON rule DSL: if/then, allOf/anyOf, field aliases such as Microsoft.Storage/storageAccounts/networkAcls.defaultAction, [*] array aliases, count expressions, and ARM template functions inside rules. You have to know exact alias names, and DeployIfNotExists needs an embedded ARM template plus a managed identity with the right role assignments. Assignment scope, notScopes, parameters, exemptions and inheritance down the management-group tree make it very hard to answer 'why was my deployment denied?' or 'what breaks if I switch this from Audit to Deny?'. Compliance evaluation can take up to 24 hours. Most teams stay on Audit forever.

**AI operator:** 'Guardrail Operator' takes a governance intent and finds a matching built-in policy, or writes a custom definition using aliases verified against the provider alias API. It assigns the policy at the right management-group scope with parameters and exemptions, and creates the managed identity and role assignments needed for DeployIfNotExists and Modify. Before enforcement it runs a what-if impact check: an Azure Resource Graph query for resources that would be non-compliant or blocked. It explains denials by joining Activity Log deny events to the policy assignment and rule, and it can start and track remediation tasks. Output can be exported as Bicep or Terraform (EPAC-style) policy-as-code.

**Killer example:** A cloud security lead says: 'Every storage account in the Prod management group must have public network access disabled. Fix existing ones automatically, except the two legacy ones in rg-finance-archive. Tell me what would break first. And why did Raj's deployment get denied this morning?' The AI picks the built-in Modify policy, confirms the alias Microsoft.Storage/storageAccounts/publicNetworkAccess, and runs a Resource Graph impact query. Result: 38 accounts are public today, and 3 of them serve static websites behind Front Door that would go dark. It proposes an exemption for rg-finance-archive and a Front Door private-link fix for the 3 websites. It then assigns the policy at mg-prod with a system-assigned identity and the Storage Account Contributor role, starts remediation and streams progress (35/35 remediated). On Raj's deployment, it joins the Activity Log denial to the 'Allowed locations' initiative inherited from the tenant root: he deployed to westus3, which is not on the list. Finally it hands over the Bicep for the IaC repo.

**Integration path:** Azure Resource Manager REST covers all of Azure Policy: policyDefinitions, policySetDefinitions, policyAssignments, policyExemptions, remediations and policyStates/summarize. Other surfaces are `az policy` and Az PowerShell, Azure Resource Graph (KQL over policyresources and resources) for impact analysis, the provider alias API (`az provider show --expand resourceTypes/aliases`), and the Activity Log for deny events. Auth is an Entra service principal or managed identity. Microsoft's open-source Enterprise Policy as Code (EPAC) is the export target.

**Demand 4/5 · Buildability 4/5**

### 4. Salesforce Sharing & Visibility model (org-wide defaults, role hierarchy, sharing rules, teams, territories, permission sets and groups, restriction rules), with Microsoft Dataverse/D365 security as a second connector `closed`

**Why it's powerful:** It is the most detailed record-level access model in mainstream SaaS. It layers org-wide defaults, role-hierarchy inheritance, owner- and criteria-based sharing rules, manual and Apex shares, account and opportunity teams, implicit parent/child sharing, permission sets with View All/Modify All, and restriction and scoping rules. Together these can express almost any regulated-industry visibility policy across 150k+ orgs.

**Why people bounce off it:** The top admin ticket is 'why can or can't user X see record Y?', and the UI can't answer it. The 'Sharing Hierarchy' button shows who has access but not why. Effective access comes from about 8 overlapping mechanisms spread over a dozen setup pages. Changing an org-wide default or a sharing rule triggers an org-wide recalculation with unpredictable effects. Tightening access for compliance ('reps must not see other regions' opportunities') becomes a spreadsheet-and-prayer project, so admins over-grant View All Data just to close tickets.

**AI operator:** 'Access Explainer & Planner' reads the org's security metadata through the Metadata API (SharingRules, CustomObject sharingModel, Role, Group, PermissionSet, RestrictionRule) and SOQL on setup objects (ObjectPermissions, FieldPermissions, PermissionSetAssignment, UserRole, GroupMember, the *Share tables with RowCause, UserRecordAccess). From these it builds a local graph of who reaches which records and why. Skills: explain_access(user, record) returns a chain of evidence. what_if(change) diffs reachable records before and after a proposed change by replaying the graph on sampled records. propose_least_privilege(policy in plain English) produces a change set of sharing rules and permission sets. find_overgrants() lists users holding View All/Modify All or broad group membership they never use, checked against login and EventLog data. Every change ships as a reviewable Metadata API package deployed to a sandbox first.

**Killer example:** An admin asks: 'Why can Priya in EMEA Inside Sales see the $2M Acme renewal owned by a US AE, and how do I stop that without breaking the US managers' view?' The AI returns a 3-link evidence chain. (1) OpportunityShare.RowCause=Rule comes from the 'All Opps > Enterprise Sales group' criteria rule. (2) Priya was added to the Enterprise Sales public group in March. (3) Her 'Deal Desk Lite' permission set also grants View All on Opportunity, so fixing the rule alone would not be enough. The proposed fix narrows the rule to Region__c='US' and replaces View All with a permission set scoped by a restriction rule. The what-if check: 1,284 opportunities leave Priya's view, 0 change for the 14 US managers, and 11 other EMEA reps lose the same accidental access. It also flags 27 more users with unused View All. It deploys to a sandbox and returns a validation report the admin can attach to the audit ticket.

**Integration path:** Salesforce REST and SOQL (UserRecordAccess, *Share objects with RowCause, ObjectPermissions, FieldPermissions, PermissionSetAssignment), the Tooling API, and Metadata API retrieve/deploy for SharingRules, Roles, Groups, PermissionSets and RestrictionRules, through a connected app with OAuth. The Salesforce CLI (sf project retrieve/deploy) is an alternative transport. It runs headless as a web app or MCP server, and every write is a validate-only deploy to a sandbox before production.

**Demand 5/5 · Buildability 3/5**

### 5. Screaming Frog SEO Spider (with Google Search Console, GA4 and PageSpeed API connectors) `closed`

**Why it's powerful:** It is the standard desktop crawler for technical SEO. It renders JavaScript and supports custom extraction (XPath, CSS or regex), structured-data validation, canonical, hreflang and pagination audits, crawl comparison, segments and custom JS snippets. It pulls GSC, GA4 and PageSpeed data for each URL, runs fully headless on a schedule, and exports 300+ issue tabs and bulk reports as CSV. Agencies and in-house e-commerce SEO teams use it for almost every large-catalog audit.

**Why people bounce off it:** There are hundreds of spider, rendering, include/exclude-regex and extraction settings, and one wrong choice silently ruins a crawl. For example, crawling a Shopify store without limits explodes on ?variant= and filter URLs, and without JS rendering the page's reviews and schema are missed. Custom extraction means writing XPath by hand. The output is also hard to use: dozens of CSV tabs, and joining 'canonicalised + non-indexable + has GSC clicks + missing Product schema' is spreadsheet work most store owners and junior marketers can't do. The CLI exists, but few people outside power users script it.

**AI operator:** 'Crawl Copilot' turns the user's goal into a crawl plan. It picks from a library of prebuilt .seospiderconfig templates (JS rendering, list mode, e-commerce faceted-navigation exclusions, Product/Offer schema extraction) and adds CLI flags. It runs the crawl headless, loads the exported tabs into DuckDB, joins them with GSC and GA4 metrics, and answers in plain language with a ranked fix list. It can also write fix payloads, such as redirect CSVs for Shopify or WooCommerce importers, or ticket text for developers. Scheduled runs are compared with the previous crawl to flag regressions.

**Killer example:** A store owner says: 'Traffic dropped 18% after our theme update. Find product pages that still get Google clicks but are now broken, and give me a redirect file I can upload.' The AI crawls the store headless with JS rendering, excludes ?variant= and ?sort_by=, extracts JSON-LD Product/Offer, pulls 90 days of GSC clicks per URL, and diffs against last month's scheduled crawl. Its answer: '212 affected URLs, 38k clicks at risk. The theme update caused 3 regressions. 96 product pages lost Offer.price because price now loads client-side, which is why rich snippets vanished. 75 pages now canonicalise to their collection page. 41 URLs 404 because of a handle change.' It produces redirects.csv, mapping each dead URL to its closest live product by title similarity in Shopify's import format, plus a developer ticket naming the exact theme snippet to fix.

**Integration path:** Official headless CLI: screamingfrogseospider --crawl <url> --headless --config <file.seospiderconfig> --save-crawl --output-folder --export-tabs "Internal:All,Response Codes:Client Error (4xx),..." --bulk-export "..." --export-custom-summary, plus list mode, GSC/GA4/PSI API toggles and database storage mode. The agent wraps the CLI as tools, keeps a versioned library of config templates (authored once in the UI, then chosen by the agent), and loads CSV output into DuckDB for plain-language-to-SQL analysis, calling the GSC Search Analytics API directly where needed. It needs a paid SF licence (about £199/yr) on the machine, so it ships as a local agent or a small VPS worker.

**Demand 4/5 · Buildability 4/5**

### 6. Microsoft Excel + Google Sheets charts and report-presentation layer (combo/secondary-axis charts, chart templates, sparklines, dynamic chart ranges, custom number formats, print setup) `closed`

**Why it's powerful:** Excel and Sheets can produce board-ready visuals: combo, waterfall, Pareto, box-and-whisker, and Gantt charts built from stacked bars. Chart ranges can grow automatically through Tables, dynamic arrays or OFFSET names. Custom number formats like [>=1e6]0.0,,"M", plus print titles, print areas and page breaks, turn a raw model into a printable report. Almost every business report ends up here.

**Why people bounce off it:** The chart UI is buried in panes and nested right-click menus. Getting a secondary axis, a set gap width, labels only on the last point, or a target line drawn as an extra XY series takes 15+ clicks per chart, repeated for every chart in a dashboard. Dynamic ranges need named formulas most people have never seen. Custom number format syntax is cryptic. Print setup (fit to 1 page wide, repeat header rows, page breaks per region) is notoriously painful. Users give up and paste screenshots into PowerPoint, or spend hours re-formatting every month.

**AI operator:** An add-in side panel (Office.js for Excel; Apps Script or the Sheets API for Sheets) with skills to build a chart from intent, restyle every chart to a house style, make charts grow with the data, apply number formats, and set up printing. The AI reads the used range and table schema, picks the chart type and series mapping, and writes the chart objects directly (series, axes, formats, data labels). It saves the house style as a reusable JSON theme, so the monthly refresh takes one sentence.

**Killer example:** A finance manager preparing the board pack says: 'Chart monthly revenue as columns with gross margin % as a line on a right axis, add a dashed 40% target line, label only the latest month, then make all 8 charts on this sheet use our brand colors, show money in $K, and fit the sheet on one landscape page with row 1 repeating. Save it so next month is one click.' The AI converts the data to an Excel Table so every chart extends automatically. It builds the column + line combo with margin on the secondary axis, adds the 40% target as a dashed series, and labels only the last point. It restyles all 8 charts to the brand palette and fonts and applies $#,##0,"K" and 0.0% formats. It sets landscape, FitToPagesWide=1 and PrintTitleRows=$1:$1, shows a before/after print preview, and saves 'Board Pack' as a theme. Next month, 'refresh board pack' re-applies everything to the new data in about 10 seconds, instead of the usual 2 hours of clicking.

**Integration path:** Excel: the Office.js Excel JavaScript API (charts.add, series.add, axisGroup, format.line, dataLabels, trendlines), the PageLayout API for print setup, numberFormat on ranges, and the Table API for auto-growing ranges. It runs as a sideloaded or AppSource task-pane add-in on web, Windows and Mac. An offline/batch mode for .xlsx uses openpyxl or ExcelJS chart objects. Sheets: Sheets API v4 batchUpdate (AddChartRequest, UpdateChartSpecRequest with basicChart series targetAxis RIGHT_AXIS, repeatCell numberFormat) or an Apps Script add-in. The LLM emits a constrained chart-spec JSON that is validated before being turned into API calls.

### 7. Broadcom Rally (formerly CA Agile Central / Rally Software) `closed`

**Why it's powerful:** It is a full enterprise agile system of record used by large banks, insurers, telcos and governments. It has a configurable portfolio hierarchy (Theme > Initiative > Feature > User Story > Task/Defect), timeboxes (Releases, Iterations, Milestones), capacity planning, and the Lookback API, which keeps full history so cycle time, burnups and CFDs can be computed as of any date. Each workspace has its own custom fields and workflow states.

**Why people bounce off it:** Casual users (PMs, executives, business stakeholders) have to learn WSAPI's nested-parenthesis query syntax, for example ((Release.Name = "PI 26.3") AND ((ScheduleState < Accepted) OR (Blocked = true))). They also have to understand workspace vs project scoping, project-tree inheritance, and why a Feature's rollup doesn't match its children. The legacy ExtJS custom apps are decaying, and the Lookback API needs MongoDB-style JSON queries over _ValidFrom/_ValidTo snapshots that almost nobody outside the Rally admin team can write. Bulk re-parenting, re-ranking and splitting stories across iterations is slow, one click at a time.

**AI operator:** 'Rally Operator' is a chat, Slack or Teams agent with skills for WSAPI CRUD, query building, Lookback snapshot analytics, and bulk changes (re-parent, re-rank, move timebox, split story, set blocked reason). Every write is shown first as a dry-run diff table, then executed in batches with an undo log. On first connect it learns the workspace's custom fields and state model by reading TypeDefinitions.

**Killer example:** A release train engineer says in Slack: 'Which PI 26.3 features for the Payments ART are at risk? Anything under 50% of points accepted with 2 or fewer iterations left. Then push their unstarted Falcon-team stories to PI 26.4 and flag the features.' The AI builds the WSAPI query and pulls Lookback snapshots to compute each feature's acceptance trend, which shows risks a point-in-time view would miss. It posts a risk table with burnup sparklines: 6 features at risk, 2 of them flat for 3 weeks because 4 stories are blocked on the same Fraud API dependency. It previews 37 story moves (Iteration=null, Release=PI 26.4) and an 'AtRisk' tag on the 6 features. After a thumbs-up, it runs them as batch POSTs, logs the old values, and replies 'Done. Say undo to revert.'

**Integration path:** Rally WSAPI v2.0 REST (rally1.rallydev.com/slm/webservice/v2.0) with API-key auth: full CRUD on every artifact type, a batch endpoint, and TypeDefinition/AttributeDefinition introspection for custom schema. The Lookback API (analytics/v2.0/service/rally/workspace/{id}/artifact/snapshot/query) covers history. The Python pyral toolkit exists. It ships as an MCP server plus a Slack/Teams bot, and nothing has to be installed inside Rally, which matters for locked-down enterprises.

**Demand 4/5 · Buildability 4/5**

### 8. GnuCash (double-entry accounting for small businesses and nonprofits) `open-source`

**Why it's powerful:** It is a mature, free, cross-platform double-entry package with real business features: customers, vendors, employees, jobs, invoices and bills with AR/AP aging, scheduled transactions, multi-currency with a price database, lot tracking for investments, budgets, OFX/QIF/CSV import with a Bayesian matcher, and XML, SQLite or Postgres storage. Many small businesses, sole traders, clubs, churches and nonprofit treasurers use it because it is free and they own their data.

**Why people bounce off it:** It is famously unfriendly. The business features sit behind a separate menu with their own rules (post an invoice to AR, then process the payment, with lot linking), and users regularly break AR aging by entering payments as plain register transactions. The import matcher and the 'Assign transfer account' flow confuse newcomers. Scheduled transactions, closing the books, multi-currency trading accounts and the Scheme-based custom reports are close to unusable for non-technical treasurers. Volunteer treasurers leave at handover time, and the next person inherits a file that looks corrupted.

**AI operator:** 'Treasurer Copilot' works on the .gnucash SQLite file or a Postgres book, using the official Python bindings for writes and piecash for fast reads. Its skills: correct AR and AP operations (post invoices and bills, apply payments with proper lot linking, issue credit notes), bank CSV reconciliation that learns the club's categories, recurring entries, period-close checklists, and plain-language financial statements for board or committee reports. Every change runs on a backup copy first, and the user sees an account-level diff before it is committed.

**Killer example:** A new volunteer treasurer for a community sports club says: 'I just took over and the AR report says 90 members owe dues, which can't be right. Here's September's bank CSV. Fix it, record the two Riverside Hall bills as paid, and give me a one-page report for Thursday's committee meeting.' The AI finds the cause of the inflated AR: the previous treasurer entered 63 dues payments as plain bank transactions, so the invoices were never closed. It re-links them as proper payments against the matching invoices. It then imports the CSV, matches 41 new deposits to open dues invoices by name and amount, posts and pays the two Riverside Hall bills, and flags 3 unmatched deposits for review. Real overdue count: 7 members over 60 days. It produces a PDF with income vs budget, cash position and the overdue list, all shown as a diff against a backup before anything is saved.

**Integration path:** Official GnuCash Python bindings (the gnucash module: Session, Book, Invoice, Customer, Vendor, Transaction, Split and lot APIs) for writes that respect the business logic. piecash (built on SQLAlchemy) for quick queries on SQLite or Postgres books. The gzipped, well-documented XML format is the fallback. Everything runs locally and headless. MVP: a Python MCP server with about 15 tools plus an LLM front end, which a solo developer can build in weeks. It could be sold as a hosted 'treasurer handover' service for clubs and nonprofits.

**Demand 3/5 · Buildability 5/5**

### 9. listmonk (self-hosted newsletter and mailing-list manager) `open-source`

**Why it's powerful:** It is an AGPL, single-binary Go + Postgres mailing-list manager with about 17k+ GitHub stars. It handles millions of subscribers on cheap hardware and can send through several SMTP or messenger backends (SES, Postmark, any SMTP) with throttling. It stores arbitrary JSONB subscriber attributes and segments with raw SQL expressions, including subqueries on campaign_views and link_clicks. It also has Go-template personalization, a transactional API, bounce processing via POP or webhooks, media storage, roles and a complete REST API. Teams use it to escape per-contact ESP pricing from Mailchimp or Klaviyo.

**Why people bounce off it:** Its main power feature is also the barrier: segmentation means typing Postgres WHERE clauses such as subscribers.attribs->>'plan' = 'pro' AND subscribers.id NOT IN (SELECT subscriber_id FROM campaign_views WHERE created_at > now() - interval '90 days'), which marketers can't write. Personalization uses Go template syntax ({{ .Subscriber.Attribs.city }}), with fallbacks through template functions. There are no drip or automation journeys and no A/B testing, which users leaving Mailchimp miss immediately. Bounce and SES setup are fiddly, so most non-technical teams go back to expensive ESPs.

**AI operator:** 'listmonk Pilot' compiles plain-language audience descriptions into segment SQL. It knows listmonk's tables (subscribers, subscriber_lists, campaign_views, link_clicks, bounces) and previews every generated query through the API with a live count and sample rows before saving. A campaign composer writes copy, inserts correct Go-template personalization with default() fallbacks, and sends test emails. A small sidecar scheduler adds what listmonk lacks: drip sequences (a scheduled segment query plus the transactional API) and A/B tests (random list split, send, compare views and clicks, then send the winner to the rest).

**Killer example:** User says: 'Email Pro-plan customers in India who signed up in the last 90 days but haven't opened anything in 30 days. Test two subject lines on 20% of them, then send the winner to the rest tomorrow at 10am IST. Greet them by first name, or "there" if it's missing.' The AI compiles the SQL (attribs->>'plan'='pro' AND attribs->>'country'='IN' AND created_at > now()-'90 days' AND id NOT IN recent campaign_views) and previews it: '1,842 subscribers, sample below.' It creates two temporary lists from a random 10% + 10% split, writes both campaigns with {{ .Subscriber.Attribs.first_name | default "there" }}, and sends them. A sidecar job compares open and click rates after 18 hours, then creates and schedules the winning campaign for the remaining 1,474 subscribers at 10:00 IST.

**Integration path:** listmonk REST API: /api/subscribers (the query parameter takes an SQL expression for search and preview), /api/lists, /api/campaigns (including test sends and schedule/status), /api/templates, /api/tx for transactional sends, and /api/bounces, authenticated with an API user token. Optional read-only Postgres access speeds up analytics. The sidecar is a small cron + SQLite service that builds drips and A/B tests on top of the API. It ships as a Docker Compose add-on next to listmonk, which suits self-hosters. The API surface is very small, which makes this a strong solo-developer MVP.

**Demand 3/5 · Buildability 5/5**

### 10. Mixpanel (product analytics: Insights, Funnels, Flows, Retention, Cohorts, Lexicon data governance) `closed`

**Why it's powerful:** It offers event-level behavioral analytics: funnels (conversion windows, holding a property constant, exclusion steps), retention curves, Flows path analysis, behavioral cohorts that sync to ad and CRM tools, group analytics for B2B accounts, and Lexicon for governing the event taxonomy. ### 11. Microsoft Word: Content Controls, Custom XML data binding, Building Blocks/Quick Parts and fields, used as a document-assembly and clause-template layer (Docassemble/docxtpl as the open-source backend) `closed`

**Integration path:** Office.js Word API: ContentControls (insertContentControl, tag/title, dropdown and checkbox types in WordApi 1.9+), the CustomXmlParts API, insertOoxml for complex blocks, document.properties, and a body API that respects tracked changes. Server-side batch assembly needs no Word at all: python-docx + docxtpl (Jinja inside .docx), docx4j OpenDoPE bindings, or open-source Docassemble for interview-driven generation.
