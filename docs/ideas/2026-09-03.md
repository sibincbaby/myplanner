### 1. Google Calendar `closed`

**Why it's powerful:** Far more than a day planner: complex RRULE recurrences with exceptions, multiple overlapping calendars with sharing ACLs, bookable Appointment Schedules with buffer/availability rules, Focus Time and Out-of-Office auto-decline, resource/room booking, and working-location tracking.

**Why people bounce off it:** Almost nobody can hand-write a correct custom recurrence ('every 2nd and 4th Tuesday except holidays, ending after 12 occurrences'), and the appointment-scheduling/availability configuration (buffers, min notice, per-day windows) is buried several menus deep — most people just book 1:1s by hand or pay for a separate tool like Calendly.

**AI operator:** A skill using the fully documented Google Calendar REST API (OAuth2, no scraping) to create/edit RRULE recurring events, manage per-calendar sharing ACLs, configure Appointment Schedules, and set Focus Time / Out-of-Office blocks from natural language.

**Killer example:** User: 'Set up a bookable slot every weekday 2-4pm for 30-min client calls, 15-min buffer between each, but block the last week of December and auto-decline anything that lands there.' AI creates the Appointment Schedule via the Calendar API with the recurrence, buffer rule, and a date-range exception, then adds a matching Out-of-Office event with auto-decline for the blackout week — a five-screen wizard collapsed into one request.

**Integration path:** Google Calendar API v3 — clean REST/OAuth2 surface, no headless-browser workarounds needed.

**Demand 5/5 · Buildability 5/5**

### 2. CrowdStrike Falcon console `closed`

**Why it's powerful:** Unifies endpoint telemetry, threat intel, identity protection, and cloud security into one console, with custom detections via Falcon Query Language (FQL), IOA/IOC management, Fusion SOAR workflows, and Real Time Response (RTR) for live remote remediation across thousands of endpoints simultaneously.

**Why people bounce off it:** FQL for hunting/detections has a steep, sparsely-documented syntax unlike SQL or KQL; building a Fusion SOAR workflow means understanding dozens of undocumented event schema fields through trial and error; triaging one real incident requires pivoting across five separate UI tabs (Detections, Investigate, Hosts, Identity Protection) to reconstruct a timeline — a widely-cited driver of slow MTTR in SOCs.

**AI operator:** A SOC copilot preloaded with FQL syntax and the Falcon API schema; analyst states intent in plain language, agent composes and runs the hunting query via the Query API, cross-references matches against threat intel, and — only with confirmation — issues containment or RTR remediation actions.

**Killer example:** User: 'Isolate every host that talked to this malicious IP in the last 6 hours, and show me a process tree from whichever one looks worst.' AI runs an indicator search for the IOC across the fleet, contains the matching hosts via the Hosts API, ranks them by detection severity, then invokes RTR's getProcessTree on the top host and hands back a readable incident timeline — a 20-minute five-tab investigation done in one turn.

**Integration path:** Falcon REST API (OAuth2): Detects API, Hosts API, Real Time Response API, and Query API for FQL — a mature, first-class programmatic surface already built for SOAR integrations, no scraping needed.

**Demand 5/5 · Buildability 4/5**

### 3. AWS CloudFormation `closed`

**Why it's powerful:** Declarative IaC natively wired into every AWS service: nested stacks, StackSets for multi-account/region rollout, change sets for safe dry-run previews, drift detection, and Lambda-backed custom resources — it's the governance backbone many enterprises are locked into via SCPs even where Terraform also exists.

**Why people bounce off it:** Real templates sprawl to thousands of lines of YAML/JSON with a mini programming language of intrinsic functions (Fn::Sub, Fn::ImportValue, Conditions); a failed update triggers automatic rollback with a terse message like 'Rollback requested by user' that forces manually cross-referencing the Events tab and CloudTrail; drift-detection output is a dense JSON diff almost nobody reads; StackSets' self-managed vs service-managed permission models confuse even certified engineers.

**AI operator:** A CloudFormation copilot using boto3/AWS CLI that turns plain-language infra requests into change sets, explains the plan in English before applying, and on failure automatically correlates stack events to the exact failing resource and root cause instead of leaving the user to dig.

**Killer example:** User: 'Add a read replica to my RDS stack in us-east-1 without downtime, and if it breaks tell me exactly why.' AI pulls the live template, generates a change set adding an AWS::RDS::DBInstance read replica, summarizes 'adds 1 resource, no replacements, no downtime,' executes on approval, and — if it fails — cross-references the Events tab against CloudTrail to name the exact IAM permission or CIDR conflict that caused the rollback, in plain English instead of a raw ARN dump.

**Integration path:** AWS CLI (`aws cloudformation`) and boto3/SDKs — fully scriptable template generation, change-set execution, and CloudTrail-based event correlation, no console scraping required.

**Demand 4/5 · Buildability 5/5**

### 4. Shopware 6 `open-source`

**Why it's powerful:** Enterprise-grade ecommerce platform with a Rule Builder (condition-based logic that drives pricing, shipping, payment methods, and promotions), a Flow Builder (Zapier-like event→condition→action automation engine built into the store), a full CMS-style Shopping Experiences page builder, native B2B suite, and dynamic customer-group/net-gross pricing.

**Why people bounce off it:** The Rule Builder forces merchants to construct nested AND/OR condition trees from dozens of condition types (cart value, customer tag, line-item property, date range, sales channel) and the same rule objects get reused across promotions/shipping/payment, so mistakes cascade silently. Flow Builder requires chaining trigger→condition→action sequences correctly. Most store owners never go past the default rules and either hire an agency or leave most of the automation power untouched.

**AI operator:** AI operator preloaded with Shopware Admin API skills for the rule, rule_condition, flow, flow_sequence, promotion, and product entities — translates a plain-language business policy into the nested rule/flow JSON and creates + activates it directly.

**Killer example:** User says 'Give free shipping to VIP customers who spend over $150 and tag the order vip-fulfillment automatically' → AI builds a Rule (customer group = VIP AND cart amount > 150), attaches it to a new free-shipping method, then creates a Flow (trigger: order placed → condition: rule matches → action: add order tag 'vip-fulfillment'), all live via the Admin API without the user ever opening the Rule Builder canvas.

**Integration path:** Shopware Admin API (REST, OAuth2 client-credentials) exposes full CRUD over rule/flow/promotion/product entities — confirmed against the official `shopware/admin-api-reference` OpenAPI spec: `POST/GET/PATCH/DELETE` on `/rule`, `/rule-condition`, `/flow`, `/flow-sequence`, with `Flow.sequences` and `RuleCondition.{type,value,position,parentId}` exposing exactly the condition-tree/flow-graph structure the builder edits. Self-hostable, so the operator can run against a merchant's own instance.

**Demand 4/5 · Buildability 4/5**

### 5. Red Hat OpenShift Container Platform (Console + oc CLI) `open-source`

**Why it's powerful:** Adds enterprise governance on top of vanilla Kubernetes: OperatorHub for one-click complex software installs, integrated source-to-image BuildConfigs/ImageStreams/DeploymentConfigs, built-in Routes for HTTP(S) exposure with edge/re-encrypt TLS, and Security Context Constraints (SCCs) for fine-grained pod security multi-tenancy across large enterprise clusters.

**Why people bounce off it:** The Console layers dozens of OpenShift-specific resource kinds (SCC, Route, BuildConfig, ImageStream, DeploymentConfig, Operator Subscriptions) on top of k8s YAML that engineers already struggle with. A pod failing to schedule due to SCC denial gives only a cryptic 'unable to validate against any security context constraint' error with no hint which of the ~8 default SCCs or field to fix; wiring build->image->deploy->public-URL requires correctly chaining four distinct resource types via CLI flags or a wizard that silently fails on misconfiguration.

**AI operator:** An OpenShift copilot preloaded with the `oc` CLI and SCC/Route/Operator semantics as skills; user states an end-state goal, agent runs the multi-resource oc commands, reads pod events/logs to diagnose SCC or network denials, and proposes the minimal-privilege fix instead of defaulting to permissive access.

**Killer example:** User: 'This pod keeps crashing with a permission error, expose it at api.mycompany.com with HTTPS.' AI runs `oc describe pod`, spots the SCC denial in the events, creates a narrowly-scoped custom SCC granting only the needed capability (instead of the lazy anyuid fix a human under deadline pressure would reach for), creates a Route with edge TLS, then curls the live URL to confirm the whole build->image->deploy->public-URL chain actually works end to end.

**Integration path:** `oc` CLI with JSON output (fully scriptable) plus the Kubernetes-compatible OpenShift REST API; can also ship as an in-cluster Operator via Operator SDK for native, continuously-running integration — no UI scraping needed.

**Demand 4/5 · Buildability 4/5**

### 6. MYOB AccountRight / MYOB Business (Australia/NZ SME accounting) `closed`

**Why it's powerful:** Full double-entry ledger plus integrated payroll (STP-compliant), GST/BAS reporting, inventory with build-item assemblies, multi-currency, job/category tracking, and bank-feed rule engines — it's the de facto backbone for Australian and NZ small-to-mid businesses, replacing what would otherwise need separate payroll, tax, and inventory tools.

**Why people bounce off it:** New users drown in tax-code mapping (GST/BAS categories that don't map intuitively to real-world transactions), bank-feed rule setup, and payroll compliance fields (STP categories, super guarantee rates, leave accrual rules) — most small business owners end up paying a bookkeeper monthly just to keep the ledger reconciled and BAS-ready rather than ever touching these screens themselves.

**AI operator:** A conversational bookkeeping copilot pre-loaded with MYOB's chart-of-accounts/tax-code semantics that watches the bank feed, proposes categorizations and GST codes in plain English, drafts BAS lodgement figures, and sets up new employees/pay items from a one-line description — with the user approving each batch instead of clicking through wizards.

**Killer example:** User: 'Reconcile this month's bank feed, match the recurring spends to the right GST codes, and tell me if my BAS is going to look off compared to last quarter.' AI runs the AccountRight bank-feed matching rules, applies existing tax-code mappings and creates new ones for unrecognized recurring vendors, flags three transactions that look mis-coded, and produces a draft BAS summary with a plain-English delta explanation ('GST payable is up 18% mainly because of the new equipment purchase in June') — replacing the monthly bookkeeper check-in.

**Integration path:** MYOB AccountRight API (developer.myob.com) — documented REST/OAuth2 API covering bank feeds, invoices, contacts, tax codes, payroll categories, and BAS/GST reporting endpoints; also MYOB Essentials/Business API for the cloud-only tier.

**Demand 4/5 · Buildability 4/5**

### 7. Sisense `closed`

**Why it's powerful:** Its ElastiCube in-chip engine handles large blended datasets fast, it's the default choice for SaaS companies embedding BI into their own products, and under the hood everything — pivots, widgets, custom code — ultimately compiles to JAQL (JSON Analytics Query Language), a full ad-hoc query layer exposed directly via REST.

**Why people bounce off it:** Modeling an ElastiCube (choosing joins, writing calculated-field SQL expressions, scheduling builds) and writing JAQL for anything beyond a drag-drop pivot requires a dedicated Sisense data engineer. Most business users only ever consume prebuilt dashboards and file tickets for 'just one more field,' creating the same single-point-of-bottleneck pattern seen across enterprise BI.

**AI operator:** An AI operator that knows the Sisense REST API (v1/v2) and JAQL syntax well enough to either add a calculated field to the ElastiCube data model or compose and execute a raw JAQL query against the existing cube, then render the result into a new dashboard widget — all from a plain-language ask, no UI needed.

**Killer example:** User: 'Add customer lifetime value as sum of paid invoices per customer, then show me the top 20 customers by that value for the last fiscal year, next to the churn-risk widget.' AI creates the calculated field via the Data Model REST API, writes and executes the ranked JAQL query directly against the `/api/datasources/{cube}/jaql` endpoint bypassing the UI entirely, and inserts the resulting widget beside the existing one via the Widget API — the exact 'just one more field' request that normally sits in a data-engineer's ticket queue for days.

**Integration path:** Sisense REST API v1.0/v2.0 (data models, ElastiCubes, dashboards, widgets) plus a documented `/api/datasources/{cube}/jaql` endpoint that runs arbitrary ad-hoc queries — one of the most AI-operator-friendly BI backends because queries can bypass the UI entirely.

**Demand 3/5 · Buildability 4/5**

### 8. GoodData (GoodData.CN Community Edition) `open-source`

**Why it's powerful:** A governed semantic layer (Logical Data Model) sits under every report so metrics stay consistent company-wide, similar in spirit to dbt's semantic layer but with full BI and white-label embedding on top; ships a modern 'analytics as code' Python SDK (gooddata-sdk, gooddata-pandas) that can version-control the entire LDM, metrics, and dashboards.

**Why people bounce off it:** Defining the Logical Data Model (entity relationships, grain, date dimensions) and writing MAQL (GoodData's Multi-dimensional Analytical Query Language) for anything beyond a basic sum/count — ratio metrics, same-period-last-year comparisons, 'over'/context-filter clauses — has a steep learning curve GoodData's own docs acknowledge; usually only 1-2 people per org can safely touch the LDM without breaking downstream reports.

**AI operator:** An AI operator loaded with the gooddata-sdk, LDM conventions, and MAQL syntax that validates a requested metric against the live LDM via the API's compute/introspection endpoints, then writes the MAQL definition (or a new LDM dataset/relationship as code), and pushes it as a versioned, testable change rather than a risky in-UI edit.

**Killer example:** User: 'I need year-over-year revenue growth percent by product line, counting only closed-won deals.' AI writes the MAQL metric with a SAME PERIOD PREVIOUS YEAR clause and a closed-won filter, validates it against the LDM via the compute API before ever touching production, creates the visualization, and adds it to the target dashboard — as a diffable, version-controlled change any teammate could review in a PR rather than an untracked in-UI edit.

**Integration path:** GoodData.CN REST API plus the official gooddata-sdk / gooddata-pandas Python packages, purpose-built for declarative 'LDM and analytics as code' (diffable, CI-runnable) — self-hostable via Docker/Kubernetes, which makes it the easiest of the four to prototype an operator against without enterprise sales/licensing friction.

**Demand 3/5 · Buildability 5/5**

### 9. YouTrack (JetBrains) `closed`

**Why it's powerful:** A full query language (YouTrack Query Language) for saved searches/dashboards, per-project custom field bundles and state machines, JS-based Workflow rules (on-change/on-schedule/action-guard), agile boards with swimlanes and burndown, and a built-in knowledge base — enough to model an entire dev org's process without leaving one tool.

**Why people bounce off it:** YQL syntax and JS workflow rules are effectively a mini programming language; configuring custom field bundles, attaching workflows to projects, and writing guard conditions requires real admin/dev skill, so most teams never get past a flat Kanban board and manual triage even though the engine can auto-route, auto-escalate, and enforce process rules.

**AI operator:** NL layer that turns plain requests into saved YQL searches/dashboard widgets, drafts JS workflow rules from a description, and manages custom field schemes/state machines across projects via the REST API plus a local deploy step.

**Killer example:** User: 'Block issues from moving to Done if they don't have a linked pull request, and ping the assignee's lead after 3 days unresolved.' AI writes the JS workflow rule — an on-change guard condition checking for a linked PR plus an on-schedule notification job — as a local workflow module, then pushes it live via JetBrains' official `youtrack-workflow upload` CLI, turning a process policy that would otherwise require a developer to hand-write JS into a one-line request.

**Integration path:** Full REST API for issues/projects/custom fields/admin (YQL searches, dashboards, custom fields are all directly writable via REST). Workflow-rule deployment is **not** a REST endpoint — verified against JetBrains' own devportal docs, which only document the in-editor scripting helpers, not a create/deploy API. The real programmatic path is the official `@jetbrains/youtrack-scripting-api` npm package's `youtrack-workflow upload` command, which zips a local JS workflow directory and pushes it to a server non-interactively via `--host`/`--token`. Still fully automatable, just via a packaged CLI rather than a documented REST call — self-hosted Standalone instance required for that upload path.

**Demand 3/5 · Buildability 3/5**

### 10. HashiCorp Consul `open-source`

**Why it's powerful:** Combines service discovery, health checking, a zero-trust service mesh (mTLS + intentions-based access control), L7 traffic management, and a distributed KV store spanning VMs, containers, and multi-datacenter/multi-cloud WAN federation.

**Why people bounce off it:** Intentions (the ACL rules deciding which services may talk to which) become an unmanageable flat list at hundreds of services, and a missing intention shows up only as a mysterious mTLS connection timeout with no pointer to 'add an intention'; L7 traffic splitting requires correctly chaining three separate config-entry types (service-splitter, service-router, service-resolver) where wrong precedence silently misroutes 100% of traffic; WAN federation setup (gossip keys, mesh gateways, ACL replication tokens) is notorious for taking platform teams days.

**AI operator:** A Consul copilot preloaded with the HTTP API and CLI as skills that translates natural-language connectivity requests into intentions, diagnoses service-to-service failures by sequentially checking health, intentions, and sidecar state, and safely stages canary traffic-split config entries.

**Killer example:** User: 'Why can't checkout-service reach payments-service, and fix it.' AI checks payments-service health (healthy), checks sidecar proxy state (up), checks intentions (default-deny, no explicit allow — the actual cause), creates the scoped intention via the API, re-verifies the mTLS handshake now succeeds, and reports the root cause in plain English — the exact debugging chain a platform engineer would otherwise walk manually across three separate consul CLI commands.

**Integration path:** Consul HTTP API (token-based ACL auth, fully documented) plus the `consul` CLI — both scriptable; can run continuously as a sidecar/operator watching cluster state.

**Demand 3/5 · Buildability 4/5**
