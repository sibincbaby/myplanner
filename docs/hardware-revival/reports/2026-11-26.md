## 1. Most interesting discoveries

### ecovacs-t20-local-control: LAN root on an Ecovacs Deebot T20 Omni with no flashing or UART (created 2026-11-20)
- **What it is:** [Syax89/ecovacs-t20-local-control](https://github.com/Syax89/ecovacs-t20-local-control) (0★, created and last pushed 2026-11-20). It is a guide plus sanitised code that takes "one Ecovacs Deebot T20 Omni" to full local control.
- **How (README "The journey"):**
  1. A narrow DNS redirect points the robot's cloud hosts at a LAN machine.
  2. A transparent MITM bridges to the real cloud and logs everything. This works because "the robot does not validate the broker's TLS certificate."
  3. The traffic is plain Ecovacs MQTT, the protocol the open-source `deebot-client` library already speaks.
  4. The cloud routinely sends an `iot/p2p/shell` command whose payload is a base64 `/bin/sh` script that the robot runs as root. Owning the broker therefore gives root over the LAN.
  5. The shipped OpenSSH 7.9p1 has three build bugs, including a seccomp sandbox built for the wrong CPU architecture. The author binary-patches a copy in `/data`.
  6. Persistence comes from a `usercustomize.py` in `/data` that ROS's Python imports at boot. The read-only rootfs is never touched, and deleting one file reverses it.
- **Result:** a Home Assistant integration with about 60 entities, a live map decoded locally from the robot's 7z/LZMA fragments, and two reversible privacy mitigations. The README says bulk uploads carry "maps, furniture, AI interior photos, wake-word audio."
- **Hardware ([HARDWARE.md](https://github.com/Syax89/ecovacs-t20-local-control/blob/HEAD/docs/HARDWARE.md)):** Rockchip RK3326 (4× Cortex-A35), 512 MB RAM, an A/B squashfs rootfs plus about 231 MB of writable `/data`, 2.4 GHz-only RTL8189FS Wi-Fi, a UART LiDAR, and a global-shutter grayscale camera with no video device.
- **Limits:** one unit, on firmware 1.24.0 where `iot/p2p/shell` "is still honoured". Firmware images and keys are deliberately not included. A vendor update could close the shell path or add certificate validation.
- **Why it matters:** this is the first no-solder root path I have seen for a current-generation Ecovacs Omni. For context, the Valetudo-side guides cited in search results describe Ecovacs rooting as UART-based. The missing TLS validation is also a security finding in its own right.
- **Score:** 8/10 · **Confidence:** medium (detailed, reproducible write-up; one unit, one firmware).

### MowgliNext v1.7.0: a ROS 2 autonomous stack on real YardForce mowers (pushed 2026-11-23)
- **What it is:** [mowglinext/mowglinext](https://github.com/mowglinext/mowglinext) (54★, 32 forks, created 2026-04-03). It is a ROS 2 (Lyrical) monorepo with Nav2, BehaviorTree.CPP, a GTSAM iSAM2 localiser, Fields2Cover coverage planning and a web GUI. The README calls it "a complete autonomous mowing stack running on real hardware — undock, mow, avoid obstacles, dock, resume."
- **Hardware (README):** a YardForce chassis, an ARM64 SBC (RK3566/RK3588 or Raspberry Pi 4/5), RTK-GNSS (u-blox F9P, Unicore UM98x or generic NMEA), and a LiDAR (LDRobot LD19/STL27L or RPLIDAR A1). The low-level side is STM32 firmware on the stock Mowgli board, or in beta stock OpenMower v1 electronics or an ArduRover Pixhawk via MAVROS.
- **v1.7.0 changes:** the mower follows an obstacle's outline and rejoins the plan, docks along the GPS track, keeps mowing through brief RTK Float using a LiDAR map anchor, adds a GOTO command over MQTT/Home Assistant, and fixes LiDAR dropouts every 32 s. Updates install from the GUI with backup, health check and rollback.
- **AI angle:** the repo ships a root `CLAUDE.md` plus `docs/claude/` codemaps and interface indexes "for Claude Code (or any coding agent)".
- **Limits:** labelled "First Public Beta". Obstacle avoidance is marked WIP. You must add an SBC, RTK and a LiDAR, so this is a retrofit rather than a pure firmware swap.
- **Score:** 8/10 · **Confidence:** medium (working on the maintainers' hardware; testers invited).

### loona-cloud + project_loona: a self-hosted cloud for the KEYi Loona pet robot (created 2026-11-25 and 2026-11-26)
- **What it is:** [EldoonNemar/project_loona](https://github.com/EldoonNemar/project_loona) (2★) is a Python SDK built by reverse-engineering the Hello Loona Android app. It covers the mTLS TCP control channel, mDNS and UDP-multicast discovery, drive, dance and voice commands, and live camera and microphone over the local WebRTC "intranet" mode. [EldoonNemar/project_loona-cloud](https://github.com/EldoonNemar/project_loona-cloud) (0★, created today) is a self-hosted replacement for KEYi's cloud. You point the robot at it "via the firmware's switchable cloud host, command `405`", and it answers with your own LLM, image generator and local Whisper.
- **What is verified (README):** the mTLS socket, the `405` redirect, traffic capture, camera and mic, and local Whisper STT, all on a real robot. The full conversation loop "is still being shaken out", and TTS is "the least-verified piece". Suggested brains range from Qwen2.5-3B on a Pi 5 to 7–14B models on a GPU.
- **Cloud status:** I found no shutdown notice. A search summary cites a KEYi notice dated 2026-01-30 about a server migration on 2026-02-02 ([keyirobot.com news](https://keyirobot.com/blogs/news); not fetched). This is preparation, not a rescue.
- **Caution:** the SDK repo includes a client certificate extracted from the APK.
- **Score:** 7/10 · **Confidence:** low (two days old, alpha, one author).

### Moxie and Jibo: replacement clouds mature for two dead companion robots
- **Moxie** ([mvalancy/moxie-robot-saver](https://github.com/mvalancy/moxie-robot-saver), 5★, MIT, pushed 2026-10-28; alongside [jbeghtol/openmoxie](https://github.com/jbeghtol/openmoxie), 100★, pushed 2026-10-26):
  - moxie-robot-saver is a clean-room backend (parent app, TLS MQTT broker, LLM "brain") plus a 3D browser simulator.
  - [revival-path.md](https://github.com/mvalancy/moxie-robot-saver/blob/HEAD/docs/architecture/revival-path.md) documents a firmware gate. On **24.10.803** a self-signed certificate works, plug-and-play, through two camera QR codes. On **24.10.801** you need a publicly signed certificate or the 801→803 OTA. Anything older needs a reflash that is "not yet proven end to end".
  - The firmware has an `IOTEndpoint` value literally named `OPEN_MOXIE`.
  - Verified so far: a real Moxie joined Wi-Fi from the project's QR code. The broker has only been tested against the simulator.
- **Jibo** ([Jibo-Revival-Group/JiboExperiments](https://github.com/Jibo-Revival-Group/JiboExperiments), 3★, pushed 2026-11-25; [BEefy](https://github.com/Jibo-Revival-Group/BEefy), 1★, pushed today):
  - OpenJibo is a .NET replacement cloud (release constant 1.0.20) with a Node "protocol oracle". BEefy is the conversation server behind a free public server, 5x1. It needs no account, uses Sherpa ASR, and has an optional "Agent Mode" skill in which the robot calls an LLM directly.
  - The supported bootstrap ([device-bootstrap.md](https://github.com/Jibo-Revival-Group/JiboExperiments/blob/HEAD/OpenJibo/docs/device-bootstrap.md)) runs: QR Wi-Fi → region config → RCM/device patch → OpenJibo cloud.
  - A candidate path that needs no hardware tools is under test. It uses DNS to the LAN plus 2017-era NTP time, so the robot accepts the old `*.jibo.com` certificate chain and then takes an OTA.
  - The README says "physical OOBE/repeat deployment is pending delivery of the test units". The repo ignores a `.codex/` tree, which suggests Codex is in the workflow.
- **Score:** 6/10 each · **Confidence:** low (firmware gates; limited hardware validation).

### DumbyLuba: local BLE control and route planning for the Mammotion LUBA 2 AWD (created 2026-10-18; pushed 2026-11-03)
- **What it is:** [cleborgne-pro/DumbyLuba](https://github.com/cleborgne-pro/DumbyLuba) (14★, GPL-3.0). It is a Kotlin Android app that reads the mower's map, computes the route on the phone, simulates it, and has the robot follow it command by command. It adds camera-view remote control and coverage heatmaps for Wi-Fi, mobile and RTK.
- **The trick:** the LUBA's Bluetooth only reaches a few metres, so "an old Android phone or an ESP32 board placed on the robot" acts as a gateway. A printable enclosure for it charges through the dock contacts.
- **Limits:** only the LUBA 2 AWD is validated for motion. LUBA 1/3/mini and Yuka connect read-only. No firmware change is involved.
- **Score:** 7/10 · **Confidence:** medium.

### Parkside PMRDA 20 "BoB the Mower": patched firmware plus an ESP32-CAM dashboard (created 2026-10-14)
- **What it is:** [dannyb131/Parkside-Robot-Lawnmower-PMRDA-20-Bob-The-Mower](https://github.com/dannyb131/Parkside-Robot-Lawnmower-PMRDA-20-Bob-The-Mower) (0★). It is a patched GD32F303ZET6 mower image that adds a guarded UART extension. An AI-Thinker ESP32-CAM serves a local dashboard with live camera, telemetry, schedules, five zones and a joystick for differential steering. The ESP32-CAM talks to the MCU's FinSH shell over UART.
- **Safety design:** manual drive needs the mower Paused, inside the wire, and free of faults. The cutter runs only while the stick is held. There is no web fault reset.
- **Limits:**
  - The image targets one matched board.
  - The public ESP image "has not been flashed/physically commissioned on a spare ESP-CAM".
  - Speed units are "not verified physical RPM".
  - Lidl's Parkside line is not sold in India.
- **AI angle:** it ships `AI-HANDOVER.md` and `AGENTS.md`. The handover lists reverse-engineered invariants such as command IDs, guard bitmaps and magic values.
- **Score:** 7/10 · **Confidence:** medium.

### Ecovacs DEEBOT OZMO T8 AIVI (PX30): corrected root-password algorithm (created 2026-10-13)
- [Alpha162/deebot-t8-aivi-px30-notes](https://github.com/Alpha162/deebot-t8-aivi-px30-notes) (1★) covers a UK 2020 unit.
- **Debug access:** an 8-pin JST header under a rubber plug next to the LiDAR carries UART, 3V3 and SWD, with no teardown needed.
- **Root password:** the per-unit root password comes from `eco_passwd`. The notes show the 37C3 formula is wrong for PX30 in three ways (product string `AI_px30`, last 8 serial characters only, base64 of the ASCII `sha256sum` output) and give the corrected algorithm. Per the README, the dontvacuum calculator did not list this model as of 2026-10.
- **Persistence and camera:** persistence via `/data/autostart/*.sh`. The camera is available locally at `/dev/video0` (1280×960).
- **Why it matters:** the T8 generation is older and cheaper second-hand than the T20, with a local camera to reuse.
- **Score:** 7/10 · **Confidence:** medium (one unit).

## 3. AI-assisted hardware hacking

- **mower-stock-reverse: an honest, unfinished Claude Code teardown** ([salonnikov/mower-stock-reverse](https://github.com/salonnikov/mower-stock-reverse), 2★, created 2026-07-29, last push 2026-09-07).
  - **What was done:** a full teardown of a `SNK_MAINBOARD_CP_V11` mower board, sold as a Villartec MI 302 and "most likely Sunseeker". Both factory GD32 firmwares were decompiled, the three-MCU and three-BLDC architecture was mapped, an SWD dump and restore toolchain was built, and a custom chip1 firmware "runs on the real hardware".
  - **Honesty note:** the README says the decompilation and analysis "were done with heavy use of Claude Code (Opus 4.8)… I re-checked the findings by hand… the agent dramatically sped the work up."
  - **What the agent got wrong or could not do:** the early docs called the motor drivers Allegro A4963. Board photos later showed they are Fortior FU6832N parts emulating the A4963 protocol (correction dated 2026-07-13). The wheels "never spun under our own firmware", and the board then died from water ingress.
  - **Takeaway:** the agent accelerated firmware analysis. Identifying parts on the board and the final step of getting motors to move still needed hands-on hardware work, and stalled there.
- **Parkside BoB** ships `AI-HANDOVER.md` and `AGENTS.md` ([repo](https://github.com/dannyb131/Parkside-Robot-Lawnmower-PMRDA-20-Bob-The-Mower)). Reverse-engineered invariants (state codes, guard bitmaps, command semantics) are written down so an agent can continue the work safely. Physical commissioning, with the cutter disconnected and wheels clear, stays a human step.
- **MowgliNext** is structured for coding agents (root `CLAUDE.md`, nested `CLAUDE.md` files per area, codemaps, ROS-interface and parameter indexes) ([repo](https://github.com/mowglinext/mowglinext)). This is agent-assisted maintenance of a working robot stack, not reverse engineering.
- **MBot for Anki Vector** ([lailoken/MBot](https://github.com/lailoken/MBot), 8★, created 2026-11-24):
  - Claude, or a local model via Ollama, runs a persistent "mind" for the robot.
  - The hardware part is a small on-robot shim that streams raw audio from all four microphones before the firmware's wake-word gate, documented in its `ROBOT_MODIFICATIONS.md`.
  - Optional cloud lookups cost "about 1-2 cents".
- **cozmo-roverd** describes itself as "Slopcoded" ([repo](https://github.com/legop3/cozmo-roverd)), an AI-written bridge on top of PyCozmo. A separate Codex branch name, `codex/macos-camera-preview`, appears in the DJI Neo 2 research fork ([neo2-open-research](https://github.com/Arda-Dinc04/neo2-open-research)).
- **Cross-sector (search summaries only; pages blocked):**
  - A hobbyist post dated 2026-11-18, reposted by Adafruit on 2026-11-19 ([Adafruit](https://blog.adafruit.com/2026/11/19/llm-assisted-reverse-engineering/)), describes an agent reading the binary with purpose-written skills while the human steers.

## 5. Hidden opportunities

1. **Ecovacs Omni robots as SLAM bases.**
   - **Hardware:** T20 Omni with RK3326, a UART LiDAR and a station.
   - **Opportunity:** LAN root without opening the case means the LiDAR stream and drive commands are reachable from Linux.
   - **Why overlooked:** Valetudo does not support this line, so attention has gone to Roborock and Dreame.
   - **What could be built:** a ROS 2 bridge similar to VacuumTiger, but on an Ecovacs.
   - **Experiment:** reproduce the root on a second unit and firmware, then read the LiDAR serial port from the root shell.
2. **Companion-robot "brain transplants" as a category.**
   - **Hardware:** Moxie, Jibo, Loona and Vector all have expressive bodies, microphones and cameras, and all are getting clouds that speak an OpenAI-compatible API.
   - **What could be built:** one shared local stack (Whisper + a small LLM + TTS on a Pi 5 or mini PC) serving several of these robots.
   - **Experiment:** run loona-cloud's suggested Qwen2.5-3B on a Pi 5 and measure end-to-end reply latency.
3. **Robot-mower drive boards as rugged outdoor motor platforms.**
   - **Hardware:** GD32 mainboards with three BLDC channels, boundary-wire sensing and IP-rated chassis.
   - **Why overlooked:** stock firmware is closed, and the one public effort stalled at motor bring-up.
   - **What could be built:** an outdoor rover base controlled from an ESP32 or SBC, without RTK.
   - **Experiment:** see §7, experiment 3.

## 7. Experiments worth attempting

1. **Reproduce the T20 Omni LAN root, then read the LiDAR**
   - **Hardware:** an Ecovacs T20 Omni you own, plus a LAN box running AdGuard Home or Pi-hole, Mosquitto and Home Assistant.
   - **Budget:** used robot price not checked; software is free. **Difficulty:** medium.
   - **Tools and software:** Python 3 and OpenSSL; [the repo](https://github.com/Syax89/ecovacs-t20-local-control) and its wiki.
   - **Expected outcome:** a root shell, HA entities and a local map.
   - **Recovery and safety:** everything lives in `/data`, so deleting `usercustomize.py` reverts it. Keep the DNS redirect scoped to the robot only. Do not apply firmware updates until you know whether the path survives them.
2. **A local brain for a companion robot on a Pi 5**
   - **Hardware:** a Loona (or Moxie on 24.10.803) and a Pi 5 with 8 GB.
   - **Software:** loona-cloud or moxie-robot-saver, llama.cpp with Qwen2.5-3B, and Whisper.
   - **Difficulty:** medium. **Expected outcome:** offline conversation. TTS is the weak link for Loona.
   - **Recovery:** both redirect the robot only through supported config channels (command `405`, or the QR endpoint). Keep the original settings so you can point the robot back.
3. **Spin a wheel on a stock mower board under custom firmware**
   - **Hardware:** a dead or cheap SNK-board mower, an ST-Link or J-Link, and a bench supply with current limit.
   - **Software:** [mower-stock-reverse](https://github.com/salonnikov/mower-stock-reverse) toolchain and dumps.
   - **Difficulty:** high. **Expected outcome:** close the "wheels never spun" gap by finding the FU6832N enable or SPI sequence. Let an agent diff the stock firmware's init sequence against the custom one.
   - **Safety:** remove the blade. Keep the boards dry; that is what killed the original.
4. **Cozmo as a telepresence rover**
   - **Hardware:** a Cozmo and a Linux box with a second USB Wi-Fi adapter.
   - **Software:** PyCozmo and [cozmo-roverd](https://github.com/legop3/cozmo-roverd).
   - **Difficulty:** low. **Expected outcome:** drive and camera from a browser through MultiRoombaRover.
   - **Recovery:** nothing on the robot is modified.
5. **DJI RC-N1 as a PC gamepad or sim controller**
   - **Hardware:** an RC-N1 (spare from a Mini 2, Air 2S or Mavic 3 kit).
   - **Software:** [rcn1-joystick](https://github.com/skchdf/rcn1-joystick); tested on controller firmware 4.04.
   - **Difficulty:** low. **Expected outcome:** a uinput gamepad. The power button cannot be mapped.
   - **Recovery:** read-only over USB serial.

## 8. Long-term opportunity radar (6–24 months)

- **Robot mowers become the next Valetudo-style ecosystem.**
  - Three layers are forming: full stacks (MowgliNext, OpenMower), vendor-protocol controllers (DumbyLuba; HA integrations for Navimow such as [navimow_pro](https://github.com/ilguala/navimow_pro), 30★), and brand-neutral control centres ([MowDeck](https://github.com/lukislp/mowdeck)).
  - Expect root paths for camera and LiDAR mowers as these models reach the second-hand market.
- **Community clouds for companion robots will standardise on OpenAI-compatible endpoints plus local Whisper.** Moxie, Jibo and Loona already do this. Watch for one stack that serves several robots.
- **Vendor TLS hygiene decides rootability.** The T20 Omni path exists because of missing certificate validation. Vendors will likely fix this in firmware, so units on older firmware become the ones worth buying.
- **AI-agent-ready repos are becoming normal in robotics.** CLAUDE.md, AGENTS.md and handover docs appeared in three of today's mower and robot projects. The bottleneck stays physical: motor bring-up, wiring and safety commissioning.
