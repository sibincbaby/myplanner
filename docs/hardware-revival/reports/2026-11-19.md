## 1. Most interesting discoveries

### OOMWOO + VacuumTiger: turning a cheap rooted vacuum into a ROS 2 / Nav2 robot
- **What it does:** [OOMWOO](https://github.com/makerspet/oomwoo) is an open-source robot vacuum you build yourself (Raspberry Pi CM4/CM5, ROS 2, Home Assistant, 2D LiDAR). While its own hardware is still being designed, it uses two **real, rooted commercial vacuums as placeholder robots**: the Proscenic M6 Pro ([ROS 2 description](https://github.com/makerspet/proscenic-m6pro)) and the Roborock S5 Max (a driver on the [`feat/roborock-s5max` branch](https://github.com/kaiaai/VacuumTiger/tree/feat/roborock-s5max/sangamio)).
- **The chain:** you root the robot, then run [VacuumTiger/SangamIO](https://github.com/codetiger/VacuumTiger) on it. SangamIO is a Rust daemon of about 4K lines that talks to the CRL-200S GD32 motor MCU and the Delta-2D lidar over serial, then streams the sensor data over TCP/protobuf. [vacuum_ros2_bridge](https://github.com/remakeai/vacuum_ros2_bridge) turns that stream into ROS 2 topics, and the makerspet package adds the URDF, an EKF, and Cartographer and Nav2 configs.
- **Why it matters:** a used CRL-200S-class vacuum becomes a ready-made, mapped ROS 2 mobile base with lidar, odometry and an IMU. That is far cheaper than buying a TurtleBot.
- **Verified today:** oomwoo has 13,152★, was created 2026-06-10 and last pushed 2026-11-19. VacuumTiger has 42★, last pushed 2026-09-20, and its README marks the CRL-200S driver "✅ Verified". vacuum_ros2_bridge has 7★ and was last pushed 2026-10-13. proscenic-m6pro has 5★ and was last pushed 2026-07-21.
- **Limits:** OOMWOO's README says it is **"Not buildable yet — you can run it in simulation today."** The S5 Max driver is still on an unmerged branch.
- **Score:** 7/10 · **Confidence:** medium (working code and tutorials, but not independently reproduced here)

### hw-harness: an AI-agent method for writing Linux drivers from Windows-driver traces (2026-10-14)
- [cschalle/hw-harness](https://github.com/cschalle/hw-harness) has 257★ and was created 2026-10-14. You run the vendor's Windows driver in a KVM VM with the real device passed through, capture USB traffic with `usbmon` on the host, then compare that against your Linux driver's trace. The README says it was "built while writing a SANE backend for a Plustek film scanner and fixing an Intel IPU7 + IMX471 laptop camera".
- **Context:** Phoronix covered Christian Schaller's 2026-10-15 write-up on using Claude Code this way ([Phoronix](https://phoronix.com/news/AI-Reverse-Engineer-Linux-HW); the article itself was blocked, so this comes from a search summary).
- **Why it matters:** it turns "only has a Windows driver" peripherals into candidates for revival. That includes lidar, servo controllers and USB sensors pulled from robots.
- **Score:** 8/10 · **Confidence:** medium

### EEVblog 121GW firmware rewritten with Claude: press says "it works", the repo says it has never run on a meter
- [EEVblog/121GW-Firmware-Claude](https://github.com/EEVblog/121GW-Firmware-Claude) was created 2026-10-31 and has 5★. The README describes "121GW-OSS", an MIT-licensed, clean-room-structured firmware for the STM32L152ZD + HY3131. It reuses the stock SD-card bootloader (hold HOLD+MEM at power-on), and SWD is the recovery path.
- **Conflict:** [Circuit Digest](https://circuitdigest.com/news/eevblog-had-claude-code-rebuild-his-121gw-multimeter-firmware-in-c-overnight-and-it-works) reports, per a search summary, that the rebuilt firmware runs on the real meter. The repo README says **"v0.10 is an early, bench-untested release. It has never been run on a real meter"**, and the repo description says it does not work. It was verified only against the original firmware in an emulator, at pin level.
- **Takeaway:** an AI agent can produce a plausible, structured replacement firmware from a binary. Proving it on real hardware is still a manual step. Treat the press framing as unverified.
- **Score:** 4/10 · **Confidence:** low

### Unitree Go2 firmware vulnerabilities (2026)
- **CVE-2026-27509:** unauthenticated root RCE from the same network, because the DDS layer has no authentication (firmware 1.1.7–1.1.9 and 1.1.11 EDU) ([NVD](https://nvd.nist.gov/vuln/detail/CVE-2026-27509)).
- **CVE-2026-27510:** no integrity check on user programs ([NVD](https://nvd.nist.gov/vuln/detail/cve-2026-27510)).
- **CVE-2026-1442:** the key that protects firmware updates is itself encrypted with key material attackers can obtain ([INCIBE](https://www.incibe.es/en/incibe-cert/early-warning/vulnerabilities/cve-2026-1442)).
- **Research and scope:** [arXiv 2512.06387](https://arxiv.org/abs/2512.06387) (2025-12-06) lists ten cross-layer flaws, including hard-coded keys and a static SSH password. [IEEE Spectrum](https://spectrum.ieee.org/unitree-robot-exploit) reports that the B2, G1 and H1 are affected too.
- **Why it matters:** for owners this is a path to local control of their own robot. It is also a serious reason to keep these robots off shared networks. Sources disagree on patch status: one reports firmware 1.1.13 in Feb 2026 fixed CVE-2026-27510.
- **Score:** 5/10 · **Confidence:** medium. Only research your own device.

## 5. Hidden opportunities

1. **Vacuum lidar + odometry as a ₹-cheap ROS 2 mobile base.**
   - **Hardware:** CRL-200S-family vacuums (Proscenic M6 Pro and its relatives).
   - **Opportunity:** SangamIO already abstracts the GD32 MCU and lidar. Once the robot is rooted, it is a networked differential-drive base with lidar.
   - **Why overlooked:** people root vacuums to clean locally, not to build robots.
   - **What could be built:** a home patrol, delivery or inventory robot; a teaching platform.
   - **Validation experiment:** root one unit, run SangamIO, and get a Cartographer map in RViz.
2. **The aftermarket the Valetudo maintainer explicitly asked for.**
   - **Opportunity:** a weld-free 18650 holder pack for Dreame robots (the W10's odd-shaped pack is called out) and 3D-printed brushes.
   - **Why overlooked:** the market is niche and battery-safety heavy.
   - **Validation experiment:** measure the pack envelope and connector, then design the holder around a certified BMS.
   - **Safety:** lithium cells are a fire risk. Only use a proper BMS and protected cells; never use unprotected bare cells.
3. **"Windows-only" USB robot peripherals revived with hw-harness.**
   - **Hardware:** discontinued USB servo controllers, depth cameras and educational robot bricks that only have Windows drivers.
   - **Opportunity:** a trace-diff method plus an AI agent cuts driver work from weeks to days.
   - **Validation experiment:** pick one cheap Windows-only USB robotics peripheral, capture traces, and reproduce one command from Linux with libusb.
4. **Salvaged LDS lidars.** [kaiaai/LDS](https://github.com/kaiaai/LDS) (238★, pushed 2026-08-25) and the [ROBOTIS HLS-LFCD driver](https://github.com/ROBOTIS-GIT/hls_lfcd_lds_driver) (pushed 2026-11-12) already support vacuum-class lidars on Arduino and ROS 2. Dead vacuums often still have a working lidar.

## 7. Experiments worth attempting

1. **CRL-200S vacuum → ROS 2 base**
   - **Hardware:** a used Proscenic M6 Pro or other CRL-200S robot.
   - **Budget:** used-robot cost, not checked.
   - **Tools:** 3.3 V USB-UART, a Linux PC with ROS 2.
   - **Software:** the root tutorial, SangamIO, vacuum_ros2_bridge, the proscenic-m6pro package.
   - **Difficulty:** medium.
   - **Expected outcome:** a Nav2-driven map of one room.
   - **Recovery:** keep a stock-firmware backup before flashing. Run on the floor with the brushes off.
2. **Valetudo on a budget robot**
   - **Hardware:** a Eureka J15 Max ("easy root").
   - **Tools:** see the Valetudo install docs.
   - **Difficulty:** low–medium.
   - **Expected outcome:** cloud-free cleaning with an MQTT/Home Assistant dock entity.
   - **Recovery:** follow the official guide exactly, and keep the robot offline until rooted.
3. **hw-harness on a Windows-only USB peripheral**
   - **Hardware:** any cheap USB device from a robot kit that lacks Linux support.
   - **Tools:** Fedora with libvirt/KVM and a Windows 11 Pro VM.
   - **Difficulty:** medium.
   - **Expected outcome:** a captured trace and one reproduced command.
   - **Safety:** only on hardware you own.
4. **Salvaged vacuum lidar on an ESP32**
   - **Hardware:** an LDS from a dead vacuum, an ESP32.
   - **Software:** kaiaai/LDS.
   - **Difficulty:** low.
   - **Expected outcome:** a live scan in RViz over micro-ROS.
   - **Safety:** check the motor and laser supply voltages before powering the lidar.
