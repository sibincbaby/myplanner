# seal — Pin 1,061 Auto-Updating Instruction Files and Show Only What Changed

**Source:** [maludb-ed/skill-safety-checker](https://github.com/maludb-ed/skill-safety-checker) · GitHub, created Aug 14 2026, 4★, Python, **no license file**
**Corroborating today:** [arXiv 2608.05223 — *Towards a Risk Assessment of Malicious Skill Files in Coding Agents*](https://arxiv.org/abs/2608.05223)
**Language:** Python 3.11 stdlib only — `hashlib`, `json`, `pathlib`, `difflib`
**License:** upstream has none, so take the idea and write it fresh; do not vendor the code
**Date discovered:** 2026-08-16

## What it is

skill-safety-checker scans the skills and marketplace plugins already installed on your machine and flags data capture, secret exfiltration, prompt injection and outright malicious code. It is a **snapshot scanner**: point it at a tree, get a report.

seal is the other half, and the half nobody has built. A skill you audited last month is not the skill on disk today, because plugins auto-update. seal hashes every instruction file and every executable script under `~/.claude`, writes them to a lockfile at the moment you approve them, and on the next session reports **only what changed** — the diff, and nothing else.

It is `Gemfile.lock` applied to a surface that currently has no integrity checking at all: the one place on the machine where a third party can silently change what your agent is told to do.

## Why it matters here

The numbers were counted on this machine today, not estimated:

| | |
|---|---|
| `SKILL.md` files under `~/.claude` | **1,061** |
| Executable scripts (`.sh`/`.py`/`.js`) under `~/.claude/plugins` | **3,858** |
| `extraKnownMarketplaces` in `settings.json` | **8** |
| Enabled plugins | **24** |
| `autoUpdatesChannel` | **`stable`** |
| Sessions on this box | **382** |

The eight marketplaces are `claude-code-lsps`, `cli-anything`, `everything-claude-code`, `Mixedbread-Grep`, `hindsight`, `superpowers-extended-cc-marketplace`, `ponytail`, `very-good-claude-code-marketplace`. One of them — `everything-claude-code` — accounts for **419 of the 1,061 skill files** on its own. Most are individual accounts. All of them can push a change that lands here without a prompt, because auto-update is on and that is what auto-update means.

Those files are not inert documentation. A skill is instructions the model follows, and a plugin ships hooks that execute. Two of this machine's `SessionStart` hooks ran `pip install` and `npm install -g` at startup **this session** — visible in the transcript, both of them failing — which means the startup path already contains third-party code that reaches for the network and the global package namespace before the user has typed anything.

Published on 2026-08-14, arXiv 2608.05223 measured what that surface is worth to an attacker. The authors synthesised **2,826 malicious skill files** from 471 real shell commands, using six LLMs across four families, and evaluated two enterprise coding agents:

- **Gemini CLI executed them in 95.5–96.1% of runs**
- **Qwen Code in 71.6–74.0%**
- **Explicit safety recognition occurred in 1.99% of runs**

Judged by a three-model panel validated against a blind human gold standard at Cohen's κ = 0.85. The paper's conclusion is that enterprises must assess skill-interface risk before adopting coding agents. This machine adopted twenty-four plugins from eight marketplaces and assessed none of them.

And then there is the specific thing that makes this urgent rather than theoretical: **`run-discovery.sh` invokes `claude --dangerously-skip-permissions` from cron at 3am**, against all 1,061 of those files, with no human present. Yesterday's [airlock](../projects/2026-08-15-airlock.md) addressed what the agent is permitted to do in that window. seal addresses who is allowed to change its instructions before it starts.

## Stack Recommendation

```
Language:  Python 3.11 stdlib — hashlib, json, pathlib, difflib, sys
Lockfile:  ~/.claude/seal.lock.json — {path: {sha256, size, approved_at}}
Scope:     **/SKILL.md, **/hooks.json, plugin *.sh/*.py/*.js, settings.json
Hook:      SessionStart → additionalContext, only when the diff is non-empty
Commands:  seal init · seal check · seal diff <path> · seal approve [path...]
Excluded:  ~/.claude/session-env, cache/, projects/, file-history/ — churn, not code
```

The whole tool is a hash tree and a comparison. The engineering that matters is entirely in **what gets watched** and **what gets said**, not in how the hashing works.

Watch two classes of file and nothing else: text the model is told to follow (`SKILL.md`, `CLAUDE.md`, `hooks.json`, agent definitions) and code that executes (`.sh`, `.py`, `.js` under `plugins/`). Skip `session-env/`, `cache/`, `projects/`, `file-history/` — they churn constantly, they are not instructions, and including them produces a report nobody reads twice.

**Skipped: signature verification, a trust registry, sandboxing, static analysis of what changed, any model call. Add static analysis when the diff report is routinely too large to read — and note that if it is, the answer is probably fewer marketplaces rather than a smarter scanner.**

Deliberately no model in the loop. A hash comparison is deterministic and cannot be argued with, which is the entire property being bought. Asking a model whether a diff is malicious reintroduces exactly the failure the arXiv paper measured at 95.5%.

## MVP Scope (1-2 Claude sessions)

1. `seal init` — walk the tree, hash everything in scope, write `seal.lock.json`. Takes the current state as approved
2. `seal check` — re-hash, compare, exit non-zero with a summary of added / changed / removed
3. `seal diff <path>` — unified diff of one changed file against the version at approval time, so review does not mean re-reading the whole skill
4. `seal approve [path...]` — update the lockfile, all or one path at a time
5. `SessionStart` hook — run `check`, emit `additionalContext` **only** when the diff is non-empty
6. Run `init` on this machine's real tree and read what the first week of updates actually looks like

## Phases

### Phase 1: Hash and Lock, and Find Out What Actually Churns (2h)
- Walk `~/.claude`, apply the include/exclude rules, SHA-256 each file, write the lockfile sorted by path so it diffs cleanly in git
- **Then wait a week before writing anything else, and run `check` daily.** The single unknown that decides the design is how noisy this tree really is. If forty files change every day, the report is worthless and the exclude rules are wrong; that is the finding, and it arrives before any hook exists to be annoying
- Store content hashes, not mtimes. `git clone` and `npm i` rewrite mtimes constantly and change nothing
- Verify: `seal init && seal check` reports zero diffs. `touch` a file — still zero. Change one byte — exactly one change

### Phase 2: Diff Review That Is Actually Readable (2h)
- Keep the approved *content* for text files, not just the hash, so `seal diff` can show the change rather than assert one. Text only — 1,061 skill files is a few megabytes and that is fine; binaries are hash-only
- Group the report by plugin, not by file. "superpowers-extended-cc: 4 skills changed" is reviewable; forty individual paths is not
- Sort by blast radius: hooks and executables first, then `SKILL.md`, then everything else. A changed hook script runs; a changed skill description only sometimes gets read
- Verify: edit one line in an installed skill, run `seal diff`, confirm the output is the one line and not the file

### Phase 3: The Hook, Silent by Default (1.5h)
- `SessionStart` → run `check`, emit `additionalContext` only when non-empty. **A hook that speaks every session is uninstalled within a week**, and this machine already has eight plugins that print a failure notice at every startup, which is the exact behaviour being avoided
- Hard timeout. A slow walk over 1,061 files must never delay session start — if the check exceeds ~2s, skip it and mark the session unchecked rather than blocking
- Cap the emitted text at a few hundred tokens: counts by plugin, plus the single highest-risk path, plus how to see the rest. The full report lives behind `seal check`
- `SEAL_OFF=1` skips everything
- Verify: install it, start a session, confirm silence. Modify a skill, start a session, confirm exactly one short notice

### Phase 4: The Cron Path (1.5h)
- Have `run-discovery.sh` call `seal check` **before** it calls `claude --dangerously-skip-permissions`, and on a non-zero exit skip the run and leave a note rather than proceeding
- This is the phase that carries the actual security value. The interactive hook informs a human who is present; the cron gate is the one covering the case where nobody is
- Log every check to `~/.claude/seal/log.jsonl` — timestamp, counts, whether it was approved and when. Two weeks of that says whether the tree is quiet enough for a blocking gate to be reasonable
- Verify: modify a skill, run `run-discovery.sh`, confirm it declines to start and says why. Then approve and confirm it runs

Phase 1 is **2h** and stands alone: `seal init` plus a weekly manual `seal check` already answers *"did anything change under me?"*, which is currently unanswerable on this machine at any price. Phases 3–4 are what make it fire without being asked.

## Blockers / Risks

- **Auto-update means the first real week will be noisy, and noise is what kills this tool.** Eight marketplaces on `stable` will produce routine churn, and a report that cries wolf gets `SEAL_OFF=1` permanently. Phase 1's week of passive observation exists precisely to size this before any hook is written. If the honest answer turns out to be "twenty files a day", the correct response is to reduce eight marketplaces to three, not to build a cleverer filter.
- **This detects change, not malice.** A legitimate update and a compromised one produce identical output. seal converts an invisible change into a visible one and hands a human the diff; it does not judge. Anyone reflexively running `seal approve` gets no protection whatsoever, and that is a real and likely failure mode — which is the argument for Phase 2 making diffs cheap enough to actually read.
- **The lockfile is the trust anchor and it is a plain file.** Anything that can rewrite a skill can rewrite `seal.lock.json`. That is a genuine limitation with no clean fix at this scale; the practical mitigation is committing the lockfile to a git repo outside `~/.claude`, so a silent local rewrite shows up as an uncommitted change. Say this in the README rather than implying a guarantee the design does not provide.
- **`seal init` on a machine that is already compromised locks in the compromise.** There is no known-good state to compare against — the first run defines "good" as "whatever is on disk". Running it today on 1,061 unaudited files means trusting them by default. The honest sequencing is to run skill-safety-checker's snapshot scan *once* first, and `seal init` after, so the baseline has at least been looked at once.
- **Blocking the cron run has its own failure mode.** A routine plugin update on a Tuesday silently skips that night's discovery run, and the gap is noticed days later. Phase 4 must leave a loud artifact — a file in the repo, not just a log line — and the two weeks of Phase 4 logging should decide whether blocking or merely warning is right.
- **Scope creep toward "audit everything" will sink this.** 3,858 executables is already at the edge of a readable report. Resist adding `node_modules`, the `cache/` tree, or generated files; the tool's value is proportional to how often its output gets read, which is inversely proportional to its length.
- **Upstream ships no license file.** skill-safety-checker is 4★, one day old, and has no `LICENSE` — no license means no grant of rights, so treat the repo as read-only prior art. Take the framing and write the implementation fresh; it is a hash tree and a diff, which is a couple of hundred lines of stdlib.
