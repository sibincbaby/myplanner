# keyward — Local Credential Broker for Agent Sessions

**Source:** [osolmaz/unyolo](https://github.com/osolmaz/unyolo) · HN Aug 9 2026, 7 pts, 11★, Go, MIT
**Language:** Go or Node 22 — a long-lived local process holding secrets; either works, Go gives a single static binary
**License:** upstream MIT · plan is a personal build
**Date discovered:** 2026-08-10

## What it is

unYOLO keeps provider credentials inside separate broker processes. The agent never receives a token — it gets a scoped client credential whose authority comes entirely from a policy file. Each request is authenticated, classified, checked against JSON policy rules, optionally routed to an operator for approval, then executed and logged. It ships brokers for GitHub (`gh-broker`), Hugging Face (`hf-broker`) and Unix commands run as another user (`sudo-broker`), plus time-limited and use-limited grants.

**Why it matters here:** `CLAUDE.md` already contains a credential policy. It says to confirm personal (`sibincbaby`) versus work (`sibinc`) before creating a remote or pushing, to use `git@github-personal:` for personal repos, and to avoid plain `git@github.com:` because it authenticates as work. That is a precise, mechanical rule — and right now the only thing enforcing it is an agent remembering to ask. One forgotten confirmation pushes a personal project to a work account, which is not a bug you fix with a revert.

A broker turns that paragraph into a policy match. mcpaudit (08-09) inspects what the connected servers can reach; keyward decides whether the credential is handed over at all.

## Stack Recommendation

```
Broker:     Go single binary (or Node 22) — long-lived, holds tokens in memory only
Transport:  Unix socket at $XDG_RUNTIME_DIR/keyward.sock, mode 0600, SO_PEERCRED uid check
Git:        git's own credential-helper protocol — `credential.helper '!keyward git-credential'`
SSH:        GIT_SSH_COMMAND wrapper selecting the key by remote host alias
Policy:     ~/.config/keyward/policy.json, first-match-wins, default deny
Audit:      append-only JSONL, one line per decision
```

Git already defines a credential-helper protocol and honours `GIT_SSH_COMMAND`. Both are stable, documented, and mean no new protocol has to be invented or taught to anything — use them instead of a custom shim.

## MVP Scope (1-2 Claude sessions)

1. `keyward serve` — broker process, tokens loaded at start from the system keyring, never written anywhere the agent can read
2. `keyward git-credential` — a git credential helper that answers with a token only when policy allows
3. `policy.json` — rules over `(client, operation, target)`, first match wins, **default deny**
4. `ask` decisions — terminal approval prompt issuing a time- and use-limited grant
5. `keyward audit` — read back every allow, deny and approval

## Phases

### Phase 1: Broker + Token Store (2h)
- Long-lived process; load tokens from the system keyring or `pass` at startup and hold them in memory only
- Socket at `$XDG_RUNTIME_DIR/keyward.sock`, mode 0600, and verify the peer uid via `SO_PEERCRED` — file permissions alone are not an identity check
- Never place a token in argv, an environment variable a child inherits, or the audit log. Disable core dumps for the process
- Verify: a second user cannot connect; `ps`, `/proc/<pid>/environ` and the audit log contain no token material

### Phase 2: Git Credential Helper (2h)
- Implement git's `get`/`store`/`erase` protocol on stdin/stdout; wire with `git config --global credential.helper '!keyward git-credential'`
- Route on the remote: `github-personal:sibincbaby/*` gets the personal token, `github.com:sibinc/*` gets the work token, **cross-account combinations are denied outright**
- Verify: attempt a push of a personal repo to a `sibinc` remote and confirm it is refused, not merely warned about

### Phase 3: Policy Engine (2h)
- JSON rules matching client, operation and target; first match wins; explicit `deny` always beats a later `allow`
- Default deny with a clear message naming the rule that would need to exist. A broker that fails open is worse than none, because it manufactures confidence in a boundary that is not there
- Verify: the account-mixing case, an unmatched target, and a malformed policy file all deny — a policy that will not parse must fail closed, not fall back to permissive

### Phase 4: Approval + Grants (2h)
- `ask` prompts on the controlling terminal and issues a grant bounded by both time and use count
- Grants live in memory only, so restarting the broker revokes everything
- **Scope `ask` narrowly**: force-push, creating or deleting a repo, adding a remote, anything touching the other account. Prompting on routine pushes trains reflexive approval within a day and quietly converts the whole thing into a slower `yes`
- Verify: a grant expires on time, a second use past the limit re-prompts, a restart clears it

### Phase 5: `gh` Allowlist + Audit (2h)
- Wrap `gh` so only allowlisted subcommands run; deny `repo delete`, `secret set` and org-level writes by default
- Append-only JSONL audit: timestamp, client, operation, target, decision, matching rule. Decision and rule, never the credential
- `keyward audit --since` for review
- Verify: a denied `gh repo delete` appears in the log with the rule that blocked it

## Blockers / Risks

- **SSH is the hole in this plan and needs deciding before any code.** The personal/work split runs on SSH host aliases, and git does not use the credential helper for SSH remotes at all — the helper covers HTTPS only. Enforcing the SSH path means a `GIT_SSH_COMMAND` wrapper or a restricted ssh-agent, which is a second mechanism. Either commit to both or scope the MVP to HTTPS remotes explicitly and say so, because a broker that covers half the remotes while feeling complete is the worst possible outcome
- **The raw credentials must actually leave `~/.ssh`, the keychain and the shell environment.** An agent with shell access reads those directly and never touches the broker. Half-migrating leaves the protection imaginary while the audit log looks healthy
- **The broker becomes the highest-value process on the machine.** Everything it holds is available to anything that can reach the socket or the process memory. That concentration is the trade being made and it should be made deliberately
- Approval fatigue is the standard failure mode of tools in this shape. If it prompts more than a couple of times a week, the scope is wrong
- Any token committed to the audit log is a permanent leak, since the log is append-only by design. Redact at the point of the decision record, not at print time
- Upstream unyolo is MIT with a working `gh-broker` already. The original work here is the personal/work routing policy and the git integration — wrap unyolo rather than reimplement the broker core, and check whether its OpenClaw approvals UI can be reused before building a prompt
- 11★ and early. Read the credential-handling code before trusting it with real tokens; that review is part of the ten hours, not extra to it
