# loopx-minimal — Durable YAML State Kernel for Multi-Session Agent Work

**Source:** [huangruiteng/loopx](https://github.com/huangruiteng/loopx) · GitHub · Python, Apache 2.0, ~5k★, v0.4.8
**Date discovered:** 2026-08-21

## What it is

LoopX is an open, provider-neutral control plane that sits above agent harnesses (Claude Code, Codex, Cursor, etc.) and provides durable state: objectives, human-approval gates, executable todos with ownership, evidence logs, quota limits, and cross-agent handoffs — all living in `.loopx/` state files on disk, not inside a model's context window.

The project's headline claim: two real agent trajectories ran for 220+ and 272+ hours without state drift, recovering the correct goal, evidence, and next step across resets. It is at v0.4.8 with 5k GitHub stars and is implemented in Python 3.11+, licensed Apache 2.0.

## Why it fits

- Core interest: **agent UIs** — ships a dashboard interface for monitoring concurrent goals

## Stack Recommendation

```
Language:  Python 3.11+ with uv
State:     YAML files in .loopx/ (no database, no server)
Claude:    Claude Code skill (SKILL.md) that reads/writes state via Bash tool
CLI:       Typer for `loopx status`, `loopx set-goal`, `loopx done <id>`, `loopx add-evidence`
Config:    None — state root is always .loopx/ in the current git repo root
```

No external services. State is git-committable. If you commit `.loopx/` you get full history of goal evolution and evidence without any database.

## MVP Scope (1-2 Claude sessions)

One file, five functions:

1. `loopx init` — create `.loopx/goal.yaml` with `objective`, `phase`, `quota` fields
2. `loopx status` — print current goal, open todos, evidence count, quota remaining
3. `loopx todo add <task> [--owner claude|me]` — add an executable todo
4. `loopx todo done <id>` — mark done with a one-line evidence note
5. `loopx evidence add <note> [--file path]` — append to `.loopx/evidence.yaml`

The Claude Code skill (`SKILL.md`) wraps these five commands: on session start, Claude runs `loopx status` and reads the current state into context. On session end, Claude runs `loopx todo done` for anything it completed and `loopx evidence add` for anything it found. The state survives the session reset.

## Phases

### Phase 1: State Schema + CLI (1.5h)
- Define YAML schemas for `goal.yaml`, `todos.yaml`, `evidence.yaml`
- Implement `loopx init`, `loopx status`, `loopx todo add/done/list`, `loopx evidence add`
- `status` output: one-page summary suitable for pasting into a Claude context window
- Verify: create a goal, add 3 todos, complete 1 with evidence, read back — fields round-trip correctly

### Phase 2: Claude Code Skill (0.5h)
- Write `.claude/skills/loopx/SKILL.md` with:
  - Trigger: "long-running", "resume", "pick up where", "continue", "multi-session"
  - On-load: run `loopx status` and include output in context
  - On-complete: run `loopx todo done <id>` for completed items
  - On-stop: run `loopx evidence add` with a one-line summary of what was done
- Verify: start a Claude Code session, run the skill, complete a todo, stop session, restart — `loopx status` shows the completed todo and evidence

### Phase 3: Gate System (1h)
- Add `loopx gate add <condition>` — a human checkpoint before a sensitive operation (deploy, push, delete)
- Gates live in `goal.yaml` under `gates:` list with `id`, `condition`, `status: open|approved|denied`
- Claude Code skill: before any gate-matching action, run `loopx gate check <id>` — if `open`, pause and print a human-readable prompt
- Verify: add a gate for "push to main", run an agent that tries to push — agent pauses and waits for `loopx gate approve push`

### Phase 4: Quota Tracking (0.5h)
- Add `quota: {turns: 50, used: 0, reset: daily}` to `goal.yaml`
- `loopx tick` — increment used; block if over quota
- Claude Code skill: call `loopx tick` on every turn; `loopx status` shows `turns remaining: N`
- Verify: set quota to 5, run 5 `loopx tick` calls, verify 6th is blocked

### Phase 5: Git Integration (0.5h)
- `loopx commit` — run `git add .loopx/ && git commit -m "loopx: <goal-title> state snapshot"`
- Add `.gitignore` exclusion for nothing (state files are meant to be committed)
- Verify: state snapshots appear in `git log` with readable commit messages

## Blockers / Risks

- **LoopX itself may be the answer.** Before building, spend 30 minutes with `pip install loopx` and `loopx init` in a real Claude Code session. If it does what Phase 1-2 does without the overhead of a new tool, use it. The plan exists for the case where LoopX's full feature set (dashboard, quota governance, multi-agent handoff) is more than needed and a lighter YAML kernel fits better.
- **YAML state diverges under parallel sessions.** If two Claude Code sessions write to `.loopx/todos.yaml` simultaneously, the file can get corrupted. Phase 1 adds a file lock (`portalocker`) before every write. This is mandatory before running parallel agents.
- **Skill trigger is hard to calibrate.** If the skill fires on every session instead of only long-horizon ones, the status output adds noise to short sessions. The trigger word list (`resume`, `continue`, `pick up`) keeps it targeted. Add a `# loopx` magic comment at the top of a CLAUDE.md as a manual trigger for sessions where you want state.
- **Evidence accumulates fast.** A week of active sessions could produce hundreds of evidence entries. Keep `evidence.yaml` as an append-only log and add `loopx evidence tail -n 20` to show only recent entries in status. Never summarize evidence automatically — summaries lose the specifics that matter at the next resume.
