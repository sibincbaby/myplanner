**Language:** Markdown skills + YAML agents (consumed by Claude Code) · MIT
**Date discovered:** 2026-08-07

## What it is

A companion toolkit for Claude Code targeting Flutter developers. Three skills activate automatically when Claude Code is working inside a Flutter project:

- **flutter-senior-review** — reviews code through three lenses (State Modeling, Responsibility Boundaries, Abstraction Timing) backed by 12 principles; designed for PR review and architectural evaluation
- **flutter-code-quality** — checks widget organisation, folder structure, and identifies common anti-patterns against project standards
- **flutter-code-simplification** — reduces complexity by extracting widgets and flattening nested logic without behaviour changes

The repo also ships agents (structural analysis, refactoring workflow), commands (`/learn-flutter`, `/make-claude-md-flutter`), and reference documentation covering Riverpod patterns, REST API conventions, and folder structure.

**Why it matters:** 1 star, 15 commits. There is no Flutter-specific Claude Code toolkit anywhere in the ecosystem — the upstream fills that gap with one developer's patterns, leaving every other Flutter developer to invent their own from scratch.

## Stack Recommendation

```
Claude Code skills  — Markdown files under .claude/skills/ or a published plugin
Claude Code agents  — YAML agent definitions for structural analysis and refactoring
CLAUDE.md template  — project-level rules auto-generated by /make-claude-md-flutter
Reference docs      — docs/flutter/ folder with Riverpod patterns, folder conventions, REST
```

No runtime code required. The "build" is authoring and validating the skill documents. Publish to the Claude Code plugin marketplace under a `flutter-skills` package name for reuse across projects.

## MVP Scope (1 Claude session)

1. Author `flutter-senior-review.md` — three review lenses with 12 principles drawn from the Flutter team's style guide and Riverpod best practices
2. Author `flutter-code-quality.md` — anti-pattern checklist (BuildContext across async gaps, unnecessary stateful widgets, missing `const`, deep nesting)
3. Create a minimal `CLAUDE.md` template capturing folder structure (`lib/features/`, `lib/core/`, `lib/shared/`) and key conventions
4. Test by running Claude Code in an existing Flutter project with the skills active — verify that code review catches at least 3 real issues
5. Package as a single `.claude/skills/` folder installable with one command

## Phases

### Phase 1: Core Review Skill (2h)
- Author `flutter-senior-review.md`:
  - Lens 1 — State Modeling: prefer immutable state, use `freezed` or sealed classes, avoid raw `setState` in complex screens
  - Lens 2 — Responsibility Boundaries: one widget = one concern; fat build methods → extract widget classes
  - Lens 3 — Abstraction Timing: resist premature abstraction in UI; extract only when the pattern appears three times
- Include a score rubric: `[pass / warn / block]` per principle
- Verify: activate on a feature file with a known anti-pattern; confirm Claude flags it with the correct lens label

### Phase 2: Code Quality Skill (2h)
- Author `flutter-code-quality.md` — checklist items:
  - `BuildContext` used after `await` without `mounted` guard
  - `StatefulWidget` where a `ConsumerWidget` (Riverpod) or plain `StatelessWidget` suffices
  - Missing `const` constructors on pure UI widgets
  - Nested `Column > Column > Column` deeper than two levels
  - `Provider` reads inside `build()` rather than in the widget body
  - Raw `print()` calls left in production code
- Verify: run on a real feature; confirm each category generates a structured finding

### Phase 3: CLAUDE.md Template + Folder Conventions (1-2h)
- Author `CLAUDE.md.template` for Flutter projects:
  - Stack declarations: Flutter version, state management choice (Riverpod/Bloc/Provider), routing package
  - Folder layout: `lib/features/<name>/{presentation,domain,data}/`
  - Naming conventions: `*_screen.dart`, `*_widget.dart`, `*_provider.dart`
  - Test file locations and naming
- Implement `/make-claude-md-flutter` command: Claude reads `pubspec.yaml`, infers stack choices, fills template, writes `CLAUDE.md`
- Verify: run command in a fresh project; generated CLAUDE.md matches the real project structure

### Phase 4: Simplification Skill + Agents (2h)
- Author `flutter-code-simplification.md`:
  - Detect `build()` methods > 80 lines → suggest widget extraction points
  - Detect logic inside `build()` that belongs in a controller or provider
  - Detect repeated style declarations that belong in a `ThemeExtension`
- Add `refactor-screen` agent: given a file, runs quality → simplification → generates an actionable refactor plan
- Verify: agent produces a structured plan for a 150-line screen; plan is directly actionable with no ambiguity

### Phase 5: Publish + Reference Docs (1h)
- Structure as a Claude Code plugin: `package.json` with `"claude-code-plugin": true`, skill list, agent list
- Write `docs/riverpod-patterns.md` — 10 canonical Riverpod patterns with right/wrong code pairs
- Write `docs/rest-api-conventions.md` — repository pattern, dio setup, error handling
- Tag `v1.0.0` and publish to the Claude Code plugin marketplace
- Verify: install via `npx claude-skills add flutter-llm-toolkit` in a clean repo; all three skills activate

## Blockers / Risks

- Skills are only as good as the principles they encode — the first version will miss Flutter patterns unique to your codebase. Plan one week of real use, then a "retro session" to add missed patterns
- Claude Code skill discovery relies on the skills being in the right directory (`.claude/skills/`) or installed via the plugin manager — document both paths explicitly
- The Riverpod reference docs will need updating when Riverpod releases breaking changes; pin to the major version you're using and mark the doc header with the version
- "Abstraction Timing" is inherently subjective; the skill should suggest, never block — make sure the rubric says `[warn]` not `[block]` for that lens
- Plugin marketplace publishing requires a verified GitHub account with a public repo; if the repo is private, distribute via a `postinstall` script in `package.json` instead
