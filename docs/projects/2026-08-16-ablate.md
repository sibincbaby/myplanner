# ablate — Delete the Lines of Your CLAUDE.md That Do Not Change Behaviour

**Source:** [evoleinik/unchatty](https://github.com/evoleinik/unchatty) · GitHub, created Aug 14 2026, 11★, Shell, MIT
**Corroborating today:** [atomic14 — *The Output Style, It Does Nothing*](https://www.atomic14.com/2026/08/15/output-style-does-nothing) · [arXiv 2608.11095 — *Why Does Claude.md Keep Growing? Catastrophic Remembering in Agentic Coding*](https://arxiv.org/abs/2608.11095)
**Language:** Bash + Python 3.11 stdlib — the model under test is the only model involved
**License:** upstream MIT — `score.py` is directly reusable, the ablation loop is new
**Date discovered:** 2026-08-16

## What it is

unchatty ships a communication-rules block for `CLAUDE.md` and, far more interestingly, the harness that proves the block does something. Same repo, same questions, headless `claude -p` sessions, rules on versus rules off. `ab-test.sh` runs each question twice, restores the file, and prints the scores. `score.py` measures four mechanical things: word count, average sentence length, mid-sentence em-dashes per 100 words, markdown headers used. The reported result is one answer going from **393 words to 62**, longest sentence from 47 words to 26, and em-dashes per 100 words from 1.3 / 1.8 / 0.8 down to 0.0 / 0.0 / 0.0.

That is a harness for validating **one block someone wrote on purpose**. Turn it around and point it at a file that already exists, one line at a time, and it becomes something different: a measurement that tells you which lines to **delete**.

Take the `CLAUDE.md` you already have. For each line, run a fixed question set twice — file intact, and file with that one line removed. If the scores do not move, that line is not doing anything. It is costing tokens in every session and buying nothing.

**ablate is a deletion tool that has to earn each deletion with a number.**

## Why it matters here

Three independent signals landed on 2026-08-15, all pointing at the same hole:

- **unchatty** — 11★ in a day for shipping the *measurement*, not the rules. The rules are twenty lines anyone could write; the harness is the part nobody had.
- **atomic14, *The Output Style, It Does Nothing*** — a first-hand report that a configuration surface intended to change model behaviour did not measurably change it.
- **arXiv 2608.11095, *Catastrophic Remembering in Agentic Coding*** — the formal version: `CLAUDE.md` grows monotonically because every incident adds a line and no incident ever removes one. There is no pressure in the other direction, because removal requires evidence and nobody has any.

On this machine, `~/.claude/CLAUDE.md` is **67 lines, 3,092 bytes**, and there is no project-level `CLAUDE.md` in this repo at all — so that global file is the whole of the written policy, applied identically to a Flutter app, a Rust CLI and this VitePress site. It contains, among others: *"Direct, concise responses (1-3 sentences typical)"*, *"Minimize token usage while maintaining quality"*, *"Only use emojis when explicitly requested"*, and a four-line section on Nuxt 4 routing. Some of those almost certainly work. Some of them are competing with the ponytail `SessionStart` hook, which injects roughly **eighty more lines** of partly-contradictory guidance about brevity into the same context — and with `using-superpowers`, which injects a third block instructing maximal skill invocation before any response.

Three overlapping instruction sets on brevity and process, arriving in the same session, written at different times, never once compared against each other. The 1-3 sentence rule and ponytail's "at most three short lines" and superpowers' mandatory-announcement rule cannot all be in force. Nobody knows which one wins because nobody has measured.

## Stack Recommendation

```
Runner:   bash — for each line: strip it, run N questions, restore, score
Model:    claude -p --output-format json, one fixed model pinned for the whole run
Scorer:   Python 3.11 stdlib — unchatty's four metrics, plus tool-call count
Corpus:   questions.txt, ~10 prompts covering the behaviours the file claims
Output:   one table — line, metric deltas, verdict (MOVES / FLAT / NOISE)
State:    results.jsonl, so a re-run compares against the last one
```

The critical design decision is **leave-one-out, not add-one-in**. unchatty tests whether adding a block helps a bare file. That answers a question nobody has: the file already exists. What you need to know is whether *removing* line 14 changes anything, holding the other 66 constant — which is a different experiment and the only one whose answer is actionable.

**Skipped: a model judging the outputs, pairwise ranking, statistical significance testing, a web UI. Add the model judge when the four mechanical metrics demonstrably miss a line you know matters — not before, because a model judging whether a model followed an instruction is exactly the unverifiable loop this tool exists to escape.**

Pin the model explicitly with `--model`. An ablation run that straddles a model update is measuring the wrong variable, and this repo has watched a whole month of digests get written by three different model versions.

## MVP Scope (1-2 Claude sessions)

1. `questions.txt` — ten fixed prompts, written before any measurement, covering what the file actually claims to control
2. `score.py` — unchatty's four metrics plus tool-call count, reading `claude -p --output-format json` from stdin
3. `baseline` — run all ten questions against the file intact, `--repeat 3`, and record the spread. **This step decides whether the tool is worth finishing**
4. `ablate` — for each line: comment it out, run the ten questions, restore, diff against baseline
5. One table at the end, sorted by effect size, with everything inside baseline noise marked FLAT
6. Run it against this machine's real 67-line file and delete what comes back FLAT

## Phases

### Phase 1: Measure the Noise Floor Before Measuring Anything Else (2h)
- Run the ten questions three times against an **unmodified** file. Same file, same model, same questions
- Record the spread on each metric. That spread is the noise floor, and every later result gets compared against it
- **If the noise floor is as large as the effect unchatty reported, stop here and the project is over.** Two hours to find that out is the cheapest possible outcome and worth more than a finished tool built on an unmeasurable signal
- Temperature is not exposed through `claude -p`, so run-to-run variance is what it is — the only honest response is to measure it and subtract it, not to assume it away
- Verify: three baseline runs, print min/max/mean per metric. Word count varying by more than about 25% between identical runs means ten questions is too few

### Phase 2: The Scorer (1.5h)
- Port unchatty's four metrics: word count, mean sentence length, mid-sentence em-dashes per 100 words, header count
- Add one it does not have: **tool calls made**. Half the directives in this file are about process (*"Search/understand codebase first"*, *"Use TodoWrite for complex multi-step tasks"*), and those are invisible to a prose scorer but show up plainly in the JSON transcript
- Read `claude -p --output-format json` rather than raw text, so tool calls and token counts come for free
- Verify: score two answers you have already judged by eye and confirm the numbers agree with your judgement. A scorer that disagrees with you on an obvious case is measuring the wrong thing

### Phase 3: The Ablation Loop (2h)
- For each non-blank, non-heading line: comment it out with `#`, run the corpus, restore the file
- **Restore in a `trap`, not at the end of the loop body.** A Ctrl-C halfway through leaves the user's global `CLAUDE.md` mutilated, and that file is the one governing every other session on this machine. Copy it to `/tmp` first and restore from the copy
- Headings and blank lines are skipped but still cost a line number in the report, so the output maps back to the real file
- Ten questions × 67 lines × one run = 670 headless sessions. **Budget this out loud before starting** — at even a few cents each it is real money, and it is the reason Phase 4 exists
- Verify: ablate a line you are confident matters (*"Direct, concise responses (1-3 sentences typical)"*) and confirm word count rises. If it does not, the corpus is not exercising the rule and Phase 1's questions need rewriting before anything else is believable

### Phase 4: Make It Affordable (1.5h)
- Bisect instead of sweeping: ablate the file in halves first, and only descend into a half whose scores moved. On a file where most lines are inert — which is the hypothesis — this collapses 67 runs into roughly 15
- Cache by content hash of (file variant + question), so a re-run after deleting three lines does not re-measure the other 64
- `--lines 12-20` to re-check a region after an edit
- Verify: full sweep versus bisected sweep on the same file agree on which lines move, at a fraction of the cost. If they disagree, the bisection is hiding interaction effects and the flat sweep is the honest one

| Phase | Hours |
|-------|-------|
| Noise floor | 2h |
| Scorer | 1.5h |

Phase 1 is **2h** and is the only phase that has to happen. It answers the question the whole tool is for — *is this signal even measurable above run-to-run noise* — and a negative answer there is a genuinely valuable result that costs two hours instead of seven.

## Blockers / Risks

- **The noise floor may swallow the signal, and that is the project's central risk.** Two runs of the same prompt against the same file already differ. If that variance is the same size as the effect of deleting a line, no amount of loop engineering rescues it. Phase 1 exists to find this out first, and stopping there is a success, not a failure.
- **The scorer measures the shape of prose, not whether the work was right.** A line that makes answers longer but correct scores as harmful. Keep the metrics as a filter for FLAT lines — lines that change *nothing* — and read the actual outputs before deleting anything scored MOVES. Automated deletion of a line the scorer disliked is how a working instruction gets thrown away.
- **Lines interact.** Deleting line 14 alone may do nothing while deleting 14 and 31 together changes everything, and leave-one-out is blind to that by construction. Full subset testing is 2^67 runs and is not happening. Accept the limitation, say so in the output, and treat FLAT as *"no independent effect"* rather than *"safe to delete"*.
- **This edits the user's global `CLAUDE.md`, the file that governs every session on the machine.** Copy to `/tmp` before the first mutation, restore from `trap EXIT INT TERM`, and never write the working file back from memory. The failure mode is not a bad measurement, it is a truncated policy file discovered three days later.
- **670 headless sessions is real spend.** Print the estimated run count and stop for confirmation before the first one. Phase 4 is what makes the tool usable more than once, which is the difference between a tool and a one-off experiment.
- **Nothing here can measure the two largest instruction blocks in a session.** ponytail's ~80 lines and `using-superpowers` arrive through `SessionStart` hooks and plugin config, not through `CLAUDE.md`, so line-level ablation cannot reach them. The honest MVP scope is the 67-line file. Extending to hook-injected text means toggling `enabledPlugins` between runs — real, but a second project, and worth attempting only after the file-level version shows the signal exists.
- **Upstream is 11★ and two days old.** `score.py` is MIT and small enough to read end to end before trusting it; do that rather than importing it, because its four metrics were chosen to demonstrate one specific block and may not be the right four for an arbitrary file.
