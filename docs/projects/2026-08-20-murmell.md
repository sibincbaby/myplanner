# murmell — Shared Browser Canvas for Parallel Team + Agent Coding Sessions

**Source:** [Murmell on Product Hunt](https://www.producthunt.com/products/murmell) · Product Hunt (2026-08-19) · Built after a hackathon where "three people, four AI agents had to work together on one laptop"
**Date discovered:** 2026-08-20

## What it is

Murmell is a cloud canvas in the browser where team members and AI coding agents (Claude Code, Codex, OpenCode, Kimi) work on the same repository at the same time. Agents claim files before they write — a file-lock layer broadcast via WebSocket — so humans and agents can move at once without overwriting each other. Close your laptop: the agents keep going on Murmell's cloud machines, and your work lands back in git. The canvas shows a live preview of each agent's current file, the team's cursor positions, and the overall branch state.

The genuinely novel piece is the file-lock-before-write protocol for AI agents, implemented as a harness layer on top of existing agent CLIs rather than as a modification to those CLIs. It does not require patching Claude Code. It interposes at the level of the Claude Code plugin/hook system: before a file is written, the agent checks the lock server; if the lock is held, it waits or claims a different file.

## Stack Recommendation

```
Lock server:    Python 3.11+ FastAPI + WebSocket; in-memory lock table; no DB for the MVP
Client hook:    Claude Code PreWrite hook (shell script) → POST /lock/{path} → wait if locked
Canvas:         Svelte + WebSocket for the live view (phase 3+)
Cloud machines: Fly.io Machines API or Modal — each agent session maps to one VM (phase 4+)
Git:            git hooks post-commit → broadcast diff to canvas WebSocket clients (phase 3+)
```

## MVP Scope — Phase 1 only (the lock server)

One session, one machine:
1. FastAPI server with in-memory lock table: `POST /lock/{path}` (acquire or queue), `DELETE /lock/{path}` (release)
2. Claude Code `PreWrite` hook: call the lock server; if locked, emit a tool result asking the agent to work on a different file
3. Claude Code `PostWrite` hook: release the lock
4. Verify: two parallel Claude Code sessions on the same repo, both given tasks touching the same file, do not produce a merge conflict

## Phases

### Phase 1: File-Lock Server (2h)
- FastAPI WebSocket server: `GET /ws` for real-time lock state, `POST /lock`, `DELETE /lock`
- Claude Code hook shell scripts: `pre-write-hook.sh` and `post-write-hook.sh`
- Lock table: `{path: {holder_session_id, acquired_at}}` — no persistence, in-memory only
- Locks expire after 60s to prevent abandoned holds from blocking forever
- Verify: two sessions competing for `src/main.py` — only one writes at a time, the other gets "file locked, try a different file" in its tool result

### Phase 2: Lock Awareness Panel (1h)
- Terminal panel (rich TUI, same stack as `agenthud`) showing the live lock table
- Who holds what, for how long, which sessions are waiting
- Refresh via WebSocket subscription
- Verify: start two sessions; the panel shows two entries updating in real time

### Phase 3: Browser Canvas (weekend two)
- Svelte single-page app connecting to the lock server WebSocket
- Canvas: a simplified file tree with coloured overlays for lock state (green = free, red = locked, yellow = waiting)
- Agent session icons showing their current file
- Git diff panel: last commit message + files changed per session, polled from `git log --oneline -10`
- Verify: browser tab open alongside two sessions shows the same state as the TUI panel

### Phase 4: Cloud Machines (beyond weekend scope)
- Fly.io or Modal: each user session gets a VM with the repo cloned and the agent running
- Session persistence: close browser → agent keeps running; reopen → canvas reconnects
- Multi-user: multiple browsers see the same canvas
- This phase turns the lock server into actual Murmell. Do not attempt before Phase 3 is stable.

### Phase 5: Agent Orchestration (beyond weekend scope)
- Leader/worker patterns: one agent decomposes the task, assigns sub-tasks to workers, releases locks when done
- Priority queue for the lock server: the leader's lock requests jump the queue
- Murmell-specific: build only if Phase 4 is working and the lock server has handled >50 real sessions

## Blockers / Risks

- **Claude Code PreWrite hook timing.** The hook fires before the file write, but the tool call has already been made. If the hook blocks for too long (waiting for a lock), Claude Code's turn timeout may expire. Keep the hook non-blocking: if the lock is held, return immediately with a "file locked" message and let the agent decide to retry or choose a different file.
- **Lock server is a single point of failure.** If it crashes, all PreWrite hooks fail. The hook should default to `exit 0` (allow the write) on connection failure, not `exit 1` (block). A stuck server should degrade to no-lock rather than no-writes.
- **Cloud machines are real money.** A Fly.io Machine running llama.cpp or Claude Code for 8 hours costs real money. Phase 4 needs a budget ceiling baked in before the first provisioning call, not after the first bill.
- **File lock is a heuristic, not a guarantee.** Two agents can still conflict between the lock-acquire and the first write if the file was modified between calls. The lock reduces conflicts; it does not eliminate them. Document this. Git is still the ground truth.
