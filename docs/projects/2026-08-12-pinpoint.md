# pinpoint — Point-and-Comment Review Layer Your Agent Resolves over MCP

**Source:** [metedata/Remarc](https://github.com/metedata/Remarc) · HN Show HN Aug 11 2026, 13★, Swift, MIT
**Language:** Python 3.11+ — the MCP server is the whole product; the capture side is three shell tools
**License:** upstream MIT · plan is a personal build (upstream is macOS/Swift, this machine is Linux 5.15)
**Date discovered:** 2026-08-12

## What it is

Remarc lets you point at anything on your Mac — a paragraph of text, a region of the screen, a web element, or a spoken note — and leave a comment on it. Your coding agent reads those comments over MCP, acts on them, and marks them resolved. It is a review layer for work an agent produced, in the place where you noticed the problem, rather than a re-description of it typed back into a chat box.

**Why it matters here:** the current loop for "this button is misaligned" is to look at the screen, translate what you see into prose, and hope the prose survives the trip. That translation is where most of the cost is, and it happens dozens of times a session. Pointing removes it.

The distinction from the eight voice tools already in this backlog is the **lifecycle**. vocalmcp, voxctrl, voicecode, localmic, voxdiary-flutter, echocode, haraduo and speakoflow all capture; the captured thing then goes into the prompt and is gone. A pinpoint comment has state: it is open until the agent closes it. That turns a stream of remarks into a work queue the agent can be held to — including across a context compaction, which is exactly when a verbal instruction is lost today.

## Why it fits

- Core interest: **Claude/LLM tooling** — an MCP server, installed once, usable from every session
- Core interest: **agent UIs** — a human-side annotation surface, which is the part of an agent UI that is actually missing here
- Core interest: **dev productivity** — removes the see-it-then-describe-it step from every UI iteration
- `novel = 1`: the backlog captures context (ContextPop 07-26) and inspects the result (Sightline 07-25, UIVerify 08-01). Neither has an open/resolved comment with a lifetime
- `fills_gap = 1`: nothing here carries a correction across a compaction; the queue survives, the chat message does not
- `daily_utility = 1`: every session that produces a UI or a document

## Stack Recommendation

```
Server:    Python 3.11 + the official `mcp` SDK, stdio transport
Store:     SQLite at ~/.local/state/pinpoint/comments.db — one table, WAL mode
Capture:   `grim` + `slurp` (Wayland) or `maim` + `slop` (X11) for region select
Text:      `wl-paste` / `xclip -o` for the current selection
Images:    written to ~/.local/state/pinpoint/shots/<id>.png, referenced by path
Voice:     OPTIONAL and last — `faster-whisper` locally, same as speakoflow
CLI:       `pinpoint add` — one command, bound to a hotkey by the compositor
```

The compositor already owns global hotkeys; do not write a key grabber. Bind `pinpoint add` in the Sway/Hyprland/GNOME config and the hardest part of the desktop integration is a config line.

Store the screenshot as a **file path, not a base64 blob**. MCP tool results go into the context window; a full-resolution PNG inlined on every list call will cost more than the comments save. Return the path and let the agent read the image only when it decides it needs to.

## MVP Scope (1-2 Claude sessions)

1. `pinpoint add` — capture a screen region and/or the current text selection, prompt for a one-line note, insert a row with status `open`
2. MCP `list_open` — return open comments as `{id, note, target_type, target_ref, created_at}`, newest first
3. MCP `resolve(id, how)` — close a comment and record what the agent did about it
4. MCP `get_screenshot(id)` — return the image path so the agent can decide whether to read it
5. `pinpoint ls` / `pinpoint reopen <id>` — human-side inspection, because a queue you cannot audit is a queue you stop trusting

## Phases

### Phase 1: Store + CLI Capture (2h)
- SQLite schema: `id, created_at, note, target_type, target_ref, status, resolved_at, resolution`. WAL mode — the CLI and the MCP server write concurrently
- `pinpoint add --region` shells to `grim -g "$(slurp)"`; `--selection` reads the clipboard; both optional, so a bare note is valid
- Detect the session type once (`$WAYLAND_DISPLAY` vs `$DISPLAY`) and pick the tool pair; **fail with the missing package name**, not a stack trace, when neither is installed
- Verify: add three comments of different shapes, confirm three rows and that the PNG exists at the recorded path

### Phase 2: MCP Server (2h)
- stdio server with `list_open`, `resolve`, `get_screenshot`; register in `~/.claude.json`
- `list_open` returns **note text and paths only** — never image bytes. This is the decision that determines whether the tool is cheap or expensive to leave installed
- Cap the response at the 20 most recent open comments and say so in the result when more exist. A silent truncation reads as "the queue is empty" and that is the one failure that destroys trust in a queue
- Verify: from a live session, `list_open` returns what the CLI just added, and `resolve` moves it out of the list

### Phase 3: Resolution Discipline (1.5h)
- `resolve` **requires** a non-empty `how` string. An agent that can close comments without saying what it did will close them without doing anything
- Reopening is a first-class operation and preserves the original note; do not delete and re-add
- Add `pinpoint ls --resolved --since` so a week of resolutions can be read back
- Verify: attempt `resolve` with an empty `how` and confirm it is rejected; reopen a resolved comment and confirm the note survives

### Phase 4: Hotkey + Workflow Integration (1.5h)
- Bind `pinpoint add --region` to a compositor hotkey; confirm it works while a full-screen app has focus
- Add a line to `CLAUDE.md` telling the agent to call `list_open` at the start of a session and after any UI change
- Verify: leave two comments while the agent is mid-task, and confirm the next turn picks both up without being told

### Phase 5 (optional): Voice Notes (2h)
- `pinpoint add --voice` records until silence, transcribes with `faster-whisper` locally, uses the transcript as the note
- Ship this **only after** Phases 1-4 have been used for a week. Typing a one-line note takes four seconds; if that is not the bottleneck, voice is 2h spent on the wrong end of the problem

## Blockers / Risks

- **The screenshot payload is the whole cost model.** Inline a PNG in `list_open` and every session that has the server installed pays for it whether or not there are comments. Paths in the list, bytes only on explicit fetch — this is not an optimisation to defer, it is the design.
- **Whether the habit forms is the actual open question, and it cannot be answered by building more.** The tool is worthless if you keep typing corrections into chat out of reflex. Build Phases 1-2, use them for a week, and only then decide if Phases 3-5 are worth the hours.
- **Wayland region capture is compositor-dependent.** `grim`/`slurp` require `wlr-screencopy`, which GNOME's Mutter does not implement — on GNOME the path is the xdg-desktop-portal screenshot API instead. Check which compositor this machine runs *before* Phase 1, because it changes the capture implementation and nothing else in the plan.
- **An agent will resolve comments it did not act on** unless resolution requires a description. This is the same failure mode as a todo list that marks itself done, and the required `how` field is the cheapest defence.
- **`target_ref` for text selections is a snapshot, not a reference.** If the file changes underneath, the comment points at text that no longer exists. Storing the file path and line number alongside the text is a nice-to-have; storing the text alone is correct for the MVP, and the staleness should be visible rather than hidden.
- Upstream Remarc is macOS/Swift and MIT — read its MCP tool schema before designing yours, but none of the code ports. This is a reimplementation of an idea, not a fork.
- 13★ and two days old. The idea is the asset here; the implementation is not something to depend on.
