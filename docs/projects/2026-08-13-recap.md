# recap — A Work Log You Never Write, Compiled from Commits and Sessions

**Source:** [shiplog](https://shiplog.life) · HN Show HN Aug 12 2026 — single binary, `curl | sh` install, signed macOS/Linux builds
**Language:** Python 3.11 stdlib + the `git` CLI — no packages to install
**License:** upstream is a closed binary distribution · this is a personal reimplementation of the idea
**Date discovered:** 2026-08-13

## What it is

shiplog crawls the git repositories on your machine, summarises what you actually shipped in your own voice using the model of your choice, and stores the result somewhere you own. `shiplog scan --since=7d` walks six repos and comes back with two sentences per repo per week: "shipped a complete password reset flow, wired up a captcha on the auth forms, migrated several type definitions from numbers to strings to support UUIDs."

**Why it matters here:** this backlog has seven journalling projects in it, and the thing they share is that *you* are the input device. agentjournal, claude-journal-mcp, moodiary, memex, voxdiary-flutter and the voice-capture tools feeding them all require a moment where you stop working and describe the work. That moment is the reason journals lapse. The commits, on the other hand, already exist. Deriving the log from them costs nothing to maintain and cannot be forgotten.

On this machine the payoff is concrete. The `lw-bugfix-lifecycle` workflow puts a Redmine issue id on every branch and commit for the Linways work; the discovery repo commits daily. A week of that compiles into something paste-ready for a ticket comment, a standup, or a monthly review — none of which anyone enjoys writing from memory on a Friday afternoon.

## Stack Recommendation

```
Language:  Python 3.11, stdlib only — subprocess, json, pathlib, hashlib, datetime
Harvest:   git log --author=<you> --since=<date> --format=... --name-only
Summarise: `claude -p` via subprocess — Claude Code is already installed and authenticated
Store:     ~/.local/state/recap/YYYY-Www.md — one markdown file per ISO week, append-only
Cache:     ~/.local/state/recap/.cache/<sha256 of repo+commit-range>.txt
Config:    ~/.config/recap/repos.txt — one repo root per line. A text file, not YAML
Schedule:  a systemd user timer, or the same cron that runs the discovery workflow
```

`claude -p` instead of an API key is the decision that makes this a weekend rather than a project. There is no key to store, no billing to wire up, no SDK version to track, and the model choice follows whatever the CLI is already configured to use.

`repos.txt` instead of auto-discovery is deliberate. Walking `$HOME` for `.git` directories finds forty repos, thirty-eight of which are clones you read once. Six lines in a text file is not the friction worth automating away.

## MVP Scope (1-2 Claude sessions)

1. `recap scan --since 7d` — for each repo in `repos.txt`, collect your commits in the range
2. Group commits by `(repo, ISO week)`; skip any group whose cache key already exists
3. One `claude -p` call per group → 2-4 first-person sentences about what shipped
4. Append to `~/.local/state/recap/YYYY-Www.md` under a `## <repo>` heading
5. `recap show` — print the current week; `recap show --week 2026-W32` — print any past week

## Phases

### Phase 1: Harvest (1.5h)
- `git log --author="$(git config user.email)" --since=<date> --format=%H%x00%at%x00%s%x00%b --name-only` per repo, parsed with a NUL split rather than a regex
- Skip repos with no commits in range **silently**; skip repos that fail to open **loudly, with the path** — a typo in `repos.txt` should not read as a quiet week
- Handle the multi-identity case: this machine has a personal and a work git identity, so match on a *list* of emails read from config, not just `git config user.email` in the current directory
- Verify: run against this repo and confirm the daily discovery commits come back with their dates and subjects intact

### Phase 2: Summarise via `claude -p` (1.5h)
- Prompt carries **commit subjects, bodies and changed file paths — never diffs**. See the blockers; this is a confidentiality decision, not a token-saving one
- Ask for first person, past tense, no bullet points, no preamble, 2-4 sentences. A summary that opens with "Here's a summary of the work" is a summary nobody reads twice
- Cache on `sha256(repo_path + first_sha + last_sha)`. A re-scan of an unchanged week must make **zero** model calls — this is what makes a nightly cron free
- Verify: run the same scan twice; the second run makes no subprocess call to `claude` at all

### Phase 3: Store and Read Back (1h)
- One file per ISO week, `## <repo name>` headings inside, appended in repo order
- Re-running a week **replaces that repo's section**, it does not append a second copy. Idempotence is the whole reliability story for a tool on a timer
- `recap show` defaults to the current week and prints the file
- Verify: scan, edit a commit range, re-scan, and confirm the file has one section per repo rather than two

### Phase 4: Session Enrichment (2h)
- Read `~/.claude/projects/**/*.jsonl` for the same date range and pull the first user message of each session plus its `cwd`
- This catches the work that produced no commit — the debugging afternoon, the investigation that ended in "not our bug", the four hours on a Redmine ticket that turned out to be a data problem. On a bad week this is most of the week
- Fold it into the same per-repo prompt as a second section: "sessions that touched this repo"
- Verify: pick a day with a known no-commit session and confirm it appears in the week's file

### Phase 5 (optional): Ticket Grouping (1.5h)
- Extract Redmine issue ids from branch names and commit subjects with one regex; group by ticket instead of by repo when ids are present
- Output a per-ticket paragraph that can be pasted straight into a Redmine comment via the `lwr` CLI
- Ship this **only after** Phases 1-4 have produced a month of files. If the per-repo grouping already reads well enough to paste, this is 1.5h buying nothing

## Blockers / Risks

- **Work code must not leave the machine in diff form.** The Linways repositories are a client codebase. Send commit subjects, bodies and file *paths* to the model; never send `git diff`. Paths and subjects are already the metadata that any commit summary needs, so this costs nothing in quality — but it has to be a hard rule in the prompt-building code, not a habit, because the first time someone adds `--stat -p` "for better summaries" the rule is gone.
- **A cache miss on every run turns a free tool into a metered one.** The cache key must be commit-range-based, not date-based: a date-keyed cache re-summarises the current week on every nightly run for seven days. Get this wrong and the nightly timer quietly makes 40 model calls a week for one week of output.
- **The output is only worth reading if it sounds like you.** The generic-LLM-summary failure mode ("This week saw significant improvements to the authentication subsystem") makes the file skippable within two weeks. Put three real examples of your own writing in the prompt and check the tone before building Phase 4 on top of it.
- **`claude -p` inherits whatever the CLI is configured to do,** including project-level `CLAUDE.md`, hooks and skills if it is invoked from inside a repo. Run it from a neutral directory with the repo content passed as *text on stdin*, or a session-start hook will inject unrelated context into every summary.
- **Multi-identity git is the most likely silent failure.** Per the global configuration, personal repos use one email and work repos another. A single-email filter returns an empty log for half the repos and reads exactly like a quiet week. Test this explicitly in Phase 1.
- Upstream shiplog is a signed closed binary with an install script, not source. There is nothing to fork or read here — only the idea and the sample output, which is enough.
