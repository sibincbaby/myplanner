# hz — Pseudocode-as-Intent Coding Tool

**Source:** [danielvaughn/hz](https://github.com/danielvaughn/hz) · TypeScript · experimental · HN Show HN (Aug 2026)
**Date discovered:** 2026-08-25

## What it is

Hz (Huzzah) is a small experimental editor built around a different model of AI-assisted coding: instead of writing natural-language prompts that are discarded after generation, you write **pseudocode** in `.hz` files. On save, Hz generates or updates the real implementation. The pseudocode is persisted alongside the generated code, creating a durable record of intent.

The key insight: in large AI-assisted codebases, the original prompt is always thrown away, leaving behind code that is increasingly hard to understand and modify. Hz makes intent first-class. Edit the pseudocode → Hz diffs → only the impacted real-code blocks are regenerated.

Pseudocode is also language-agnostic: one `.hz` file can target Python, TypeScript, and Go simultaneously.

## Why it fits

- Core interest: **Claude/LLM tooling** — the prompt lifecycle is rethought at the tool layer
- Core interest: **Dev productivity** — solves the "loss of intent" problem in large AI-assisted codebases
- `novel = 1`: no prior plan or tool in the toolkit persists prompt-intent alongside generated code
- `daily_utility = 1`: every session that involves multiple iterations of AI-generated code benefits directly

**Note:** The plan below builds a lightweight personal version of the hz concept — a CLI watcher + Claude API backend — rather than the Huzzah editor itself. If the original repo ships a binary for your platform, try it directly first. The plan exists for the case where you want Claude-backed generation, a simpler format, and tight integration with an existing dev workflow.

## Stack Recommendation

```
Language:      TypeScript with tsx (or Python 3.11+ with uv)
File format:   .hz files — structured pseudocode blocks with target-file annotations
Watcher:       chokidar (Node) or watchfiles (Python)
LLM:           Claude claude-sonnet-5 via Messages API (streaming)
Diff/patch:    diff + patch (shell) or jsdiff (Node)
Storage:       .hz files live alongside src files; no DB needed
CLI:           hz watch [dir] | hz compile [file] | hz diff [file]
```

## MVP Scope (1-2 Claude sessions)

Three commands and a file format:

**File format — `.hz` pseudocode block:**
```
@target: src/auth/login.ts
@lang: typescript

// Pseudocode: validate email + password, call Supabase auth,
// return session token or throw AuthError with code
```

1. `hz compile <file.hz>` — read pseudocode, call Claude, write generated code to `@target`
2. `hz watch [dir]` — watch for `.hz` file saves; auto-compile on change; diff if target already exists
3. `hz diff <file.hz>` — show what would change in the target without writing it

## Phases

### Phase 1: Format + Compile (1.5h)
- Define `.hz` front-matter schema: `@target`, `@lang`, optional `@context` (files to include in context)
- Implement `hz compile`: parse front-matter → build Claude prompt (pseudocode + context) → stream response → write to `@target`
- Prompt: "You are implementing code from pseudocode intent. Write only the implementation — no explanation. Match the style of the context files if provided."
- Verify: write a 3-line pseudocode block, compile, inspect output

### Phase 2: Watcher + Diff (1h)
- `hz watch [dir]`: chokidar watches `**/*.hz`; on change calls compile internally
- Before writing, diff the current `@target` against new output; log changed line ranges
- If `@target` doesn't exist, create it; if it does, show a one-line diff summary then overwrite
- Verify: edit pseudocode, save, watch output update within 2s

### Phase 3: Partial Re-generation (1h)
- Add named pseudocode sections within a single `.hz` file: `## login`, `## logout`, etc.
- On save, Hz re-generates only sections whose pseudocode changed (compare against a `.hz.lock` shadow file)
- Reduces unnecessary churn in large files — only the changed intent block triggers an LLM call
- Verify: two-section file, change one section's pseudocode, confirm only one LLM call fires

### Phase 4: Context Inclusion (0.5h)
- `@context: src/types/auth.ts, src/lib/supabase.ts` — included as read-only context in the Claude prompt
- Ensures generated code uses the project's actual types and imports
- Verify: a pseudocode block that references a type from a context file — generated code imports it correctly

### Phase 5: `hz status` (0.5h)
- `hz status [dir]` — list all `.hz` files, their targets, and whether target is in sync (hash of last-compiled pseudocode matches `.hz.lock`)
- Outputs: `[in-sync] src/auth/login.hz → src/auth/login.ts` or `[stale]`
- Verify: compile a file, edit only its pseudocode (not the target), `hz status` shows it as stale

## Blockers / Risks

- **Huzzah itself may be the answer.** Before building, check `danielvaughn/hz` for a binary release. If there is one, run it for a session and see if the format and workflow fit before investing in a custom version.
- **Generated code drift.** If someone edits the `@target` directly (not via Hz), the `.hz.lock` hash diverges. `hz status` will flag it as stale on the next pseudocode edit. Document: "The generated file is owned by Hz — treat it as a build artifact."
- **LLM consistency across re-generations.** Re-generating a changed section may produce subtly different output for unchanged behavior. Use `temperature: 0` for compile calls to maximize reproducibility. Accept that some variance is inherent; the pseudocode block is the canonical source.
- **Large context files slow compile.** If `@context` includes large files, the prompt grows quickly. Add a 4KB cap per context file (truncate from the end) and note it in the lock file. Let the user override with `@context-full: filename` if they need the entire file.
- **No IDE integration in Phase 1.** The watcher runs in a terminal. IDE-level integration (save → trigger in-editor) is a future extension via an LSP or VS Code extension. Keep it out of the MVP.
