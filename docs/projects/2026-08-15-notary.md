# notary — Refuse to End the Turn on a Completion Claim You Have Not Checked

**Source:** [MohamedEmbarak/SLL](https://github.com/MohamedEmbarak/SLL) · GitHub, created Aug 13 2026, 1★, Python, MIT
**Mechanism from:** [rcolman6/clean-recap](https://github.com/rcolman6/clean-recap) — the `Stop` hook as the last undiluted position in context
**Language:** Python 3.11 stdlib only — no model call at all in the MVP
**License:** upstream MIT — take the three enforcement ideas, write the hook against Claude Code's payloads
**Date discovered:** 2026-08-15

## What it is

SLL is three Claude Code hooks that make an agent's claims checkable rather than merely stated: a claimed test result has to reproduce, a fabricated import never reaches disk, and every command's real output is recorded so the transcript cannot drift from what happened. No model is asked to be honest; the hooks make dishonesty not land.

clean-recap supplies the placement. Its README makes the point better than its product does: an instruction in `CLAUDE.md` works for ten turns and is then 150k tokens back, competing with everything else in context. The `Stop` hook fires the instant the model decides it is done, and returning `{"decision": "block"}` refuses that stop and feeds `reason` back as the next instruction — with nothing after it to dilute it. It is the only position in a session where an instruction is guaranteed to be the most recent thing the model has read.

Put together: **when the agent says it is done, check before letting it be done.**

## Why it matters here

The project memory for this repo is, in substance, a list of runs that reported success and had not worked:

- **2026-07-09** — `write-digest` made zero tool calls, returned injected boilerplate, never created `docs/daily/<date>.md`. The next step listed the directory, did not see the file, silently omitted it from the sidebar, and the commit went through saying "N viable".
- **2026-08-03** — `derive-date` returned the literal string `date +%F`; the commit message shipped as `chore: daily discovery date +%F — 0 viable project(s)`.
- **2026-08-11** — the digest existed on disk and was left out of `config.ts`, unreachable in the site for a full day.
- **2026-08-14** — `read-seen` returned `[]`, dedup silently disabled, four already-seen URLs re-surfaced as new and were re-appended to `seen.json`.

The standing remedy has been a five-point checklist that a human runs afterwards, written down in memory because it kept being needed. And `verification-before-completion` is installed here as a *skill* — an instruction delivered at session start, which is to say roughly 200k tokens before the moment it is supposed to fire. Every one of those four failures happened on a machine where that skill was loaded.

The checklist is already written. It is not being run. That is a hook, not a discipline problem.

## Stack Recommendation

```
Language:  Python 3.11, stdlib only — json, re, subprocess, pathlib, sys
Hook:      Stop → {"decision": "block", "reason": "<failures>"} to refuse the ending
Trigger:   deterministic scan of the final assistant message for completion claims
Checks:    <repo>/.claude/verify.sh — exit 0 passes, non-zero blocks with its stderr
Loop guard: stop_hook_active in the payload — hard exit 0 when true
State:     none. Everything needed is in the hook payload and the transcript file
```

No model call anywhere in the MVP. Detection is a regex over the last assistant message; verification is a script the repo already knows how to write; the failure text is the script's own output. The one place a model is involved is the one that already exists — the agent reading the blocked reason and fixing what it claimed. **Skipped: per-claim classification, a model judging whether the claim was warranted, cross-session reporting — add when the regex proves too blunt in practice, not before.**

`.claude/verify.sh` is deliberately per-repo and deliberately a shell script. This repo's version is five lines that already exist in prose: the digest exists and is non-empty, its date appears in `config.ts`, the `daily/` and `projects/` file sets match the sidebar link sets, `seen.json` grew and has entries dated today, and no URL in today's digest carries an earlier `date_seen`.

## MVP Scope (1-2 Claude sessions)

1. `notary check` — reads a `Stop` payload on stdin, prints either nothing (exit 0) or the block JSON. Standalone and testable without a live session
2. Claim detection: scan the final assistant message for completion language — done, fixed, committed, all tests pass, wrote N files, verified
3. On a claim, run `<cwd>/.claude/verify.sh` with a 60s timeout
4. Non-zero exit → `{"decision": "block", "reason": "<stderr, truncated>"}`
5. `stop_hook_active` true → exit 0 immediately, always
6. Write this repo's `verify.sh` from the five checks already in memory

## Phases

### Phase 1: `verify.sh` for This Repo First (1.5h)
- Write the checks before the hook. If the script is not worth having on its own, the hook has nothing to enforce
- Five checks, in order of what has actually broken: digest exists and is non-empty; `grep <date> docs/.vitepress/config.ts` matches; the `docs/daily/*.md` and `docs/projects/*.md` file sets equal the sidebar link sets — set difference, not counts, because `grep -c "daily/"` also counts the nav entry; `seen.json` grew and has entries dated today; no URL in today's digest table has an earlier `date_seen`
- Each failure prints one line naming the file and what was expected. That line becomes the agent's next instruction, so it has to be actionable on its own
- Verify: `git stash` today's sidebar edit and confirm check 3 fails and names the missing file

### Phase 2: The Claim Detector (1.5h)
- Read `transcript_path` from the payload, take the last assistant message, scan for claim phrases
- The bar for adding a phrase is that its absence caused a real miss. Start narrow — the four historical failures all claimed completion in the same handful of ways
- Two exclusions, both learned from how these failures actually read: negated claims (*"not done"*, *"could not verify"*) and questions (*"should I commit?"*) are not claims
- Verify: run the detector over the last thirty turns in `~/.claude/projects/**/*.jsonl` and count the hits by hand. More than roughly one in three is too blunt; zero on the 08-14 run's final message means the phrase list is wrong

### Phase 3: The Hook, With the Loop Guard First (2h)
- Register `Stop` in `~/.claude/settings.json`. Note this machine already has `Stop` hooks configured — this is an addition to an existing array, not a new key
- **Write the `stop_hook_active` guard before anything else.** Claude Code sets it when the turn is already continuing because of a stop hook. Without the guard, a check that stays red blocks forever and the session cannot be ended: block → respond → `Stop` fires → block. Hard exit 0 the moment it is true, no exceptions
- Missing `verify.sh` means this repo has opted out — exit 0 silently. A hook that nags in every unrelated repo is uninstalled by Tuesday
- 60s timeout on the script; a timeout is a pass, not a block, because a slow check must not be able to trap a session
- Verify: install it, deliberately break the sidebar, claim completion, confirm exactly one block and that the second attempt ends cleanly

### Phase 4: Truncation and the Escape Hatch (1h)
- Cap `reason` at ~2000 characters, keeping the first failure whole rather than a fair share of each — the agent fixes them one at a time anyway
- `NOTARY_OFF=1` in the environment skips everything. Needed for the case where the checks are wrong and the fix is to the checks
- Log each block to `~/.claude/notary/log.jsonl`: repo, which check failed, whether the retry passed. Two weeks of that answers whether this catches real failures or only annoys
- Verify: force three simultaneous failures and confirm the first is legible and unclipped

## Blockers / Risks

- **The infinite-loop failure mode is the one that makes this dangerous rather than merely annoying.** A check that cannot pass — a network-dependent assertion, a genuinely broken repo — blocks every attempt to end the turn. `stop_hook_active` is the guard and it is Phase 3's first line of code, not a later hardening step. Test it by making `verify.sh` `exit 1` unconditionally and confirming the session can still be ended.
- **A regex deciding what counts as a claim will be wrong in both directions.** False positives run checks nobody needed, which is cheap. False negatives let exactly the 07-09 failure through again, which is the whole point of the tool. Tune toward false positives and keep the phrase list short enough to read.
- **`verify.sh` is arbitrary code executed at the end of every turn.** It runs with the session's privileges. Keep it in the repo, keep it in review, and never fetch it or generate it — a checking tool that can be talked into running something is worse than no checking tool.
- **Blocking costs a full model turn.** Every false positive is real tokens and real latency at the moment someone wants to be finished. The Phase 4 log is what decides whether that trade is worth keeping, and it needs two weeks of data, not a first impression.
- **This enforces that the checks ran, not that they were the right checks.** A `verify.sh` that greps for a filename passes on an empty file. The 07-09 failure would have been caught by a non-emptiness check and missed by an existence check — the difference between the two is the entire value, and it lives in Phase 1, which is why Phase 1 comes first.
- **The `Stop` hook does not fire when the process is killed or the API errors out** — `StopFailure` is a separate event whose output is ignored. A cron run that dies mid-way is not covered by this and still needs the run script to check for the digest afterwards.
- **Upstream is 1★ and three days old.** Take the three enforcement ideas and the framing; write the hook against the payload spec directly, and confirm the accepted `decision` value against the installed version before trusting `"block"` over `"deny"`.
