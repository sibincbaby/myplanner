# hivemind — Parallel Claude/Codex/Gemini CLI Across Git Worktrees + SSH via MCP Kanban

**Source:** [dip497/hivemind](https://github.com/dip497/hivemind) (GitHub, Oct 2026 trending)  
**Tagline:** "Fan your codebase across four agents in isolated worktrees — coordinate via a shared MCP Kanban board."  
**Discovered:** 2026-10-25 (cloud backup)

---

## Why it fits

The parallel-agent lane in seen.json (OpenRig, Orca, AgentMux, etc.) mostly handles orchestration via a process manager or TUI. hivemind takes a different approach: each agent runs in its own **git worktree** (fully isolated branch/checkout) and all agents share a single **markdown Kanban board exposed via MCP**. The Kanban board is the coordination layer — agents pick up tasks, mark them in-progress, and close them, all through MCP tool calls. Remote execution goes over SSH, so the agents can run on a beefy cloud VM while you monitor locally.

The user interest profile calls out **Claude/LLM tooling**, **Agent UIs**, and **Dev productivity**. hivemind fills a specific gap: git-worktree isolation (agents can't clobber each other's files) combined with MCP-native coordination (no custom orchestrator needed — the Kanban is just a markdown file Claude reads/writes).

Closest seen.json entries are `shadok-ai` (TUI parallel runner, no worktrees) and `tenex` (parallel runner, no MCP Kanban). Neither uses git worktree isolation + MCP as the coordination layer.

## Shape

This is an **adopt upstream** project.

The workflow: define tasks in the Kanban markdown file → start hivemind → it creates one git worktree per task, opens the right agent (Claude, Codex, Gemini CLI, or opencode) in each, and exposes the Kanban via an MCP server each agent can query.

## Stack

- Bash / Python script runner (hivemind CLI)
- `git worktree` (built-in git, no extra deps)
- MCP server (exposes the Kanban markdown as MCP tools: `read_kanban`, `update_task`, `close_task`)
- SSH (for remote agent execution)
- Claude Code, Codex, Gemini CLI, opencode (whichever agents you have installed)

## MVP scope

1. Clone hivemind and run `hivemind init` in a real project.
2. Write 2–3 tasks in the Kanban markdown.
3. Start hivemind with `--agents claude,gemini` — verify two worktrees are created.
4. Confirm each agent sees the Kanban board via MCP and can mark tasks.
5. Let both agents work a real (small) task in parallel. Merge both worktrees.

## Phases

1. **Install + first run (0.5 h).** Clone, install deps, verify `hivemind init` creates the Kanban and the MCP server starts.
2. **Two-agent parallel task (1 h).** Write two small tasks (e.g., add a util function in two different modules). Start with `--agents claude,claude` (two Claude Code sessions). Watch the worktrees.
3. **MCP Kanban verification (0.5 h).** Inside one Claude session, call the Kanban MCP tools directly: list tasks, update one to in-progress, close it. Confirm the markdown file updates.
4. **SSH remote execution (1 h, optional).** Point hivemind at a cloud VM. Confirm agents start on the remote machine and the MCP Kanban is accessible locally.
5. **(Later) Merge workflow.** After both agents finish, run `git merge` or `git rebase` for each worktree back to main. Automate with a `hivemind merge` command if the upstream supports it.

## Effort

About 2 h for Phases 1–3. Phase 4 (SSH) is 1 h extra. The core value (isolated worktrees + MCP Kanban) is usable in the first session.

## Blockers / risks

- **MCP server conflicts:** If you already run other MCP servers on the same port, adjust hivemind's MCP port config.
- **Worktree disk usage:** Each worktree is a full checkout. On a large monorepo, 4 worktrees × repo size can fill disk quickly. Use sparse-checkout or limit worktrees to 2.
- **Agent API costs:** Four agents running in parallel × long tasks = significant token spend. Start with 2 agents and short tasks.
- **Creation-date caveat:** Date confirmed via awesome.ecosyste.ms only — local agent should verify the repo's creation date is within the 7-day window.
