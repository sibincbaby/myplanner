**Source:** [omnara-ai/omnara](https://github.com/omnara-ai/omnara) (Apache 2.0, self-host or cloud)  
**Tagline:** "Run agent workflows anywhere — self-hosted, open-source, any model."  
**Discovered:** 2026-10-25 (cloud backup)

---

## Why it fits

Claude Managed Agents is powerful but fully closed — you can't see the state machine, migrate off Anthropic's infra, or use other models. Omnara is the open-source alternative: an agent control plane that stores durable state in Postgres, advances agents via temporary workers on new messages or tool results, and lets execution machines connect as external tools. Apache 2.0 means it's self-hostable for free.

The user interest profile calls out **Claude/LLM tooling** (wrappers around Claude) and **Agent UIs** (custom agent interfaces). Omnara hits both: it's the missing operational layer for anyone who wants to build agents backed by Claude but doesn't want vendor lock-in on the orchestration layer.

Nothing in seen.json covers the self-hosted agent control plane lane at the level Omnara does — the closest entries are single-agent wrappers or UI skins, not a durable-state orchestration platform.

## Shape

This is an **adopt upstream** project, not a build-from-scratch.

Option A — **self-host via Docker Compose.** Omnara Cloud is free for small workloads; the self-hosted path requires Postgres and a worker runner. Set up locally or on a small VPS.

Option B — **use Omnara Cloud** (hosted) as the control plane while keeping your own execution machines (where your Claude Code agents actually run). Zero infrastructure to manage.

## Stack

- Postgres (durable state + FTS)
- Omnara worker (Node or Python, depending on release)
- Claude Code / any other coding agent as the execution machine
- Apache 2.0 — use in any project

## MVP scope

1. `docker compose up` the Omnara stack locally.
2. Register one Claude Code session as an execution machine.
3. Create a simple 2-step workflow: (a) Claude reads a file, (b) Claude writes a summary.
4. Trigger from a webhook or CLI call.
5. Watch state transition in the Omnara dashboard (sessions, messages, tool results).

## Phases

1. **Local setup (1 h).** Clone the repo, run `docker compose up`, verify the Postgres connection and the worker comes online.
2. **First agent (1 h).** Wire a Claude Code session as an execution machine. Send it a simple task via the Omnara API. Confirm the response is stored durably.
3. **Workflow (1 h).** Build a 2-step workflow with a tool-result handoff. Test failure recovery (kill the worker mid-task, confirm resume).
4. **(Later) Model swap.** Replace Claude with Gemini CLI on the same workflow to confirm model-agnosticism.
5. **(Later) Prod deploy.** Postgres on Supabase + workers on Fly.io or Render.

## Effort

About 3 h to get a working local setup with one real workflow. Phase 4–5 are 1–2 h each.

## Blockers / risks

- **Archived flag:** AlternativeTo lists the repo as archived — this may be stale data from an earlier product iteration. Verify the current repo status before investing setup time.
- **Worker docs:** The architecture (temporary workers + execution machines) may require reading the full architecture doc, not just the README quickstart.
- **Scope vs. need:** If the user's agent workflows are simple (single-step, no durable state), Omnara is overengineered. The right bar is: "do I want multi-step agents that survive process restarts?" If yes, this is the right tier.
