# mcpaudit — Local MCP Auth & Exposure Auditor

**Source:** [authgent/authgent](https://github.com/authgent/authgent) · HN Show HN Aug 7 2026, 4★, Apache-2.0, Python + TS SDK
**Language:** TypeScript (Node 22) — matches the local MCP config surface
**License:** upstream Apache-2.0 · plan is a personal build
**Date discovered:** 2026-08-09

## What it is

authgent scans an MCP server's OAuth 2.1 posture against ten RFC-mapped checks (RFC 9728 protected-resource metadata, RFC 8414 AS metadata, RFC 7636 PKCE including advertise-drift, RFC 8707 resource indicators, RFC 7591 DCR and DCR mirroring, implicit grant, RFC 9207 `iss`, RFC 9449 DPoP, unauthenticated tool endpoints) and grades it A–F. It ships a CLI, a GitHub Action CI gate, and a public registry of vendor scores — built after the author scanned 30 production MCP servers.

**Why it matters here:** authgent points *outward*, at servers you might publish. The version worth building points *inward*, at the servers already connected. This session alone reaches roughly fifteen MCP servers — Gmail, Google Drive, Google Calendar, Supabase, Vercel, Figma, Firebase — several holding live OAuth grants against real accounts, plus four more sitting unauthorized. Nothing in the toolkit answers "what do these actually have access to, and which of them is misconfigured?"

## Why it fits

- Core interest: **Claude/LLM tooling** — reads `~/.claude.json`, `.mcp.json` and the settings cascade directly

## Stack Recommendation

```
Runtime:    Node 22 + TypeScript, single bin (`mcpaudit`)
Config:     node:fs — ~/.claude.json, ~/.claude/settings.json, ./.mcp.json, ./.claude/settings*.json
Probing:    node:fetch against /.well-known/oauth-protected-resource and /.well-known/oauth-authorization-server
Protocol:   @modelcontextprotocol/sdk — connect and call tools/list for the inventory
Output:     plain text table by default, --json for scripting, --markdown for a report file
```

No database. An audit is a fresh read every time; caching an audit is how an audit goes stale and starts lying.

## MVP Scope (1 Claude session)

1. `mcpaudit list` — merge every MCP config in the settings cascade, print each server with its transport, scope (user/project/local) and which file declared it
2. `mcpaudit tools` — connect to each reachable server, call `tools/list`, print the tool count and names
3. `mcpaudit scan` — for each HTTP/SSE server, fetch the two well-known metadata documents and run the RFC checks that need no credentials
4. `mcpaudit scan --grade` — roll findings into an A–F per server and a summary table
5. `mcpaudit secrets` — flag servers whose config carries an inline token or API key in plaintext

## Phases

### Phase 1: Config Inventory (2h)
- Resolve the full settings cascade in precedence order: managed → user (`~/.claude.json`, `~/.claude/settings.json`) → project (`.mcp.json`, `.claude/settings.json`) → local (`.claude/settings.local.json`)
- Record for every server: name, transport (stdio/http/sse), command or URL, declaring file, and whether a later scope overrides it
- Classify each as local-process (stdio) or remote (http/sse) — the two get entirely different checks, and conflating them is the easy mistake
- Verify: `mcpaudit list` matches `claude mcp list` exactly, including the servers that fail to connect

### Phase 2: Tool Surface (2h)
- Connect over `@modelcontextprotocol/sdk`, call `tools/list`, record names and descriptions
- Flag write-capable tools by name heuristic (`create|update|delete|send|deploy|execute|apply|merge|pause|restore`) — a rough signal, and label it as one in the output rather than implying certainty
- Timeout every connection at 10s and report unreachable servers as `unreachable`, never as `clean`. A server that fails to answer must never be graded as passing
- Verify: tool counts match what `ToolSearch` reports for three known servers

### Phase 3: OAuth Posture (3h)
- For each remote server, `GET /.well-known/oauth-protected-resource` (RFC 9728) and `/.well-known/oauth-authorization-server` (RFC 8414)
- Run the credential-free checks: PKCE advertised (`code_challenge_methods_supported` contains `S256`), implicit grant *not* offered, `authorization_response_iss_parameter_supported` present (RFC 9207), `resource` indicators supported (RFC 8707), DCR endpoint present and whether it is open
- Probe one tool endpoint without a token and record whether it answers — an unauthenticated tool endpoint is the finding that matters most and the cheapest to test
- Tier every finding as spec-required (affects grade) or advisory, exactly as upstream does
- Verify: run against a server authgent has already graded and confirm the letter matches

### Phase 4: Local Secrets + Report (2h)
- Scan config values for inline credentials: `sk-`, `ghp_`, `xox[baprs]-`, `AIza`, bare JWTs, and any key matching `/token|secret|password|api_?key/i` with a non-`${ENV}` value
- Print only the match position and a masked prefix — never the secret itself, and never to a file that might get committed
- Check file permissions on every config that holds one; flag anything group- or world-readable
- `--markdown` writes a dated report; add `*.audit.md` to `.gitignore` in the same run so a report never becomes a leak
- Verify: plant a fake `sk-` value in a scratch config, confirm it is caught and that the output masks it

### Phase 5: Drift Check (1h)
- `mcpaudit snapshot` writes a hash of the current server + tool inventory to `~/.mcpaudit/baseline.json`
- `mcpaudit diff` reports servers added, tools appearing or disappearing, and grades that dropped since the baseline
- This is the rug-pull check: a server that quietly grows a `delete_everything` tool between sessions shows up here
- Verify: snapshot, add a server, confirm `diff` names it

## Blockers / Risks

- **This is a scanner pointed at your own accounts, and it must stay that way.** Probe only servers already in the local config, only unauthenticated endpoints, and never replay a stored OAuth token to enumerate scopes. Anything beyond reading public metadata on servers you have configured stops being an audit
- **Never print or log a discovered secret.** Mask on the way out of the matcher, not on the way into the report, or the first `--json` run leaks everything the text output was careful to hide
- Interactively-authorized claude.ai connectors may not expose standard well-known endpoints at all — expect `unknown` for several and make sure `unknown` renders distinctly from `pass`
- Write-capable detection is a name heuristic and will both over- and under-report. Say so in the output; a security tool that overstates its confidence is worse than none
- The MCP auth spec is still moving. Pin the RFC set checked, print it in the report header, and expect to revisit within months
- Upstream authgent is Apache-2.0 and already implements the ten checks. Wrap it rather than reimplement — the original work here is the local config cascade, the secret scan and the drift baseline, not the RFC logic
