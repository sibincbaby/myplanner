## What it is

Every session Claude Code has ever run on this machine left a `.jsonl` transcript in `~/.claude/projects/`, and every assistant message in it carries a `usage` block with `input_tokens`, `cache_creation_input_tokens`, `cache_read_input_tokens` and `output_tokens`. There are **1,198 such transcripts here, 1.8 GB of them**. Nobody has ever read one for this purpose.

Five separate tools for watching that number have already passed through this digest — aiusage, cc-usage-awareness, tokentab, tokenBar-companion, and today's claude-trofeo-hud, which streams session and weekly limits to a $38 LCD over USB. All five answer the same question: *how much am I spending, right now.*

None of them answers the question that decides anything: **what did the spending produce.**

yield joins the transcripts to the git history. A session ran in a working directory between two timestamps; commits landed in that directory in that window; those commits have a diff. That join gives one number per run — tokens per commit, tokens per file written, tokens per digest — and one number per week for the two unattended cron jobs that spend most of it.

**It is a receipt with the deliverable stapled to it.**

A single night's run on 2026-08-15 made **77 requests and read 8.1 million cached tokens**. The night before, 72 requests and 6.1 million. The output of each is one digest, two project plans, and a commit.

Two more facts sharpen it. First, the same box on the same day started sessions at **31,645** tokens under `claude-opus-4-7` and **45,378** under `claude-opus-5` — a 43% difference in what it costs to say hello, invisible unless something reads the transcripts. Second, `discovery.log` runs at 01:00 and `idea-discovery.log` at 01:33, both unattended, both on the same subscription budget as every interactive session on this machine. Yesterday's HN thread quoted a status line reading `5h:100% 7d:100%` and an organisation whose year of tokens was gone by April. When that happens here, it will happen at 01:33 and the log will say `Done`.

## Stack Recommendation

```
Reader:   python3 stdlib — stream ~/.claude/projects/**/*.jsonl line by line
Model:    one row per session: cwd, start, end, model, 4 token counters, request count
Join:     git log --since --until --numstat in that cwd → commits, files, insertions
Prices:   prices.json, hand-maintained, one entry per model id, dated
Output:   a table to stdout; --json for the cron footer
State:    none. Recompute from the transcripts every time
```

Stream the files, never load one. Transcripts here reach 1 MB and the directory is 1.8 GB, but every line is independent and only the ones containing `"usage"` matter — a substring test before `json.loads` is the difference between a two-second run and a two-minute one.

**Do not price it in dollars from a table you guessed.** Report tokens by default. Put the rates in `prices.json` with the date they were read and the URL they came from, print `$` only when that file exists, and print the token counts alongside it always. A cost report that is quietly wrong about the rate is worse than one that reports raw counts, because it gets believed.

**Skipped: a daemon, a TUI, a database, live tailing, per-tool attribution, a web dashboard. Add per-tool attribution when a run is expensive and the reason is not obvious from the request count — not before.**

## MVP Scope (1-2 Claude sessions)

1. `sessions()` — walk `~/.claude/projects/**/*.jsonl`, emit one dict per transcript: path, cwd (from the directory name), first and last timestamp, model set, summed token counters, request count
2. `commits(cwd, start, end)` — `git log --numstat` in that repo restricted to the window, returning shas, files touched, insertions and deletions
3. `join()` — one row per session with its commits attached, and a bucket for sessions that produced none
4. `report()` — a table sorted by cost: session, day, model, tokens in and out, commits, lines, and tokens-per-commit
5. Run it against `~/.claude/projects/*myplanner*` and read the four weeks of nightly runs already sitting there
6. `--json` and a one-line summary suitable for appending to `discovery.log`

## Phases

### Phase 1: The Reader, and Nothing Else (1.5h)
- Stream every `.jsonl`, skip any line without the substring `"usage"` before parsing, accumulate the four counters
- The `usage` block also carries an `iterations` array that repeats the same counters — sum the top-level fields only, or every number doubles. Verify against one session by hand before trusting the aggregate
- Derive `cwd` from the encoded project directory name (`-home-sibin-my-works-myplanner`), and keep the raw name too; the mapping is lossy for paths that contain a hyphen
- Verify: total output tokens for the `myplanner` directory should land near **2,707,923**, and the 60-transcript count should match `ls | wc -l`. A figure far above that means the `iterations` double-count is in

### Phase 2: The Git Join (2h)
- `git -C <cwd> log --numstat --since=<start> --until=<end>` — one subprocess per session, not per commit
- A session that ends at 01:12 and a commit at 01:13 belong together: pad the window by a few minutes at both ends and say so in the output
- Sessions whose `cwd` is no longer a git repository, or no longer exists, are a normal case and get a row with `commits = 0`, not an exception
- **A session with zero commits is a finding, not a gap in the data.** Those rows are the interesting ones — exploration, failed runs, and the 08-03 night when the commit message came out as the literal string `date +%F`
- Verify: pick the 2026-08-15 run by hand, confirm its commits are the ones `git log` shows for that night, and confirm nothing from the 01:33 idea-discovery run is attributed to the 01:00 discovery run

### Phase 3: The Report (1h)
- Default table: one row per session, sorted by total tokens descending, with tokens-per-commit and tokens-per-1k-lines
- A second block grouping by day, so the two nightly jobs can be compared with each other and with themselves over four weeks
- `--json` for machines, plain text for humans, no colour, no progress bar
- Verify: the top row on this box should be a discovery run in the 6-8 M cached-token range. If a two-minute interactive session outranks it, the accumulation is wrong

### Phase 4: Wire It Into the Night (1h)
- Append one line per run to `discovery.log`: date, tokens in and out, commits, files — so the log stops saying only `Done`
- The transcript is still being written when the run's own agent would read it, so this runs **after** `claude -p` exits, from the shell script, not from inside the session
- `--since 7d` for the weekly read, which is the cadence this tool is actually for
- Verify: tomorrow's log line exists, and its numbers match a fresh full run of the report over the same window

## Blockers / Risks

- **The transcript schema is undocumented and belongs to someone else.** `cache_creation_input_tokens`, the nested `iterations` array, and the `ephemeral_1h` / `ephemeral_5m` split are all observed, not specified, and a Claude Code update can rename any of them. Fail loudly on an unrecognised `usage` shape rather than silently summing zeros — a cost report that quietly reads `0` looks exactly like a cheap week.
- **Cache reads are not billed like cache writes, and treating them as equal makes every number wrong.** This repo's headline figure is 85.8 M cache-*read* tokens against 10.8 M written; those two are an order of magnitude apart in price. Keep the four counters separate all the way to the output and never sum them into one "tokens" column.
- **Attribution by time window is a heuristic.** Two sessions in the same repo at once, a commit made by hand while an agent is running, or an agent that writes files but commits nothing — all of these misattribute. Print the window with each row so a wrong join is visible rather than merely wrong, and treat the output as a ratio to watch over weeks, not an invoice.
- **Reading 1.8 GB of other sessions' transcripts is reading everything ever typed on this machine.** It stays local, it stays read-only, and it never gets committed to this repo. The report prints paths and counts, never message content — that rule is easier to keep from the first line than to retrofit.
- **Prices change and subscription plans do not price per token at all.** The plan-limit view (`5h:100% 7d:100%`) and the API-rate view are different currencies, and the honest output states which one it is showing. Token counts are the only figure that is true in both.
- **The obvious next step is the wrong one.** With the numbers in hand it is tempting to start trimming the 32,122-token startup context; `/context` already reports that breakdown natively and interactively. This tool's job stops at the ratio — what a run cost against what it produced — and [nightwatch](2026-08-17-nightwatch.md) is the sibling that checks the second half of that ratio was real.
