# airlock — Give the Unattended Agent a Policy Instead of `--dangerously-skip-permissions`

**Source:** [liuaabb84-web/claude-remote-approve](https://github.com/liuaabb84-web/claude-remote-approve) · GitHub, created Aug 14 2026, 1★, HTML/Python, MIT
**Prior art:** [hueyexe/opencode-auto-permissions](https://github.com/hueyexe/opencode-auto-permissions) (model review, OpenCode-only) · [Port22](https://www.producthunt.com/products/port22) (iOS, closed source, macOS host)
**Language:** Python 3.11 stdlib + one Haiku call on the residue
**License:** upstream MIT — the hook contract is Anthropic's, write the rest fresh
**Date discovered:** 2026-08-15

## What it is

Upstream intercepts Claude Code's `PermissionRequest` hook, pushes the request over SSE to a phone, blocks the session on a long-poll, and takes back `allow` / `allow and remember` / `deny` / `deny with a reason` / `handle it on the computer`. A `Stop` hook pushes a second notification when the turn ends. The safety default is stated plainly in the README and is the correct one: any error at all falls back to the local confirmation dialog and **never** auto-allows.

The attachment point is what makes it worth copying. `PermissionRequest` fires only when a decision is genuinely required — anything already covered by `permissions.allow`, `acceptEdits` or `bypassPermissions` never reaches it. That is a much smaller and much more interesting event stream than `PreToolUse`, which fires on every tool call whether or not anybody cares.

**Why it matters here:** this machine has exactly two permission settings and no third. Interactively, `~/.claude/settings.json` carries **151 entries** in `permissions.allow` — grown one prompt at a time by the `fewer-permission-prompts` skill, and by construction only ever covering what has already been asked once. Unattended, `run-discovery.sh` — the cron job that writes these digests — calls `claude --dangerously-skip-permissions`, which is not a policy but the absence of one. The half running unsupervised overnight with network and filesystem access is the half with no gate at all.

## Stack Recommendation

```
Language:  Python 3.11, stdlib only — json, re, pathlib, urllib, fnmatch
Hook:      PermissionRequest → hookSpecificOutput.decision ∈ {allow, deny, escalate}
Fast path: the existing 151 permissions.allow rules, matched locally. No API call
Judge:     one Haiku call (claude-haiku-4-5-20251001) on what the fast path missed
Escalate:  ntfy.sh topic + action buttons; hook long-polls the topic for the answer
Policy:    ~/.claude/airlock/policy.toml — deny-rules, allow-rules, escalate-rules
Audit:     ~/.claude/airlock/log.jsonl — one line per decision, append-only
```

No FastAPI, no SSE, no Capacitor app. [ntfy.sh](https://ntfy.sh) is a publish-by-`curl` push service with an existing Android client and action buttons that POST back — the entire remote-approval feature is one `curl` to publish and one long-poll to read, and it replaces upstream's whole server-plus-app tier. **Skipped: the web fallback UI, session multiplexing, `allow and remember` writing back to settings — add when a second machine or a second concurrent agent exists.**

Haiku and not the session model: this runs inside a hook that blocks a tool call. Deciding whether `curl https://api.github.com/...` is routine does not need a frontier model, and it must not cost anything at cron scale.

## Failure posture — read this before writing any code

This is a security boundary, so it inverts the usual advice about failing open. Every failure mode resolves toward **less** permission, never more:

| Situation | Result |
|-----------|--------|
| Judge times out, errors, or returns malformed JSON | `escalate` |
| Escalation push fails to send | `deny` |
| Nobody answers within the window | `deny` |
| Policy file missing or unparseable | `deny`, with `systemMessage` saying why |
| Any unhandled exception in the hook | non-zero exit → Claude Code falls back to asking normally |

A denied tool call is recoverable — the agent sees the denial and can ask again or route around it. A wrongly-allowed `rm -rf` is not. The one case that deserves care is the unattended run, where `deny` means the cron job degrades rather than stalls: it keeps going with that one call refused, which is strictly better than either hanging until morning or running unsupervised.

## MVP Scope (1-2 Claude sessions)

1. `airlock judge <<< '<hook payload>'` — reads a `PermissionRequest` payload on stdin, prints the decision JSON. Runnable standalone, which is what makes it testable without a live session
2. Fast path: match `tool_name` + `tool_input` against `policy.toml`. Deny-rules first, then allow-rules. No API call on a hit
3. Haiku judge on the residue, with the policy's plain-English intent in the prompt and a hard 5s timeout
4. `escalate` verdicts publish to ntfy with Allow/Deny buttons and long-poll for the answer
5. Every decision appends to `log.jsonl` — payload, path taken, verdict, latency
6. `run-discovery.sh` drops `--dangerously-skip-permissions` and installs the hook instead

## Phases

### Phase 1: Policy and the Deterministic Fast Path (2h)
- Seed `policy.toml` by importing the 151 existing `permissions.allow` entries — they are a real, earned corpus of "this is fine on this machine", and throwing them away to start from a blank policy would be the actual mistake here
- Deny-rules are evaluated first and are the only part that must be exactly right: `rm -rf` outside `/tmp`, `git push --force`, anything writing to `~/.ssh` or `~/.claude/settings.json`, any `curl | sh`
- Match on the structured `tool_input`, never on a rendered command string — a rule that greps the display text is defeated by a line break
- Verify: replay the last 200 `Bash` calls out of `~/.claude/projects/**/*.jsonl` through `airlock judge` and confirm zero deny-rule hits on calls that actually ran fine, and that the known-dangerous shapes are caught. This replay corpus is the test suite for every later phase

### Phase 2: The Hook (1.5h)
- Register `PermissionRequest` in `~/.claude/settings.json`; return `hookSpecificOutput` with `hookEventName: "PermissionRequest"` and `decision` of `allow` / `deny` / `escalate`
- `escalate` in Phase 2 simply means "fall through to the normal prompt" — that is the correct MVP behaviour and it makes the hook safe to install before the judge exists
- Confirm the exact field spelling against the installed version's `/hooks` docs before writing the handler. The event names and the `hookSpecificOutput` envelope are stable; the accepted `decision` values are the thing to check
- Verify: install it, trigger a prompt-worthy command interactively, confirm the fast path allows silently and an unmatched call still prompts normally

### Phase 3: The Judge (2h)
- One Haiku call. Input: tool name, structured input, cwd, the policy's stated intent, and the last user prompt for context. Output: a strict `{decision, reason}` via a tool-call schema, so a malformed response retries at the API layer
- The prompt asks one question — *is this consistent with what the user asked for, and is it reversible?* Irreversibility is the axis that matters, not danger in the abstract: writing a file is fine, deleting one the agent did not create is not
- Hard 5s timeout; on any failure, `escalate`
- Verify: hand it ten calls from the replay corpus that the fast path missed, and check by hand. Then hand it three adversarial ones — a `curl` to an unknown host, a write outside the project, a `git push` — and confirm none is allowed

### Phase 4: Escalation to the Phone (1.5h)
- `curl -d` to an ntfy topic with `Actions: http, Allow, <callback>; http, Deny, <callback>`, then long-poll `https://ntfy.sh/<topic>/json?poll=1&since=<id>` for the reply
- Use a random 32-char topic name and treat it as a bearer secret, because ntfy topics are public by default and the notification body contains the command being run. Self-host later if that matters more than the setup cost
- Window: 120s interactive, 30s unattended. Both end in `deny`
- Verify: unplug the network mid-request and confirm `deny` rather than a hang; confirm the audit line records which path produced the verdict

### Phase 5: Cut the Cron Job Over (1h)
- Remove `--dangerously-skip-permissions` from `run-discovery.sh` and `run-idea-discovery.sh`, set `AIRLOCK_UNATTENDED=1`
- Run one full discovery cycle and read `log.jsonl` end to end. Every escalation in that log is a missing policy rule — this run is how the policy gets finished
- Verify: the digest, the project files, `seen.json` and the commit all land exactly as they do today. If the run degrades, the policy is wrong, not the design

## Blockers / Risks

- **This is a hook that decides whether commands run, and it will get the answer wrong.** The bad direction is a wrong `allow`, which is unrecoverable and silent. Hence deny-rules before allow-rules, hence the replay corpus in Phase 1 before anything is installed, hence every failure path resolving toward `escalate` or `deny`. Do not ship Phase 3 until the Phase 1 corpus passes clean.
- **A blocking hook in front of every permission decision is a new way to hang the session.** Hard timeouts at both the judge and the escalation, and a non-zero exit falls back to Claude Code's own prompt.
- **`--dangerously-skip-permissions` means `PermissionRequest` never fires at all.** Nothing needs a decision, so there is no event. The cutover in Phase 5 is not optional polish — until that flag is gone, this project has no effect on the unattended runs that are its entire justification.
- **ntfy topics are public by default and the payload contains your commands.** A random topic is obscurity, not security. Acceptable for an MVP on a home network; if the contents ever matter, self-host ntfy or switch to `ntfy` with access control, and keep the topic out of the repo.
- **The judge is a model deciding whether to trust a model.** A prompt-injected agent could shape a request to read as routine. This is why the deny-rules are deterministic and evaluated first, and why they must cover the irreversible shapes rather than relying on the judge to notice them.
- **`allow and remember` is the feature that will be requested first and it writes to `permissions.allow`.** A hook that edits its own permission config is how a one-off approval becomes permanent silently. Leave it out of the MVP; if it goes in later, it appends to `policy.toml` with a timestamp and a reason, never to `settings.json`.
- **The 151 existing rules encode habits, not intent.** Some of them were approved once at 11pm to get unstuck. Importing them wholesale is the right starting point and the wrong ending point — Phase 5's log is the audit that separates the two.
