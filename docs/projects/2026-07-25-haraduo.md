# HaraDuo

> TypeScript CLI that decomposes tasks into a plan DAG and routes each node to the right AI role — architect, coder, reviewer, writer — with explicit approvals and persistent MEMORY.md per project

**Inspired by:** [hara-cli/hara](https://github.com/hara-cli/hara) (GitHub trending July 25 2026, 3★, brand new)  
**Date discovered:** 2026-07-25

---

## What gap it fills

Claude Code is excellent at single-threaded autonomous execution but has no concept of *roles* — the architect role and the coder role should have different system prompts, different tool access, and different approval gates. Hara proves this model: route a task to the "Architect" role first (produces a plan DAG), then fan out each leaf to the "Coder" role, then route the diff to the "Reviewer" role. HaraDuo is a leaner, personal version of this idea: a TypeScript CLI that the user configures with named roles, runs a planning pass through Claude Sonnet, and then executes each plan atom with human approval between roles. It fills the gap between "run everything autonomously" and "babysit every single tool call" — approvals happen at role boundaries, not per-tool.

## Stack recommendation

| Layer | Choice | Why |
|-------|--------|-----|
| Runtime | Node.js 22 + TypeScript | Same as hara; fast startup, good Anthropic SDK |
| Anthropic | `@anthropic-ai/sdk` | Streaming, tool use, system prompts per role |
| CLI UI | `ink` (React for terminal) | Rich interactive TUI for plan DAG display + approvals |
| Plan format | JSON DAG saved to `.haraduo/plan.json` | Persistent; resumable if user kills process |
| Memory | `MEMORY.md` in project root | Role-specific memory files: `MEMORY-architect.md`, `MEMORY-coder.md` |
| Config | `~/.haraduo/roles.yaml` | User-defined roles with system prompt + allowed tools |

## MVP scope (1 Claude session)

A CLI (`haraduo "add unit tests for auth module"`) that:

1. Sends the task to the **Architect** role → returns a JSON plan: list of atoms `{id, description, role, deps[]}`
2. Displays the plan as a tree in the terminal (ink TUI) with an "Approve plan → execute?" prompt
3. On approval, executes leaf atoms in order, each via the named role's system prompt + tools
4. After each atom, shows the diff/output and prompts "Accept / retry / skip"
5. Writes a `.haraduo/log.jsonl` entry per execution for later review

Two built-in roles: Architect (planning only, no file writes) + Coder (file edits + bash). User can add more in `roles.yaml`.

## Phases

### Phase 1 — Role config + Architect call (1 h)
- Parse `~/.haraduo/roles.yaml`: `name`, `model`, `system_prompt`, `tools[]`
- Default roles file ships with Architect and Coder pre-configured
- Architect call: send task text + project file tree summary; return structured JSON plan via tool_use
- Validate plan JSON schema with `zod`

### Phase 2 — Plan DAG display + approval (45 min)
- Ink component: renders the plan as a tree (indented lines with role badges and dependency arrows)
- Bottom prompt: `[A]pprove all  [E]dit  [Q]uit`
- Edit mode: inline text area to modify any atom description before execution

### Phase 3 — Atom execution loop (1.5 h)
- For each atom (topological order of DAG), instantiate the named role
- Role system prompt = `roles.yaml` system_prompt + content of `MEMORY-<role>.md` (if exists)
- Allowed tools per role: `read_file`, `write_file`, `bash` for Coder; nothing for Architect
- Stream response to terminal; on completion show diff of changed files
- Prompt: `[A]ccept  [R]etry  [S]kip  [Q]uit`

### Phase 4 — Memory + log (30 min)
- After accepting a Coder atom: append a one-sentence summary to `MEMORY-coder.md` ("Added tests for `login()` in `auth.test.ts` — 2026-07-25")
- `.haraduo/log.jsonl`: one line per atom with role, model, input_tokens, output_tokens, outcome, timestamp
- `haraduo history` command: pretty-print recent log entries

### Phase 5 — Resume + multi-model (45 min)
- If a `.haraduo/plan.json` exists for the current directory: `haraduo resume` re-enters the pending atoms
- `roles.yaml` supports `model` per role — so Architect can use Sonnet and Coder uses Haiku
- `haraduo roles list` shows configured roles; `haraduo roles add` opens `$EDITOR` on roles.yaml

## Effort estimate

~4 hours for Phases 1–3 (working plan + execute loop) · 1 Claude session  
~6 hours complete with memory + resume + multi-model

## Blockers / risks

- **Tool access for Coder role**: Giving a sub-role arbitrary bash is a security risk. Mitigation: allowlist tools in `roles.yaml`; default Coder has no `bash`, only file reads/writes.
- **Plan quality from Architect**: Small tasks produce trivial 1-atom plans; complex tasks produce plans Claude can't fully execute. Mitigation: add a `max_atoms` config; if plan exceeds it, ask Architect to simplify before approval.
- **ink TUI compatibility**: `ink` requires a real TTY. Mitigation: detect non-TTY (`!process.stdout.isTTY`) and fall back to plain text output with `readline` prompts.
- **Overlap with hara itself**: Hara is 3★ and brand new — the risk is it grows into exactly this. Treat HaraDuo as a personal learning project / thin wrapper rather than a publishable tool; the value is in understanding role routing for your own workflow.
