# agentmux — Structured Multi-Agent Pipeline via tmux Injection

**Source:** [markuswondrak/AgentMux](https://github.com/markuswondrak/AgentMux) · GitHub · Python · 34★
**Date discovered:** 2026-08-24

## What it is

AgentMux orchestrates a deterministic PM → Architect → Plan → Code → Review workflow by **injecting prompts into existing CLI agent sessions via tmux**, rather than calling the API directly. Each role runs in a separate tmux pane using whatever agent you're already subscribed to (Claude Max, GitHub Copilot, Codex, Gemini CLI). Agents communicate through **shared YAML files** on disk — one agent writes a spec, the next picks it up — rather than through API-to-API messaging.

The key idea: multi-agent orchestration without extra per-token API costs, because you reuse existing subscriptions.

## Stack Recommendation

```
Language:   Python 3.11+ with uv
tmux:       libtmux (pip install libtmux) for pane control
Handoffs:   YAML files in .agentmux/<task-id>/ (spec.yaml, plan.yaml, diff.yaml)
Agents:     Any CLI agent that accepts stdin prompts; Claude Code, Codex, or gemini-cli
Config:     .agentmux/config.yaml — which agent binary runs each role
CLI:        agentmux run <task> | agentmux status | agentmux advance
```

No API keys needed beyond what your existing agents already use. The orchestrator reads phase output files, decides whether a phase is complete (a sentinel line in the file, e.g. `STATUS: DONE`), then injects the next phase prompt into the next pane.

## MVP Scope (1-2 Claude sessions)

Two roles and three phases:

1. **Role: PM** — given a task description, writes `spec.yaml` with `title`, `acceptance_criteria[]`, `out_of_scope[]`
2. **Role: Coder** — reads `spec.yaml`, implements the change, writes `diff.yaml` with `files_changed[]` and `summary`
3. **Role: Reviewer** — reads `spec.yaml` + `diff.yaml`, returns `review.yaml` with `verdict: APPROVE|REQUEST_CHANGES` and `comments[]`

The orchestrator:
- Creates a tmux session with three panes (one per role)
- Starts each agent in its pane (e.g., `claude` in the Claude pane)
- When a phase file (`spec.yaml`, `diff.yaml`) is written and complete (polls every 2s), injects the next-phase prompt into the next pane via `pane.send_keys()`
- Prints a status line: `Phase: PM ✓ | Coder ⋯ | Reviewer ⏸`

## Phases

### Phase 1: tmux Plumbing (1h)
- Create a tmux session with named panes (`pm`, `coder`, `reviewer`)
- Start an agent binary in each pane (configurable per role in `config.yaml`)
- Implement `send_prompt(pane, text)` using `libtmux` `send_keys`
- Implement `wait_for_file(path, sentinel="STATUS: DONE")` — polls until the sentinel appears
- Verify: start three panes, inject "say hello" into each, confirm they respond

### Phase 2: PM Role (0.5h)
- PM prompt: `"You are the PM. Given this task: {task}\nWrite spec.yaml to .agentmux/{task_id}/spec.yaml with: title, acceptance_criteria (list), out_of_scope (list). End with STATUS: DONE on its own line."`
- Orchestrator injects PM prompt, waits for `spec.yaml` with `STATUS: DONE`
- Verify: a real task description → `spec.yaml` is written within 60s

### Phase 3: Coder Role (0.5h)
- Coder prompt: `"You are the Coder. Read .agentmux/{task_id}/spec.yaml. Implement the changes. When done, write .agentmux/{task_id}/diff.yaml with: files_changed (list), summary. End with STATUS: DONE."`
- Orchestrator injects Coder prompt after spec is ready, waits for `diff.yaml`
- Verify: PM output → Coder implements changes → diff.yaml written

### Phase 4: Reviewer Role (0.5h)
- Reviewer prompt: `"You are the Reviewer. Read spec.yaml and diff.yaml in .agentmux/{task_id}/. Write review.yaml with: verdict (APPROVE or REQUEST_CHANGES), comments (list). End with STATUS: DONE."`
- Orchestrator injects Reviewer prompt after diff is ready, waits for `review.yaml`
- `agentmux status` prints the current verdict; `REQUEST_CHANGES` re-triggers the Coder with the comments appended
- Verify: APPROVE and REQUEST_CHANGES both produce correct review.yaml; REQUEST_CHANGES re-injects the Coder

### Phase 5: Loop Until Approved (0.5h)
- If `review.yaml` has `verdict: REQUEST_CHANGES`, re-inject the Coder with: `"Reviewer comments: {comments}. Revise and rewrite diff.yaml. End with STATUS: DONE."`
- Max 3 revision rounds (configurable); after 3, stop and prompt for human intervention
- `agentmux status` shows current round: `Round 2/3 — Coder revising`
- Verify: inject a task with an intentional bug; confirm the loop triggers and terminates

## Blockers / Risks

- **Agent prompts must be injected correctly.** `pane.send_keys("text", enter=True)` in libtmux sends the text as keystrokes, not as stdin. If the agent is in a multi-line edit mode (e.g., waiting for `Ctrl-D` to submit), `send_keys` won't work. Test with `claude --no-interactive` flag or use subprocess stdin if the agent supports it.
- **File polling is fragile if agents write incrementally.** An agent may write `spec.yaml` in multiple bursts before the `STATUS: DONE` sentinel. The poll loop must not read a partial file. Use an atomic rename: agent writes to `spec.yaml.tmp`, then renames to `spec.yaml`. The PM prompt must include this instruction explicitly.
- **Different agents have different UIs.** Claude Code's TUI captures the terminal differently from `codex` or `gemini-cli`. Test each agent binary in isolation first; some may need `--no-color` or `--plain` flags to produce clean file output rather than ANSI sequences.
- **The loop can hang if an agent stops responding.** Add a 5-minute timeout per phase; if `wait_for_file` exceeds the timeout, mark the phase as `STALLED` and surface it in `agentmux status`. Never silently spin.
- **loopx composes with this.** If loopx is installed, initialize a loopx goal at the start of each agentmux run (`loopx set-goal "Implement: {task}"`). Each phase completion maps to a loopx todo (`loopx todo done pm-phase`). This is optional but makes the pipeline recoverable if the orchestrator itself crashes.
